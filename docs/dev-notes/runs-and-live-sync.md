# Run execution core, run queue, SSE live sync, output streaming

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **`src/lib/server/run.ts` = the one cell-execution core.** The UI `/run` route, MCP `runCell`, and `runImportsCell` all call `executeCellRun({nb, cellId, actor, source, originId, onEvent})`: execute → persist outputs → stamp the runtime-only `lastRun` (session epoch captured from `execute()`'s `kernel` event, never re-read) → publish `run:start`/`run:output`/`run:end`. It is NOT the queue: claiming the kernel stays with each caller, because each answers a refused (`duplicate`) or dropped (`cancelled`) ticket in its own shape. `onEvent` is what the UI route forwards down its NDJSON stream. A third run path can no longer drift from the run_status doctrine.
- **Live server→client run feedback (SSE, P0+P1).** An open browser reflects *agent* (or other-tab) runs with no reload: running indicator + streaming outputs. `src/lib/server/events.ts` = in-process `EventEmitter` pub/sub (`publish`/`subscribe`); it stamps each event with a per-notebook monotonic `seq`. `src/routes/api/events/+server.js` = one SSE stream per browser tab (`text/event-stream` `ReadableStream`, `hello` + 15s heartbeat + abort/cleanup) carrying events for **all** notebooks. `src/lib/events-client.ts` = a **single shared `EventSource` per tab** (ref-counted; stays under the HTTP/1.1 ~6-conn cap) plus a per-tab `originId`; every `LiveNotebook` subscribes to it. Both run entry points publish `run:start`/`run:output` (first frame of each stream element; subsequent growth rides `run:output-append` deltas — see the Streamed-output deltas entry)/`run:end`: the UI `/api/cells/[id]/run` route (`actor:'user'`, carries the caller's `originId`) and MCP `service.ts` `runCell` (`actor:'agent'`; `runCells`/`runAll`/`runRange` funnel through it). **Canonical notebook id (the P0 gotcha):** events are tagged with the notebook's **absolute** path; `LiveNotebook` learns that id from its `GET /api/notebooks` load response (`body.notebook.path`) and filters SSE on it — the workspace-relative `path` prop is only for the REST API (server resolves it via `resolveNotebookPath`/`resolveAbs`). **Echo:** the initiating tab drops its own events by `originId` match (it renders that run from the `/run` NDJSON response), so a user run never double-renders; agent runs carry no `originId` so every tab renders them. **Backstop:** on `EventSource` (re)connect or a detected `seq` gap, the notebook refetches. Deferred to later phases (NOT built here): unified server-side run function, the busy/queue hang fix (run metadata landed later in P3, see below).
- **Follow the running cell (viewport).** `LiveNotebook`'s follow effect keys off **`runningId`** (the cell running in THIS notebook, whatever the actor - the user's own run, another tab's, or an agent's), so the viewed notebook follows its running cell however it was started. The load-bearing scope is the **`active`** guard: a run in a notebook the user is NOT looking at (an agent working a background notebook) never moves the viewport, which is what preserves the active/viewed-notebook decoupling (no background hijack). A **user opt-out** (`follow` prop, default on) gates the whole behavior; the shell (`+page.svelte`) owns it as a global viewer preference persisted via the per-project UI-state store (`getUi`/`setUi` `cellar-follow-running-cell`, NOT the `.ipynb`), toggled from the Navbar app-menu "View" section (`data-testid=toggle-follow-running-cell`, styled like the hide-all-code toggle). There is no `agentRunningId`: following any run in the viewed notebook is the intended behavior, and the `active` guard alone scopes it. Guards, in order: the `follow` preference must be on; the tab must be `active` (a hidden pane is `display:none`, so it has no geometry - the effect re-fires on activation and follows a still-running cell); the user must not have typed inside this notebook in the last 3s (`lastTypedAt`, a capture-phase keydown listener on the notebook root; focus alone is too coarse - a cell keeps editor focus long after typing stops, and following would silently never happen); the cell must not already be visible (follow-tail: "visible" = its **top** edge is on screen, since the run affordance lives there). A cell hidden by a folded heading is revealed first (`revealCell` drops exactly the folded headers whose own section contains it) - fold state is runtime-only, so this costs a re-fold, not a git diff. The scroll runs inside `untrack()`: it reads (and `revealCell` writes) fold state, which would otherwise re-fire the effect on every edit and loop. Cell lookup is scoped to `rootEl` because **cell ids repeat across notebooks** and every open notebook stays mounted. `rootEl` is the notebook's single subtree handle, shared with the modal keyboard: it must be a real, focusable box (`tabindex=-1`), **not** `display:contents` - the shell's `overflow-y-auto` pane is the scroll ancestor, so a plain wrapper stays layout-neutral. Its scroll helper (`scrollElementIntoView`, centers or top-pins a cell, called with `settle:'visible'` so it corrects the mount-drift but never chases a growing streaming cell) is deliberately distinct from the keyboard's smallest-movement writer `scrollElementIntoViewNearest` (`block:'nearest'`, the tail of `scrollCellIntoView`'s mount → land → reveal → release sequence): run-follow reframes the viewport, selection must not. Both go through `ensureCellMounted` first, so either can land on a cell virtualization has windowed out (see the virtualization entry's P4 note). Selection (`activeId`) is never touched; `Cell.svelte` marks the running cell with a `warning`-hued accent bar + ring (`data-running`, `data-testid=running-bar`) that outranks the `primary` selection accent, so "executing" and "selected" read as different things. Covered by `tests/e2e/follow-running-cell.spec.ts` (follow ON scrolls to the running cell, OFF stays put, the choice persists across reload, and a background notebook's run never hijacks the view).
- **Live structural sync (SSE, P2).** Agent-driven (and cross-tab) *structural* changes also reflect live with no reload. **Single chokepoint:** `notebook.ts`'s mutation ops (`addCell`/`setSource`/`setCellType`/`deleteCell`/`deleteCells`/`clearOutputs`/`clearOutputsForCells`/`moveCell`/`moveCellTo`) `emit()` `cell:added`/`cell:edited`/`cell:type`/`cell:deleted`/`cell:cleared`/`cell:moved` (schema per scout report §3.3), tagged with the doc's absolute path + `seq` + an optional `originId` threaded through from the UI REST routes (MCP calls pass none → every tab renders). `LiveNotebook` `applyStructuralEvent` patches its `cells` in place (insert/remove/reorder/retype), gated by the same `originId` echo-suppression + `seq`-gap-refetch backstop as runs. **Editor-safety rule (report §3.4):** a `cell:edited` hands the new source to `Cell.svelte` via `cell.remoteEdit`; the Cell applies it to CodeMirror only when the cell is **not** focused / has no pending local edit — otherwise it shows a "Changed on server" affordance (`data-testid=remote-changed`) with a **Load** button, so remote edits never clobber active typing. Applying a remote edit sets `applyingRemote` so the editor's update listener doesn't echo it back as a local save. **The marker is the EDITOR's channel, never the model's, so `cell.source` must be written wherever no mounted Cell owns it** - with windowing on by default a far cell has no instance, and `cell.source` is what every non-editor reader falls back to: `runCodeIds` reads it for a bulk run and `/api/cells/[id]/run` PERSISTS whatever it is POSTed, so a stale value would run the pre-edit code AND write it over the agent's edit in the `.ipynb` (it also feeds `onCellsChange` → find bar / sidebar search / outline, so the edit would be unfindable until the cell scrolled back). Two write points, both gated on "nothing owns the editor": `applyStructuralEvent` writes the model when `cellApis[id]` is absent at delivery, and the Cell's teardown hand-back writes it alongside re-arming the marker - its `currentSource() === savedSource` guard already proves there is no local text to lose. Covered by `tests/e2e/virtualization-remote-edit-run.spec.ts`. **New/active notebooks surface live:** MCP `create_notebook(name?)` really creates (or opens) a workspace `.ipynb`, makes it active, and publishes `notebook:opened {nb,relPath,name}`; the shell (`+page.svelte`) subscribes and opens/focuses a tab via `openFilePermanent` (own-action echo dropped by `originId`). Because the agent's write ops default to `activePath` (the notebook the UI last focused / just created), agent edits land in the exact in-memory doc the open tab shows.
- **Editor edit-flush (no-run persistence).** `Cell.svelte` autosaves source on a 500ms debounce; it also `flushEdit()`s immediately on editor **blur** and window **`pagehide`**, and teardown flushes rather than cancelling - so a cell edit survives closing Cellar even inside the sub-debounce window, without a run. `LiveNotebook.editCell(id, source, {keepalive})` sets `keepalive:true` **only** from the unload flush (Cell passes `{keepalive:true}` from `pagehide`); normal page-alive autosaves stay plain `fetch` because the browser caps a keepalive body at ~64KB - routing every autosave through keepalive silently drops edits to cells >64KB (the regression to avoid). PATCH is `.catch`'d so a rejected unload flush never surfaces as an unhandled rejection.
- **Kernel run queue (`src/lib/server/run-queue.ts`).** Cellar runs ONE kernel per notebook, so the queue is **sharded per notebook** (`Map<nbPath, {active, pending}>`): one cell of a notebook runs at a time, while DIFFERENT notebooks execute in parallel against isolated namespaces - a run queued in notebook B waits only behind notebook B's own cells, never behind notebook A. A run requested while that notebook's kernel is busy is **queued FIFO**, never dropped (the old behavior: the UI early-returned and MCP raced into `execute()`). The queue lives on the **server** because the kernels do - an agent's MCP run must interleave with a user's UI run on the same notebook in submission order, and no per-tab flag can see both. Entries are keyed by `(absolute notebook path, cellId)` - **cell ids repeat across documents**, so the notebook half is load-bearing. It is a *slot* primitive: it decides who runs next, never how. Both run entry points keep owning their own execution + streaming and just take a ticket first (`enqueueRun` → `await ticket.wait()` → `finally ticket.done()`); `ticket.done()` fires only **after** `run:end` is persisted + published, so the wire order stays `run:end` → next `run:start`. **Dedupe:** a cell already running or already queued is not enqueued twice; the second submission instead **refreshes the pending entry's source** (`ticket.source()` is read at dequeue), which is what makes dropping it safe - a queued cell runs what you last submitted. **Cancellation:** `clearRunQueue(nb)` drops every *pending* run **of that notebook** (another notebook's queue is untouched) and is called from `restartKernel`/`interruptKernel`/`rebindKernel`/jupyter's `autorestarting` (in `kernel.ts`, **before** the restart is issued) - queued work was submitted against a namespace that is about to vanish, and running it against a fresh kernel would execute cell N+1 without cell N's definitions. The *active* run is not touched: the kernel op ends it, and its owner then releases into an empty queue. `deleteCell` calls `cancelRun` so a removed cell can't dequeue later; the `/run` route's stream `cancel()` drops its own pending entry (identity-checked via `ticket.cancel()`, **never by key**, so a duplicate request's stream closing cannot cancel the real pending run). A cancelled entry rejects with `RunCancelled`; `enqueueRun` pre-attaches a no-op `.catch` so an owner that already returned never surfaces an unhandled rejection. **Interrupt-clears-the-queue (the non-obvious client half).** `interruptKernel` calling `clearRunQueue` is necessary but NOT sufficient: with a large queue (Run All) the interrupt HTTP request could not even REACH the server. Each queued/running `/run` holds its NDJSON response open, so N of them saturate the browser's ~6-connection HTTP/1.1 pool, and the interrupt `fetch` gets no connection until a run finishes on its OWN - by which point the queue has already drained (the running cell ran to completion, `sleeper_ran` set, every marker executed). Fix is client-side and MUST stay paired with the server clear: `LiveNotebook` tracks each run's `AbortController` in `runControllers`, and the shell's `interruptKernel(path)` calls `notebookApis.get(path)?.cancelQueuedRuns()` FIRST (synchronous, no network) - it aborts every run fetch **except `runningId`'s**, which frees the held connections (so the interrupt request goes through) AND cancels the queued/browser-held runs at once (an aborted stream → the `/run` route's `cancel()` → `ticket.cancel()`; a never-sent one is dropped before the kernel). The running cell's fetch is kept so `kernel.interrupt()`'s KeyboardInterrupt still renders. An `AbortError` in `runCell`'s catch is an intentional cancel (no error output). Bumping `interruptGeneration` also stops an in-flight sequential bulk-run loop (`runCodeIds` for **runAll**/runAbove/below/stale) from advancing to the next cell after its current run is aborted - those hold only one connection at a time, so the connection-pool half doesn't bite them, but the loop-keeps-going half does. **Run all is now this same sequential loop** (`cellar-runall-kernel-wedge-z3`; see the staleness entry), so the connection-pool saturation the client-half fix guards against no longer arises from Run all - it can still arise from a user mashing Run on many cells at once, which is why `cancelQueuedRuns` stays. Covered by `tests/e2e/interrupt-clears-queue.spec.ts` (+ the server seam in `tests/unit/kernel-manager.test.ts`).
- **Queue state is a broadcast snapshot, not a delta.** Every queue change (and every run start, including the uncontended one) publishes `queue:changed` via `events.ts`'s **`publishGlobal`** - it carries `{running:[…], queue:[{nb,cellId,actor,position}]}` for EVERY notebook at once (one `running` entry per busy kernel - notebooks run in parallel, so there can be several - and every notebook's pending runs, each tagged with its `nb`, which the client filters to its own), has **no `nb` and no `seq`** (it is a full snapshot, so a missed one self-heals), and is dispatched in `LiveNotebook` *before* the per-notebook `nb`/`seq` filter and *without* `originId` echo-suppression - a queue is shared state, not one tab's action. The SSE route seeds one on connect and `events-client.ts` replays the latest to a late subscriber, so a tab connecting (or a notebook mounting) mid-run sees both the queue **and** the running cell; the snapshot's `running` is why `LiveNotebook` reconciles `runningId` from it (a tab that missed `run:start` would otherwise render cells "queued · 1" behind a cell it shows as idle). Reconciling `runningId` here also lets a tab that connects mid-run and is VIEWING that notebook follow the running cell - the intended behavior (it is looking at the notebook that runs); a background tab stays put via the follow effect's `active` guard. **The latest snapshot is RETAINED per notebook (`LiveNotebook.lastQueueEvent`), never a consumed one-shot, and every `load()` RE-APPLIES it after its `clearRunning()` stale-state wipe** - on a page reload the mount load can resolve before the SSE connect, so the `sse:open` backstop triggers a second load whose wipe landed AFTER the connect-seeded snapshot had marked the running cell, erasing the spinner for the rest of the run while the kernel badge stayed busy (the queued badge, set by the same `applyQueueEvent` from the same snapshot, survived - `load()` deliberately does not reset `queued` - which is what proved the seed was applied and then destroyed). Re-applying is always safe: each snapshot is the server's full statement, a newer one overwrites, and an empty one clears - so a retained snapshot can never resurrect a dead run. Covered by `tests/e2e/reload-running-spinner.spec.ts`, which forces the failing interleaving deterministically with route delays. The `/run` NDJSON gains `run:start` (the initiating tab drops its own SSE echo, so this is how it learns its run actually *started* rather than merely being accepted), plus terminal `run:duplicate` / `run:cancelled` frames that close the stream without ever touching the cell's outputs. `runCell`'s `finally` clears `runningId` only when it truly `started`, so a refused duplicate can't erase a live indicator. **`runBusy` in `+page.svelte` is no longer a gate** - it is an in-flight *counter* (`runsInFlight`) feeding the kernel badge; the `busy` prop is gone from `LiveNotebook`.
- **Queued-cell affordance.** `Cell.svelte` `queuedPosition` (null | 1-based position **within this notebook's own queue**) → a static `bg-warning/50` left bar + `border-warning/30` + an amber clock and `queued · N` label, the deliberately quieter sibling of the running affordance (`bg-warning` pulsing bar + spinner), which outranks it (`isQueued = queuedPosition != null && !running`). Label text is `base-content`, **not** `warning/70`: a dimmed warning washes out to near-illegible on a light theme. Positions are per notebook - a cell only ever waits behind its OWN notebook's cells, so `queued · 3` means three of this notebook's runs are ahead of it.
- **Live elapsed on the RUNNING cell (`running 12s`), and its ONE server-stamped origin.** The running indicator carries a whole-second clock that ticks beside its spinner, the in-flight sibling of the settled `ran … · 1.2s` badge (a long Spark/SQL query used to give no feedback at all while it ran). Three parts, each with a trap.
  - **A SECOND ticker, not a faster one.** `nowTicker.ts` gained `RUN_TICK_MS` (1s) beside `NOW_TICK_MS` (15s) and `now.svelte.ts` a second `createNowTicker` instance (`runNowMs`/`subscribeRunNow`). **Do NOT drop `NOW_TICK_MS` to 1s** - that cadence is set by the coarsest unit `ran 2m ago` can show, so it would wake every idle badge in a 200-cell notebook 15x more often to redraw unchanged text. The fast instance is ref-counted the same way and a cell subscribes only while `showRunning` (the 180ms-delayed reveal) is true, so a cell fast enough never to flash the indicator never arms a timer either, and **nothing ticks while nothing runs** - verified in a real browser by instrumenting `setInterval`: 0 timers at rest, exactly 1 while running, 0 after, re-armed once per run with no accumulation. Never a per-cell `setInterval`: one cell per notebook runs, but every cell mounts `Cell.svelte`.
  - **The start is stamped ONCE, by the run, and reaches a client three ways.** `executeCellRun`'s `startedAt` is what `run:end` measures `durationMs` from, so timing the clock from it is what makes the handover to the badge seamless (observed: last live `1m 16s` → badge `1m 17s`). It rides the SSE `run:start`, this run's own NDJSON `run:start`, and - new - the queue snapshot, as `RunningView.startedAt` (`noteRunStarted`, which BROADCASTS, so a tab whose SSE stream connects or a notebook that MOUNTS mid-run is seeded with it; one extra `queue:changed` per RUN, the same order as the `run:start` it accompanies, not per output flush). **The queue must NOT stamp its own at dequeue** - a second clock would let a client seeded from the snapshot show an elapsed the badge then contradicts, and would claim a start for a kernel claim whose owner bails before executing (`cell_removed`). BOTH halves of that are pinned BEHAVIORALLY, never by a grep: a run driven through the REAL `executeCellRun` hands ONE instant to all three channels and measures `durationMs` from it, and a dequeued entry reports `startedAt` undefined until the run reports in - so a queue that stamped at dequeue is caught by the SNAPSHOT disagreeing with the run, which is exactly the disagreement a client would render. Absent `startedAt` is honest ("running, start unknown") and renders the indicator with NO clock rather than inventing an origin - never derive it from when a tab noticed `running` flip, which restarts at `0s` on every reconnect for a query already ten minutes in.
  - **`runningId` and `runningSince` are ONE fact**, written only through `LiveNotebook`'s `markRunning`/`clearRunning` (the `wipeVariablesLocally()` precedent, with the same shape of source guard): a site that moved one without the other would time the run BEFORE it. `Notebook.svelte` hands the start to the running cell alone, so no cell can draw a clock without the affordance it belongs to.
  - **Format: `formatElapsed` DELEGATES to `formatDuration` past a minute**, so `1m 5s` is spelled in one place and the live clock cannot drift from the badge; only the sub-minute tier differs, flooring to whole seconds (`formatDuration`'s `1.2s`/`820ms` are written for a value that has stopped moving and would read `1.0s`, `2.0s`… once a second). It feeds the delegate a WHOLE second, which is also what keeps `formatDuration`'s `Math.round(s % 60)` from rendering the impossible `1m 60s` (`formatDuration(119_700)` really is `1m 60s`; that pre-existing edge is unchanged and pinned). A non-positive/absent duration reads `0s`, which is the one reachable case: the first frame after a run starts, reading a `runNowMs()` frozen since the last run released the ticker - and that IS a just-started run.
  - **The width reservation is measured, not decorative, and the obvious probe for it is VACUOUS.** The far-right slot is `justify-end`, so the group grows LEFTWARD: an unreserved clock moves the delete/⋮ controls **7px at 9s → 10s** - inside the first ten seconds of every run - and 34px over an hour. `min-w-[2.75rem] text-left tabular-nums` on the NUMBER holds them dead still from `0s` through `9m 59s` (the row's own slack absorbs the rest; measured drift 0px), and reserving it on the number rather than on the group is what keeps the spinner and the word still too. Left-aligned so the number reads with its label and the slack falls before the stop button. **`cell-interrupt` is the LAST child of a `justify-end` slot, so it can never move** - a layout-stability assertion aimed at it passes against any regression; probe `delete` (or `cell-actions`), which sit to the LEFT of the indicator.
  - Covered by `tests/unit/run-elapsed.test.ts` (format incl. the `1m 60s` sweep, the fast ticker's ref-counting under fake timers, the queue snapshot in all three shapes + its broadcast + its no-ops, the single-origin invariant driven through the REAL `executeCellRun` against a faked `execute` and a stubbed clock - all three channels carrying ONE instant and `run:end` measuring `durationMs` from it - and source guards on both component halves; the "the queue mints no clock of its own" half is BEHAVIORAL, a dequeued entry reporting `startedAt` undefined until the run reports in, plus a case where the kernel is claimed and the run only BEGINS later so the two candidate origins are different numbers - the claim-time one is what a dequeue stamp would produce, and a shared clock reading cannot tell them apart - never a grep over `run-queue.ts`) and `tests/e2e/run-elapsed.spec.ts` (real kernel: the clock advances and TRACKS wall-clock over a measured interval, the controls to its LEFT do not move across an explicit `9s`->`10s` digit-count change, the handover to the badge never goes backwards, an agent's run gets the same clock, and a fast cell still flashes nothing).
- **Streamed-output deltas (`run:output-append`) - the wire is O(size), never O(size×ticks).** A growing coalesced stream element used to re-broadcast its **whole** buffer on every ~40ms `OutputAccumulator.flush()` tick (a full `run:output` at a stable index), so the server re-`JSON.stringify`d and fanned out the entire buffer to every tab each tick - **measured 91× traffic amplification** (audit finding K1, scout `cellar-perf-scout-b5`). Fixed by emitting **deltas**: `OutputAccumulator.flush()` sends the full element on its **first** materialization (client establishes it), and every later tick emits a `StreamDelta {base, keep, chunk}` of what changed since the last emission (`onEmit(out, index, delta?)`); `run.ts`'s `emit` publishes it as `run:output-append {index, base, keep, chunk}` (SSE) / `{type:'output-append',…}` (NDJSON), otherwise the unchanged full `run:output`. Client (`LiveNotebook.applyOutputAppend`) reconstructs `prev.slice(0, keep) + chunk`. **Reconcile with the terminal reducer** (the reduced stream is NOT append-only - a `\r`-overwrite rewrites earlier bytes): the delta is a **tail-splice**, not a pure append. A **non-terminal** stream reduces to identity and only appends, so `keep === base === prevLen` with **no scan** (the O(new bytes) fast path that kills the measured 91×); a **terminal** buffer diffs to the common prefix (`keep < base`). **`base` = the length the client's element must currently have** - a mismatch (dropped establishing frame/delta, or a reconnect refetch racing a live delta) means out-of-sync, so the client resyncs with **ONE `load()` refetch** (`applyOutputAppend` returns false → the SSE path calls `load()` guarded by `!fetching`, so a burst of mismatches triggers at most one in-flight refetch; the NDJSON initiating-tab path treats false as a no-op, it renders from its own ordered stream). **The resync backstop is the `load()` refetch, made authoritative by keeping the in-memory doc CURRENT on every flush** - `run.ts`'s `emit` calls `notebook.ts`'s `setOutputsLive(cellId, acc.outputs.slice(), nb)` (in-memory only: **no persist, no event**, mirroring `clearOutputsLive`) after each publish, so `getNotebook`/`GET /api/notebooks` returns the last-flushed outputs for a running cell. The doc is therefore authoritative at ALL times - mid-stream, in the final tail after the last delta, and at `run:end` - so a mid-run `load()` returns the current text (not empty) and STOPS firing once `base` matches again (no refetch storm). This replaced an earlier periodic-full-frame-checkpoint design: the doc-current approach is simpler (no checkpoint cadence, no counter, no constant) and covers the final-tail window a checkpoint bounded only to ≤N ticks. Persist still happens **once**, at `run:end` via `setOutputs`; `outputs` (persisted `.ipynb`) always holds the full reduced text - deltas are purely a wire optimization. An idle flush (reduced === emitted) broadcasts nothing. Covered by `tests/unit/output-accumulator.test.ts` (delta emission, append-vs-tail-splice decision, one-full-frame-per-element, the O(size) wire bound, base-guard, and byte-exact replay) + `tests/unit/notebook-model.test.ts` (`setOutputsLive` updates the doc in-memory without persisting).
- **Terminal-style stream output reduction (`src/lib/server/terminal.ts`) - two tiers, zero deps.** A cell running a CLI (tqdm, spinners, `uv pip install`, any progress bar) emits hundreds of `\r`-overwrite / cursor-repaint frames + ANSI escapes; raw, a `<pre>` stacks every frame and the same pile is persisted + read by the agent. `terminal.ts` is a **pure, zero-dep** reducer with a cheap gate `isTerminalStyle(text)` (has `\r` or CSI `ESC[`) and two tiers: **(1) `reduceCheap(text)`** - strip SGR color, then collapse `\r` overwrites per physical line with **true** terminal semantics (`abcdefghij\rXYZ` → `XYZdefghij`, tail survives; a `\r` never crosses a `\n`). Fixes single-line bars/spinners; **cannot undo a VERTICAL repaint** and leaves non-SGR escapes in place. **(2) `reduceFull(text)`** - a minimal **VT screen emulator** (line-array screen + `(row,col)` cursor) that applies the **BOUNDED escape set** and collapses the multi-line cursor repaint of `uv pip install` / multi-bar tqdm to its final rendered screen. The bounded set (enumerated from a real `uv` PTY capture): `\r`, `\n` (ONLCR - resets column, like the cheap tier), `\b`, SGR `m` (stripped), erase-in-line `K` (0/1/2), erase-in-display `J` (0/1/2/3), cursor up/down `A`/`B`, forward/back `C`/`D`, column-absolute `G`, absolute position `H`/`f`. **Every OTHER CSI, private-marker CSI (`ESC[?…`), OSC (`ESC]…`), and non-CSI ESC is a defensive DROP** - never printed as garbage; an **incomplete trailing escape is held back** (dropped this pass) so a sequence split across a flush boundary resolves on the next flush's whole-buffer re-reduce. Render = join rows, each right-trimmed of trailing blanks, trailing blank rows dropped (the "final screen" a terminal-capture tool shows). A full-screen TUI / alternate-screen program is out of scope by design. **A huge cursor escape is bounded, NOT honored** - because `reduceFull` re-reduces the WHOLE raw buffer on every flush, an unclamped cursor move (`ESC[9999999B`, `ESC[1;9999999H`) would append millions of empty rows/cells per ~10-byte escape, repeatedly; so the cursor row/col and every screen allocation are clamped to `MAX_ROWS` (100k) / `MAX_COLS` (10k - tighter, because a far move followed by a write PADS the gap with real space cells while an empty row is nearly free), both orders of magnitude beyond any real capture (uv/tqdm/colored logs stay byte-identical). **The pipeline uses `reduceFull`** (it supersedes the cheap tier for stream output); `reduceCheap` stays exported + independently tested. **Hooked at the single chokepoint** - `OutputAccumulator.flush()` keeps `pending.text` RAW (coalescing + byte caps + the emulator's whole-buffer re-reduce all depend on the full reassembled text) and emits the reduced COPY, so persist (`.ipynb`), the SSE broadcast, the agent MCP read, and the render all collapse to the final screen at once; `finish()` reduces the tail via the same `flush()`. **Coordinates with the streaming-delta protocol:** a full-tier reduction can rewrite an EARLIER line, so the delta is a tail-splice from the first divergence (`commonPrefixLen` → `keep < base`), reconstructed as `prev.slice(0,keep)+chunk` and resync-guarded by `base` (the existing delta layer already handles arbitrary rewrites - no change needed). **`reduceFull` is verified byte-identical against an independent VT emulator (`pyte`, ONLCR-applied)** on a battery of cases + a genuine 18KB `uv pip install` PTY capture committed at `tests/unit/fixtures/uv-pip-install.{raw,final}.txt`.
