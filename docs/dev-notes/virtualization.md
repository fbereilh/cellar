# Cell virtualization (windowed rendering)

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Cell virtualization (windowed rendering) - ON BY DEFAULT since P5 (P2 windowing + P3 pinning + P4 jump paths).** **Triage before you read any of this: a blank region that starts at the SAME cell every time, arrow-keys/jump-to-running going dead with it, or a notebook that renders nothing under "Render all cells", is NOT a windowing bug** - an uncaught throw during render does exactly that, and windowing only changes WHEN it fires. Each row is now walled off (see the per-cell render error boundary entry above), so such a throw should surface as ONE `cell-render-error` placeholder plus a `[cellar] cell <id> failed to render` console error rather than a blank region; the DataFrame-grid duplicate-key defect is the known instance of the class - see that entry. Check the browser console first. Every cell of a notebook is fully mounted when it is turned OFF; baseline ~137 nodes/cell at N=50/150/300, captured by `scripts/gen-large-notebook.js` + `scripts/virtualization-baseline.md`. The plan (`data/cellar-perf-cell-virtualization-a2/report.md`, §3 controller / §4.1 heights / §4.2 scroll stability) is a hand-rolled, flow-preserving **spacer window** — NOT a library — driven by a pure controller. **`src/lib/virtualization.ts`** = pure, DOM-free `planWindow()` (mounted cells + **coalesced** spacers; a pin splits a spacer) + `estimateHeight(cell, collapsed)` (line-count + coarse output allowance, short-circuiting to the header-only `COLLAPSED_CELL_PX` when the caller says the cell is fully collapsed - the verdict is passed IN, never read off the cell, since this module may not read the document model), unit-tested (`tests/unit/virtualization.test.ts`). **What P2 added (windowing active when ON):** `Notebook.svelte` renders TWO branches from ONE shared `{#snippet cellRow(cell,i)}` — flag OFF iterates `cells` and mounts every one (byte-identical to the old eager `{#each}`), flag ON iterates the render **plan** (mounted rows via `cellRow`, one inert `aria-hidden` `data-testid=cell-spacer` per collapsed off-screen run). Only cells overlapping `[scrollTop − overscan, scrollTop + clientHeight + overscan]` (overscan = `max(800, 1.5×viewportHeight)`) plus the `pinned` set mount. **Fold-hidden cells are excluded from the window `order` (`visibleOrder`)** so they contribute 0 height and never mount (a folded cell is absent from the DOM under ON, vs `display:none`-mounted under OFF). **Scroll stability is the browser's, NOT an explicit compensation:** the scroll pane keeps its **native `overflow-anchor`** (default `auto`, unchanged in both flag states — there is deliberately NO `overflow-anchor:none` and NO `scrollCompensation`/`offsetOf`; PATH-2 replaced the earlier explicit-delta design after it proved unable to reconcile its parallel pixel model with the real layout). Native anchoring re-anchors the viewport when an off-screen cell mounts (spacer→cell) or an above-fold cell resizes. For native anchoring to track the layout, **`planWindow` accounts for the `space-y-4` inter-cell gap** (`ROW_GAP_PX = 16`, passed as `gapPx`): the running offset advances by `h + gap` between cells (cell k's model top = Σheights + k·gap) so the window tracks the real `scrollTop` and never blanks the viewport, and a coalesced spacer's px = Σ(its cells' heights) + (K−1)·gap so it reproduces the exact flow space its run occupied (the outer gaps to its neighbors are drawn by `space-y-4` around the spacer div). A `heights: Map<id,px>` cache fed by `Cell.svelte`'s `onMeasure` (ResizeObserver on `cardEl`, `borderBoxSize` — margin-excluded, hence the explicit `gapPx`) replaces estimates as cells mount; `recordHeight` only writes the cache + bumps `heightsVersion` to re-plan. The scroll-pane metrics `$effect` also attaches a **`ResizeObserver` on the pane itself**, so a notebook that loaded on a hidden (`display:none`) tab refreshes its viewport height on the `display:none`→visible activation (and on sidebar-drag / other container resizes) - otherwise it would window against a zero-height viewport and blank until the first scroll/resize. **Pinning (P3, complete): the pinned set is `{runningId} ∪ queued heads ∪ {activeId} ∪ {focused cell} ∪ scrollPins`, and its union + the REASON each member is in it live in ONE pure, unit-tested place, `virtualization.ts`'s `pinnedCellIds`** (`Notebook.svelte`'s `pinned` derived is only the wiring - do not re-inline the union there). Each reason: **running** - a streaming cell keeps a live node so its measured height GROWS with its output and the scroll height tracks the run instead of freezing at a stale spacer (correctness never depended on it - `applyOutput` writes the MODEL, which is live whether or not the cell is mounted - so P3 needed **no** buffer/replay machinery and left the streaming-delta protocol and terminal reducer untouched); **queued heads** - the next cells to run, capped at `QUEUED_PIN_LIMIT` (3) by `queuedHeadIds` because `queued` is a global FIFO an agent's `run_cells` can fill with dozens of this notebook's cells, and pinning all of them would mount most of the notebook exactly when the machine is busiest; **active** - the selection must not vanish mid-series (j/k, a/b, dd); **focused** - the cell holding DOM focus, tracked OFF THE DOM in `LiveNotebook` (a `focusin`/`focusout` listener on `rootEl`, attached only while windowing is on) and deliberately distinct from `activeId`, because an unmounted editor loses its CodeMirror cursor + undo (never its text - `Cell` flushes on blur AND on destroy, and `cell.source` is authoritative). The pin is added EAGERLY on `focusin` but dropped LAZILY - `focusout` only schedules a re-read of the settled `document.activeElement`, since focus moves as blur→focus within one task and acting on the intermediate state would unpin a cell that is about to keep focus. **We deliberately do NOT pin every cell edited this session** (report §7 Q2): that would keep every visited editor alive and defeat the memory win; a blurred, scrolled-away cell is unmount-eligible with its text already flushed. Every pin is dropped the moment its reason lapses, so a finished run costs the window nothing. **The corollary, and the rule for every future Cell feature: a Cell instance is DISPOSABLE, so any per-cell state that must outlive a scroll belongs in `LiveNotebook`, not in Cell-local `$state`** - windowing destroys and rebuilds a Cell whenever it leaves and re-enters the window, and pinning is not the answer (it exists for the handful of cells above, not as a state-preservation mechanism). Two things obey it beyond the pre-existing `editorCollapsed`/`foldedIds` (`cellCollapsed` later joined that list for the same reason - see the Full-cell collapse entry): **`rawEdits`** (which markdown cells the user opened for RAW source editing - lifted into `LiveNotebook` + `onSetRawEdit`, borrowing `editorCollapsed`'s plumbing SHAPE, because a Cell-local flag snapped a cell the user was editing back to its rendered view the moment it scrolled out of sight), and **`cell.remoteEdit`, which is a ONE-SHOT command and is CONSUMED (nulled) by `Cell.svelte`'s remote-edit effect the moment it is handled**. **`rawEdits` deliberately drops `editorCollapsed`'s PERSISTENCE half**: it is an in-session `$state` map with no UI-store key, because the notebook stays mounted for the life of its tab - which is all a windowed unmount/remount needs - while persisting it would reopen a notebook with every markdown cell the user ever edited showing raw source instead of rendered HTML, a far louder change than a collapsed editor (pinned in `virtualization-pinning.spec.ts` from BOTH directions: survives the unmount, does NOT survive a reload). Entries are dropped on delete (`setRawEdit(id, false)` - which deletes the key rather than storing a `false`, so it is the only helper - from both the local `deleteCell` and the `cell:deleted` event) so the map cannot grow for the life of the tab, and **`cell:rendered` clears the flag through the notebook's own `setRawEdit`, not only through `cellApis[id].showRendered()`** - an agent rendering a markdown cell windowing has unmounted has no Cell to call, and a mounted-only clear left that cell stuck on raw source when it scrolled back. The `remoteEdit` consumption is load-bearing, not tidiness: an unconsumed marker is REPLAYED by the fresh instance and overwrites a NEWER local edit the user has since made (`cell.source`/`savedSource` reset to the stale remote text with no re-PATCH to correct it), so it is consumed on EVERY branch - the STASH included, since the user resolving the banner (Load, or dismissing by typing on) and then editing reaches that same replay. It may only be cleared once a mounted Cell has actually processed it, since the marker is what carries the new text into a mounted cell's EDITOR; the MODEL is not left to it - `cell:edited` writes `cell.source` itself whenever no Cell owns the editor (the *Live structural sync* entry's two write points), so a windowed-out cell's source is current for every non-editor reader and the marker drives the mounted-editor safety UX only. **The mirror of that rule is the teardown hand-back**: an UNRESOLVED stash ("changed on server", never loaded nor dismissed) lives only on the Cell, so windowing the cell out would drop the agent's edit outright - the destroy handler therefore re-arms `cell.remoteEdit` from `pendingRemoteSource`, but ONLY while the user's own text has not diverged (`currentSource() === savedSource`, checked BEFORE `flushEdit` moves `savedSource`), since a restored marker is applied unconditionally by the next instance and would clobber their typing. **That hand-back is what makes the supersede rule load-bearing on EVERY local-source path, so it lives in ONE helper (`clearRemoteStash`) - never inline**: a stash left standing over a deliberate local write is re-armed on teardown and the remount adopts the PRE-write text while the server holds what that path persisted. Typing (the update listener), `replaceSource` (split / heading restamp - invisible to that listener, which skips the remote-apply path), `loadRemote`, `doRun` (the run route PERSISTS the source it is handed) and `flushEdit`'s persist branch all drop it; four of those were found one at a time, which is why a new source path must call the helper rather than re-derive the rule. There is deliberately no per-instance `appliedRemote` dedupe any more: consuming on every branch makes reference-equality dead state that only tells a misleading story. `fullImages` (the natural-size image toggle) and `remoteChanged` (the "changed on server" banner) are deliberately NOT lifted: both are transient and re-derivable with no data loss. Plus the transient **`scrollPins`** set owned by `LiveNotebook`, which forces a jump target to mount before anything queries its DOM node. **P4 (complete): EVERY scroll-to-cell / reveal / focus path in the app goes through the ONE shared seam `ensureCellMounted(id)`** (reveal/unfold + `pinScrollTarget` + `tick` + rootEl-scoped `querySelector`) - `revealRunning` (tab-spinner jump), `followCell` (follow-running), `jumpToCell` (find bar **and** the shell's outline / sidebar-search rows), and `scrollCellIntoView`/`selectAndAct` (keyboard `j`/`k`, `a`/`b`, moves, paste/undo selection, `insertAndRunCode`, plus the run/split paths `runAndAdvance`, `runAndInsertBelow` and `splitActiveCell`) - there are no unstated exceptions left. `+page.svelte`'s `scrollToCell` no longer does its own `document.querySelector` - it opens/focuses the notebook then delegates to that notebook's `jumpToCell(id, {foldKey})`, which owns the fold reveal, the mount pin, the heading-row sub-target (an outline row addresses ONE heading of a cell that may hold several) and the flash; so there is exactly one jump implementation, not two. **Two rules the paths must keep.** (1) **A select-and-focus path must mount BEFORE it lands** - an unmounted cell has no node and no registered API, so focus would silently go nowhere and the whole modal keyboard (which reads a keystroke's mode + target off the focused element) would go dead at the window edge. That rule lives in ONE seam, **`selectAndAct(id, act)`** = `setActive` then the shared mount/land/reveal/release tail **`scrollCellIntoView(id, land)`** (`ensureCellMounted` → `land(api)` → `scrollElementIntoViewNearest` → `releaseScrollPin`), whose other caller is `insertAndRunCode` (no `land` - that path deliberately never touches `activeId`, so nothing else pins its appended cell); the sites differ only in `act` - `focusCell` (plain selection, wrapped as `selectAndFocus`), `focus` (run-and-advance landing on the next cell's editor), or `enterEdit` (run-and-insert-below / split-cell, which must open the created cell in edit mode because a markdown cell with text mounts in its rendered view whose editor is `display:none`). Do not hand-roll a second mount-then-focus variant. `j`/`k` happen to survive without it today (`activeId` is in P3's pinned set, so the selection mounts itself), but that is a coincidence of the pin order, not a guarantee - stating the requirement is what keeps it true, and it is what makes `insertAndRunCode` work at all (that path deliberately never touches `activeId`, so nothing else pins its appended cell). (2) **A transient pin is released by `releaseScrollPin(pin, settled)`, never inline** - it waits for the scroll to SETTLE *and* two more frames, because `Notebook.svelte` reads the pane metrics rAF-coalesced: unpinning in the same frame re-plans against the PRE-scroll viewport and unmounts the very cell just jumped to. **The `pinSeq` ownership token is captured at PIN time** - `pinScrollTarget` RETURNS a `{id, seq}` `ScrollPin` and `ensureCellMounted` hands it back alongside the node, so a release is tested against the seq its OWN jump took. Re-reading `pinSeq.get(id)` at release time is the bug that shape exists to prevent: two jumps to the same cell interleave across `ensureCellMounted`'s `await tick()` (A pins seq 1, B pins seq 2), so A would read back 2, pass its own equality check, and unpin a target B is still scrolling to - after which B's settle loop aborts on the `isConnected` guard and lands nowhere. Map entries are deliberately never deleted (a deletion would let a stale release unpin a fresh pin). The release still runs if the scroll rejects, so pins can never accumulate (accumulated pins = virtualization undone). **The release must never depend SOLELY on rAF** - a backgrounded tab suspends it, so `nextFrames` and the tween in `tweenScrollTop` each carry a `setTimeout` backstop (whichever settles first wins); rAF stays the fast path, since the two-real-frames wait is what the re-plan timing needs, and the timeout is only a floor so a hidden tab cannot leak one pin per followed run. **That floor is gated on `document.hidden`, NOT fixed** (`FRAME_TIMEOUT_HIDDEN_MS` 50 vs `FRAME_TIMEOUT_VISIBLE_MS` 1000 per frame, re-armed by a `visibilitychange` listener in BOTH directions if the tab flips mid-wait - tight when it is backgrounded, and **widened back on return to visible**, since otherwise the tight floor armed while hidden fires once rAF has resumed but before two real frames land, which is the premature unpin the visible floor exists to prevent; each re-arm replaces the pending timer rather than stacking one): this app has long main-thread frames during a run (it drives its own tween precisely because of them), so a tight floor is reachable on a VISIBLE tab - and a timeout winning there unpins BEFORE the metrics read lands, re-planning against the pre-scroll viewport and unmounting the very cell just jumped to, i.e. exactly the failure the two-frame wait exists to prevent. `tweenScrollTop`'s own backstop snaps to the SAME destination it was heading for, so winning that race costs the animation, never the landing. **A long jump lands TWICE, by design (`scrollElementIntoView`'s bounded settle loop).** The first scroll is computed against the window's *estimated* heights for every cell it flies over; the moment it moves, those cells mount and their real heights replace the estimates, so the target slides out from under the tween - MEASURED at ~2.6k px of drift on a 64k px jump in the 300-cell harness (the target ended up four viewports below the fold and then unmounted again). So the helper re-measures and re-scrolls, bounded by `SCROLL_SETTLE_PASSES`; pass 0 tweens (the movement the user perceives) and the corrections snap. Do NOT 'simplify' it back to a single tween - that is the bug. **WHAT counts as settled is an explicit per-call `settle` mode, never a branch on the `virtualize` flag** - the real distinction is discrete-target vs continuous-follow, and keeping it in the caller is what stops a future caller inheriting the wrong behavior: `'frame'` (DISCRETE targets - `jumpToCell` for the find bar / outline / sidebar-search rows, and `revealRunning`) converges on the exact framing within `SCROLL_SETTLE_TOLERANCE_PX`, while `'visible'` (the CONTINUOUS `followCell`) stops the moment the cell is on screen, because its target is *streaming*: its own height (and, once it outgrows the viewport, its framing rule) keeps changing, so an exact-framing loop would re-snap a viewport the user is reading up to four extra times - the regression that reached the shipping flag-OFF default. Correcting only until visible is still REQUIRED under windowing (the window does not catch the mount-drift up by itself, so a single tween leaves a followed cell mounted but permanently below the fold - proved by the follow-running case in `virtualization-jump-paths.spec.ts`). Omitting `settle` is one scroll, no re-measure. When layout is static - windowing OFF - both modes settle on pass 1 (~0 delta / already visible), so the flag-OFF path is one tween exactly as before. **`scrollGen` is the per-pane supersession guard** (distinct from `pinSeq`'s per-cell pin ownership - keep both, do not collapse them): `scrollElementIntoView` bumps it on entry and both the loop and the in-flight `tweenScrollTop` return the instant they are superseded. **EVERY writer of that pane INSIDE `LiveNotebook` bumps it**, the instant `block:'nearest'` keyboard-selection scroll (`scrollElementIntoViewNearest`, that component's one native-scroll choke point - do not add a second there) included: a selection scrolling OUTSIDE the guard would be undone by an in-flight loop's next corrective pass, and - selecting the SAME cell - its newer `pinSeq` would take pin ownership and unpin that target two frames later, so the older loop abandons on its `isConnected` guard and the jump silently lands nowhere. That helper is deliberately NOT a settle-loop caller (settle is for discrete jump targets; keyboard selection and follow-running stay single-scroll). **The known exception is `Cell.svelte`'s search-highlight scrolls** (the active match's anchor `scrollIntoView` + `EditorView.scrollIntoView` for a match inside a built editor, both pre-existing from Search P4): they write the same ancestor pane WITHOUT bumping `scrollGen`, and they fire during the find-bar jump's own settle loop. Bounded, not a fight - they target the very cell that jump is scrolling to, so the two converge - but their ordering relative to the loop's passes is not guaranteed; whether they should participate in the guard is a future call, deliberately not made here. So overlapping scrolls - the find bar's Enter-repeat, rapid outline/search clicks, a follow-running scroll landing mid-jump (a Run all fires one per cell) - never fight over the same pane, and it rests where the LAST caller asked rather than wherever the slowest loop exhausted. A superseded loop still returns normally, so its caller's release path runs and the seq check keeps it from unpinning what the newer jump now owns. Because the loop spans frames of DOM churn it re-checks `el.isConnected` each pass and abandons a target deleted/moved out from under it - a detached node measures an all-zero rect, which would otherwise read as "scroll to the top" on every remaining pass. **Print escape-hatch (done, in Search P5):** `+page.svelte` registers `beforeprint`/`afterprint` handlers that flip a `printing` `$state` and `flushSync()`, and threads an `effectiveVirtualize = virtualizeCells && !printing` into both `LiveNotebook`s - so a print/PDF un-windows and mounts every cell before the browser snapshots, then restores windowing (see the search-engine entry's P5 note; the Ctrl+F escape-hatch is subsumed by cellar Search owning Ctrl/Cmd+F). **Enablement (P5): windowing is ON by default for every notebook, and the only thing left to decide is how to turn it OFF.** There is deliberately **NO cell-count threshold anywhere** (the earlier plan's "default-on ≥~60 cells"): `planWindow` already emits no spacers when every cell fits the viewport + overscan, so a small notebook renders exactly as the eager `{#each}` did and a second, drifting copy of that rule in the shell would buy nothing. The precedence is pure and unit-tested in **`src/lib/virtualizePref.ts`** (`resolveVirtualize`, `tests/unit/virtualize-pref.test.ts`): the **`?virtualize=` URL param ALWAYS wins** (`0`/`false`/`off`/`no` off, `1`/`true`/`on`/`yes` on; anything else - including the bare `?virtualize` - is NO override, never a guessed side), else the persisted viewer preference, else on. The preference lives in the **per-project UI-state store** (`$lib/uiState` `cellar-virtualize-cells`, like follow-running-cell) - **not `localStorage`**, which is reset whenever the app port moves (a folder now usually keeps its port, but only when nothing else has taken it) - and it is toggled from **TWO surfaces, one preference**: the navbar View menu (`data-testid=toggle-virtualize-cells`, "Render all cells" / "Render only visible cells") and the Settings pane's "Windowed rendering" row (`Settings.svelte`, `data-testid=settings-virtualize-cells`, the discoverable home). Neither keeps a copy - `+page.svelte` owns the one `virtualizeCells` `$state` + `toggleVirtualizeCells()` and threads both into `Navbar`/`Settings` as props, so flipping either updates the other in-session and exactly one `VIRTUALIZE_PREF_KEY` value is ever persisted; a second control that read the pref itself would drift the moment the other one wrote. A session a URL param owns renders BOTH controls **disabled** rather than offering a switch that would change nothing (`virtualizeForced`), the Settings one adding a note naming the param (`data-testid=virtualize-forced-note`). `+page.svelte` threads the resolved value into both `LiveNotebook`s as `effectiveVirtualize = virtualizeCells && !printing`, so **print/PDF still un-windows and mounts every cell** (`beforeprint`/`afterprint` + `flushSync`, unchanged by the flip). `Notebook`/`LiveNotebook`'s `virtualize` prop still DEFAULTS to false - the shell is what turns it on - so a standalone mount renders eagerly. **This module is render-only** — it must never read, gate on, or mutate `cells` (the document model lives above the renderer, so MCP/agents, folding, staleness, git diff, streaming all ignore what's mounted). Covered by `tests/e2e/virtualization-scroll.spec.ts` (N=300: O(viewport) mounted, ~96% fewer DOM nodes, 0px scroll drift, flag-OFF reload mounts all N with 0 spacers) + `tests/e2e/virtualization-pinning.spec.ts` (P3, flag ON on the same N=300 harness: a cell streaming with follow OFF stays mounted and GROWS while scrolled away and its output is complete afterwards; queued heads mounted while an equally-far unqueued neighbour stays a spacer; the tab spinner jumps to the live running cell; an interrupt still clears the queue; an edited cell scrolled far out NEVER re-mounts - proved by a marker attribute a re-mount would destroy - and keeps its caret + undo history), both leaning on the shared browser-side helpers in `tests/e2e/notebook-scroll.ts`. P4 adds `tests/e2e/virtualization-jump-paths.spec.ts` (outline row, sidebar-search result, `j`/`k` across the overscan boundary with focus asserted, and follow-running - each to a target that starts as a spacer - plus a flag-OFF regression of the same jumps). There is deliberately **no clickable error/traceback link** in the app (tracebacks render as plain text), so that listed jump path has nothing to make virtualization-safe. P5 adds `tests/e2e/virtualization-default-on.spec.ts` - the ONE spec that passes no `?virtualize` param, pinning the default itself (large notebook windowed, `?virtualize=0` mounts all 300, a small notebook mounts the SAME cells with zero spacers, print safety, the View-menu opt-out surviving a reload while `?virtualize=1` still overrides it, and the Settings row driving that SAME preference - flipped in either surface the other agrees, it persists across a reload, and a `?virtualize=` session shows it locked with the reason). **Only the specs whose SUBJECT is a mode state one** (`&virtualize=0|1`): the four `virtualization-*` specs, the three `find-*` specs, and `lazy-editor-scale`, which pins `virtualize=0` because it measures the lazy EDITOR at full mount, a different axis. **Every other e2e spec (~28) passes no `virtualize` param at all** and therefore runs at the shipped default - they are unaffected only because their notebooks are small enough that `planWindow` mounts every cell with zero spacers (the same small-notebook transparency that makes the no-threshold decision safe), NOT because anything pins their mode. The one that outgrew that (`output-table-styling`, whose every test persists an output until the bottom cells start as spacers) addresses cells by `data-cell-id` and scrolls them into the window via `notebook-scroll.ts` rather than opting out - the pattern to copy, since `getByTestId('cell').nth(i)` counts only MOUNTED cells and so silently addresses the wrong one. Two of them lean on that deliberately: `follow-running-cell` and `tab-jump-running-cell` exercise following/jumping AT the windowed default, since that is the ordinary user path now, so their "the seeded notebook opened" proxy reads the SERVER document instead of counting mounted cells. The report §7 calls are all resolved and shipped (intercept Ctrl+F to app Search; don't pin edit-history - focused/active only; default-on, minus the threshold). The Ctrl+F and print escape-hatches are DONE (Search P5) and P4 re-verified the print one: ONE `beforeprint`/`afterprint` pair in `+page.svelte` (no second path).
