# Notebook search engine and find bar

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Notebook search engine (`src/lib/search.ts`) — P1-P5 of the phased find-in-page plan (COMPLETE; Search is the Ctrl/Cmd+F surface)** (design: `firstmate/data/cellar-search-findgrade-s4/report.md`). Pure `searchNotebook(cells, query, opts, cache): Match[]` over the **client model** `LiveNotebook.cells` (never the DOM), so it stays complete under virtualization. Returns **every** match in document order (not one-per-cell) so a caller can show a real `i/total`; each `Match` carries the `field` it came from (`source`/`markdown`/`output`/`id`, + `outputIndex`) so a later phase highlights the right surface. Substring, case-insensitive default (`SearchOpts` carries `caseSensitive`/`wholeWord`/`regex` — all honored: **`regex` (P5)** compiles the query once per call via `compileRegex(query,opts)` (`i` flag unless caseSensitive; `g` always), scanned by `scanFieldRegex` on the ORIGINAL text — the literal path keeps its cached-lowercase optimization untouched; an **invalid pattern returns `[]`, never throws** (the fail-safe the find-bar's invalid state reads), and a zero-length-capable match (`^`/`\b`/`a*`) nudges `lastIndex` so it can't spin). **`scope` is honored and defaults to `'all'`** (captain Q1 decision): `'all'` searches source + **rendered-markdown text** + **output text**; `'source'` narrows back to raw code/markdown source (P1 behavior). `DEFAULT_SEARCH_OPTS.scope` is `'all'` — unit tests that want the P1 source-only contract must pin `scope:'source'` explicitly. **Cell ids are a searchable field too (`field:'id'`, `scope:'all'` only), so the find bar answers a cell's HANDLE**: a cell surfaces its id in the toolbar `cell #xxxxxxxx` chip (which survives a full collapse), in multi-select and to agents, so typing it is a navigation Search should serve. The rule is the ONE exported predicate `matchesCellId` (used by the engine AND by `Cell.svelte`'s chip highlight, so a painted highlight and the count can never disagree): a **prefix** of the id — never a substring, matching the agent surface's `resolveCellId` — **floored at `ID_HANDLE_MIN` (8, kept in lockstep by value with `MIN_HANDLE` in `mcp/cellHandle.ts`, which a browser module may not import)**. That floor is the load-bearing part: a UUID is hex + dashes, so without it an ordinary short content query (`ca`, `de`, `abc`) is a valid id prefix and would silently address whichever cells happen to start with it, corrupting the `i/N` of a plain content search. **Regex mode matches no ids** (a pattern has no prefix semantics — `.*` would tag every cell), and `wholeWord` is not applied (an id is one opaque token; a boundary after the prefix would reject every prefix short of the whole UUID, i.e. the handle itself). One match per cell, emitted BEFORE that cell's content matches, so a cell matching by both counts as id + content and neither is double-counted; `dedupeMatchesForDisplay` leaves it alone. The view side is a fourth surface in `Cell.svelte`'s `applyHighlights` (`K_ID`, the `cell-id-copy` chip) which — deliberately unlike the source/output surfaces — is **NOT gated on `!cellCollapsed`**: the toolbar is exactly what a collapsed cell keeps on screen, so an id match there is the one match that stays visible (the good case). Navigation needs nothing new — `jumpToCell` mounts/reveals/flashes as for any match. The MCP `search_cells` tool is deliberately untouched (a separate implementation, and an agent already addresses a cell by handle directly). Covered by the cell-ids block in `tests/unit/search.test.ts`, the `id` case in `search-highlight.test.ts`, an id-query case in `search-perf.test.ts` (whose N=300 harness now carries real UUID ids, so every query at/past the floor really does prefix-test all 300), plus `find-bar.spec.ts` (prefix + full + below-floor, windowed-out) and `find-highlight.spec.ts` (the chip highlight, collapsed and not). **Rendered-markdown** is derived model-side by `strippedMarkdown(source)` (a light md-syntax strip — headings/emphasis/links/code/list markers — so a heading's *visible* words match; never parses HTML/DOM). **Output text** is extracted browser-safe by mirroring `Cell.svelte`'s `renderOutput` (stream text, `text/plain` repr, ANSI-stripped tracebacks, and the structured `application/vnd.cellar.dataframe+json` payload flattened to header+index+cell values); rich non-text output (image/plotly/iframe-html with no `text/plain`) contributes nothing. **The mechanical primitives (`asText`/`stripAnsi`/`DataFramePayload`) live in `$lib/outputText.ts` and are shared with `$lib/copyCell.ts`, but the PRIORITY above is deliberately NOT** - it differs in two places (see the copy-input/copy-output note in the UI entry), so changing what an output contributes as text means deciding for both surfaces, not editing one. Output scanning is **capped per cell at `SEARCH_SCAN_CAP=100_000`** (own constant, kept in lockstep with the MCP `search_cells` cap in `mcp/service.ts` — NOT imported, to keep server code out of the browser bundle) so one query can't serialize megabytes; a match past the cap in one giant output is the accepted miss. **The perf primitive is a per-cell searchable-text cache** (`SearchCache = Map<cellId, CacheEntry>`) with **independent invalidation per field**: `sourceLC`/`markdownLC` key off a cheap content **signature** (`contentSignature` = FNV-1a folded with length — an integer pass, no allocation) so a source edit rebuilds them in place (the entry object is REUSED, not replaced — do not re-assert object identity on edit), while the **outputs cache keys off the outputs' ELEMENT identities** (length + per-element ref, snapshotted in `outputElems`) — NOT the `cell.outputs` array identity, because LiveNotebook grows/rewrites that array IN PLACE during a run (each mutation replaces the element object at an index) so array identity would serve stale mid/post-stream text — so editing source never re-extracts unchanged outputs and vice-versa. A cache hit reuses the lowercased buffers and never re-folds case; lowercasing/extraction is once-per-content-change, not per-keystroke. Snippet extraction is **bounded** (`snippetFrom` reads ≤`SNIPPET_CAP`+64 chars from a line-start tracked in O(1) by `scanField`), so a pathological single 100k-char line with thousands of matches never costs O(lineLength) per match. **The cache is owned by `LiveNotebook`** (`createSearchCache()`, registered up via `onRegisterSearchCache` → `+page.svelte` `searchCaches[path]` → `activeSearchCache` → Sidebar's `searchCache` prop); the sidebar falls back to a private cache when none is registered. **Sidebar Search** (`Sidebar.svelte`) is rewired onto it: query **debounced ~120ms**, a **Source/All scope toggle** (`data-testid=search-scope`, default All), `searchNotebook` → `groupByCell` gives one row per cell (navigation to the cell, unchanged) with a per-cell count badge + a real **total match count** (`data-testid=search-count`). Match offsets/lines assume length-preserving case folding (true for realistic scripts; the pathological expand-on-lower like `İ` is a known limit). Covered by `tests/unit/search.test.ts` (positions/counts/order/unicode; output+markdown coverage; per-cell cap; per-field cache invalidation; toLowerCase-call-delta proofs) + `tests/unit/search-perf.test.ts` (N=300 single-call within a frame; N=300 with multi-MB outputs stays bounded; steady-state flat vs cold). **P3 — the floating find-bar (`src/lib/FindBar.svelte`).** A find-in-page widget over the top-right of the active notebook pane (mounted once in `+page.svelte`'s `<main>`, `data-testid=find-bar`): a query box, a live **`i / N`** count (`find-count`), prev/next chevrons, and case (`Aa`, `find-case`) / whole-word (`\b`, `find-word`) / **regex (`.*`, `find-regex`, default OFF, P5)** toggle chips. It runs the SAME `searchNotebook` engine + shared `activeSearchCache` as the sidebar (never a second engine; the sidebar list view **stays**), deduped for display so the count is visible-occurrences. Keyboard: **Enter**=next, **Shift+Enter**=prev, **F3/Shift+F3**=next/prev (a window capture listener so they work with focus anywhere), **Escape** closes and returns focus to the notebook; opening seeds the query from the current text selection (`window.getSelection()`). **Entry points (P5 makes Ctrl/Cmd+F the primary one):** the `open-find` shortcut is bound to **`Mod-f` AND `Mod-Shift-f`** (`shortcuts.svelte.ts`), handled shell-level in `+page.svelte`'s capture keydown beside `command-palette`/`save-notebook` - it **intercepts the browser's native find** (`preventDefault` + `stopPropagation`) and opens this bar instead, ONLY when a notebook is active and no modal is up (a plain file tab / a modal lets Ctrl+F fall through to the browser). A repeat Ctrl+F while the bar is **already open** re-focuses + re-seeds it (native-find behavior) rather than closing: `openFindBar()` bumps a **`reseedSignal`** the bar watches (do NOT toggle `findOpen` on a repeat). Also opens from the sidebar Search-section button (`open-find-bar`). **Regex fail-safe:** an invalid pattern shows a subtle `find-invalid` "bad regex" state (input tinted `text-error`, `aria-invalid`) and matches nothing - never a crash. **The single navigation seam is `LiveNotebook.jumpToCell(id, opts?)`** (on `NotebookApiHandle`, reached via `activeNotebookApi()`), built on **`ensureCellMounted(id)`** — reveal (unfold) + `pinScrollTarget` + `tick` + query the node — the ONE primitive that makes an off-screen cell reachable; `revealRunning`/`followCell`/keyboard selection share it, and virtualization P4 routed the sidebar outline + search rows onto the same `jumpToCell` (see the virtualization entry). **This is the virtualization cooperation:** under windowing (the default since P5) a match in a windowed-out (spacer) cell still navigates because `jumpToCell` mounts it before scrolling. `jumpToCell` centers + flashes the whole cell (P3's §5.3 fallback, still the coarse "you're here" cue); match-precise scroll + in-place highlight is P4. Covered by `tests/e2e/find-bar.spec.ts` (count, next/prev/F3 in doc order + wrap, Escape+focus, seed-from-selection, folded-section unfold, virtualization windowed-out jump, case/word toggles). **P4 — in-place highlight of every match + active-match emphasis (view-only overlay, mounted cells only).** The find-bar (sole owner of the search) publishes its query/opts/deduped matches/active index into ONE shared `$state` `SearchHighlightState` (`+page.svelte`, `searchHighlight.ts`), scoped to the searched notebook by `notebookPath === path` in `LiveNotebook` (cell ids repeat across the several mounted notebooks, so this gate is what keeps a background notebook dark). `searchHighlight.ts` (pure, unit-tested) maps the flat match list onto a per-cell payload via **`buildCellHighlights(matches, activeIndex)`** (a cell appears iff it has ≥1 match; exactly one carries the `active` descriptor `{field, outputIndex?, ordinal}` — `ordinal` = the active match's position among the cell's matches of the same field-group), and exposes **`findOccurrences`**, the literal substring/whole-word scanner the DOM highlighters reuse (mirrors the engine's `scanField`, so highlighted spans match the count). Two paint mechanisms, split by surface, **never mutating `cells`** (mirrors the virtualization render-only invariant): (1) **`domHighlight.ts`** — the **CSS Custom Highlight API** for the *rendered* surfaces (`static-code` `.cm-static-content`, `markdown-rendered`, output `outputInner`, plus the toolbar `cell-id-copy` chip - the fourth surface, added with cell-id search above, and the one that is NOT gated on `!cellCollapsed`): `buildTextRanges` walks a container's text nodes (concatenate + binary-search offset→node, so a match spanning inline syntax-highlight tokens still paints; a typeset-math subtree is substituted by its source TeX and the returned array is **POSITIONAL with `null` holes** — see the TeX-math entry, index by ordinal and never compact it) and registers two named highlights, `cellar-search` (all) + `cellar-search-active` (priority-1, distinct opaque style), rebuilt from the union of live per-surface contributions (coalesced to one microtask); keys are per-cell-INSTANCE (`allocSurfaceKey()`, never the cell id). A reversible `<mark>`-wrap fallback covers engines without the API (Chromium always has it). (2) **`cmSearchHighlight.ts`** — for a BUILT editor, a decoration ViewPlugin driven by `setCmSearch` reusing `@codemirror/search`'s `SearchQuery` matcher + the theme's existing `.cm-searchMatch`/`.cm-searchMatch-selected` classes (NOT `@codemirror/search`'s own highlighter — it paints only when its panel is open). So a code cell's source highlights on its StaticCode stand-in (CSS) until its editor is summoned, then on CM decorations — the active emphasis is a `cellar-search-active` range OR a `cm-searchMatch-selected` node accordingly. `Cell.svelte`'s `applyHighlights` (a `$effect` that re-runs on query/opts/active/editorBuilt/mode/codeHidden/**cellCollapsed**/**segHidden**/outputs/source, applied after a `tick`; that collapse dep is load-bearing, not tidiness - see the Full-cell collapse entry, and `segHidden` is the same rule one level finer: an OUTER heading fold drops a still-visible cell's BODY via `{#if}` too, so unfolding re-creates it as fresh DOM and detaches the Ranges registered into it) paints its visible surfaces + scrolls the active match into view (`block:'nearest'` + `EditorView.scrollIntoView`); clears on find-close (query empties) and on cell unmount. Colors: `--cellar-search-all` / `--cellar-search-active-bg`/`-fg` in `app.css` (`::highlight()` + `mark.cellar-search-mark*`), theme-aware. Both DOM highlighters (`findOccurrences`) and the CM decoration plugin (`SearchQuery({regexp})`) honor `regex`, so a regex query highlights the SAME spans the count reports. Covered by `tests/unit/search-highlight.test.ts` (findOccurrences + buildCellHighlights, incl. regex) + `tests/e2e/find-highlight.spec.ts` (all-surface highlight incl. StaticCode CSS AND built-editor CM path, single active emphasis that follows next/prev, active scrolled into view, view-only no-`<mark>` proof, clear-on-close, virtualization windowed-out cell highlights once navigated-to). **P5 (find-in-page COMPLETE):** Ctrl/Cmd+F intercept + regex toggle landed (see the P3 entry's entry-points note); **print safety** - because virtualization windows cells out of the DOM, `+page.svelte` registers `beforeprint`/`afterprint` that flip a `printing` flag and `flushSync()` so an `effectiveVirtualize = virtualizeCells && !printing` derived un-windows (mounts every cell) before the print snapshot, then restores. Covered by `tests/e2e/find-ctrlf.spec.ts` (intercept prevents native find, seed-from-selection, repeat re-seeds not closes, regex on/off/invalid, and beforeprint mounts all cells under virtualization).
