# Notebook code roots and git worktrees

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Notebook code roots — one instance, several checkouts of one repo (`src/lib/notebookRoot.ts` + `src/lib/server/notebookRoot.ts` + `notebook-root-actions.ts`).** A notebook may declare `metadata.cellar.root = "roots/pr-482"` (inside the workspace) **or `"../winrate-model-pr398"` (a registered git worktree OUTSIDE it)** — in the allowlisted `cellar` namespace so it round-trips clean-on-save with zero git diff; absent/empty = the workspace root, which is the DEFAULT and byte-for-byte today's behavior. The use case is a review notebook pointed at the branch under review, re-run after a fix to see which findings clear. **A root changes EXACTLY two bindings, both already parameterised on a path** — the kernel PROCESS's cwd (`getKernel` sends the root as the `path` field of the kernel-start request; jupyter_server resolves it under its `root_dir` = the workspace via `cwd_for_path`) and the `sys.path` entry `initKernel` injects (`projectRootAddCode`). **Everything else stays WORKSPACE-scoped and must not be "extended" into a root**: the file tree, git status/decorations/blame, search, checkpoints, the UI-state store, `.cellar/` runtime + harness config, the instance registry, and the INTERPRETER (one venv per instance, unaffected). Kernels were already per notebook, so two notebooks on two roots are already two processes with two namespaces — this only changes where each one's code comes from.
  - **THE GUARD is load-bearing, not the rule "roots live inside the workspace" — and the difference is the whole design.** `resolveInWorkspace` (`fstree.ts`) is UNCHANGED, byte for byte, and stays the sole authority for every FILE path in the app (the tree, `/api/fs/*`, `gitHeadFile`, `gitBlameFile`, the export target, the notebook path guard). **Do not widen it.** What was added is a SECOND, strictly NARROWER admission rule, and only for `metadata.cellar.root`: a path outside the workspace is admitted only when **`git worktree list --porcelain`, run in the workspace, names that exact directory** — so the admitted set is authored by the user's own `git worktree add` runs against the workspace's OWN repo (same-repo only; a worktree of a different repo stays refused). `resolveRootDir` branches ONCE — `inside` -> the untouched guard, `outside` -> the worktree gate — and both branches then share the same existence + directory-ness checks, because a REMOVED worktree still lists (`prunable`): the listing authorises, `statSync` decides usability. **THE GUARD ITSELF PICKS THE BRANCH, and that is what makes "the authority" structural rather than a coincidence**: `isOutsideWorkspace` (exported from `notebookRoot.ts`) ASKS `resolveInWorkspace(toRel(dir))` and treats its THROW as the outside verdict, so `notebookRoot.ts` holds no containment rule of its own. A local `insideWorkspace` copy of the guard's lexical prefix test deciding the branch — and then calling the guard inside it, where `classifyRootPath` had already made the call unreachable — meant the doctrine held only for as long as the two rules happened to agree. **That helper is the app's ONE answer to "is this directory inside the workspace", and every site asks it**: the branch, `ResolvedRoot.kind`, the picker's `external` flag (`notebook-root-actions.ts`) and the sidebar's worktree rows (`/api/fs/git/roots`) - because the rule then got written again in those last two, one comparing LEXICAL paths and one REALPATH'd ones, so the picker could label a checkout internal while the sidebar labelled the same checkout external, the exact misreading that tag exists to prevent. It must be asked about a LEXICAL path, so the route mints the declaration (`worktreeDeclaration`) first and resolves it from the workspace - git's realpath'd path would read a worktree genuinely inside a symlink-traversing workspace as external. Pinned by SOURCE GUARDS in `tests/unit/worktree-roots.test.ts` covering ALL THREE files (no `startsWith(... + sep)` anywhere, no `insideWorkspace`, the guard really called on the declared directory, and both label sites reaching the shared helper) - the first version watched `notebookRoot.ts` alone, which is precisely how the two divergent copies got in. **WHICH RULE ADMITTED A ROOT AND WHERE THAT ROOT SITS ARE TWO QUESTIONS, and `kind` answers the second, off the CANONICAL directory**: read off the branch it was a property of the INPUT, so pasting the absolute path git printed for a worktree that lives INSIDE `roots/` (on any symlink-traversing workspace, i.e. every `mkdtemp` one) failed the lexical guard, was admitted by the gate, and came back `kind:'worktree'` while `rel` normalized straight back to `roots/pr-1` - so an INTERNAL root got agent config written into it and had its external-root cwd verification run, and the same directory declared relatively classified as `'workspace'`. The gate's `GitWorktree` still names the repair for a registered-but-gone directory (`git worktree prune`), which is what it, and only it, knows. **REGISTERED IS NOT SUFFICIENT — a checkout that CONTAINS the workspace is REFUSED** (`enclosesWorkspace`, the enclosure sibling of that containment rule, defined once in `notebookRoot.ts` and asked everywhere): `git worktree list` walks UP to find the repo, so a workspace that is a SUBDIRECTORY of a checkout (`cd repo/analysis && cellar`) sees its own PARENT as the listing's first entry, and the gate's only exclusion was the workspace ITSELF. Admitted, it rooted the kernel ABOVE the tree Cellar is serving (its cwd and `sys.path` covering the workspace) and wrote `.mcp.json` into the workspace's parent - never a designed capability, only a side effect of the main checkout always being listed. It is refused AFTER the gate so the message can say what is TRUE (it is registered, and it encloses) rather than the gate's "not a registered worktree", which would be false here, and it is dropped from the detection listing, the sidebar's WORKTREES rows and the gate's own "what IS registered" message, so it is neither offered nor accepted. **A worktree root grants a kernel cwd and NOT ONE BYTE of file reach**: every other surface stays workspace-scoped and still resolves through the guard, which is what `tests/e2e/notebook-roots-worktree.spec.ts` asserts against `/api/fs/tree` and `/api/fs/file`, and what the SOURCE GUARD in `tests/unit/worktree-roots.test.ts` pins (that test asserts `fstree.ts` contains no worktree branch at all — e2e runs only on the PR, not in the pre-push no-mistakes gate, so the security-shaped invariant needs a unit-level assertion that fails BEFORE a push rather than after one). What genuinely changed, and is stated rather than glossed: **the kernel PROCESS's cwd may now sit outside the workspace.** That is the feature, and it is what `git worktree list` is being asked to authorise.
  - **THE TWO-NAMESPACE RULE — verify by realpath, BIND and PERSIST lexically.** The subtlest thing here, and the one that gets "simplified" into a single `realpathSync` and then breaks on one platform. `git worktree list` returns **realpath'd** paths while `CELLAR_WORKSPACE` and jupyter's `root_dir` are the **lexical** `resolve()`d string (macOS: `/tmp` -> `/private/tmp`, `/var/folders` -> `/private/var/folders`, i.e. every `mkdtemp` workspace, so real users AND the e2e harness). So VERIFICATION compares `realpathSync` of both sides for IDENTITY — safe, and NOT what the symlink note below forbids, which is about realpathing one side of a PREFIX containment test. **That applies to EVERY "are these the same directory" test, the "this declaration IS the workspace" short-circuit in `resolveRootDir` included, where a LEXICAL `===` may be a fast path in front of the canonical one but never the whole rule**: `git worktree list`'s FIRST line is the MAIN CHECKOUT, realpath'd, and this branch accepts absolute paths precisely so a user can paste what git printed — so on a symlink-traversing workspace that paste missed the lexical short-circuit, reached the worktree gate and MATCHED (the main checkout being a listed worktree), yielding a root that IS the workspace, persisted as `../../../private/var/…` in a COMMITTED `.ipynb` and labelled `kind:'worktree'`, which would run the external-root cwd verification against the workspace and write agent config INTO it — rewriting the very `<ws>/.mcp.json` that "an ordinary workspace launch is untouched" promises. The canonical check is confined to the outside branch, so an ordinary `roots/…` root pays no `realpathSync` for it. But BINDING and PERSISTING stay LEXICAL, because `to_os_path` joins onto the lexical `root_dir` without resolving symlinks; the realpath'd relative form would put a machine-specific `../../private/var/…` into a COMMITTED `.ipynb`. The one conversion from git's namespace to a declaration lives in `worktreeDeclaration()` (`server/notebookRoot.ts`) and is used by **every** producer of a declaration — the picker, the sidebar route, and `resolveRootDir` ITSELF, whose worktree branch normalizes through the `GitWorktree` the gate matched rather than measuring `relative(lexicalWs, dir)`. That rule has now been got wrong once per site that re-derived it, always the same way and always SILENTLY (the wrong form still resolves, it is just machine-specific and is a SECOND spelling of one checkout, so the sidebar kept offering "Use as root" for the root a notebook was already on) — so do not inline a fifth. The helper VERIFIES its own answer rather than assuming it: the hop is measured in the real namespace and applied in the lexical one, which is exact only while the symlink separating them sits ABOVE the hop, so a declaration that does not resolve back to the worktree git reported falls back to the lexical measurement — ugly beats pointing elsewhere. Pinned by the SYMLINKED-workspace block in `tests/unit/worktree-roots.test.ts`, which drives the path GIT PRINTS (never a `mkdtemp` string, whose two namespaces coincide — that is what made three previous fixes look verified) through resolve-from-absolute, resolve-from-`..`, detection, the route and the MAIN CHECKOUT's own path (which must resolve to NO root, never to a `kind:'worktree'` one), and asserts they all agree on ONE spelling; a SOURCE GUARD there pins the canonical identity test too, since the round-5 guard watched only the CONTAINMENT rule and this is the same failure mode asking a different question. **NEVER hand jupyter an ABSOLUTE path**: `to_os_path` strips the leading `/` and joins, so `/Users/x/repo` becomes `<ws>/Users/x/repo`, which does not exist, and `cwd_for_path` then walks UP and silently starts the kernel elsewhere — the exact silent degrade this feature exists to prevent. That is why `ResolvedRoot` splits `rel` (the persisted declaration) from **`apiPath`** (what `getKernel` sends) and carries `kind`; and why `initKernel` VERIFIES a `kind:'worktree'` kernel's real cwd once at startup and **FAILS the start** on mismatch (`verifyKernelCwd`), so the promise "a root never silently degrades" holds against the TRANSPORT and not only the filesystem. **BOTH callers of `initKernel` must tear the kernel down on that refusal - and publish the `kernel:status` snapshot before rethrowing, like every other `teardownKernel` caller, since `teardownKernel` publishes only the per-notebook `kernel:shutdown` and the sidebar's cards come from that snapshot (else a refused restart leaves a card on screen with its controls enabled for a kernel that is gone) - not just `getKernel`** — `restartKernel`'s entry is ALREADY in the `kernels` map with a resolved `startPromise`, and `getKernel` short-circuits on an existing entry without re-verifying, so a refusal that merely propagated left every LATER run executing against the kernel whose cwd had just been refused: the exact silent degrade the check exists to prevent, reached through the one door that looked safe. Pinned in both directions by `tests/unit/kernel-root.test.ts`.
  - **What is PERSISTED is the `..`-relative form** — an ABSOLUTE path is accepted at the API (it is what `git worktree add` prints and what a user pastes) and normalized at the ONE validate-and-store site, `resolveRootDir`, which returns the stored form so no caller keeps a divergent copy (the nbdev export-target precedent, for the same reasons: portable to any machine reproducing the layout, and leaking no home directory into a shared repo). Its limit is stated rather than hidden: a checkout that does not reproduce the layout gets a root that REFUSES loudly, which is the correct direction. Re-declaring one directory in its other spelling is a genuine NO-OP — compared by resolved DIRECTORY (`isSameDeclaredRoot`), never by text, since `sameRoot` is pure/browser-safe and cannot resolve a path; getting that wrong costs the user their namespace on every re-declare. **Every refusal names its own repair**: gone-but-registered says `git worktree prune`; removed says it is no longer registered; **MOVED names the NEW path**, matched by the worktree's REGISTRATION NAME (`<repo>/.git/worktrees/<name>`, read from the worktree's own `.git` file), which survives `git worktree move` — a basename match would not, since a move usually changes it. A move is deliberately NOT auto-followed: rewriting a committed `.ipynb` because a directory moved is a silent change to the user's file.
  - **A root that is a SYMLINK out of the workspace still resolves** — the guard is lexical and `statSync` follows links — and that narrowing remains **accepted, and must not be "fixed" in `notebookRoot.ts`**: the same lexical guard backs the file tree and `/api/fs/file`, so such a symlink already reads outside everywhere else, and realpathing the root alone would refuse legitimate setups (the `/tmp` -> `/private/tmp` case above). It is now the WIDER of the two out-of-workspace routes — a symlink may point anywhere, whereas the worktree gate admits only checkouts of this repo — which is also the argument that the gate does not widen the boundary. The picker DOES now enumerate a symlinked root (`listWorkspaceRoots` accepts a dirent whose `statSync` target is a directory): such a root already resolved and already ran, so the picker was the one surface that could not see something the rest of the app happily used. Reasoning lives at the seam, in that module's header. The conventional home is a visible `roots/` directory (`ROOTS_DIR`) — deliberately not `.roots/`, since `buildTree` skips dot-prefixed entries and the review files must be browsable; a root may sit anywhere inside the workspace, `roots/` is just one of the three things `list_roots` and the picker enumerate.
  - **Detection: every registered worktree is OFFERED, and being listed is not being authorised.** `listWorkspaceRoots` reads three sources — `roots/`, live notebook declarations, and `git worktree list` — deduped by REALPATH (a worktree under `roots/` appears in two of them) with the workspace-relative declaration WINNING where both spellings exist, and the workspace's own checkout excluded (it would duplicate the picker's "workspace root (default)"). Branch/HEAD for a detected root come from the porcelain stanza, so detection costs no `gitRefAt` spawn per root; each candidate is validated through `resolveRootDir`, so the picker can only ever offer a declaration that really resolves. Internal roots sort first, then external. Detected external worktrees are offered **by default and are LABELLED** (`external: true` to agents, "(external worktree)" in the picker, an `external` chip in the sidebar) so nobody adopts a sibling checkout believing it sits inside the workspace. **`resolveRootDir` re-verifies on EVERY resolve**, so a worktree removed after a listing is still refused — and, on a MISS, it re-reads the listing once before refusing, because the 1.5s cache would otherwise be a window in which a worktree the user created seconds ago is reported as unregistered. **That forced re-read is itself bounded, by `WORKTREE_FORCE_TTL_MS` (250ms) and by the FORCED reads alone** — misses arrive in BURSTS (the roots route resolves every open notebook in ONE request, up to `MAX_PATHS`, and that panel refetches on mount, on `sse:open`, on `fsRefreshSignal` and on every window focus), so unbounded it was a blocking `spawnSync` per notebook per focus on the process carrying the kernel websockets and the SSE fan-out. It is served from cache only when a previous FORCED spawn is that recent, **never merely because an ordinary read repopulated the entry** — an ordinary listing may predate the very `git worktree add` this caller is about to refuse, which is exactly what the force exists to get past, while a forced listing milliseconds old cannot tell a different story to the next refusal in the same burst.
  - **`listWorktreesAt` (`git.ts`) is the ONE worktree reader, and it is SYNC on purpose.** `resolveRootDir` is called synchronously from `getKernel`, `assertRootUsable` and the roots route, so an async rule would thread through all three while a second async reader beside it could answer differently. One cheap `spawnSync` (it reads `.git/worktrees/*`, touches no objects) on the `jupytext.ts` persist precedent; it logs through the same `noteSpawn` as `runGit`, so the "this refused without spawning" measurements the suite depends on stay honest. Cached on the tight `STATUS_TTL_MS` (1.5s) tier - a burst (picker + `list_roots` + sidebar) is one spawn while a `git worktree add` in a terminal shows up promptly - and deliberately NOT memoized for the process lifetime the way `preflight` is: preflight caches repo IDENTITY, which does not change, whereas the worktree set changing is the entire point. **Comparing a candidate against that listing costs ONE `canonicalPath` walk for the candidate and one per ENTRY, memoized on the entry OBJECT (`canonicalWorktreePath`) - not `samePath` per row, which resolves BOTH sides.** `samePath`'s string fast path essentially never hits here (the candidate is lexical, git's path realpath'd - the reason it exists), and `listWorkspaceRoots` resolves once per DETECTED worktree, so the per-row form was O(N²) blocking `realpathSync` walks on a path `LiveNotebook` runs at every notebook mount - measured 520 walks at N=20, versus 81 hoisted+memoized. Keying the memo on the object rather than the path string is what makes it safe: `listWorktreesAt` hands back the same entries for the life of its cache and mints fresh ones on the next spawn, so the memo expires with the listing it belongs to and can never outlive the answer it caches. **The WORKSPACE side of those comparisons is HOISTED, not memoized** (`canonicalWorkspace()`, exported; `enclosesWorkspace` and `worktreeDeclaration` take it as an optional argument defaulting to it, so a lone call is unchanged): it is the right-hand operand of nearly every identity/containment question here, and left to the defaults the sidebar route re-walked it THREE times per registered worktree - one in `enclosesWorkspace`, two in `worktreeDeclaration` - on a panel that refetches on mount, on `sse:open`, on every `fsRefreshSignal` and on every window focus, with a worktree per PR under review (`MAX_WORKTREE_PROBES` bounds the git subprocesses, never these syscalls). Its per-row `realpathOrSelf(w.path)` is computed ONCE and reused as both the workspace-exclusion operand and the commit-map key, rather than walked twice to ask the same thing. Deliberately NOT a process-wide memo keyed on the workspace path: that is the silent staleness this module is written against, and hoisting expires with the request.
  - **Agent config in an ADOPTED worktree (`worktree-agent-config.ts`), ON by default.** An agent working in a review notebook rooted at a sibling worktree runs its own tools with that worktree as the cwd, so without a `.mcp.json` there it cannot reach the Cellar serving the notebook. Five rules, each a decision: it is **adoption-scoped** (only a worktree actually SET as a root - never on detection, or a picker open would drop untracked files into every checkout of the repo as the side effect of a READ); it goes through the **existing** `configureHarness(name, dir, opts)` and never a second writer; **the entry it writes NAMES THE INSTANCE (`instanceArgs`), because the canonical one cannot reach it** - `cellar mcp` with no argument reads `<cwd>/.cellar/runtime.json` and does NOT walk up, so the canonical `{command:'cellar', args:['mcp']}` is right only for a config at the root of the workspace Cellar runs in and is INERT in a worktree (the agent's cwd is that checkout, no instance is running there, the bridge exits 1) - i.e. Cellar dropped a file into a checkout the user did not open, added a repo-common ignore rule for it, and the agent still had no Cellar tools; so the worktree copy carries `--workspace <absolute workspace path>`, which is exactly what that flag is (an instance selector), reaching **every** allow-listed harness's FORMAT (a `.codex/config.toml` without it is inert the same way) since `opts.args` is a property of the one writer rather than of one format, and it also decides IDEMPOTENCE there so a re-adoption is still `already`. **But it NEVER TAKES OVER an existing `cellar` entry that says something else** (`preserveExisting`), which is the cost of naming the instance: once the entry carries a selector, rewriting someone else's is a REDIRECT, not a repair - a worktree the user ALSO runs Cellar in has the canonical bare `['mcp']` written by its OWN launcher (correctly carrying no selector, that instance being reachable from that cwd), and adopting it re-bridged every agent working there to the ADOPTING workspace, after which that instance's next `reconcileHarnesses` wrote it back and the two churned the file, each redirecting the other's agent. Such an entry is left byte-identical and reported `skipped` naming the conflict - the refuse-rather-than-clobber stance both writers already take - and its exclude is taken back with it, since nothing was written. Scoped to THIS path: the WORKSPACE's own config is still repaired on every start, which is what makes the allow-list a standing instruction. The absolute path is machine-specific and that is acceptable HERE AND ONLY HERE - this file is excluded from git and never committed - so do not "fix" it into a relative path, which cannot resolve from an arbitrary agent cwd; **what an ordinary workspace launch writes is untouched and stays byte-identical** (pinned in both directions by test). It is gated on the **WORKSPACE's** allow-list (`readAllowList`, which already returns only allowed registry-normalized names - never re-asked per harness) and on `--no-mcp-config` (the workspace is where the user answered the harness question; a worktree cannot be asked, there being no TTY). **What it writes is EVERY allow-listed harness's config, not `.mcp.json` alone** - a workspace that ran `cellar harness add codex` gets `.codex/config.toml` there too, which is the several-harness case the per-name verdicts below exist for, so the Settings toggle NAMES both files rather than implying one (it is the control that decides whether Cellar writes into a checkout the user did not open, so it may not understate that) and `--no-mcp-config` subtracts only the harnesses whose config file IS `.mcp.json`. **A skip is attributed to that flag only when the flag really removed something**: `cellar harness remove claude` leaves an explicitly EMPTY allow-list, so nothing would have been written whatever the flag said, and since this message rides `agentConfigNotice` onto the root bar and the sidebar, naming a cause that did not happen is worse than the `undefined` that honestly says nothing was addressed. And it is caught per harness and **REPORTED on `SetRootResult.agent_config`, never thrown** - agent wiring may never abort a root change. That report is only worth anything if it REACHES someone, so it rides the MCP `set_notebook_root`/`use_notebook` result and both human surfaces (the notebook's root-bar feedback line and the sidebar's "Use as root") through the ONE shared `agentConfigNotice`, which decides from the **STATUS and an explicit `warning` field, never from the presence of a `message`** - `configureHarness` sets a message on EVERY outcome ("added the cellar MCP server", "already configured"), so keyed off that the notice appended a line to every single adoption and buried the one case it exists to surface in that chatter. Silent on an ordinary success (`created`/`updated`/`already` with nothing wrong), never silent on a `skipped` harness or on the case that leaves the checkout dirty. **The write is paired with an entry in the repo-COMMON `info/exclude`, reached by `git rev-parse --git-common-dir`** and written BEFORE the config so the file is never briefly visible as an untracked change. **That ordering is what makes the write TRANSACTIONAL rather than merely ordered**: the entry is in place before the writer has said whether it will write anything, so a harness that comes back `skipped` (an existing `.mcp.json` it refuses to edit, an unreadable one, an EACCES) would leave an ignore rule for a file Cellar never wrote - and at repo-common scope that hides the user's OWN root `.mcp.json` from `git status` in every working tree of the clone and makes `git add` refuse it. So a skipped harness's entry is TAKEN BACK (`revertGitExclude`), and only the exact bytes THIS call appended are spliced out, so an entry the user or an earlier adoption already had is untouched and the file comes back byte-identical - and byte-identical LITERALLY, including for a repo that had no exclude file at all: `ensureGitExclude` records that it CREATED one and the revert then removes it rather than leaving a zero-byte `info/exclude` behind (git treats absent and empty the same, so that is the header's honesty claim rather than behavior, which is exactly why it has to hold; the removal is gated on this CALL having created the file AND nothing else having landed in it since - decided for the call, NEVER per harness, because the exclude loop runs for every allow-listed harness before any config is written, so with two allowed the first append creates the file and the second sees one already there, and reverting both then wrote back an empty file where the repo had none). **THE SEPARATOR NEWLINE OBEYS THAT SAME CALL-SCOPED RULE, and is the other reason a revert may only ever remove bytes this call ADDED**: an exclude that does not end with `\n` needs one before an entry can be appended, and that newline is ours - but it TERMINATES the user's last line, and once a second harness has appended after it, it is load-bearing for a block that is STAYING. Folded into the first harness's own appended slice (`prefix + marker + entry`), a PARTIAL revert (claude refused, codex written) spliced it out with claude's block and joined the user's final entry to the surviving marker - `build/# added by cellar…`, so their `build/` pattern was gone and a line that no longer starts with `#` became an ACTIVE ignore pattern across every working tree of the clone. So each harness's `appended` is SELF-CONTAINED and the separator lives on the CALL (`ExcludeCall`, beside the baseline `original`, read ONCE before the loop): it is taken back only when the remainder is exactly `original + '\n'`, i.e. every block this call wrote is gone - compared against the original BYTES, so a line something else appended meanwhile keeps it. Pinned in both directions (a partial revert leaves the original plus ONLY the surviving harness's block, asserted as a whole string since "does not contain /.mcp.json" passes against the corrupted form too; a full revert restores the missing newline). Cellar does not leave an ignore rule behind for a file it did not write, and does not rewrite one byte of what the user wrote. **The pattern it writes is `/`-SEPARATED, through `excludePattern`, never the platform separator sliced off the worktree prefix**: a gitignore pattern uses `/` on every platform while `HARNESSES` builds codex's path with `join`, so a Windows run wrote `/.codex\config.toml`, which matches nothing - the file stayed untracked-dirty while `warnings()` read the exclude as arranged and said nothing, a silently false "ok". Pinned by a SOURCE guard, since on POSIX `join` already yields `/` and a behavioural assertion passes against the broken form. **Its scope is repo-common, NOT per-worktree, and that must be stated rather than glossed:** `info/` is in git's `common_list`, so git resolves `info/exclude` through the common git dir whatever worktree asks - an entry written to a linked worktree's own `$GIT_DIR` (`<main>/.git/worktrees/<name>/info/exclude`) is read by **nothing at all** (verified against git 2.50.1: `git status` there still reports `?? .mcp.json` and `check-ignore` says not ignored), so `--absolute-git-dir` is the wrong question and must not come back. The entry therefore covers every worktree of that clone AND the main checkout. **It is ANCHORED (`/.mcp.json`), which is what bounds that scope to the TOP LEVEL of each working tree rather than to any depth:** a gitignore pattern with no slash in it matches everywhere, so an unanchored entry in the repo-COMMON exclude made every untracked `.mcp.json` anywhere in the clone invisible to `git status` and refused by `git add` - wider, and a worse surprise, than the dirty checkout the mitigation removes (it also made the two harnesses inconsistent, `.codex/config.toml` containing a slash and so already being root-anchored). Pinned in BOTH directions by test, since an assertion on the root file alone passes against the unanchored pattern too. What the on-by-default decision actually rests on is unchanged: `info/exclude` is never committed and never reaches teammates, so no `git add -A` can put Cellar's config onto the branch under review. That mitigation is what makes on-by-default defensible: `.mcp.json` is tracked-by-convention and ignored by nothing, so without it Cellar would dirty a checkout it is also REPORTING on in its own sidebar. **The excludes are attempted for EVERY harness before the aggregate verdict, and each verdict is kept AGAINST ITS OWN NAME** - a short-circuiting `.every` skipped the rest after the first failure and left their configs written with no ignore entry, and a single AND'ed boolean then made the warning name whichever file was written FIRST, i.e. told the user `.mcp.json` was untracked-dirty when the file that really was is `.codex/config.toml`. For the same honesty reason **the aggregate reports only what happened**: the old `N harnesses configured` summary CLAIMED both were configured when one was refused and discarded that refusal's reason, which is the actionable part - so a skipped harness is NAMED with its own reason, and each untracked-file warning names the file it is about. **An exclude that could not be arranged is reported on the IDEMPOTENT path too, because the state that must never be silent is a fact about what is ON DISK, not about whether THIS call wrote it** - gated on `created`/`updated` it was said exactly once, so a re-adoption (the `already` path: a retry after a failed first attempt, the entry deleted by hand, the common git dir gone unwritable) reported nothing while `?? .mcp.json` really was there. A `skipped` result is deliberately NOT covered: the writer refused a file it could not edit, so that file is not Cellar's config and its own message says so. A Settings toggle turns it off (`WORKTREE_AGENT_CONFIG_KEY`, declared in the browser-safe half so the toggle and the writer share ONE constant rather than mirroring a literal) and persists through **`setUiNow`, never the debounced `setUi`** - the server re-reads this preference during a LATER user action (adopting a root), so an opt-out still sitting in the debounce window would let that adoption write into the user's checkout, which is precisely what the setting exists to prevent (the Databricks runtime toggle documents the same shape for the same reason).   - **Changing a root FREES the kernel (teardown), it does not `restart()` it.** A process's cwd is fixed at spawn and `restart()` reuses the same argv+cwd, so a restart would put `sys.path` and the real cwd in disagreement. `setNotebookRootAndRestart` (in `notebook-root-actions.ts`, the ONE place that pairs the declaration with the kernel — `jupytext-actions.ts` precedent) resolves first, persists, then `rebindKernel(nb)`; teardown bumps the epoch and publishes `kernel:shutdown`, so the cells honestly read "not run this session" and the result reports `namespace_cleared`. An UNCHANGED declaration is a genuine no-op — no write, no teardown — compared by RESOLVED DIRECTORY (`isSameDeclaredRoot`), falling back to `sameRoot`'s text rule only when the stored value no longer resolves; one directory has two legal spellings once a root may be external, and `sameRoot` is pure/browser-safe so it cannot resolve either. For the same reason `NotebookKernel.codeRoot` records the root the PROCESS was started at (the `databricksRuntime` precedent) and `initKernel` re-injects THAT, never the document's current value.
  - **A `.py` (jupytext / Databricks source) notebook REFUSES a root outright, and its picker is not rendered — the same refuse-never-degrade rule, applied to PERSISTENCE.** `persist` writes a `.py` notebook back through jupytext / the Databricks converter, which rebuilds the file from its CELLS: no notebook-level metadata survives, so a declaration would live only in memory and be gone on the next reload, after which the notebook would silently run at the workspace root while still claiming the tree under review. So `setNotebookRoot` throws `textNotebookRootError` (naming `.py` and the fix) — at that ONE writer, so no surface can route around it — and `setNotebookRootAndRestart` checks it BEFORE resolving the directory, so the message names the real reason rather than reporting a perfectly good directory as the problem. **CLEARING (`''`/null) stays allowed everywhere**: it can only remove state, never strand it. The two halves must agree, so `NotebookView.isPy` (from `doc.jpFormat`) rides to the browser and gates `showRootBar` — a notebook that cannot hold a root is offered no control for one. Making them root-aware is a separate task. The file tree also lists every root's files, so a repo with several same-repo worktrees shows its files several times; scoping the tree to the active notebook's root is a documented follow-up, not a defect. For an EXTERNAL root the same rule reads the other way and is the surprising one worth stating in the UI (the root bar does): **the kernel runs in the worktree while the file tree still shows the workspace**, and the worktree's files are not readable through any Cellar API at all — that is the boundary holding, not a gap.
