# Cell staleness, dataflow graph, SQL cells

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Cell staleness + dependency graph.** A code cell that ran this session but whose inputs changed since is **stale** - the flagship correctness signal for an agent-first notebook (cells run out of order). Three layers: (1) **dataflow** `src/lib/server/dataflow.ts` runs a Python **`ast` + `symtable`** analysis in a project-venv subprocess (`projectPython()`, like `databricks.ts` - NOT the kernel and NOT a regex, for the same reasons `imports.ts` avoids both: no force-boot, no queue, works with no kernel; results cached by source string) to get each cell's `{defines, uses}`. **A batch the probe fails on is NEVER cached** (a false `fresh` is the one verdict staleness must not invent), which alone is a CPU trap: a notebook whose analysis genuinely exceeds `PROBE_TIMEOUT_MS` (10s, `CELLAR_DATAFLOW_PROBE_TIMEOUT_MS`) times out, caches nothing, and every debounced pass (load/run-end/edit/structural) resubmits the IDENTICAL batch - deterministic, so it burns ~10s and is SIGKILLed again forever, pinning a core. So a **timed-out batch BACKS OFF** (`probeBatch` in `dataflow.ts`): keyed by a signature of the SET of uncached source strings, it is not re-spawned until an **exponential window** (`CELLAR_DATAFLOW_BACKOFF_BASE_MS` 30s, doubling, capped at `CELLAR_DATAFLOW_BACKOFF_MAX_MS` 5min) elapses OR the batch content changes (a real edit adds/removes/rewrites a source ⇒ new signature ⇒ immediate re-probe), so a persistently-slow notebook converges instead of storming. While backed off (and on the timeout pass itself) those cells are reported **UNAVAILABLE**, which `computeStaleness(cells, dataflow, sid, unavailable)` renders as a conservative **`stale`** (reason "dependency analysis timed out; treated as stale") - **never a false `fresh`**. **ONLY a timed-out / backed-off batch is UNAVAILABLE** (`probeBatch` returns `unavailable:true` only then): a **non-timeout failure** (missing interpreter, spawn error, probe crash/parse failure) is deliberately NOT backed off AND NOT reported unavailable - it returns fast, burns no CPU, may resolve once the venv exists, and its cells degrade to **empty dataflow that reads as `fresh`** exactly as before this backoff (no broadening; the conservative-stale path is scoped to genuine timeouts). A **single probe per signature** is in flight at once (concurrent UI+MCP passes fold into one). Covered by `tests/unit/dataflow-timeout-backoff.test.ts`. **The split is the design, do not collapse it.** *Module scope* is an ordered **`ast` load-before-store walk**: a `Load` of a name the cell has not yet bound is a use, one it already bound is not. Order is the whole question and `symtable` cannot express it - it knows only that a name is referenced *somewhere* and assigned *somewhere*, so it cannot tell `x = x + 10` (reads upstream) from `df = read(); df.head()` (reads its own). Both rules available to it are wrong: subtracting assigned names (`uses = referenced − defined`, the rule this replaced) dropped the `x = x + 10` read and left the cell falsely `fresh`, while counting every reference over-reports the `df = read(); df.head()` idiom into a **permanent, uncleanable** stale chip (`upstream_unrun` keys off the upstream's run state, and `run_stale` only re-runs cells already stale). The walk drives on **evaluation order, not field order** (`Assign._fields` is (targets, value) but the RHS evaluates first; `For` evaluates `iter` before binding `target`), which is also what reaches `count += 1` - `symtable` reports `is_referenced()==False` for an `AugAssign` target. *Nested scopes* stay **`symtable`'s**, order-INSENSITIVE (`used_nested - defines`): a def/lambda body is DEFERRED, so "bound so far" for it is "bound anywhere in the cell", which is what keeps `def f(): return pd.x` a use of `pd` while a recursive `def fact(): fact(n-1)` gets no self-edge. Keeping `symtable` there is deliberate - global vs. local vs. free vs. `nonlocal` is exactly what it already gets right. The ast walk therefore never descends into a def/lambda body, only into the parts that DO evaluate at module scope (decorators, defaults, annotations, bases). Covered by `tests/unit/dataflow-load-before-store.test.ts`, which spawns the REAL probe - its positives and negatives fail in opposite directions and are one contract; (2) the **pure rule** `src/lib/staleness.ts` (`computeStaleness(cells, dataflow, sid)`) builds the preceding-definer graph (B depends on A when B uses a name A defines; nearest preceding definer wins; acyclic, so doc order = topological order) and marks each code cell `not_run`/`fresh`/`stale`/`n/a`. A cell is stale if it was edited after it last ran (`metadata.cellar.editedAt`, a NEW runtime-only stamp set in `setSource`, stripped from disk by `clean.ts`'s renamed `stripRuntimeMeta` alongside `lastRun`), or a (transitive) upstream was edited / re-ran / didn't run this session, all vs the existing `lastRun.{at,session}`. Never-run reads `not_run`, distinct from stale. **An imports-cell edit stales only the cells that depend on a binding that ACTUALLY changed, never the whole downstream** (task `cellar-import-staleness-scope-i8`). The graph is per NAME but `editedAt`/`lastRun` are per CELL, so an edge used to transmit staleness whenever its upstream was touched at all - and since an imports cell defines a name almost every cell below it uses, one added import (or agent routing re-adding a line, or a plain re-run) lit the entire notebook amber, which is how "stale" stopped carrying information for most of an agent session. The fix rests on the ONE property strong enough to be safe: a name bound by a MODULE-LEVEL import is a pure function of its import statement, so re-executing it rebinds the same `sys.modules` object. `src/lib/server/importBindings.ts` (pure) identifies each binding by `renderImport`'s canonical rendering - the SAME dedup key consolidate/routing already uses, so the two cannot drift - folds each source change into a THIRD runtime-only stamp, `metadata.cellar.importBindings` (name → `{spec, at, sinceAt, removedAt?}` = its last KNOWN-GOOD statement, when that binding last changed (`at:0`/absent = unchanged), when it first APPEARED, and - once a knowable source stops providing it - when it went; stripped by `stripRuntimeMeta` alongside `lastRun`/`editedAt`, same zero-diff AND anti-forgery reason - an ABSENT stamp reads as "unchanged"; an EMPTY map is stored as absent so an ordinary code cell ships no stamp over `cell:edited`/checkpoints). **Three write points, and all three are required**: `setSource`; `newCell` (so a cell BORN with a source - paste / split / undo-delete - stamps what it introduces; without it a pasted `import polars as pd` became the nearest preceding definer of `pd` carrying no stamps, i.e. exempted the very edge it just rebound - a false `fresh`); and **`applyCellType` on the way IN to a code cell**, the other way a cell acquires Python bindings with no edit - `newCell` stamps only a CODE cell, so one born markdown/raw with an imports-only source carries none, and converting it (an agent `add_cell` with the wrong `cell_type`, a paste) would have exempted the edge it just rebound. Seeded from an EMPTY previous source exactly as the birth stamp is, and **only where there is none to preserve**: a code→code sql toggle must not re-stamp and claim a change that did not happen, and a cell that was code before carries real history a there-and-back conversion must not discard. **The fold diffs the new source against that STORED baseline, NEVER against the previous source text**: `Cell.svelte` autosaves on a 500ms debounce, so an unparseable mid-edit snapshot (a bare `import `, the instant after a select-all) really is persisted, and stamping every name whenever a side was unknowable re-stamped ALL of them - the blanket-stale this task removes. An unknowable next source therefore FREEZES the baseline (safe: `importBindingNames` is empty for it, so that cell grants no exemption at all until it parses again); only a baseline that was never knowable stamps everything. **An EMPTIED source is the mirror case and must NOT be frozen** - it is perfectly knowable (it provides nothing), so freezing would silently swallow a genuine "delete all imports", the false `fresh` the removal ledger exists to prevent. Instead the removal is recorded but kept UNDOABLE: `spec` survives it and only `removedAt` is set, so retyping the same block after a select-all-DELETE matches the baseline, clears `removedAt` and stamps nothing (overwriting `at` instead - what this used to do - meant the retype read as "this binding just changed" and staled the notebook after a round trip that ended byte-identical). `buildDefinerGraph` now also returns `edgeNames` (per edge, the names it carries) and `staleness.ts`'s `edgeCarriesChange` exempts an edge whose names are ALL unchanged import bindings. **The exemption is a WHITELIST, so every unmodelled case keeps the old conservative behavior** rather than inventing a false `fresh`: an ordinary define, a name whose import moved, `upstream_unrun` (deliberately never gated - an upstream that did not run has nothing bound to exempt), and any cell whose bindings are UNKNOWABLE. Unknowable is decided by the tokenizer, never a regex: `importBindingSpecs` (ONE tokenizer pass feeding every check - it ran six, on every 500ms autosave of every cell) returns null unless the source is imports-only (so nothing else at module scope can shadow an import - `os = shim`, `for os in …`, `del os` - a MISSED shadow being exactly the false `fresh` this forbids) and null for any `import *`. A mixed `import os` + code cell therefore stays conservative; the imports cell is imports-only by construction, which is the case that matters. **LINE MAGICS are discounted for that structure test, like comments** - `%matplotlib inline` / `%pip install …` above the import block is one of the commonest headers there is, and without this the whole map degraded to null and the reported bug stayed unfixed for most real notebooks. The vocabulary is `magics.ts`'s own (`isBareMagicLine`, the same shape the probe's `blankLineMagics` blanks), never a second regex, and the assignment form (`files = !ls`) is not one, so it still reads as ordinary code and disqualifies. **Only magics PROVEN inert are discounted, via an ALLOWLIST** (`magics.ts`'s `INERT_LINE_MAGICS`, read through the one-pass `scanMagics`: `%matplotlib`/`%config`/`%pip`/`%conda`/`%autoreload`) - "a bare magic binds no Python name" is NOT unconditionally true, since `%run script.py` executes it IN the namespace (so `setup.py` may rebind `pd`), `%store -r name` / `%load` inject names, `%pylab` is a star import, and **`%load_ext`/`%reload_ext` run an extension's own `load_ipython_extension(ip)`, which may `ip.push({...})` - so they are NOT on the list either (the bar is proof, and `%load_ext autoreload`, the common case, already disqualifies notebook-wide; `%matplotlib inline` keeps the refinement)**. Those, and any magic not on the list, DISQUALIFY the cell, so an unrecognized or future magic fails toward conservative staling rather than a false `fresh`. **Three deliberate exceptions keep the conservative rule:** a `%%cell magic` cell (its body is not module-level Python), a name-injecting/unknown line magic (above), and **`%autoreload`** - autoreload exists precisely to make re-executing an import NON-idempotent, i.e. it retires the one premise the whole exemption rests on, so exempting its edges would be a false `fresh`. **The autoreload gate is NOTEBOOK-WIDE, not per cell** (`dataflow.ts` `analyzeDataflowDetailed`: if ANY code cell satisfies `hasAutoreloadMagic`, `imports` is omitted for EVERY cell, so no edge anywhere is exempt). Arming it is a KERNEL-global act and the ubiquitous header puts `%load_ext autoreload`/`%autoreload 2` in its OWN cell - which Cellar makes the default outcome, since `ensureImportsCell` adopts a first cell only via `isImportsOnly` and so inserts a separate magic-free imports cell above it - so the per-cell check in `importBindingSpecs` (kept as the local half) would have granted the exemption in exactly the arrangement where autoreload is most commonly used. **A REMOVED import is tracked, not forgotten** (`foldImportChange` keeps the name, its spec and a `removedAt`): removal leaves no definer, hence no edge, so `computeStaleness` carries a small in-order removal ledger and stales a reader of a name nothing defines any more - closing a pre-existing false `fresh` this refinement would otherwise have widened. That ledger needs BOTH halves: the name must be absent from the cell's CURRENT `imports` **and** carry a `removedAt` (the fold actually watched it leave a knowable source), else a mid-edit cell - which lists no imports at all - would read as "every binding here was just removed" and blanket-stale the notebook on each keystroke. **Removal records are PRUNED to the names something could actually have READ** (`pruneImportBindings`, applied wherever the fold is stored, keyed off the new `sinceAt` = first appearance, which - unlike `at` - never moves on a rebinding): a debounced autosave persists PARSEABLE intermediates (`import numpy as n` on the way to `as np`), and without the prune each minted a permanent phantom entry that grew the map for the whole session, rode every `cell:edited`/checkpoint, and made the ledger report a removal that never happened for any cell using a short name like `n`. The test is deliberately "was it bound while the notebook was running", NEVER "is it in the source now" - the latter would delete exactly the records the ledger exists for, since a genuinely deleted import is also absent from the source. **The reference is the DOCUMENT's newest `lastRun.at` (`notebook.ts` `latestConsumeAt`), never the providing cell's own stamp**: `clearLastRunStamps` (the wipe-variables route) DELETES `lastRun` from cells precisely BECAUSE they ran, so dating the prune per cell read a wiped imports cell as "never bound anything", dropped its removal records, and left a reader of a since-deleted import with no definer, no ledger entry and a false `fresh`. A reader with no stamp reads `not_run` and never reaches the ledger, so the newest stamp anywhere bounds every consumption the ledger can be asked about; when NOTHING in the notebook carries one, nothing is pruned at all (an undatable record is kept - an unbounded map is a cost, a false `fresh` is a defect). The probe-timeout-backoff path is untouched: `imports` is computed in JS with its own cache (`importCache`, cleared by `__resetDataflowState`) so it survives a probe failure, and an UNAVAILABLE cell has empty `defines` ⇒ no edges ⇒ no exemption ⇒ still conservative-stale. Known limits (in `staleness.ts`): the exemption assumes imports are idempotent, so `importlib.reload` / an import with side effects is not modelled (`%autoreload`, which breaks the same premise, IS detected - notebook-wide - and disqualifies every cell); and **the ledger covers a removal only while the cell that provided the name SURVIVES** - it is read off that cell's stamps, so DELETING the imports cell outright takes them with it and its readers (now with no definer and no ledger entry) read `fresh`. That is pre-existing (a deleted definer never produced an edge either), but do not read the in-cell ledger as covering removal in general; the same family covers an edit that drops a binding and leaves the cell unanalyzable in one step. Covered by `tests/unit/import-bindings.test.ts` (pure), `tests/unit/imports-staleness-scope.test.ts` (real probe + real `setSource` + the real `routeImports` path) and `tests/e2e/imports-staleness-scope.spec.ts` (the amber chip in the real UI, both directions). The precedent is a rule about the two POINTED surfaces, not about the palette. Its handler is the SHELL's (`+page.svelte`'s `consolidateImports`, a fetch to `/api/notebooks/imports`), forwarded through `LiveNotebook` untouched alongside its `consolidating` busy flag - **and BOUND PER NOTEBOOK at the shell (`() => consolidateImports(tab.path)`), the `onInterruptKernel` shape**, so each toolbar sweeps its OWN notebook rather than whichever tab is focused. The busy flag is **PER NOTEBOOK, not shell-wide** (`consolidatingPaths`, a `Set` keyed by notebook path - the Kernels sidebar's `actingPaths` idiom, with the entry dropped in a `finally` so a rejected fetch cannot strand a notebook disabled forever): the handler is bound per notebook, so the flag has to be as honest as the binding - a single boolean disabled every OTHER mounted notebook's button and showed it a spinner for a sweep that was not its own, which is the exact inaccuracy the per-notebook binding removed one layer up. Two DIFFERENT notebooks may therefore sweep concurrently while a second click on the SAME one still sends nothing, and that flag is the button's ONLY disabled input: there is deliberately **no "nothing to consolidate" gate**, since the menu item had none either and the sweep is idempotent - predicting emptiness would be a new claim rather than the same button in a new place. **A FAILED sweep is REPORTED, on the shell's existing `showNotice` line and never a second error channel** (the `exportPy` path), and the two failure shapes are told APART because they know different things - the `openKernelNotebook` `refuse`/`noVerdict` split, applied here: a reply that ARRIVED and is not `ok` is a REFUSAL the server made, so it may say the sweep FAILED and carries the route's own 400 message with any absolute path stripped (`reasonWithoutServerPath`); a REJECTED FETCH establishes nothing at all - the reachable shape is the server persisting the whole sweep and the reply dying on the way back (a second `cellar` launch reaping the instance, a transient socket error) - so it may say ONLY that the outcome could not be confirmed and that a retry is safe, never that it failed. Both **NAME THE NOTEBOOK**, because the button is bound per notebook while this line is shell-wide, so a sweep can legitimately belong to a tab the user has since left; and neither says anything about WHICH cells moved, which this side never learns. The busy entry is released in the `finally` on every path, so a failure leaves that notebook clickable rather than latched shut. Gating comes from state the notebook ALREADY tracks and must stay there: Interrupt off `runningId`/`queued` **plus `bulkRunning`**, Clear-all off the cells' `outputs` in the MODEL, so a cell windowing has never mounted still counts (`clearAll` iterates the model for the same reason). **`bulkRunning` is required, not belt-and-braces: `runningId`/`queued` both go EMPTY BETWEEN the cells of a sequential bulk run** - `runCell`'s `finally` clears `runningId`, and dispatch is sequential so only one `/run` stream is ever open and nothing is ever server-side queued - so gating on those alone dropped Interrupt for a round trip per cell, flickering it and silently swallowing a click that landed in the gap while the batch ran on. It is a COUNTER in `LiveNotebook` (`bulkRuns`, incremented around `runCodeIds`' loop and decremented in a `finally` so an interrupted early return or a throw can never strand it; a counter rather than a boolean so two overlapping batches cannot have the first to finish declare the notebook idle), surfaced as the `bulkRunning` prop (defaulting false, so a standalone `Notebook` mount is unchanged). **Every one of the three inputs is per-notebook - never the shell's global `runsInFlight`** - because notebooks run in parallel and another notebook's run must never arm this button. **`clearAll` clears EVERY cell that has outputs, the one whose run is IN FLIGHT included** - there is deliberately no skip and no notice, and the clear is PERMANENT: the shared clear path in `notebook.ts` (`clearOutputs` and the batch `clearOutputsForCells`, so the toolbar button, the per-cell Clear, the palette command and every REST caller share one seam) calls **`truncateActiveRunOutputs`** (`src/lib/server/run-output-registry.ts`) BEFORE emptying the document, which resets that run's `OutputAccumulator`. So the output produced before the clear is dropped for good - it is not restored into the live doc by the next flush and it is NOT written back at `run:end`; only what the cell produces AFTERWARDS accumulates and is persisted. **The registry is its OWN module for an import-cycle reason**: `run.ts` already imports `notebook.ts` (`setOutputs`/`setOutputsLive`), so the seam cannot live in `run.ts`; `run.ts` registers its accumulator at run start and drops it in a `finally` that spans the persist, so a clear landing between the last flush and `setOutputs` still keeps the pre-clear buffer off disk, and a finished run leaves nothing behind. **Resetting the accumulator also restarts its element INDICES at 0, and that half is a crash fix, not tidiness**: the clear empties the client's array, so a later element emitted at the server's stale index N landed past the end of it and left a HOLE, which throws while rendering - the per-cell render error boundary now BOUNDS that to the one cell's placeholder (a bound, not a license); before it, it took the whole notebook's render tree down (the archetypal shape being a cell that prints progress and then returns a value: the `execute_result` is the second element). `applyOutput` keeps a defensive bail on an index it cannot place contiguously, as defence in depth - **and its two consumers answer that bail DIFFERENTLY on purpose**: the SSE path resyncs with one `load()` (guarded by `!fetching`), while a tab's OWN `/run` NDJSON loop treats it as a NO-OP, exactly like its delta branch. A refetch there would be actively harmful - it rebinds `cells` and nulls `runningId` while that loop captured its `cell` once before the await, so every later frame and `run:end`'s `stampLastRun` would write into a detached object with nothing left to correct it (this tab echo-suppresses its own `run:end` SSE) - and it loses nothing, since the only way to reach it is the window between this tab optimistically emptying `cell.outputs` and the server truncating that run's accumulator, i.e. a frame the truncate is about to discard anyway. MCP `clear_outputs` answers differently ON PURPOSE - it SKIPS an in-flight cell and names it in `skipped` - because an agent's call is a one-shot report rather than a live view; the two surfaces are not meant to agree here, so do not "reconcile" them. `hasOutputs` models none of this: it is read off the cells' outputs in the MODEL and nothing more. Both feed `LiveNotebook`'s `runCodeIds` (Run all → `runAll`; Run above → `runAboveCell(id)`, addressed by the cell's OWN id, not the active selection) - one shared **SEQUENTIAL** bulk-run path that `await`s each `runCell` before the next, so the server-side FIFO queue serializes them and the interrupt-cancels-the-queue behavior applies automatically. **Run all's reused-kernel wedge is FIXED (task `cellar-runall-kernel-wedge-z3`), at its root, in two independent layers - do not undo either.** The OLD `runAll` fired every cell's `/run` POST at once (fire-and-forget) and relied on the FIFO to serialize them; on a reused kernel that intermittently left a trivial cell stuck "running" while later cells stayed "queued", recovered only by the ~120-210s watchdog (worse with more run-to-run transitions - ~40% at 3+). Root cause was NOT the queue but **concurrent `execute()` on ONE kernel**: the sidebar variables inspector (`inspect.ts` `inspectVariables`, fired after every run) calls `execute({internal:true})` which BYPASSES the run queue, so during a bulk run its probe put a second `requestExecute` on the wire alongside the next cell's - and two concurrent executes make @jupyterlab mis-pair the interleaved iopub `status:idle`/`execute_reply`, so one run's `future.done` never resolves. **Layer 1 (the invariant): `kernel.ts` `NotebookKernel.execChain` + `acquireExecLock()`** - every `execute()` (queued OR internal) serializes on a per-kernel promise-chain lock so no two `requestExecute` are ever on the wire at once; released in `execute()`'s `finally` (abort path included, so a watchdog-killed run can't block later executes). This alone fixes the wedge and is proven by `tests/unit/kernel-status-broadcast.test.ts` ("execute serialization"). **Layer 2 (dispatch): `runAll` routes through `runCodeIds`** (sequential, one open `/run` stream at a time) instead of fire-and-forget, so Run all can never oversubscribe the browser's ~6-connection HTTP/1.1 pool. **Layer 3 (keep the probe non-blocking): `inspectVariables` short-circuits `busy`** (mirrors `kernelState`'s guard, incl. the queue's `running` truth) so the lock never makes a probe queue behind a run - it returns `{variables:[], busy:true}` and `/api/kernel/variables` forwards `busy` so the client (`+page.svelte` `refreshVariables`) KEEPS its current variables rather than clearing them mid-run (poll, don't single-read, that endpoint in tests - it reports empty while busy). **Interrupt-cancels-queue still holds** and its e2e was reworked for the sequential model (only the running cell's stream is open, so there are no queued badges during a Run all; the `interruptGeneration` bump stops the loop + the kernel interrupt ends the running cell). Covered by `tests/e2e/run-above-run-all.spec.ts` (Run all reliable on a WARM kernel, four code cells = three transitions) + `tests/e2e/interrupt-clears-queue.spec.ts`. **Target-id selection is the pure, unit-tested seam `src/lib/runTargets.ts`** (`codeIdsAll`/`codeIdsAbove` - skip non-code cells, above-exclusive; covered by `tests/unit/run-targets.test.ts` + e2e `tests/e2e/run-above-run-all.spec.ts`); `codeIdsInRange`/`runAll` delegate to it so the rule can't drift from what the UI runs. MCP: `get_notebook_map` carries `stale_state`/`stale`/`stale_reason`/`stale_upstream` per cell, `kernel_state` carries `stale_cells:[{id,reason,upstream}]`, `read_cell`/`read_cells`/`read_by_location`/`read_section`/`run_cell` carry the same (those read tools became **async** to compute it), new **`run_stale`** tool re-runs everything stale in dependency order, and `INSTRUCTIONS` clause 3 gained a staleness doctrine (re-run/distrust stale cells; editing a cell stales its dependents) - **plus the imports-cell exception**, so an agent does not read the resulting quiet as staleness being broken: because its own write tools route imports on nearly every `add_cell`, clause 3 says an imports edit stales only the readers of a binding that actually moved, that a rebound or removed import DOES still stale its readers, and that the exception is withdrawn where re-running an import is no longer harmless - notebook-wide under `%autoreload`, or for an imports cell carrying any magic not proven inert (so "do not re-run everything to be safe"). Staleness is computed fresh each time, never persisted (zero git diff). **Staleness is static analysis + timestamps, NOT a runtime check** - `lastRun` carries `{at,durationMs,actor,status,session}`, never the names a cell read or wrote, and nothing inspects the namespace. So it is a **floor**: every blind spot in the graph is a blind spot in the verdict, and there is **no backstop** - `find_symbol`/`cell_impact` are derived from the SAME graph (`symbolGraph.ts`) and under-report identically, so never document one as catching what another missed (the false claim removed in `1812cea`). `cell_impact` additionally **OVER-reports in exactly one direction, deliberately**: it is the blast radius of the WHOLE cell asked BEFORE an edit exists, so it must assume every name the cell defines may move, while `computeStaleness` runs after the edit and exempts an edge carrying only unchanged import bindings - for an imports cell, `dependents` is "everything reading any of these imports" and the cells that actually go stale are only those reading an import the edit moved (documented in `symbolGraph.ts` + the tool description). The one runtime-derived input is `lastRun.session`: a restart bumps the epoch and correctly resets everything to `not_run` - epoch tracking, not name tracking. Known limits (documented in `staleness.ts`): dynamic names (`exec`, `globals()`), forward references, a **conditional bind** (`if flag: df = load()` then `df.head()` - the sequential walk counts it bound, so no upstream edge; no worse than what shipped before), and an **`AugAssign` to a `global`-declared name inside a function** (`def g(): global c; c += 1` - a deferred body, so it is `symtable`'s half and hits its `is_referenced` blind spot; module-scope `count += 1` IS caught). **Read-then-rebind is FIXED** (the `ast` load-before-store walk) - do not re-document it as a limit, and if you are tempted to "simplify" the ast walk back into a `symtable` subtraction, read the `dataflow.ts` header first: that subtraction is the bug.
- **SQL cells: the `-- >> name` result binding (`src/lib/server/sql.ts`).** A SQL cell (`metadata.cellar.language='sql'`, see `cellLanguage.ts`) is compiled to Python at RUN time only (`run.ts`: `sqlToPython`) and executed by the ordinary Python kernel against the live `spark`; the stored source stays SQL. **The binding syntax:** a cell may open with `-- >> sales_df` to bind its result to `sales_df`. It is a plain SQL **line comment** on purpose - the cell still parses as SQL in any other tool, survives a round-trip through plain Jupyter, the CodeMirror `sql()` grammar highlights it as a comment, and an agent reads it over MCP with no new tool. Recognized **only as the first non-blank line** (never scanned for in the body, so a `-- >>` mid-query stays an ordinary comment) and **stripped** before the query reaches `spark.sql`. **The binding rule:** a named cell binds **BOTH** `<name>` **and** `_sql_df` - `_sql_df` is documented to agents (`mcp/server.ts` clause 10) as the "last SQL result" chain-off point and that contract must keep holding, so the named var is the *stable* binding and `_sql_df` stays the (last-write-wins) alias it always was. **No prefix line ⇒ byte-for-byte the legacy output** (one assignment to `_sql_df`, no alias line) - existing notebooks are unmoved; the display expression is always `<var>.limit(SQL_ROW_CAP).toPandas()` on the LAZY Spark DF, never the capped pandas one. The name is interpolated into generated Python, so it is **validated, never merely quoted** (strict ASCII identifier + not a Python keyword - deliberately stricter than Python's own unicode rule - **and not a name Cellar itself binds in the kernel**: `spark`/`w` are legal identifiers, so without that reserved set `-- >> spark` would compile to `spark = spark.sql(...)` and silently destroy the live session the next cell needs); an unusable name compiles to a lone `raise RuntimeError(<why>)` so the cell **fails visibly** instead of emitting broken Python or silently ignoring the line. **`parseSqlCell` is the single source of truth for both halves** and must stay so: `sqlToPython` compiles from it, and `dataflow.ts` reads its `resultVars` to give each SQL cell a **synthetic `defines`** - SQL cells stay OUT of the probe (their source is SQL; `ast`/`symtable` would misparse it), but their run really does bind names, so without the synthetic contribution a Python cell reading a SQL result gets no upstream edge and never goes stale when the query is edited. A SQL cell is a graph **source**: `uses` is always `[]` (reading table names out of SQL is lineage analysis, deliberately out of scope). Covered by `tests/unit/sql-binding.test.ts`.
