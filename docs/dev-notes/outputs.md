# Rich outputs: DataFrame grid, HTML tables, ipywidgets

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Interactive DataFrame grid.** A pandas DataFrame/Series output renders as a sortable/filterable/paginated data grid instead of the static text/HTML repr. **Kernel-side** (`kernel.ts` `DATAFRAME_FORMATTER_CODE`, injected by `initKernel` alongside the matplotlib magic, re-run on every start/restart): registers an IPython `BaseFormatter` (`_return_type = (dict, str)` - the default `str` rejects a dict payload) for the custom mimetype `application/vnd.cellar.dataframe+json`, emitting `{columns, dtypes, index, index_name, data, total_rows, total_cols, shown_rows, shown_cols, truncated_rows, truncated_cols}`. Bounded at MAX_ROWS=500 × MAX_COLS=100 so a huge frame never lands in the output (nor the DOM). Values come from pandas' own `to_json(orient='split', date_format='iso', default_handler=str)` - deterministic (NaN→null, dates→ISO, numpy→native), so an identical re-run yields an identical payload (zero git diff). **A MultiIndex column or row label is flattened with `' / '` (`_cellar_flat`), the same separator `dataframeHtml.ts` uses**, so live and re-opened show the same header; it used to emit python's tuple repr `('A', 'x')` and the comma-joined `a,1`. A scalar label is returned untouched, so a plain frame's payload is byte-identical and a numeric index label stays a number for the grid's sort. All guarded: no pandas / old IPython = silent no-op; pandas' text/plain + text/html reprs are untouched, so a bare `df` degrades anywhere the mimetype isn't understood. Spark DataFrames are deliberately **not** auto-collected (a bare `df` must not trigger a hidden job) - use `.toPandas()` / the Databricks table preview. **Persistence:** `clean.ts` `cleanOutput` **strips** the mimetype on the way to disk, so it is purely a live render - kept in the in-memory doc (open tabs show the grid, SSE renders it live across tabs) but never bloats the `.ipynb`; a reopened-not-rerun notebook is re-parsed back into a grid from its `text/html` repr by `$lib/dataframeHtml` (see its own entry below), which is why LIVE and RE-OPENED are two different code paths for one output and any claim about "the grid" has to be checked on both. **Frontend:** `Cell.svelte` `renderOutput` detects the mimetype (before the image branch) → `{dataframe}`; `src/lib/DataFrameGrid.svelte` renders it (dtype headers, click-to-sort cycling none→asc→desc with a numeric-aware compare, global filter box, page-size + first/prev/next/last pagination, row/col counts, truncation banner, index column, sticky header, overflow scroll). The grid owns its own height/scroll, so `Cell.svelte` skips the outer output-scroll auto-contraction + hides its toggle when `hasDataframe` (else it double-scrolls and clips the pager). Styled with daisyUI semantic classes so both themes are clean for free. **The row `{#each}` is keyed by the row's POSITION (`row.key`, the `.map()` index), NEVER by the pandas index label (`row.idx`) - and that is a correctness rule, not a style choice.** A pandas index carries no uniqueness guarantee: `set_index()` on a column with repeated values, `groupby().apply()`, `concat`, `explode`, `melt`, and a flattened MultiIndex (whose parts `dataframeHtml.ts` joins with `' / '`) all produce duplicate labels routinely. A duplicated key throws Svelte's `each_key_duplicate` **during render**, and at the time **nothing in the app wrapped a cell in an error boundary**, so that uncaught error took down the WHOLE notebook's render tree, not just this grid - it was the single root cause behind four separate-looking failures, all reproduced on a real notebook: with windowing ON the render loop dies the instant the offending cell scrolls into the window, so everything below it stays permanently blank (a deterministic "gap" in the same place every time, surviving a restart) and arrow-key navigation and the jump-to-running-cell spinner stop working with it (`ensureCellMounted` can never materialize a node, and both `scrollCellIntoView` and `revealRunning` then take a SILENT no-op branch - which is why a render crash presented as "the arrow keys are stuck"); with windowing OFF ("Render all cells") it throws at load and **nothing renders at all**. Positions are unique by construction and stable under the grid's own filter/sort, which reorder rows but never change a row's identity. Note this is emphatically NOT a virtualization bug - a 3-cell notebook reproduces it - so do not go looking in `planWindow`/the height cache; windowing only changes WHEN the bad cell mounts, and therefore where the damage shows. Covered by `tests/unit/dataframe-grid.test.ts` (the real parser proving ordinary pandas output really does carry duplicate labels, plus a source guard on the key - vitest runs without the SvelteKit plugin, so the component cannot be mounted there) + `tests/e2e/dataframe-duplicate-index.spec.ts` (both modes over a committed fixture; **its load-bearing assertion is that ZERO page/console errors are raised** - the throw's blast radius varies by where in the flush it lands, so a "the cells are visible" check alone passes against the bug on some runs).
- **`$lib/dataframeHtml` - the SECOND path to the grid, and the one that MUST NOT GUESS.** Every output carrying `text/html` and no structured MIME reaches it, so it runs LIVE too (it is the only grid a producer that emits no Cellar MIME ever gets) and it is the whole of what a RE-OPENED notebook has, clean-on-save having stripped the MIME. **THREE dialects, told apart STRUCTURALLY rather than by a producer name:** pandas (`class="dataframe"`, a leading index `<th>`, `<p>N rows × M columns</p>`), **polars** (the SAME `class="dataframe"` but NO index column, a second header row of `<td>` dtypes, and `<small>shape: (r, c)</small>`), and a pandas **Styler** (no `dataframe` class at all; `th.col_heading` / `th.row_heading` / `th.index_name` / `td.data` and a `<caption>`).
  - **THE LAYOUT IS READ, NEVER ASSUMED - the central rule.** It hardcoded pandas' leading index cell (`firstThs.slice(1)`), so polars and `df.to_html(index=False)` had their FIRST REAL COLUMN deleted and its values promoted to the row index with every dtype shifted along: an entirely normal-looking grid showing the wrong data (measured against real polars 1.44, a 17-column frame came back as 16 with `uuid` gone; 32 of the reporter's notebooks import polars). The index column count is read from the **BODY** (`<th>` row headers, one per index LEVEL) and **never from the header**, because `df.columns.name = 'X'` puts a NON-EMPTY label in that first `<th>` while the index is still there - so a leading non-empty cell does not mean there is no index. The same count also stopped a MultiIndex-ROW frame gaining a phantom empty first column. With an EMPTY body there is nothing to read it from, and that case REFUSES unless a positive signal answers - see `emptyBodyIndexCols` below; it deliberately does NOT fall back to the declared column count, which drops a real column on a truncated frame.
  - **AND THE ANSWER IS CHECKED AGAINST THE PRODUCER'S OWN DECLARED SHAPE - the non-negotiable.** polars writes `shape: (r, c)` (a Series' `(n,)` means one column); a parsed count that disagrees REFUSES (null → the honest static table) rather than rendering a confident wrong grid. Truncation is the one legitimate way to hold fewer columns than were declared and it is VISIBLE, as the dropped ellipsis column, so an ellipsis is required to be present exactly when the counts differ, **in both directions** - a missing column with no ellipsis is the bug; an ellipsis over a complete count means the layout is not what we read it to be. A body row whose cell count disagrees with the header is refused for the same reason. **A future polars layout change therefore costs the grid, never the data** - keep that direction. (The pandas truncation footer is deliberately NOT such a declaration: it appears only when pandas truncated, so it is a lower bound and stays a `Math.max`.)
  - **polars specifics, all measured against 1.44:** its DECLARED dtype row is used instead of inferring from rendered text - which is what keeps a `str` column's `"5006"` the string 5006 rather than the number - its own quotes are stripped from `str`/`cat`/`enum` columns (it does NOT escape an inner quote, so `say "hi"` renders `"say "hi""` and one matched pair is exactly what comes off), a bare `null` is missing (unambiguous, because a string column's values are quoted), and its truncation row carries NO `<th>` so the skip accepts an absent label as well as an ellipsis one. `binary` (`b"ab"`) is deliberately left alone.
  - **A Styler is read HERE rather than by teaching the kernel formatter about it, because this is where MORE survives.** The values in this HTML are the FORMATTED ones (`{:,.2f}` → `1,234.50`) and the caption is beside them, while the only PUBLIC handle the formatter would have is `styler.data`, the RAW frame - so that route would have silently discarded exactly the number formatting the user wrote `.style` to get (`_translate`/`_display_funcs`, which hold the rendered values, are private). **PRESERVED:** every column and row, the formatted values, the caption (payload `caption`, shown in the grid header and carried into a copy), and `.hide(axis='index')`, which lands on the same no-index layout polars uses. **DROPPED:** the CSS - gradients, per-cell colours, bars - which the grid structurally cannot express. **A Styler whose DATA CELLS HOLD MARKUP is REFUSED outright rather than flattened** (`holdsCellMarkup`, decided on real element children in a `td`, never on a guess about intent): `Styler.format` defaults to `escape=None`, so a formatter emitting `<a href=…>link</a>`, an `<img>` or an inline SVG sparkline is the USER'S CONTENT, and the grid reads a cell as `td.textContent` - which flattens the link to unlinked text and renders the image cell as the EMPTY STRING. That is content loss rather than a lost decoration, so it keeps the sandboxed iframe with the markup intact; a correct static table beats a grid that quietly ate a sparkline. **Scoped by what the table IS (`th.col_heading`), never by which selector resolved it** - `set_table_attributes('class="dataframe"')` is a documented Styler idiom, so a Styler really can be found by the `table.dataframe` lookup and a route-based test skipped the refusal for it; a plain `to_html(escape=False)` frame emits no `col_heading`, so the `class="dataframe"` path has always flattened the same way and is deliberately left alone. **Unconditional rather than heuristic:** a rule like "only when the `<style>` block is empty" measured 22/23 correct on the reporter's own corpus and **0/7** on another (their `set_table_styles` padding boilerplate), so it would be unpredictable in exactly the way a routing rule must not be. Never keyed on the `id="T_<hex>"`, which is a per-render uuid and settable by the user.
  - **The Styler admission alone is size-capped (`MAX_STYLER_HTML_CHARS`, 2 MiB).** A `_repr_html_` DataFrame is bounded by pandas' display options; a Styler's is not - it renders every cell until `styler.render.max_elements` (262144), measured at 21 MB for a 60000-row frame - and DOM-parsing that on the thread carrying the kernel websockets and the SSE fan-out is not worth a payload the grid then paginates. The `class="dataframe"` path stays uncapped and unchanged. **The cap is decided by the Styler's OWN structural token (`col_heading`), never by the ABSENCE of the word `dataframe`** - a caption reading "Sales DataFrame", a cell value mentioning it, or the documented `set_table_attributes('class="dataframe"')` idiom all put that word in a Styler's html, and keyed on it the cap was skipped while the Styler branch resolved the table anyway, i.e. the multi-MB parse went ahead through the one route the cap exists to close. The cheap length compare comes FIRST, so an oversized non-`dataframe` bundle is refused without the second full-string scan. **`MAX_HEADER_COLUMNS` (4096) is its sibling on the OTHER axis**: the per-cell `MAX_COLSPAN` clamp bounds one cell and says nothing about the total, so ~50k `<th colspan="1000">` (1.3 MB of html) expanded to a 50-million-entry array and that many joined label strings before any refusal could fire - `expandRow` now stops ONE past the ceiling so the caller can SEE the overflow and refuse, rather than silently truncating a header, and the refusal sits ahead of every O(width) allocation.
  - **MULTIINDEX COLUMNS ARE FLATTENED WITH `' / '`, not refused**, and `kernel.ts`'s formatter flattens identically so live and re-opened agree. The grid is a flat table, so a nested header must flatten somehow, and `' / '` is already the separator for a flattened MultiIndex ROW label. Collisions are harmless for a COLUMN (the grid's column `{#each}` is unkeyed, unlike the row one). **An EMPTY frame is a frame** - a zero-row frame whose header parsed is what the live grid already shows - so the blanket empty-body refusal is gone and the grid says "This DataFrame has no rows." rather than "No rows match" over an empty query. **But the index column can only be read from the BODY, so with none it is decided by a POSITIVE signal or REFUSED** (`emptyBodyIndexCols`), never guessed from the declared shape: a dtype row means polars, which has no index; otherwise an EMPTY leading header cell is pandas' index placeholder, which `_repr_html_` always emits; anything else refuses. Guessing there reopened the very defect the module exists to close - an empty `to_html(index=False)` frame lost its first column to a phantom index, and a zero-row polars frame wide enough to TRUNCATE its columns lost its first column with the declared-shape check unable to see it (truncation legitimately makes the counts differ).
  - **A pandas SERIES is the one shape deliberately left degrading** (grid live, plain text re-opened): it has no `_repr_html_` AT ALL, so a saved notebook carries only `text/plain` and there is nothing to parse. Closing it needs either keeping the structured MIME through clean-on-save - the zero-git-diff doctrine that MIME is stripped for - or emitting an html repr pandas itself never produces, changing what the saved `.ipynb` contains and how every other tool renders it. Both are worse than the gap.
  - **`has_index` and `caption` are OPTIONAL and ABSENT MEANS TRUE / NONE**, so every payload the kernel formatter emits is unchanged; `DataFrameGrid` and `$lib/copyCell` both omit the index column only on a literal `false` (a blank one would claim an index that does not exist, and in a copy it pastes as a real empty column).
  - Covered by `tests/unit/dataframe-html-parse.test.ts` (every input a VERBATIM repr captured from a real pandas 2.3.3 / polars 1.44.1 in `tests/unit/fixtures/dataframe-html-reprs.json`, regenerated by its committed `.gen.py` - a hand-typed approximation is the parser's own assumptions written twice, which is exactly how the old MultiIndex-row fixture came to describe a table pandas never emits) + `tests/e2e/dataframe-polars-styler.spec.ts`, which runs every shape against a real kernel, asserts the LIVE rendering, **kills the instance and boots a fresh one on the same workspace** so the second reading comes from the file alone, and re-runs ONE shared assertion body - a divergence IS a difference between those two passes, so asserting the halves separately is how these went unnoticed.
- **Rich `text/html` output tables get comfortable defaults, at LOW specificity (`src/lib/htmlOutputStyle.ts` → `HtmlOutput.svelte` `buildSrcdoc`).** An arbitrary `IPython.display.HTML` table (and a pandas **Styler** the grid refuses) renders inside the sandboxed output iframe, whose srcdoc wrapper Cellar owns; `app.css` cannot reach in (no `allow-same-origin`), so the browser's 1px cell padding was all a bare table got - which is why users hand-rolled a `set_table_styles` helper (7px 20px padding, right-aligned data, left-aligned row headings, a styled caption) and called it on **every** table. `OUTPUT_HTML_CSS` now supplies exactly that as the default: `7px 20px` cells, right-aligned data with `tbody th` (the index) left, hairline row separators + a header rule (from `thead th`, so only where the table declares a `<thead>` - see the known limits below), `set_caption` as a left-aligned 600-weight title, `tabular-nums`, and `border:0` so pandas' `border="1"` presentational grid is replaced rather than layered under. **Scope, stated as it really is: these are defaults for EVERY `<table>` in a rich `text/html` output, not for pandas-shaped tables alone** - the reach was measured, not overlooked. A third-party `_repr_html_` (statsmodels' `summary()` → `<table class="simpletable">`, dask's array summary, a folium/bokeh legend table) gets the same padding, the same hairline row separators, and the same inherited right-align wherever its cells hold bare inline text and so take no `:has()` escape (the known limit below). The padding is a universal scannability win and dropping the default border is precisely what declutters a bare table; every default is overridable by explicit CSS or a pandas Styler, which is what the specificity rule guarantees. `border:0` also outranks the deprecated `border=` presentational attribute (author CSS always beats a presentational hint), so a hand-written `display(HTML('<table border="1">…'))` loses that grid - restore it with explicit CSS (a `style` attribute or a stylesheet rule the output carries), and reach for explicit CSS or a Styler rather than `border=` when a specific grid is wanted. **Two narrowings are REJECTED, do not reintroduce them:** carving `border:0` back to preserve `border=` buys one legacy case for a permanently more complicated rule, and scoping the block to pandas-shaped tables needs a class or id selector, i.e. exactly the specificity problem the rule below exists to close. **The specificity rule is the whole contract, not a style choice:** every selector stays element-level (`table`, `th,td`, `thead th`, `tbody th`, `caption`), because a Styler emits `#T_xxxx td{…}` and `set_properties` emits per-cell `#T_xxxx_row0_col0` - so anything the user states explicitly still wins the cascade, reproducing their helper's `overwrite=False`. Adding one class or id here would silently start overriding user styling with nothing else failing, so `tests/unit/html-output-style.test.ts` fails the build on a `#`/`.`/`[` in any selector - and on an `!important` anywhere, which defeats the same contract by another route with every selector still element-level (it also guards the `allow-scripts`-without-`allow-same-origin` sandbox, mirroring `html-preview.test.ts`). **`text-align:right` is declared on `table`, NOT on `th,td`, precisely so a user's table-level rule wins - do not move it onto the cells.** An inherited value is used only where no declaration applies to the element itself, so a cell rule would outrank ANY value the user sets on an ancestor, and `set_table_styles([{'selector': '', …}])` - the standard Styler idiom for aligning a whole table - emits exactly that (`#T_xxxx{text-align:left}` on the table element); declared on `table` the two meet on one element, the id wins, and it inherits down. **That governs the DATA alignment and GENERALIZES through ONE mechanism: a DIRECT declaration of an INHERITED property beats an inherited value whatever the specificity, so every such declaration on a NON-`table` element sits outside the reach of the whole-table Styler idiom** (`set_table_styles([{'selector':'','props':…}])` → `#T_xxxx{…}`, which moves the data cells but not these). The complete list: `tbody th{text-align:left}` (the index reads as a label - the pandas convention), `caption{text-align:left}` (a caption reads as a title, and one that INHERITED would pick up the table's numeric right-align, which is worse than what it costs), `caption{font-weight:600}` for the same title-not-datum reason, and `th{color}`/`caption{color}` (the darker heading ink). Each stays overridable through the id-scoped escape hatch (`#T_xxxx th{color:…}` / `#T_xxxx caption`), so the user-always-wins contract holds **literally, not merely nearly** - these are documented exceptions to ONE idiom, never unbeatable rules. Keep them direct - the last direct `text-align` is the `:has()` escape below, for the same beat-the-inherited-default reason. **Two of those are NOT reach Cellar took away, so do not re-raise them as regressions:** the UA sheet already declares `th{font-weight:bold}` and `caption{text-align:center}` directly, so a table-level rule never reached either property in the first place - Cellar's `th{font-weight:600}`/`caption{text-align:left}` change what they look like, not what can override them; the genuinely new ones are `th{color}`, `caption{color}` and `caption{font-weight}`. **The table also stays a REAL table** (no `display:block`, which would wrap the rows in an anonymous `width:auto` table box and leave a user's `<table width="100%">` / `table-layout:fixed` applying but doing nothing, and no `display:block` on `caption` either, which on a `display:table` parent would get it wrapped in an anonymous cell, i.e. rendered as a row) **and carries NO `max-width`** - which is why `table` was dropped from the pre-existing `img,svg,canvas,table{max-width:100%}` rule (the `img,svg,canvas` half is unrelated and stays). It reads like an obvious safety net, and it is the ONE declaration a user could not override: their `width:1500px` is a DIFFERENT property, so no amount of id specificity beats a `max-width` and their columns are silently squeezed. It also buys nothing - auto table layout already sizes an auto-width table as `max(min-content, min(max-content, available))`, so it fits its container unaided; it cannot prevent min-content overflow anyway; and a genuinely wide table overflowing into the output document's horizontal scroll is accepted by design here. Cells therefore **wrap normally** (the pandas/Jupyter default), so a long text column reads instead of scrolling; a genuinely wide table - many numeric columns, which cannot wrap - overflows and scrolls the output iframe's OWN document. The app page must still never gain a horizontal scrollbar from an output; it cannot, since the iframe is fixed-width and clips. **That deliberate document-level overflow is why the srcdoc's height reporter is `reportedHeight()` in `src/lib/htmlOutputHeight.ts`** (a pure function serialized into the srcdoc with `toString()`, since the reporter cannot import): a bare `scrollHeight` excludes the horizontal scrollbar, so where the platform paints a classic space-taking bar (Windows/Linux) a frame sized to the content exactly loses ~15px to it and grows a VERTICAL scrollbar that clips the last row. The gutter is `window.innerHeight - documentElement.clientHeight` (the viewport including vs excluding a rendered bar), added only when `scrollWidth > clientWidth` - **never re-derived from the root's own `offsetHeight`**, which is the `<html>` box's content height, not the viewport, so the difference grows with the content and, since the parent feeds the reported height back as the frame height, makes the measurement oscillate. macOS overlay scrollbars measure 0px, so the local e2e cannot see this at all - it is guarded by unit-testing the ARITHMETIC, deliberately not an observed pixel gap. **The one non-obvious rule is `td:has(p,div,ul,…)`**: the same iframe renders arbitrary HTML where a `<table>` is sometimes two-column *layout*, and there the table's right-align inherits into each prose cell and ragged-rights a paragraph. A cell holding block-level content is a container, not a datum - a pandas cell only ever holds text - so those cells take start alignment back, deliberately as a DIRECT rule since it exists to beat the table-level default it would otherwise inherit; `:has()` takes the specificity of its most specific argument, so with only type selectors inside it stays element-level. **Known limit, accepted deliberately (do NOT add a heuristic, and do NOT grow the allowlist):** that escape is a HARDCODED ALLOWLIST of block tags, not a general block-level test, so it misfires BOTH ways - it UNDER-reaches a layout table whose prose cells use a block element not on the list (`blockquote`/`section`/`figure`/`article`/`dl`) or hold bare inline text at all (statsmodels' `summary()`, dask's array summary, pint, awkward), which read right-aligned (the alignment half of the scope note above), and it OVER-reaches a genuine data cell that wraps its value in a `div`/`pre` (xarray/dask-style nested reprs), which loses the numeric right-align this block exists to supply; both are cosmetic and fully overridable (the specificity rule guarantees an explicit user or library rule wins), so the allowlist stays as-is - adding the missing tags would only widen the under-reach half and leave the over-reach half - and widening the signal with a content-length rule was REJECTED because it misfires in both directions too (a long id wrongly left-aligned, a short label still right-aligned); right-align is the pandas numeric convention, and any library can style its own table. **Same class, same verdict: a table that declares no `<thead>`** - the HTML parser auto-inserts `<tbody>` but NEVER `<thead>`, so those header `<th>`s land in the inserted tbody, match `tbody th{text-align:left}` and read as index labels (left-aligned while the data below stays right-aligned), taking the plain `th,td` hairline instead of the darker header rule; statsmodels' `summary().as_html()` is exactly that shape, so it gets no header rule at all. Without a `<thead>` no selector tells a header row from an index column, so it is not CSS-fixable - and it is cosmetic + overridable like the rest, hence documented rather than worked around. Untouched by all of this: the native `DataFrameGrid` (a `_repr_html_` carrying `class="dataframe"`, AND a pandas **Styler**, are both routed to the grid by `dataframeHtml.ts`, never to this iframe) and markdown-cell tables (`.cellar-md table` in `app.css`). **So the tables this stylesheet still serves are the OTHER rich ones** - statsmodels' `simpletable`, folium/Bokeh chrome, hand-written markup, and a Styler the grid refuses (past its size ceiling, one whose data cells hold markup rather than text, or a shape mismatch) - which is why its e2e fixtures deliberately carry NO `col_heading`/`row_heading`/`data` classes: with them they would render as grids and never reach this stylesheet at all. Covered by `tests/unit/html-output-style.test.ts` + `tests/e2e/output-table-styling.spec.ts` (real kernel, real cascade in the real browser: bare defaults, a wide table staying a real table and overflowing the output document while the app page does not scroll, a long text column wrapping into view, a Styler's own rules still winning - both the per-cell form and the TABLE-level `text-align` that regression-tests the inheritance rule above - a layout table + a div-only output unharmed, and `_repr_html_` still reaching the grid).
- **ipywidgets support (progress bars + common INTERACTIVE widgets, two-way).** tqdm bars AND interactive controls (`IntSlider`/`FloatSlider`/range, `IntText`/`Bounded*`, `Checkbox`/`ToggleButton`/`Valid`, `Dropdown`/`RadioButtons`/`Select`/`ToggleButtons`, `Text`/`Textarea`/`Password`, `Button`, `Box`/`HBox`/`VBox`/`GridBox`, `Output`) render live, and interactive ones send changes BACK to the kernel. **Receive (kernel→FE, #86):** `kernel.ts` `registerWidgetComm` (once per connection - `restart()`/autorestart keep the connection+target, a rebind rebuilds both) does `registerCommTarget('jupyter.widget', …)` for every `comm_open`+`comm_msg` `update`. **Registering this target also SILENCES @jupyterlab's `Exception opening new comm` spam** - thrown for ANY `jupyter.widget` comm_open with no registered target - so the callback must handle ALL widget types, never throw. Server store `src/lib/server/widgets.ts` keeps `comm_id → {state}` (cleared by `beginSession()`), rebroadcasting `widget:open`/`update`/`close`/`clear` as **global** SSE (`publishGlobal` - model ids unique per session, one store spans all notebooks); the events route seeds `widget:sync` on connect. **Send (FE→kernel, the interactive core):** `kernel.ts` keeps the live `IComm`s in `widgetComms` (cleared in `beginSession`) and `sendWidgetComm(commId, data)` calls `comm.send`; route `POST /api/widgets/[commId]` forwards `{method:'update',state:{<trait>:<value>}}` (a value/`index` change) or `{method:'custom',content:{event:'click'}}` (a Button), so ipywidgets updates the Python model + fires `observe`/`interact` callbacks. The route ALSO `updateWidget`s the store (optimistic broadcast) because the kernel does NOT echo a frontend-originated change back as a plain `update` - only ipywidgets-8 `echo_update`, which the receive path **deliberately ignores** (applying it mid-drag snaps the slider back). **Client** `src/lib/widgetActions.ts` posts on interaction: continuous controls (slider drag) THROTTLE (leading+trailing, `THROTTLE_MS=80`), discrete ones flush immediately; `widgetStore.svelte.ts` `setWidgetTrait` optimistically updates locally for lag-free feedback, then reconciles via SSE. No loop: sends happen only on user `input`/`change`, never on receiving a store update. **`Output` widget / `interact`:** an Output widget does NOT sync its rendered outputs over its comm - it publishes a `msg_id` trait and every iopub output whose `parent_header.msg_id` matches is captured. `kernel.ts` `registerWidgetOutputCapture` (connects `kernel.iopubMessage` once per connection) routes those into the Output's `outputs` (`appendWidgetOutput`/`clearWidgetOutput`, honoring `clear_output(wait=True)`); `setOutputCapture` tracks the `msg_id`↔comm mapping (updated from the comm's `msg_id` trait, which lands as an earlier iopub message so ordering is safe). `execute()` SUPPRESSES a captured output from the cell (`outputCommForMsg(parentId)`) so `interact`'s result renders once, in the widget, not double. This is what makes `interact(f, x=IntSlider())` re-run `f` and update its output area live as the slider moves. **Render** `src/lib/WidgetOutput.svelte` (recursive) by `_model_name` via pure helpers in `src/lib/widgetModel.ts` (`widgetKind`, trait projections); selection widgets bind `index`+`_options_labels`; `src/lib/WidgetOutputArea.svelte` renders an Output's nbformat outputs (stream/text/html/image/nested-widget). All daisyUI semantic classes → clean in both themes; unknown types render `[unsupported widget]`, never crash. **Persistence: runtime-only** - `clean.ts` strips the per-output `widget-view` mime + drops an empty-bundle output, and THAT is what delivers the zero git-diff (the blob carries a fresh UUID every run, so it is the whole of the churn). Notebook-level `metadata.widgets` is a DIFFERENT key and is now PRESERVED by the notebook allowlist - safe because Cellar never writes one, only ever into `metadata.cellar` (see the Persistence + clean-on-save entry). A reopened notebook shows no live widget (state is volatile, by design).
