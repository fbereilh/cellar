# Exports: nbdev `.py`/`.mojo` module export, nbdev metadata protection, HTML export

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

The nbdev field-policy study lives outside the repo at `firstmate/data/nbdev-study-n8/report.md`.

- **nbdev-style cell export to a `.py` module (`src/lib/server/export-py.ts` + `src/lib/exportRole.ts`).** A per-code-cell **on/off** flag `metadata.cellar.export = true` (nbdev's `#|export`, rides the `cellar` allowlist → round-trips clean-on-save with zero git noise) plus a **notebook-level** target pair `notebook.metadata.cellar.export_target` + `export_base` (nbdev's `#|default_exp`; also honored as a `#|default_exp <module>` directive in any cell, dotted→path - a directive never reads `export_base`, since it lives in a cell and a stray stored base must not bend it, and its ROOT is nbdev's own: the project's `lib_path` in an nbdev project, else the workspace exactly as before - see `docs/design/nbdev-export-directives.md`). **The target is stored RELATIVE TO ITS BASE** (`$lib/exportTarget`'s `ExportBase` = `workspace` | `notebook` | `git`), and **an ABSENT `export_base` key permanently means workspace-relative - the legacy spelling, never migrated and never rewritten on open or save** (the setter DELETES the key for `workspace` rather than storing it, so a pre-base notebook and a round trip back to workspace are byte-identical; pinned by the legacy-pin test driving a hand-written on-disk artifact through the real doc layer). `notebook` measures from the notebook's own folder; `git` from the repository enclosing the NOTEBOOK (`git.ts`'s `gitRootOf`, a sync, spawn-free upward `.git` walk - a directory OR a worktree/submodule pointer file - deliberately NOT the code root, which may be an external worktree and governs the kernel, not this file; no enclosing repo is a first-class named refusal). **A base changes how the path is EXPRESSED, never what may be written**: every base resolves through the SAME `resolveInWorkspace` containment guard, so a git root ABOVE the workspace (`cd repo/analysis && cellar`) is fine exactly as far as the resolved module lands inside the workspace. **`resolveExportTarget(doc)` (`export-py.ts`) is the ONE resolution rule** - the exporter, `getNotebook`'s view fields and MCP's `exportTargetFields` all read it; it never throws, returning null (nothing configured) or an `ok:false` union naming why a CONFIGURED target cannot resolve (git base with no repo, an escape, an unknown hand-edited base value - each fails CLOSED, never silently read as workspace-relative). **CLEARING (`''`/null) is the one write exempt from base validation, and it is the universal repair** (`setExportTarget` checks `base` only inside the branch that really STORES a target, the `setNotebookRoot` rule that clearing can only remove state, never strand it): the tab keeps no copy of server state and sends the HELD base back with every path commit, so validating it up front made a notebook carrying an unresolvable base (a hand edit, or a `git` base whose repository has gone) unrepairable from the UI - the clear was refused, retyping was refused, and re-expression is impossible when nothing resolves, leaving a target that silently generates no module on every export. A clear deletes BOTH keys whatever the base says, and every remaining refusal on that path NAMES it as the repair (never `setExportBase`'s old "set the path again under the new base", which was exactly what the same unknown base blocked). An unknown base is still never coerced to `workspace`. **Switching bases RE-EXPRESSES the same file** (`notebook.ts` `setExportBase`: resolve the stored form to its absolute file, store it relative to the new base) - never reinterprets the typed text against the new base, which would silently retarget a different file; with no stored target it is an honest no-op (a base is a fact ABOUT a stored target, so none is ever minted alone), and the UI holds a pre-target base choice client-side and sends it with the first path commit. `export-py.ts` reads the marked cells IN ORDER and writes a clean module: header `# AUTOGENERATED BY CELLAR! DO NOT EDIT!` + `# Source notebook:` line (plus one `# Also from notebook:` line per other notebook whose `#| export <module>` cells it holds), a best-effort `__all__` (top-level `def`/`class`/simple assignments via `imports.ts`'s `logicalLines`, private `_names` skipped), then the sources joined by blank lines + trailing `\n` - **deterministic + idempotent** (skips the write when on-disk bytes match, so re-export is a zero git-diff no-op). This is DISTINCT from the jupytext whole-notebook `.py` mirror (`jupytext-actions.ts`): that mirrors every cell with markers; this is a lean library module of only the marked cells, **committed to git** (NOT gitignored, per nbdev). **EXPORT RUNS ON AN EXPLICIT ACTION AND ON NOTHING ELSE - `persist()` does NOT export.** It used to (`persist` called `autoExportPy` after every write), and writing a git-tracked file on every debounced keystroke-save is the wrong default: the concrete harm was an ESTABLISHED nbdev repository, where the target names a module nbdev generated, so every save reached for a file Cellar did not write, the clobber guard below correctly refused it, and the refusal was recorded on `doc.lastExportError` - which only the agent surface reads. A failure the user could never see, once per save, forever. Making the export explicit fixes that at the root rather than by softening the guard: a refusal now has an obvious home, the button (or tool call) that asked for it. **THE THREE EXPLICIT CALLERS** (`notebook.ts` `regenerateExportModule`, the renamed `autoExportPy`, plus `exportPy`): (1) **`exportPy()`** - the export bar's Export button and the `op:'export'` route, the loudest of the three, which **THROWS** a real error at the caller rather than recording it, so the route answers 400 and the failure lands on the notice channel of the very click that asked; (2) **`setExportTarget`** - naming the module's file; (3) **`setCellExports`** - choosing which cells are IN it. (2) and (3) regenerate BEST-EFFORT (try/catch, so a bad target never costs the notebook write the same call just made) but NOT silently: the throw is recorded as `lastExportError`, which is what the agent tools' conditional `module` field reports; both are no-ops unless a target is set AND ≥1 cell marked, and both skip `.py` jpFormat docs, which carry no cell metadata. **EVERY OTHER SAVE - an edit, a run, an add, a move - now leaves the module exactly as it was**, so a marked cell edited and not re-exported is genuinely STALE on disk (see the stated follow-up below). Since only the explicit paths write it, `lastExportError` now describes the last time the module was actually ASKED FOR rather than the last keystroke. `exportPy` REFRESHES it in BOTH directions for the same reason its two siblings do: it writes without going through `persist`, so a stale success was still reported by the next idempotent `set_cell_export` (which skips the persist and the regeneration that would have cleared it), while a failure left UNRECORDED is worse - with the record null that same call emits no `module` field at all, which under the conditional contract reads as a module that WAS regenerated. Reached via the **export section** (`data-testid=export-bar`) of the notebook's language-and-export menu - a native `popover` opened by the `notebook-settings` button at the right end of the notebook toolbar (`Notebook.svelte`; the section names "export bar" below refer to it): a base `<select>` (`export-base-select`, non-optimistic - driven by the settled model value, held back only while a change is in flight, the root picker's own resync idiom) + target input + "N cells marked" + an export button whose label names the target's OWN module ("Export" with none configured, else "Export to .py"/"Export to .mojo" - no surface may name a target the notebook does not have) + inline feedback. The toolbar's `toolbar-export` button beside the menu button runs the shell's `exportPy` in one click, so its result lands on the notice line, and opens the menu at the target field when no target names a module - **offered on every `.ipynb`** (`showExportBar = !isPy`), so a target can be set BEFORE any cell is marked. A non-workspace base also echoes the RESOLVED workspace-relative path (`export-resolved`; under the workspace base it would restate the input), a configured-but-unresolvable target shows its reason (`export-resolve-error`), and **`export-import-warning` states the one trap a SUCCESSFUL export can leave: the module resolves outside the notebook's declared code root, so the kernel - whose imports resolve from that root - cannot `import` what was just written** (`$lib/exportTarget`'s pure `exportImportWarning`, computed from the RESOLVED path so it is exact whatever base expressed it, and null whenever it does not apply - no target, no root, the module sits under the root, or **the target is `.mojo`** - the root bar's kernel-restart warning being the model: accurate, and only where it applies; **the `.mojo` silence is a claim about the LANGUAGE, not the rule being switched off**: every clause here is about PYTHON import, since the kernel's `sys.path` carries the code root (`projectRootAddCode`) and that is what puts an outside module beyond a code cell's reach, while a `%%mojo` cell reaches the compiler through a SUBPROCESS, so the code root decides nothing about a `.mojo` module. Warning only for the outside case would advertise a remedy (move it under the root) that cannot work, and warning for BOTH cases would be permanent chrome on every Mojo notebook - the same over-warning `mojo-main-kept` was demoted for - so silence is the honest answer, and it is pinned in both directions; WHICH shape a declared root is comes from `classifyRootPath`, the ONE browser-safe owner of that rule, never a local prefix test (the repo already source-guards that re-derivation in three other files after two copies disagreed) - and a declaration that owner REFUSES outright (a `~` path, which `readRoot` hands to the browser verbatim) warns like any other root that cannot contain the module rather than throwing, since this runs in a render-time `$derived` in the export bar, which sits OUTSIDE the per-cell render error boundary (that wraps only the cell rows below it); warning tint on the ICON, `base-content` copy, per the contrast doctrine)) and the command palette's "Export to module" (`export-module`, `+page.svelte` → `activeNotebookApi().exportPy()` → toast). **`PATCH /api/cells/[id]` applies `source` BEFORE `export`, and that order is load-bearing rather than cosmetic:** `setCellExport` READS the cell's source twice over - to decide its `export-directive-owns-cell` 409, and to REGENERATE the module - so a body carrying both fields was answered from the text the request was about to replace (the module built from the pre-edit source, a state that never existed; the refusal judged against a directive the stored cell would no longer have). It sat the other way between #102 and the fix, which broke two `export-target-section` e2e cases and merged green because Playwright runs in NEITHER CI nor the gate - hence the pin is `tests/unit/cell-patch-field-order.test.ts`. The stated cost is that a refused `export` leaves that body's `source` persisted, which is the right direction and is asserted. **That route REPORTS three of `setCellExport`'s refusals as a 409 - `export-directive-owns-cell`, `not-code` and `py-notebook` - while `no-such-cell` and every sibling setter stay silent** (widening those is still a separate change). `not-code` was widened deliberately once eligibility became a NOTEBOOK-level fact the tab mirrors over SSE: another tab's or an agent's `set_export_target` in flight leaves this tab deriving the OLD language, so it renders the toggle for a cell the document then refuses, and `{ok:true}` left a phantom `cellar.export` the export bar counted as marked for a mark that exists in no file. `LiveNotebook`'s `setExport` reverts on BOTH reasons and says which, through `exportIneligibleNotice` - which states only what is OBSERVED of the cell (it contributes no module source at all, or it does not match this notebook's module) and NEVER names an extension, since the stale target is the very thing that produced the refusal. The revert is purely LOCAL: the stale language heals on its own when `notebook:export-target` lands, so no cross-tab coordination is involved. **UNMARKING is never refused** (`setCellExport` gates only a MARK on eligibility), which is what keeps the stranded-toggle contract - the greyed toggle sends `false` - working. Full reasoning in the route's own header. **Wiring:** an always-visible per-cell toggle in the cell ROW (`Cell.svelte`, `data-testid=toggle-export`, beside the copy buttons - see the cell-row-toggles entry below; there is deliberately no separate `export-badge` any more) → `onSetExport` → `LiveNotebook.setExport` → `PATCH /api/cells/[id] {export}` → `setCellExport` → `cell:export` SSE; target via `POST /api/notebooks/export-py {op:'set-target'|'set-base'|'export'}` → `setExportTarget`(+optional `base`)/`setExportBase`/`exportPy` → `notebook:export-target` SSE (every set-target/set-base reply - the 400 refusals and the writeFailed 5xx included - answers with the HELD state, so the field adopts what the document really holds on every outcome, read through the doc layer's OWN `getExportTargetState` rather than a route-local copy, since a refusal is the only thing that can correct the tab's field and select and a second rule there answered a refusal and a success with two different readings of one document. **The BASE is adopted only when the document really HOLDS a target**: a base is a fact ABOUT a stored target, so with none stored the reply's `workspace` says nothing while the select holds a client-local pre-choice not yet persisted - adopting it there discarded that choice on any REFUSED first commit (a missing `.py`, an escaping path) and the corrected retype then stored the path under a base the user never chose, a different file. The resolution is null in that case anyway, so it is adopted either way). `getNotebook`/`NotebookView` carry `exportTarget` plus `exportBase`/`exportResolved`/`exportResolveError` so the browser seeds all of it on load; the SSE `notebook:export-target` event and both write replies carry the same full `ExportTargetState`, so the tab's keep-no-server-mirror rule extends to the base. `setCellType` KEEPS the export flag through every conversion (see the mojo-module-export entry): the mark survives, `isExportCell` still ignores an ineligible cell so nothing reaches the module, and the cell STRANDS - visible on the greyed row toggle and clearable there - rather than being silently unmarked in the user's committed `.ipynb`. **WHICH cells may be marked is the LOGICAL type MATCHED AGAINST THE TARGET's language, and `isExportCell` is where that is decided - never an nbformat `cell_type === 'code'` test.** A SQL cell IS an nbformat `code` cell tagged `cellar.language='sql'` (see `cellLanguage.ts`), so a `cell_type` test admits one and `export-py.ts` then concatenates its raw SQL into a module git TRACKS - invalid Python in a committed file, with the toggle offering no way to mark it in the first place (`Cell.svelte` gates it on `canExportCell`, which excludes SQL under either target; a stale flag it already carries strands instead, and the greyed toggle clears it). The rule therefore lives in the ONE identity every surface reads (the exporter's filter, the badge, the agent map), so a stale or hand-edited flag on a SQL cell is inert everywhere rather than only at whichever setter last remembered to check. Its ELIGIBILITY half is **exported as `canExportCell`** and `isExportCell` is expressed in terms of it, so both SETTERS (`notebook.ts`'s `setCellExports`, `mcp/service.ts`'s per-cell check) call the SAME function rather than each re-deriving it from `isLogicalCellType` and agreeing only by coincidence - the drift this very fix argued against, reintroduced one layer down. **Agent side: `set_cell_export(ids, export)`** (`mcp/server.ts` → `mcp/service.ts` `setCellExport` → `notebook.ts` `setCellExports`) is the MCP equivalent of that per-cell toggle - batch, handle-addressed, all-or-nothing, and marking only a code cell whose language MATCHES the target's (`canExportCell`, target-aware since `.mojo` targets landed) - and it pairs with `set_export_target` (owned here, not by the display-settings entry, which points back to this one). It regenerates the `.py` through the SAME `regenerateExportModule` path every explicit export uses, so there is no second export path; `setCellExports` is the BATCH form (one document write + one regeneration - a loop would rewrite both files once per cell) and the singular `setCellExport` the UI drives is now that batch of one. **A `.py` TEXT notebook is refused UP FRONT** (`isPyTextNotebook` → `{ok:false, refused:'py-notebook'}`, surfaced through the ONE shared `pyNotebookRefusal(what)` message naming the cause, never a generic not-found), mirroring `exportPy`'s own throw. **Every export surface asks ONE rule for that, `exportRole.ts`'s `notebookHoldsExport(isPy)`** - the server refusals (both MCP tools, `exportPy`, the target route, and the doc-layer `setCellExport`/`setCellExports`, whose `py-notebook` refusal the PATCH route answers as a 409) and the browser gates (the row toggle is HIDDEN on a `.py`, like the export bar; `LiveNotebook.setExport` mirrors and reverts). Before it the row toggle was ungated there: the doc layer applied the mark IN MEMORY, so it survived a page reload and was lost on relaunch (pinned by `tests/e2e/export-toggle-py-notebook.spec.ts`): such a doc carries no cellar cell metadata, so the flag can never be stored AND the regeneration skips it, i.e. reporting success would promise a module that can never exist while spending a blocking jupytext `spawnSync` on byte-identical output. **`set_export_target` takes the SAME refusal through the SAME predicate - and so does the UI's own target route** (`src/routes/api/notebooks/export-py/+server.js`, `op:'set-target'`, refusing with an actionable 400; `op:'export'` was already refused inside `exportPy`), because the symmetry is required rather than tidy: one half accepting a target the other half refuses to act on left an agent following INSTRUCTIONS clause 5 - or a human reading the sidebar's target input - holding a target it was told is set, for a module that can never be built (it survives neither a reload nor a regeneration). **The CLIENT half of that refusal is required too, or the fix stops one layer short** (`LiveNotebook.svelte` `setExportTargetValue`): the write is optimistic and the route emits `notebook:export-target` only on SUCCESS - which this tab would echo-suppress anyway - so a swallowed 400 left the input showing the rejected path and the export bar reading as configured over metadata holding nothing, i.e. the same shown-a-setting-that-does-nothing failure the refusal exists to prevent. It reads `res.ok`, REVERTS and sends the server's message to the shell's transient notice channel (`onNotice`, the one the delete refusals already use - never a second surface). **The target input commits ONCE PER EDIT, on its `change` (a blur after typing, or Enter) - never per keystroke, and that is what keeps the revert from fighting the typist.** Writing per keystroke was harmless only while the route could refuse nothing: with real refusals it made EVERY character of a bad path (an absolute one, a `..`, a non-`.py`) 400, revert the state-driven field, move the caret and raise another notice - and the debounce, generation guard and pending-value mirror stacked to contain that were themselves a race (a superseded-but-successful write never advanced the confirmed baseline, so a clear typed inside the window was dropped while the server kept regenerating the old target). One commit per edit removes all of it: `change` does not fire on an unmodified blur, so clicking through the field writes nothing. **`change` is not reliably delivered before UNLOAD, though**, so the field also flushes an uncommitted value on `pagehide` (`Notebook.svelte`'s `flushExportTarget`, the idiom `Cell.svelte` already uses for its debounced edit, with `keepalive` there): without it a target typed and then reloaded or tab-closed on was simply lost. **It deliberately does NOT flush on TEARDOWN, unlike its `Cell.svelte` model** - `LiveNotebook` renders `Notebook` behind an `{:else if fetching}` gate, so every `load()` refetch destroys it (an SSE reconnect, a seq gap from an agent's edit, `notebook:restored`, a refused bulk op), and a teardown commit therefore fired MID-EDIT from a background event the user never caused: a half-typed path raised a spurious refusal, or one that happened to parse was silently persisted and the module regenerated to a stray target. Losing an uncommitted value to a refetch is the accepted, far better half of that trade - do not "fix" it with new machinery to preserve it. It writes only while the input still diverges from the model, so the per-edit commit model is untouched. **THE BASE SELECT AND THE TARGET INPUT WRITE TO ONE DOCUMENT, so the base change AWAITS the in-flight path commit** (`setExportBaseValue` awaits `exportTargetCommit`, the `exportPy` rule and for the same reason): clicking - or tabbing into - the select BLURS the input, which is what fires its `change`, so the everyday "type the path, then pick the base" gesture put both writes on the wire at once and whichever reply landed first won, the other being thrown away by the `superseded` guard - leaving a (path, base) pair the server does not hold until a reload, and with NO stored target destroying both (this function read the OPTIMISTIC path, took the re-express branch, and the server's honest no-op `{target:null, base:'workspace'}` was adopted over the typed path AND the client-local pre-choice). The commit is CONSUMED by the wait - it drops itself from `exportTargetCommit` on settle - and deliberately NOT nulled up front, which would instead let an export clicked during the wait skip the commit it must await; both branch conditions are then re-read against the SETTLED value. **That base write also owes the SAME refusal-vs-failed-persist split its path sibling makes, decided by the `writeFailed` FLAG and never by the status code**: `setExportBase` validates before it mutates, so a 500 carrying that flag means the document HOLDS the re-expressed target under the new base and only the save failed - and that reply carries NO `message`, so a client reading the message alone fell through to "the server could not be reached", denying a change the select was visibly showing and naming a cause that did not happen. It says accepted-but-not-saved instead, keeping the unreachable wording for a reply that landed no verdict at all. **And the held-guard has ONE exception, without which the documented repair for an unknown hand-edited base LOOPED**: a locally-held value that is not a legal base at all can only have come from the DOCUMENT (the select cannot produce one), so it is no pre-choice to protect - clearing the target deletes both keys and answers `held:null`, the guard kept the dead base, and the very next path commit sent it again and was refused with "clear the export target to reset the base, then set the path again", the advice just followed. `isExportBase` decides it, so "an unknown base renders unmatched rather than masquerading as workspace" is untouched. Both are pinned behaviorally in `export-target-section.spec.ts` (the path commit HELD by a route so the interleaving is deterministic rather than a race). **THE TAB KEEPS NO COPY OF THE SERVER'S TARGET, and that is the design - do not reintroduce one.** EVERY `set-target` reply carries **`target` = the value the document HOLDS once the call is done** (which is why the route's refusals are RETURNED as a json 400 rather than thrown through `error()`, whose body is a bare `{message}`), and the field simply ADOPTS it on every outcome the server answered at all - a success (so a normalized absolute path is taken up too), a refusal (so the revert goes back to what the server really holds), and a failed WRITE (where the document already holds the new path, so the field keeps it and the two cannot diverge). This replaced two client-side mirrors - the last value the server confirmed and the last value SENT - which each needed a rule to stay agreeing with each other and with the server, and every rule had its own hole: a failed write left the two describing different paths, so retyping the previous one hit the skip-check and wrote NOTHING while the server kept the newer one (and, since `change` does not fire when the value at blur equals the value at focus, the documented retry was unreachable); and a background refetch resolving inside a commit window seeded both staler than the write in flight, so that write neither advanced them nor adopted the stored value. There is therefore **no skip-check** - a redundant identical POST is the accepted price, the setter being idempotent and byte-identical - and `load()`/the SSE event just show what they were handed. **The ONE comparison left is against the FIELD, not against any memory of server state** (`exportTarget !== next` ⇒ `superseded`, checked BEFORE anything is written back, the success path included): while a write is on the wire the value can move on - the user typing again, another tab's or an agent's `notebook:export-target`, a refetch - and writing our reply back would discard state that write knows nothing about. **`exportPy()` AWAITS the in-flight commit** (`exportTargetCommit`) before the manual export POST: pressing the button blurs the input, so the edit is committed, but that POST is still on the wire - without the await a freshly typed target exported against the previous one, reporting "Set a target module path (.py, .mojo or .rs) in the notebook's Language and export menu first." while the field visibly showed the new path. **A commit that did NOT LAND ABORTS the export**: that path was never (verifiably) stored, so exporting on ran against the previous/absent target and its outcome REPLACED that commit's own reason on the single nonce-keyed channel - typing `utils.txt` and pressing Export answered "Set a target module path (.py, .mojo or .rs) …", telling the user to do exactly what they had just tried. **`commitExportTarget` therefore reports FIVE outcomes, never a boolean** (`TargetCommit`), because one flag conflated three of them and each conflation was its own defect: `committed` (the field adopts the target the reply reports as stored), `refused` (the server rejected the path - adopt the target it reports still holding + say why), `unreachable` (the request landed no verdict we can READ - the server was unreachable, or something other than this route answered: a proxy 502/503, an HTML error page - so nothing is claimed and the field is left alone, since reading it as a success left the field showing a path the server may never have stored while the export ran on to report "Exported N cells → \<the OLD target\>" over it), and `superseded` (the field moved on - another tab's/an agent's `notebook:export-target`, or a refetch - so a newer value owns it: touch NOTHING, and **do not abort the export**, which turned the button into a dead control that issued no request and rendered no message). The superseded check runs BEFORE anything is written back. **`writeFailed` is the fifth, and it is the ONE failure that KEEPS the value rather than reverting it**: `setExportTarget` (both in `notebook.ts` and at the UI route) VALIDATES BEFORE IT MUTATES, so a throw after that point is the `persist` - a disk failure (EACCES/ENOSPC, a read-only checkout) over a path that was never wrong and that the live document already HOLDS and will write with its next successful save. Both surfaces therefore tell the two apart by TYPE (`InvalidExportTargetError`, thrown only where the path is checked), never by matching the message text: MCP answers `writeFailed` instead of `invalid`, and the UI route answers a **5xx carrying `writeFailed`** instead of the refusal's 400 - collapsed into that 400 the tab took its refusal branch, reverting the field and telling the user the target was not set over a change that DID take, with nothing left to correct it (the success event is never emitted, and this tab would echo-suppress it anyway). **The client decides it from that FLAG, never from the status code**: any OTHER 5xx (a proxy 502/503, an HTML error page) landed no verdict at all, so treating a status as the signal told the user the target was "accepted but not saved" over a request the server may never have received - the same false acceptance `unreachable` exists to prevent, reached through the other door. It keeps the field (adopting the `target` the reply reports, which on this path is the new one the document holds), says only that it could not be SAVED, and does **not** abort the manual export (the document holds the target, so the export runs against the path the field shows and reports its own failure if the disk is still broken). **The abort is scoped to a commit still IN FLIGHT**, which is what makes it belong to the blur-then-click interaction and nothing else: the promise DROPS ITSELF the moment it settles (and is CONSUMED by `exportPy` on top, so one refusal cannot abort two exports), because a settled refusal left in `exportTargetCommit` silently aborted the NEXT manual export - one that would have run fine against the stored target - and produced NO message at all, since that export never issued a request to report on, so a dead click read as an ordinary failure. **The manual export reports the SERVER's reason** through that same `onNotice` channel, from BOTH entry points - `Notebook.svelte` renders NO inline string for a failure and `+page.svelte`'s navbar item adds none either, since that channel is single and nonce-keyed, so a generic string posted after the reason simply REPLACES it - the refusals this path can hit (a non-`.py` or escaping target, an unreadable file at the target) exist for their actionable message, so a bare "Export failed." was both a second surface and a less informative one. **The navbar item also does NOT pre-emptively `clearNotice()`**, for the same reason: opening the app menu BLURS the target input, so its `change` commit has usually already SETTLED and posted its refusal reason by the time the item is clicked, and clearing on click erased a message the user had not read yet (the in-flight case survived it only by accident of ordering). Nothing needs clearing - every branch there, and every failure path inside `LiveNotebook.exportPy`, ends in exactly one message that REPLACES whatever was up. A failure on the two BEST-EFFORT explicit paths (`setExportTarget`/`setCellExports`, which record rather than throw) still has no UI home of its own - it is recorded as `lastExportError` and read only by MCP - so the manual button, which throws, is the human's route to it. `setCellExports` also guards its persist with `doc.jpFormat` like `clearOutputsForCells` (the pre-existing UI PATCH path reaches it directly), while the `cell:export` events still fire so open tabs update. **A refusal echoes the handle the AGENT supplied**, not the full UUID `resolveMany` expanded it to - an id absent from its own call reads as the tool answering about some other cell. **The regeneration is REPORTED, never promised** (`moduleWarning`), and EVERY way it can fail to happen is covered - because `module` is CONDITIONAL, so its ABSENCE is what says the module was written. (a) The write THREW: the regeneration these two tools drive is best-effort by design (a bad target must never cost the notebook write the same call just made), so a target whose parent is a file, an EACCES or an ENOSPC left the module unwritten while the result claimed nothing at all, and there is no MCP export tool through which an agent could ever learn otherwise.
