# Notebook documents, persistence, clean-on-save, cell types, imports cell, display settings

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Notebook documents (server-owned, multi-doc).** `src/lib/server/notebook.ts` holds in-memory notebooks keyed by absolute path in a `docs` Map — the default `notebook.ipynb` **and** any other workspace `.ipynb` opened live. Every exported op takes an optional trailing `nb` (workspace-relative or absolute path); omitting it targets the **active** notebook (`activePath`). `setActiveNotebook(nb)`/`getActiveNotebookPath()` track which notebook the agent-facing (MCP) tools default to; the UI POSTs `/api/notebooks` to follow tab focus. **Loading never writes to disk** (`loadDoc`): the default notebook is materialized *in memory* if missing so callers get a valid shape (SSR seeds the shell from the canonical notebook through `readDefaultNotebook()`, which never throws - see below), but no `.ipynb` is written on a bare startup/open — so opening Cellar in a folder drops **no** uninvited file. Every notebook (default included) persists only on a genuine mutation (add/edit/run/…) or an explicit `createNotebook`, which materializes the file (and the UI's empty-state "New notebook" button → `POST /api/notebooks {create:true}` → `createNotebook`); an arbitrary opened `.ipynb` must exist and is likewise NOT rewritten until mutated (no surprise git diff on open). Startup with no `notebook.ipynb` shows the shell's empty state (`+page.svelte`, `data-testid=empty-state`). Cellar owns cell IDs (uniqueness enforced **per document** on load via `enforceUniqueIds`; ids may legitimately repeat across notebooks — do NOT assume global uniqueness).
  - **A new `.ipynb` is a VALID notebook the moment it EXISTS (the WRITER), and a file that is ALREADY blank on disk is REFUSED rather than opened (the READER stays strict).** `createEntry` (`fstree.ts`) is the only place a new empty file is minted and it wrote `''` for every kind, so the file explorer's "New file" -> `analysis.ipynb` produced a ZERO-BYTE file and opening it answered `Unexpected end of JSON input` (`JSON.parse('')`, straight out of `readNotebook`) - while the empty-state "New notebook" button and every MCP create went through `createNotebook` and wrote a real skeleton, which is why the failure looked route-specific. **The fix is the writer**: `POST /api/fs/op`'s `create` passes `blankNotebookText()` to `createEntry`, so the file is valid nbformat 4.5 for EVERY tool and not just Cellar. `ipynb.ts`'s `blankNotebook()` is the one definition of what it contains (nbformat 4.5, ONE empty code cell - never zero, the invariant `deleteCells` also refuses to break) and it goes through `serialize`, so a brand-new notebook is byte-identical to that same notebook re-saved. **The `initialContents` argument of `createEntry` is a FUNCTION OF THE NORMALISED NAME, not a string**: `assertSimpleName` trims, so a caller deciding from its own raw input answers about `"notes.ipynb "` while creating `notes.ipynb`, minting exactly the blank notebook this exists to prevent; `fstree` itself stays notebook-agnostic so the path/name guards keep their one copy, and the notebook consequence lives in the route beside its siblings (`delete` drops docs + kernels, `rename`/`move` rekey them). **THE READER IS DELIBERATELY STRICT, and the reasoning is worth keeping because the leniency was tried twice and withdrawn.** Reading a blank file as an empty notebook buys exactly ONE thing: repairing an `.ipynb` that is already blank on disk (a `touch`, a rename or a copy of an empty file, or one an older Cellar left behind). Its cost was measured. (1) "No bytes, so nothing to lose" is true of a GENUINELY empty file and FALSE of a MOMENTARILY empty one - a non-atomic external writer (nbdev's `fastcore/nbio.py` opens with `'w'`) truncates before it writes, and this repo has MEASURED a 0-byte read in exactly that window (`fileWatch.ts`'s header, which is why its settle debounce exists) - so a real notebook was cached as a blank document and the next save overwrote it. (2) Guarding that at the first write then cost a PERMANENT LOCKOUT (`loadDoc` caches the blank-inferred document and never re-reads, so the refusal's advised reload could not work and every later save refused for the life of the process) plus a refusal INVISIBLE on its likeliest paths (an autosave PATCH is deliberately swallowed by the client, and in the run route the throw closes the NDJSON stream with no `run:end` and no `lastRun` stamp). Every fix needed another fix, in the notebook WRITE path, which is the user's PRIMARY data - while the repair it bought is now one delete-and-recreate away, because creating a notebook works. So: refuse, never degrade. **THREE DISTINCT REFUSALS, because they are three distinct facts, and each is a typed `NotebookReadError` carrying its `reason`** (`empty` | `unparseable` | `unreadable`, `$lib/server/types`'s `NotebookReadFailure`): a BLANK file (no bytes, or whitespace only) says `the file is empty, so there is no notebook to open - delete it and create it again from the file explorer`; bytes that are PRESENT but do not parse keep `not valid JSON (<parser detail>)`; and a file that could not be OPENED names its errno. None repeats the file name (every caller already prefixes it). **The reason is a DISCRIMINATOR rather than a message match (the `InvalidExportTargetError` rule), and what hangs off it is a data-safety decision, not copy: ONLY `empty` may advise DELETING the file.** A blank one holds nothing; an `unparseable` one holds the user's own bytes - the very bytes this reader refuses to overwrite - so a shared guidance paragraph telling them to delete it destroys by hand exactly what refusing protects. `readDefaultNotebook` forwards the reason beside the message as `notebookErrorReason`, and the shell's empty state branches on it (`unparseable` says to repair or restore the file OUTSIDE Cellar and reload; `unreadable` says to fix access and reload; both also name an in-app way forward that leaves the damaged file alone - a notebook under a DIFFERENT name from the explorer's New file - since `notebook.ipynb` may be the workspace's only one; every branch names the reload, the reason being a one-shot SSR fact). It **fails safe by construction** - only the exact `empty` match reaches the delete advice, so an absent or unrecognised reason falls through to the non-destructive branch. `loadDoc` still persists nothing on open, so an unedited file stays exactly as it is, and a refusal writes nothing at all. **THE CANONICAL NOTEBOOK IS THE ONE FILE WHOSE REFUSAL MUST NOT REACH SSR** (`readDefaultNotebook`, read by `+page.server.js`'s `load()`): the refusal names the file explorer as the repair, and the shell seeds itself from `notebook.ipynb`, so an unguarded read there took the WHOLE PAGE down instead of one tab - the explorer was unreachable and a production build sanitises a load error into a generic page, so the user was not even told why. It now returns a **display-only stand-in** (never entered in the `docs` map, so every mutation still reaches `docFor` -> `loadDoc` and still THROWS - no write can land on top of bytes Cellar could not read, which for a CORRUPT notebook would be real data loss) plus the reason as its own `notebookError` field, which the shell's empty state renders instead of "No notebook open" - a state that would imply there is simply no notebook. It is the same best-effort rule `detectMcpConfig`/`detectNbdev` in that `load()` already follow. **That reason is a ONE-SHOT SSR fact and the message names a RELOAD to make its remedy complete** - deliberately NOT re-probed. The only read that could answer goes through `loadDoc`, which serves a CACHED document and MATERIALISES a starter one for this very path, so it cannot observe the file: on a canonical delete it would resurrect the entry `dropDocs` had just cleared, and once that phantom is cached a replacement file at that path reads as fine while the first mutation persists the starter over its bytes. A probe that cannot observe what it probes is not worth that hazard on the shell's startup path, so the message carries the reload instead and stays true for as long as it is on screen. The empty state also **withholds its "New notebook" button** in that state: `createNotebook` OPENS an existing file rather than overwriting it, so over an unreadable canonical notebook it could only throw. **NO REFUSAL FROM THIS READER CARRIES A SERVER PATH, and it is fixed at the READ rather than stripped downstream** - the two authored refusals never had one, and the door the leak came through is `readFileSync`, which Node reports with the file it failed to open (`EACCES: permission denied, open '/Users/…'`); it is wrapped and re-raised as its errno alone (`the file could not be read (EACCES)`). Stripping paths downstream instead was tried and withdrawn: the parse refusal's detail is the file's own CONTENT, so a path-stripper eats exactly the token identifying the corruption (a renamed `.js` reports `Unexpected token '/', "// hello" is not valid JSON`, which came back as `Unexpected token , hello"`), and the intent requires a corrupt notebook's message to stay useful. `$lib/serverMessage`'s `reasonWithoutServerPath` is therefore untouched and still serves its one caller, the stale-kernel-card refusal. **Stated adjacent hazard, NOT fixed here:** `deserialize` tolerates a parsed value with no `cells`, so a file that is VALID JSON but not a notebook (`{}`, `[]`, a renamed `package.json`) opens as a ZERO-cell notebook and the first mutation persists nbformat over it - a real data loss, and out of this fix's scope because refusing it means deciding how loose a hand-written notebook may be. Covered by `tests/unit/new-notebook-file.test.ts` (the writer, the three refusals and the delete-and-recreate repair), `tests/unit/canonical-notebook-load.test.ts` (the SSR half: the shell resolving over a blank or corrupt canonical notebook, WHICH reason it reports, and the stand-in staying unwritable) + `tests/e2e/new-notebook-file.spec.ts` (the end-user path: the explorer's click, the tab rendering a notebook rather than a load error, a cell that runs, a blank file rendering the actionable refusal rather than the raw parser text, and a broken canonical notebook leaving the shell and its explorer usable - never advising a delete for a corrupt one).
- **Persistence + clean-on-save.** `src/lib/server/ipynb.ts` (de)serializes canonical doc ↔ real nbformat 4.5 with **deterministic** output (**keys SORTED recursively**, 1-space indent, trailing `\n`) so identical re-runs produce zero git diff. **The sorted keys are the ECOSYSTEM's convention, not an nbdev concession, and that is why the change is unconditional:** `nbformat` - the reference writer behind JupyterLab, Jupyter Notebook, nbconvert and papermill - writes `sort_keys=True, indent=1`, and fastcore/nbdev's writer (`fastcore/nbio.py`) writes the same plus `ensure_ascii=False` and a trailing newline. Cellar wrote INSERTION order (`cell_type, id, metadata, source, outputs, execution_count`) where everything else writes alphabetically, so ANY notebook touched by both Cellar and Jupyter churned 100% of its lines. `JSON.stringify` already agrees with Python on unicode (both emit literal characters), so `sort_keys` was the remaining difference for everything a notebook is MADE of - pinned by a test asserting Cellar's bytes are IDENTICAL to `json.dumps(sort_keys=True, indent=1, ensure_ascii=False)`, which is a far stronger claim than "the keys are sorted". **The claim is scoped, and the scope is checkable:** key order (recursively, numeric-string keys included), string escaping, unicode, indent, trailing newline, array order and empty containers all match; **NUMBER FORMATTING is the one stated residual**, because primitives go through `JSON.stringify` and so are spelled by ECMAScript's rule rather than Python's `repr`. Measured: an integral float (`1.0`->`1`), a negative zero (`-0.0`->`0`) and an integral value in exponent form (`1e16`->`10000000000000000`) differ on the first save and then CONVERGE (Python re-reads Cellar's spelling and keeps it, so they fold into the one-time reformat below), while a float the two writers spell with different notation (JS goes exponential below `1e-6`, Python below `1e-4`: `1e-5`->JS `0.00001`, Python `1e-05`) or with a differently padded exponent (`1e-7`->JS `1e-7`, Python `1e-07`) ALTERNATES forever, one line per such number. Deliberately NOT chased: `JSON.parse` erases the source lexeme, so matching Python means reimplementing its float `repr` - a large, risky change for a cosmetic divergence between two valid JSON spellings - and Cellar's own determinism and idempotence are untouched either way. Do not restate this as "sort_keys was the ENTIRE difference": the next person measuring residual churn on a plotly/altair payload full of `1e-07` would go hunting an emitter regression that is not there. Sorting is done by a HAND-ROLLED emitter (`emitJson`) that writes the JSON text itself, and it may NOT go back to a `JSON.stringify` REPLACER: the JS spec fixes the property order of any object - canonical array-index keys (`"0"`, `"2"`, `"10"`) come FIRST, ascending NUMERICALLY, whatever order they were inserted in - so a replacer that inserts keys sorted as strings still emitted `2, 10, a` where Python writes `10, 2, a`, and integer-like keys reach a notebook through any ordinary payload (`display(JSON({"2020": …}))`, a `to_dict()` over an integer index), i.e. exactly the residual churn the sort exists to remove. Keys are compared by CODE POINT (not JS's default UTF-16 code UNIT, which orders a surrogate pair before `U+E000`-`U+FFFF` where Python does the opposite), so the byte-identity claim holds for any key rather than only ASCII ones. PRIMITIVES are still delegated to `JSON.stringify`, so string escaping stays byte-for-byte the native rule (= Python's `ensure_ascii=False`) and the multi-MB payloads (base64 rasters, stream text) never leave the native path - this does not undo `clean.ts`'s no-deep-clone rule. Measured cost: ~2x the replacer (15ms vs 8ms on a 4 MB, 200-cell notebook), scaling with node COUNT not payload SIZE, on a save that already does a synchronous fsync + rename. **ONE-TIME COST, accepted knowingly:** every pre-existing notebook reformats once on its next save; proven a PURE KEY REORDERING (parsed deep-equality before/after) across 49 real notebooks - nbdev's 33 `nbs/` + its 14 deliberately-weird `tests/` + Cellar's own two committed ones - of which 47 genuinely changed bytes. **Watch the knock-on: sorted keys change the notebook's PHYSICAL LINE GEOMETRY** (`outputs` now precedes `source` inside a cell), so anything reasoning about where a cell's source sits in the file - `cellSourceLines`, the git-blame `-L` scoping - must be written key-order-agnostically rather than against a measured gap. `src/lib/server/clean.ts` is the field policy: nulls all `execution_count`, deny-by-default metadata allowlists, normalizes `kernelspec.display_name`→`name`, scrubs `<… at 0x…>` memory addresses. Must stay **idempotent**. **The allowlists are Cellar's own keys plus nbdev's ENTIRE CURRENT base lists** (`nbdev/clean.py` 3.3.12) - notebook `kernelspec, cellar` + `nbdev, jupytext, widgets, doc, jekyll`; cell `cellar` + `nbdev, hide_input` - and each foreign key earns its place: **`nbdev` is load-bearing, not cosmetic**, because since nbdev 3.3.0 a cell's directives may live in `metadata.nbdev` (`{"export": "true"}` IS `#| export`), so dropping it made a Cellar save SILENTLY FATAL to such a notebook (`nbdev-export` afterwards generated nothing, exit 0, no warning); `hide_input` is Jupyter's own key and is DISTINCT from `cellar.hide_input`, which is what every Cellar reader actually reads, so keeping it is pure preservation; and **`widgets` REVERSES an earlier deliberate drop, safely** - the ipywidgets churn Cellar guards against is the per-output `WIDGET_VIEW_MIME` blob (a fresh UUID every run), which is still stripped, whereas notebook-level `metadata.widgets` is the saved widget-STATE blob that Cellar NEVER WRITES (it only ever writes into `metadata.cellar`), so preserving it can only keep what JupyterLab put there and can never manufacture a diff. `language_info` is still dropped. The notebook list carries ONE key that is NOT from nbdev's base list, **`solveit`**, and the reasoning is worth keeping because it is the template for the next such key: nbdev preserves it only because nbdev's OWN `pyproject.toml` opts in via `allowed_metadata_keys`, so nbdev's DEFAULT `clean_nb` strips it exactly as an unwidened Cellar did (measured both ways) - but it is the same ACT as the five keys beside it (preserve another tool's metadata rather than destroy it) and it was **100% of the remaining churn** when Cellar saved nbdev's own repository. Reading a project's `allowed_metadata_keys` is the general form of this, and is the same mechanism that would stop nbdev's own `nbdev-clean` destroying `metadata.cellar` in return, so it belongs with any future nbdev-project detection; until then a key that demonstrably shows up in the wild is added here BY NAME. **Note the deliberate asymmetry**: solveit's cell-scope sibling `solveit_ai` is NOT in the cell list - it appears in nbdev's project config but in NONE of its notebooks, so no measured churn turns on it and it was not added blind. **Neither list relaxes deny-by-default** - both are FIXED, NAMED lists, anything outside them is still dropped, and widening either is an explicit per-key act. Measured over nbdev's own 33 notebooks through the real save pipeline: **31 files / 2278+ / 2350- before, ZERO after** (`git status --porcelain` empty), generated library unchanged in both cases. Getting to zero took BOTH fixes independently - sorted keys were 100% of the byte churn, the allowlists 100% of the semantic loss. Covered by `tests/unit/nbdev-roundtrip.test.ts`. **Stated limit:** that zero is over nbdev's 33 `nbs/` notebooks, which are real nbformat 4.5. nbdev's 14 deliberately-antique `tests/` fixtures still churn, entirely from Cellar's OWN long-standing rules and not from anything here - the `kernelspec.display_name`→`name` normalization above, and serializing as 4.5 (so a 4.4 notebook gains `nbformat_minor: 5` and an `id` per cell). **Writes are atomic + serialized (the notebook is the user's PRIMARY data):** `writeNotebook` snapshots the cleaned JSON synchronously, then persists via `src/lib/server/atomic-write.ts` `atomicWriteFileSync` — write a **unique** temp *in the target's own dir* (a cross-device `/tmp` rename is NOT atomic), `fsync`, then `renameSync` over the target; on any error the temp is removed and the original is left untouched, so a crash/disk-full/SIGKILL mid-write can never truncate the `.ipynb` (a reader sees only the complete old or complete new file). Persist stays **synchronous** (the on-disk file must exist the instant persist returns — the unload flush and the git-blame/diff paths read it right after writing), so `src/lib/server/write-lock.ts` `serializeWriteSync(resolvedPath, fn)` runs inline when the path is idle (the normal case — a synchronous critical section can't be interrupted) and only queues behind an in-flight **async** writer; `withPathLock` is the async `Map<path,Promise>` tail-chain for that case, with the map entry deleted when a path's chain drains (never grows). Unique temp names mean even two racing writes to the same path each own a private temp — neither observes the other's half-written bytes; last complete rename wins. `.py` (jupytext) writes go through the external jupytext writer (`writePyNotebook`), unchanged. Covered by `tests/unit/atomic-write.test.ts`.
- **API.** `+page.server.js` load returns the default notebook + seeds the sidebar. `src/routes/api/notebooks` (`GET ?path=` loads a live doc's cells; `POST {path}` sets the active notebook, or `POST {path,create:true}` materializes it on disk via `createNotebook`). Cell ops under `src/routes/api/cells/…` (`POST` add, `PATCH` source/type, `DELETE`, `POST …/run` streams NDJSON + persists, `…/move`, `…/clear`) all carry an `nb` path (body field, or `?nb=` query for clear/delete) so they mutate the addressed notebook, not just the active one.
- **Cell types - all THREE nbformat types are real, `sql`/`chat` are the LOGICAL-only types, and `nbCellType` is the single mapping between them.** On disk a cell is nbformat `code`, `markdown` or **`raw`**; the type the UI toggle speaks adds `sql` and `chat`, each a `code` cell tagged `metadata.cellar.language` (`'sql'` / `'chat'` - see the chat-cells entry for what each runs through). **`mojo` is deliberately NOT a cell type** - a code cell's LANGUAGE is the NOTEBOOK's (`metadata.cellar.language` one level up), so a per-cell spelling would be a second setting able to contradict it; see the notebook-language entry. **The reasoning INVERTS between `sql` and `raw`, and that inversion is the design** (`src/lib/cellLanguage.ts`'s header): `sql` is a metadata tag precisely BECAUSE nbformat does not define it and an invented `cell_type` would break jupytext/nbconvert/Jupyter, while `raw` **is** one of nbformat 4.5's three, so encoding it as a tagged code cell would be that same interop breakage with the sign flipped - Quarto reads `"cell_type": "raw"` to find frontmatter and nbconvert/nbdev route raw cells by it, so a tagged code cell would be executed or rendered by every downstream tool. Cellar already wrote raw cells to disk long before it could author one (`deserialize` passes a foreign `cell_type` through verbatim), so this widened a type to match data that was already there - **no migration, and no persistence change at all**: `serialize`/`cleanCell` key on `cell_type === 'code'`, so a raw cell round-trips with no `outputs`/`execution_count`, idempotently. Markdown and raw carry source + no outputs; clean-on-save + UUID ids apply the same. `addCell(afterId, cellType)` / `setCellType(id, type)` (PATCH `cell_type`) / the `POST /api/cells/bulk` `type` op all speak the five logical types, while MCP's four `cell_type` enums deliberately speak only four - `chat` is absent from every agent WRITE enum, so an agent can run an existing chat cell but never create or convert to one (a billed model turn is the human's call; see the chat-cells entry); converting AWAY from a code cell clears outputs and drops the imports role (nothing that reads as executable may sit on a cell holding no Python), but **KEEPS the nbdev export flag** - see the mojo-module-export entry: a mark the new type cannot honour STRANDS rather than being silently deleted from the user's committed `.ipynb`; the `hide_input` override is deliberately KEPT, since `$lib/hideInput` reads it only for a code cell - it is already inert on markdown/raw, so dropping it would only lose a report-view choice across a there-and-back conversion.
  - **`nbCellType(logical)` is the ONE logical→nbformat mapping** (`cellLanguage.ts`, beside `isRawCell`/`isSqlCell`/`logicalCellType`/`isLogicalCellType`). It replaced **four** hand-written copies of `cellType === 'markdown' ? 'markdown' : 'code'` - a shorthand that reads every third type as code, which is exactly how a raw cell got silently retyped by whichever copy was not updated. Never re-inline it. **`isLogicalCellType(rawCell, 'code')` must stay FALSE** (it requires the nbformat type AND the logical type to match): if it flips, the bulk retype silently stops converting a raw cell while the single-cell setter still does - the divergence that predicate exists to close, pinned by `tests/unit/raw-cell-type.test.ts`'s truth table and the `raw`→code case in `bulk-cell-ops.test.ts`. The one place a foreign/stored type is still checked by hand is `replaceCells`' `NB_CELL_TYPES`, which **validates** a checkpoint snapshot's type rather than coercing it - the old coercion silently turned a restored Quarto frontmatter cell into code.
  - **Every run entry point refuses a non-code cell, and the check sits at EACH DOOR - `executeCellRun` is deliberately NOT the gate.** There are three (`POST /api/cells/[id]/run`, MCP's `run_cell`, and `jupytext-actions.ts`'s `runAllCells`, which filters to `cell_type === 'code'` before calling the core), because each owes the caller a different refusal SHAPE - this route's terminal `run:refused` NDJSON frame, MCP's `status:'skipped'` result - which the shared core has no way to speak. So a new run path must bring its own refusal; it does not inherit one. MCP's `run_cell` always did (`service.ts`, and a raw cell gets a note NAMING raw rather than the generic "not a code cell", so an agent is not left guessing); `POST /api/cells/[id]/run` did not, so it handed markdown/raw source straight to the kernel - the `SyntaxError` landed in the cell's in-memory `outputs` where the UI showed it, then vanished on reload because `serialize` drops outputs for a non-code cell. It now refuses **before `enqueueRun`** (so a cell that can never execute never takes a queue slot) with a terminal `run:refused` NDJSON frame at HTTP 200 - the route's own idiom for `run:duplicate`/`run:cancelled`, and one the client's reader ignores, so no client change was needed for correctness. **The submitted source is still SAVED first**: refusing to run an edit is not refusing to keep it. `LiveNotebook.runCell` guards the same shape client-side to spare the round trip; the authoritative rule stays on the server.
  - **UI: a raw cell is inert and shows it.** `Cell.svelte` derives `isRaw`/`isRunnable` and every execution-shaped affordance gates on `isRunnable`, **never on `!isMarkdown`** - that shorthand is what rendered a Run button on frontmatter. No Run, no Run-above, no Clear, no copy-output, no output block, no ⋮ actions menu, no stale/not-run badges; it keeps drag, collapse, insert/move/delete, copy-INPUT, the id chip, the type toggle (which is how you leave raw) and the row's hide-from-agent toggle, which is deliberately ungated because withholding a cell from an agent is orthogonal to whether that cell runs. `langFor()` returns `[]` (no Lezer grammar ⇒ plain text) and `staticLang` is `'plain'` (`staticHighlight.ts`), so the static and live renders match pixel-for-pixel. A neutral `raw-badge` (ghost, unlike the tinted `sql-badge` - raw is the ABSENCE of an execution mode) says the cell is deliberate. Command-mode **`r`** and the palette's "Change cell(s) to raw" convert; there is deliberately **no "+ Raw" insert button** (the type menu covers a once-per-notebook type - the deliberate contrast with CHAT, which recurs through a session and so earns real add buttons in the gap strip and the bottom row; see the cell-ops note in the UI entry). `applyCellTypeLocally` + the remote `cell:type` handler mirror the server's drops for the `clampMoveIndex` reason - `cell:type` carries no metadata, so a client half that skipped them would keep drawing a badge the server has already stripped.
  - **HTML export renders a raw cell as a muted `<pre>`** (`export-html.ts` `renderRawCell`, `.raw-cell`), deliberately - the export shows what the notebook CONTAINS - and **emphatically NOT as raw HTML**, which would make a shared report an XSS surface; the source is escaped exactly like a code cell's and takes no highlighting. (nbconvert instead OMITS a raw cell whose mimetype is not `text/html`; Cellar shows it so nothing silently disappears.) An empty one is dropped, and report view keeps it - a raw cell is not code.
  - **A raw cell keeps its `raw_mimetype`/`format` metadata through a clean** (`ALLOWED_RAW_CELL_METADATA`, applied in `cleanCell` **only** when `cell_type === 'raw'`): nbformat defines `format` on a raw cell and Jupyter's "Raw NBConvert Format" toolbar writes `raw_mimetype`, and both name the output formats the cell belongs to, so dropping them silently repurposed it. Deliberately **NOT** a widening of `ALLOWED_CELL_METADATA` - a code/markdown cell's foreign metadata is still dropped, so the deny-by-default policy the zero-git-diff clean rests on is untouched. Keep the list narrow: a key belongs there only if nbformat defines it ON a raw cell.
  - **A `.py` TEXT notebook REFUSES a raw cell, at the doc-layer WRITERS - refuse, never degrade.** That same jupytext coercion (below) applies to a LIVE `.py` document: `persist` rebuilds the file from its cells, so a raw cell declared on one lived only in memory while disk held a `code` cell, and after a reload the frontmatter sat in a cell with a Run button - the exact failure a first-class raw type exists to prevent, and worse from MARKDOWN, whose prose lost its markers on the way too. So `assertCanHoldType` throws `TextNotebookCellTypeError` (`$lib/cellLanguage`, which owns the ONE list of refused types and their messages; the `textNotebookRootError` precedent, for the identical rebuilt-from-cells reason) at the four writers that can put `raw` into a document - `setCellType`, `setCellTypes` and **both creators, `addCell` and `addCellAt`**, the CREATE path being how the convert guard is otherwise routed around (`addCellAt`'s only caller passes `'code'`, so it is guarded to make the every-writer claim true by construction rather than by that caller's argument) - so the type menu, the `r` chord, the palette, the REST routes and every MCP add/convert tool are covered by ONE rule. Nothing is written: the batch and `addCells` refuse BEFORE their first write (and before the agent checkpoint), so a refused call mints no snapshot and reports no `changed` a client could read as a legitimate skip. **Only the types `PY_UNSUPPORTED_TYPES` names (`raw`, and later `chat` - see the chat-cells entry), and only on a `.py` doc** - every other conversion there, and every raw cell in an `.ipynb`, is untouched. Surfaced as a 400 `{reason, message}` by the three cell routes, the reason code (`raw-in-py-notebook`) riding on the error itself so a per-type refusal cannot be reported under the wrong code, and as a named MCP refusal (`setType`'s `{ok,refused}`; `unsupportedTypeRefusable` wraps the three add tools, whose service layer THROWS rather than returning a union - a union return broke `addCells`' inferred shape across ~20 test files); INSTRUCTIONS clause 11 carries the agent-facing rule. The BROWSER mirrors it optimistically (the `clampMoveIndex` pairing): `Cell.svelte` filters every refused type out of the type menu when `isPy` (the flag that already gates `showRootBar`, now threaded to `Cell`), reading WHICH from the shared rule rather than naming them again, `LiveNotebook`'s `refuseUnsupportedType` says so on the shell's transient `onNotice` line for the keystroke paths (which send no request that could fail), the cross-notebook PASTE refuses the WHOLE paste for any refused type (asked of the LOGICAL type, not `cell_type` - see the Cut/copy/paste/undo-delete entry, which owns that rule), and a refusal the tab did not predict is still noticed + resynced - the route emits no `cell:type`, and this tab would echo-suppress it anyway. Covered by `tests/unit/raw-cell-py-notebook.test.ts` (every writer, the routes, the MCP surface, the `.ipynb` non-regression, plus source guards on both client halves).
  - **Every route that accepts a `cell_type` VALIDATES it against `$lib/cellLanguage`'s `LOGICAL_CELL_TYPES`/`isLogicalCellTypeName`** - `PATCH /api/cells/[id]`, `POST /api/cells` and the bulk route, which now share that ONE vocabulary rather than each keeping a copy (the list grew by one when `raw` landed, and three hand-maintained copies is how it grows by a fifth in only one of them). Not a style point: `nbCellType` maps anything it does not recognize onto `code`, so a malformed value ('RAW', a trailing space) silently converted the target into a RUNNABLE Python cell - harmless while every non-markdown type was code, a real downgrade of a cell holding frontmatter now. An out-of-vocabulary value is a 400 `bad-cell-type` (the bulk route's existing shape) and changes nothing; an ABSENT `cellType` on the add route still means `code`. The client `addCell` no longer reads `cell` out of a refusal body (a bare `TypeError` that said nothing and left the model unreconciled) - it notices, reloads and throws, which is the "an insert can reject" contract `undoDelete` already handles. Covered by `tests/unit/cell-type-route-validation.test.ts`.
  - **Two known limits, documented rather than fixed.** (1) `jupytext.ts` coerces `cell_type` to markdown|code on BOTH read and write, so a raw cell does not survive a `.py` round trip ("Save as .py" a Quarto notebook and the frontmatter comes back as code) - Cellar's Databricks/percent converter has no raw marker to speak (jupytext itself uses `# %% [raw]`), so carrying it is a separate task with its own format questions; do not "fix" it by widening the coercion (the LIVE-editing half of this is refused outright - see above). (2) Raw source is still SEARCHABLE and copy-input still works, deliberately. Covered by `tests/unit/raw-cell-type.test.ts` (model + persistence + checkpoint restore), `raw-cell-mcp.test.ts` (the agent surface, incl. a source guard that all four enums carry `'raw'`), `raw-cell-run-refused.test.ts` (the HTTP refusal, no kernel) and `tests/e2e/raw-cell.spec.ts` (real browser + real kernel: inert render, `Mod-Enter` producing nothing while the code cell below proves the kernel is live, Run all skipping it, and a code↔raw round trip on disk).
- **User-choosable imports cell (unpinned).** ONE code cell per notebook, `metadata.cellar.role = 'imports'` (rides the `cellar` allowlist, so it round-trips clean-on-save with zero git noise), living at **any** index. The user designates any Python code cell via the per-cell **⋮ actions menu** (`Cell.svelte`, `data-testid=cell-actions` → `toggle-imports-role`): "Mark as imports cell" / "Unmark as imports cell", wired `onSetRole` → `LiveNotebook.setRole` → `PATCH /api/cells/[id] {role}` → `setCellRole` (which enforces one-per-notebook: designating a cell strips the role from any other, atomically + optimistically) → `cell:role` SSE. A pin-glyph **"imports" badge** (`data-testid=imports-badge`) is the position-independent marker. Three things fill the cell: that manual designation, the **Consolidate imports** action (the notebook toolbar's `data-testid=consolidate-imports` in `Notebook.svelte`, plus the command palette → `POST /api/notebooks/imports` → `consolidateImports`; see the notebook-toolbar entry for why it does NOT also sit in the navbar Options menu) and **agent routing** in the MCP write tools. A human typing `import os` into cell 7 is *never* touched — that is the deliberate line. `src/lib/importsRole.ts` is the shared browser-safe identity (`isImportsCell`, `importsCellIndex`, position-independent); `clampMoveIndex` is now the **identity** function (the top-pin was removed) — kept at every move site (`moveCell`/`moveCellTo`/`moveCells` server - the bulk plan abandons the WHOLE move on a step it refuses - and `Notebook.svelte` client) as the one seam to reintroduce a positional rule if ever wanted. `ensureImportsCell` no longer hoists a designated cell; it returns it in place, and only creates/adopts a top cell as the fallback when NONE is designated. `setCellType(…,'markdown'|'sql')` demotes the role (only a Python code cell can hold it, else it would strand every future routed import).
  **Parsing is a JS tokenizer, not the kernel's `ast` and not a regex** (`src/lib/server/imports.ts`, pure): the kernel would force-boot / queue behind a running cell and make a structural edit depend on the runtime, while a regex cannot see that `import evil` inside a triple-quoted string, `if TYPE_CHECKING: import pandas`, or `def f(): import json` are not module-level. `logicalLines()` understands comments, all four string forms + prefixes + escapes, bracket and backslash continuation, and reports each logical line's **indent** — only indent-0 lines whose first token is `import`/`from` are lifted. Anything that does not parse into a canonically re-renderable record is **left exactly where it is**. `mergeImportSources` returns the existing source **untouched** when nothing is new, which is what makes consolidate idempotent in the strong sense (second run: zero document change, zero kernel re-run). Ordering: `__future__`, plain `import`, absolute `from`, relative `from` — sorted by code unit, deliberately NOT isort's stdlib/third-party grouping (needs a package classification Cellar has no business guessing). **Staleness is a second consumer of this same tokenizer** (`importBindings.ts`, see the Cell staleness entry): `renderImport`'s canonical rendering is not only the dedup key, it is the IDENTITY of a binding, and `isImportsOnlyResidual` (the exported residual half of `isImportsOnly`) is what proves nothing else in a cell can shadow an import - so changing either changes what "this import did not move" means downstream.
  **Adoption:** an existing role cell wins; else a first cell that is *only* imports/comments/blanks is adopted (`isImportsOnly`); else a fresh cell is inserted at 0 (`addCellAt`, which is why `cell:added` now carries an explicit `index` — `afterId` cannot express "at the very top"). New event `cell:role`. Consolidate deletes cells its sweep emptied (never the last cell, never the imports cell) and runs the imports cell **only when something moved**.
  **Agent routing** (`service.ts` `routeOne` → `finishImportRouting`): `add_cell`/`add_cells`/`edit_cell`/`add_and_run` lift module-level imports out of the submitted code into the imports cell, then run it **once** (all specs of one `add_cells` merge into one cell → one run, not one run per cell); `add_and_run` routes *before* creating the cell, so the code that needs `pd` finds it. Opt-out per call: **`route_imports: false`**. Editing the imports cell itself never routes into itself. Source that is *only* imports creates no cell (`routed_to_imports: true`). The `run_*` tools are deliberately **NOT** routed: they submit no code, and yanking imports out of an existing cell at run time would rewrite a cell a human may have authored (and `run_all` would strip the whole notebook).
- **A newly inserted CODE cell INHERITS the KIND of the code cell above it (`src/lib/cellInherit.ts`).** "Add a code cell" is one gesture with two readings: the user means "another cell like the ones I am writing", not "a plain Python cell". Mojo needs nothing from this rule - it is the NOTEBOOK's language, so a plain "+ Code" insertion in a Mojo notebook is already Mojo - and must never be added back to the allowlist; what is left to carry across is SQL, which really is a per-cell kind. **The rule:** nearest PRECEDING code cell wins (nothing BELOW the insertion point is consulted); markdown, raw and chat cells are SKIPPED rather than stopped at (prose between code cells is what a documented notebook looks like, and stopping would flip a SQL run back to code at every heading); no preceding code cell means the caller's default, which is `code` everywhere - i.e. the notebook's own language - so the common case is byte-unchanged. **What may be inherited is an ALLOWLIST (`INHERITABLE_CODE_TYPES` = code, sql), and the exclusion that proves the point is CHAT**: a chat cell is an nbformat code cell, so a naive `logicalCellType(prev)` would let a click on "+ Code" create a cell whose Run button spends money on a model turn - the same surprise Cellar already refuses to let AGENTS spring (`chat` is absent from every MCP write enum). **It is resolved CLIENT-side, at the GESTURE, not inside `addCell`**, because three server-side callers legitimately mean the literal "a Python cell" and a blanket rule would break all three: `imports-cell.ts` creates the pinned imports cell (which must hold Python or every routed import is stranded), `LiveNotebook`'s `insertAndRunCode` appends the Databricks table preview (which IS `spark.read.table(...).toPandas()`, appended at the END of whatever notebook is open), and every MCP write tool states its `cell_type` explicitly because an agent has already decided what it is writing. `LiveNotebook`'s `codeTypeAt`/`codeTypeAfter` are the only wiring; the scan lives in the pure module. Covered by `tests/unit/cell-inherit.test.ts` - the rule, plus a SOURCE GUARD that ENUMERATES every `addCell`/`insertCellAt` call site and requires each to either resolve through the shared rule or name a non-code type for a stated reason, which is what makes "find them all" checkable once the paths outlive whoever found them (vitest runs without the SvelteKit plugin, so `LiveNotebook.svelte` cannot be mounted, and e2e is absent from the pre-push gate).
- **jupytext / Databricks `.py` notebooks (`src/lib/server/jupytext.ts` + `jupytext-actions.ts`).** A `.py` opens as a **live, kernel-attached** notebook exactly like an `.ipynb` — the `.py` ⇄ cells boundary is `jupytext.ts`, called from `notebook.ts` `loadDoc`/`persist` at the same seam `ipynb.ts` sits at, so everything above it (cell ops, run, events, MCP, live-sync) is **format-agnostic**. The doc records `jpFormat` (the format it was opened in) and round-trips back to the SAME `.py` in that format. **Two engines:** jupytext (a Python lib) handles percent/light/etc. in a short-lived subprocess of the **project venv's** python (same split as `databricks.ts` — `projectPython()`; the helper is embedded as a string because `$lib/server` is bundled into `build/`); the **Databricks source format** (`# Databricks notebook source` / `# COMMAND ----------` / `# MAGIC %md|%sql`) is a dedicated pure-text converter **inside the helper** — jupytext has NO native Databricks format (it mis-reads it as "light"), and the converter round-trips byte-for-byte with `%md`→markdown and other magics kept intact as code cells. **Text has no outputs by design** (good for git/Databricks): a `.py` persists only on SOURCE/structural changes — `setOutputs` updates the in-memory doc for live display but writes nothing (`if (!doc.jpFormat) persist`). **Persist is sync** (`spawnSync`), matching the existing sync-persist model. **Detection is JS, no python** (`detectPyNotebook`): only an explicit marker (Databricks header / `# %%` / jupytext front-matter) counts, so a plain script still opens as **text**; the frontend probes `GET /api/notebooks/jupytext?path=` once per `.py` (caches the kind, persists it in tab session memory) to pick a live-notebook vs file tab. jupytext YAML headers are suppressed on write (`notebook_metadata_filter=-all`) so a re-save from a different jupytext version is a zero git-diff. **Two human actions** (navbar app menu, `POST /api/notebooks/jupytext {op}`): **Save as .py** (`exportNotebookAsPy`, format picker defaulting to Databricks) and **Convert to .ipynb** (`convertPyToIpynb` — runs every cell through the run-queue to materialize outputs, writes `<base>.ipynb`; a cell that errors still lands its error output, convert never aborts). jupytext is auto-installed into the project venv on demand (`ensureJupytext`, uv) with a clear `jupytext_missing` message if it can't be. **Known v1 limits:** `.py` carries no cellar cell-metadata, so the pinned-imports role is lost on reopen (in-session only); light-without-header reopens as text; converting onto an already-open `.ipynb` leaves that live doc stale until reload.
- **Hide code input (report view) - per-cell + notebook-wide.** Hide a code cell's INPUT (editor) while keeping its OUTPUT visible - a clean output-only report view, display-only (source untouched, cell still runs, `.ipynb` git-clean). **Distinct from `editorCollapsed`** (the tall-editor scroll-box contraction, runtime-only): hide-code is an EXPLICIT, PERSISTED hide regardless of length. **Two flags in the allowlisted `cellar` namespace (round-trip through clean-on-save):** per-cell `metadata.cellar.hide_input` (tri-state: undefined = follow the notebook default, true = hidden, false = shown) and notebook-level `notebook.metadata.cellar.hide_all_code` (report view). **Precedence:** `effectiveHidden = hide_input ?? hide_all_code` - a per-cell explicit choice always wins; the notebook-wide toggle is the default for cells with no explicit choice, so a per-cell "show code" reveal works even under global hide. **Server** (`notebook.ts`): `setHideInput` (code cells only; emits `cell:hide-input`) + `setHideAllCode` (emits `notebook:hide-all-code`), mirroring `setOutputScrolled`/`setHeaderNumbering`; `getNotebook` carries `hideAllCode`. **API:** `PATCH /api/cells/[id] {hideInput}`; `POST /api/notebooks/hide-code {hidden}`. **Client:** `LiveNotebook` `setHideInput`/`toggleHideAllCode` (optimistic + persisted), `hideAllCode` state (loaded + kept live via SSE + published up via `onHideAllCodeChange`); both events flow through `applyStructuralEvent`. `Cell.svelte` derives `codeHidden`, hides the editor block (same `hidden` mechanism as markdown rendered-mode, so CodeMirror stays mounted) and shows a slim, discoverable **"show code" bar** (`data-testid=show-code`) that reveals in place; the ⋮ actions menu (now shown for ALL code cells incl. SQL, not just Python) gains a Hide/Show code item (`data-testid=toggle-hide-input`). The toolbar (run controls, run-status, running/queued affordances) stays visible when hidden, so a running hidden cell is legible and a run still updates the visible output. **Notebook-wide toggle** lives in the Navbar app-menu "View" section (`data-testid=toggle-hide-all-code`), state reflected from the active notebook. Markdown cells are unaffected (no code to hide). **HTML export honors hide-code (report-style export).** `renderNotebookHtml({cells, hideAllCode})` (`export-html.ts`) applies the shared `isCodeHidden` rule from `src/lib/hideInput.ts` (per-cell `hide_input ?? hideAllCode`, markdown never hides - the SAME module `Cell.svelte` and the agent map use): a hidden code cell renders **output-only**, and a hidden code cell with NO output (imports, `df = load()`) is dropped from the report entirely, so a report-view export reads as pure markdown + results. The route `GET /api/notebooks/export` couples to the saved notebook setting by default (`getHideAllCode(path)`) so a notebook read as a report in Cellar exports as one; `?hideCode=1|0` forces report style on/off for a one-off export regardless. This is a deliberate reversal of the earlier "export shows all cells" stance (the feature's whole point is a code-free report); the `hidden_from_agent` FILTER stays MCP-only and orthogonal - the flag itself now has a row toggle of its own (see the cell-row-toggles entry), but no export path reads it. Covered by `tests/unit/export-html.test.ts`.

All live in the allowlisted `cellar` namespace on the NOTEBOOK's metadata (`header_numbering` = which heading levels 1-6 auto-number, `hide_all_code` = report view, `export_target` + `export_base` = the nbdev-style `#|default_exp` `.py` module, stored relative to its base) and all are readable AND settable by the agent. **`export_target` is agent-exposed** (`set_export_target`, session-targeted like the other notebook-level setters, and `get_notebook_map`'s `display` block reports it beside `header_numbering`/`report_view`) - but it is NOT owned here: the stored path is measured from a base, so the tool's `base` argument, the conditional `export_base`/`export_path`/`export_target_error` fields, the resolution rules and their tests live in the **nbdev-style cell export** entry above. Read that one; do not restate it here. Header numbering and report view (the two this entry does own): **Numbering is computed at render time and NEVER written into a cell's source** (`computeHeadingNumbers` in `headings.ts`, pure + hierarchical over the enabled levels; `setHeaderNumbering`/`setHideAllCode` in `notebook.ts` persist only the setting and emit `notebook:header-numbering`/`notebook:hide-all-code`). **MCP:** `set_header_numbering` / `set_report_view` tools (`server.ts`), thin session-targeted wrappers in `mcp/service.ts`; `get_notebook_map` carries a **`display`** block (`{header_numbering, report_view}`) and each numbered section its rendered `number`, and `read_section`'s header carries its `number`. `read_cell`/`read_cells`/`search_cells` deliberately do NOT - they return raw source, which is exactly where the number is not. The whole point is `INSTRUCTIONS` clause 5: agents hand-number headers (`## 1. Setup`) because nothing told them Cellar already does it. **The double-numbering hazard is by design, do NOT "fix" it:** a source `## 1. Setup` under numbering renders `1. 1. Setup`, and there is deliberately **no defensive strip** of a leading number anywhere - Cellar cannot tell an agent's stray auto-number from a title the human meant (`3. Third Attempt`), so the sanctioned fix is the instructions clause telling the agent to clean the source with judgment. Adding a strip re-introduces the bug it looks like it fixes. **Per-cell `hide_input` (which overrides `hide_all_code` in either direction) IS now agent-exposed** (`set_hide_input` tool → `mcp/service.ts` `setHideInput`, session-targeted like the notebook-level setters; tri-state `hidden:true|false|null`, code cells only, emits the same `cell:hide-input` SSE + `metadata.cellar.hide_input` persistence as the UI). `get_notebook_map` leaves carry the effective `code_hidden` (only when hidden) and the explicit `hide_input` (only when a cell overrides), so an agent enabling report view CAN now see the one cell whose code a human deliberately kept shown (it reports `hide_input:false` with no `code_hidden`) - INSTRUCTIONS clause 5 tells it not to "fix" that cell back to hidden. **The `hide_input ?? hide_all_code` precedence now lives in ONE pure browser-safe module, `src/lib/hideInput.ts`** (`isCodeHidden`/`hideInputExplicit`), shared verbatim by `Cell.svelte`, `export-html.ts`, and the agent map so the three surfaces cannot drift. Covered by `tests/unit/mcp-display-settings.test.ts` + `tests/unit/mcp-hide-input.test.ts`.
