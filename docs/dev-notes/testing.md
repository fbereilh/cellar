# Testing: unit suite, e2e harness, CI, flake triage

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **The no-mistakes Test step runs `npm test` (vitest) AFTER `commands.prepare` installs dependencies - both in `.no-mistakes.yaml`.** no-mistakes builds every run in a fresh `git worktree` holding TRACKED files only, so the gitignored `node_modules` is absent there. Without `commands.prepare: 'npm ci --prefer-offline'` the test command died with exit 127 (`sh: vitest: command not found`) on every run and the step was approved over the failure, so the suite never ran while the run ended `passed-with-override`. A failing prepare FAILS the Test step outright, before the test command and with no approval gate (measured with a lockfile out of sync: run `failed`, `prepare command exited with code 1`). `commands.test` exists so the step runs the real suite as a deterministic baseline instead of the "no test command configured" agent fallback, whose harness exits 1 and reads as a test failure. `tests/unit/no-mistakes-pipeline-config.test.ts` pins the pairing. **no-mistakes loads `commands` from the DEFAULT branch, not the pushed branch** (a security gate against a PR injecting commands), so a change to this file takes effect only for runs that start after it merges to `main`; a PR changing it cannot exercise the change in its own run. The same file sets `test.evidence.store_in_repo: false` to keep evidence out of the repo (the default, made explicit).
- **`npm run test:e2e` BUILDS FIRST and runs at `workers: 2` - a stale build used to masquerade as real failures.** The e2e harness boots the REAL launcher **without `--dev`** (`tests/e2e/harness.ts`), so every spec exercises the production build `build/index.js`. `test:e2e` had no build dependency and the launcher guarded only a **missing** build, never a **stale** one, so the suite silently validated code that was never compiled: measured at 11 false failures burning **901s of a 1434s (23.9 min) run** - one spec file swung **853s/10-fail stale → 14s/11-pass fresh**. Worse than slow: a green run certified uncompiled code, a red run sent you chasing failures that did not exist. Two layers now, and they share **one** staleness rule in `src/lib/server/build-freshness.js` (node-builtins only, so `bin/cellar.js` can import it like `venv.js`; it is in `package.json` `files`) - do not add a second: (1) the guard runs from **Playwright's own `globalSetup`** (`tests/e2e/global-setup.ts` -> `scripts/ensure-build.js`) and rebuilds **only when stale, absent or incomplete**, so an already-fresh re-run costs single-digit ms (MEASURED at 5-8ms), not a 45s `vite build`. **DO NOT EDIT ANYTHING UNDER `src/` WHILE AN E2E RUN IS IN FLIGHT.** The guard runs ONCE, in `globalSetup`, and `assertUsableBuild()` is then re-checked per launcher - so a source edit part-way through a run makes the build STALE and every spec from that moment on fails with `launcher exited early (1)` plus `production build is STALE (<file> is newer than build/index.js)`. That is the guard working, not a regression, but the run's remaining results are worthless and the failure list looks exactly like a broad breakage (measured: a full run reduced to `366 passed / 84 did not run` by one mid-run edit). Finish every edit, then start the suite. **Never run a bare `npx playwright test` - use `npm run test:e2e`**; both build first today only BECAUSE the guard sits in `globalSetup` rather than in the `pretest:e2e` npm hook it replaced (an npm hook covers `npm run test:e2e` and nothing else, so the single-spec `npx playwright test <spec>` a developer or an agent types bypassed it entirely). It is wired in **exactly one** place - do not re-add the npm hook, which would re-walk the source tree for an answer `globalSetup` is about to compute again. **An INCOMPLETE build classifies as `missing`, not `fresh`** (`REQUIRED_BUILD_ARTIFACTS` = `index.js` + `client`): adapter-node serves the client bundle from `build/client`, so a `vite build` killed part-way leaves an entry point that PASSES the mtime comparison - the launcher boots, the pages are broken, and every spec fails on its assertions with nothing naming the build (MEASURED against the base wiring: a 2-test spec, 65s all-fail vs 2.5s all-pass, i.e. ~33s burned per test; the STALE case is cheaper only because `assertUsableBuild` refuses it outright - 0.74s - and even then Playwright reports `launcher exited early (1)` with the reason buried in interleaved stdout, which is why `bootCellar`'s two failure paths now carry the build verdict plus the launcher's output tail, and its ready bound is 60s (`CELLAR_E2E_BOOT_TIMEOUT_MS`), ~46x a warm boot MEASURED at 1.2s at load 4 - deliberately generous, since the cost of being wrong is a whole spec file's worth of false failures and the override covers a genuinely cold uv cache); (2) `bin/cellar.js` **`assertUsableBuild()`** refuses a stale build outright, placed at the **top of `main()`** - before venv resolve/create and the Jupyter sidecar - so a build we will not serve costs no boot (`CELLAR_SKIP_BUILD_CHECK=1` overrides; `--dev` skips it). Staleness is **mtime-based** (`src/` + `static/` + root `package.json`/`vite.config.js`/`svelte.config.js`/`tsconfig.json` vs `build/index.js`), deliberately: no build system, no hash pass, no state file, and every legitimate change - an edit, a `git pull`, a `git checkout` - moves an mtime forward. **A packaged install must classify `unknown`, never `stale`**, and that CANNOT key off the absence of `src/` — `files` ships `src/lib/server/*.js` and Docker/Homebrew copy source too, so the source tree is present in real installs. So `isSourceCheckout(repo)` gates the mtime comparison on a POSITIVE signal: a `build/build-info.json` `source` of `release`/`env` is a stamped packaged build (Homebrew stable tarball / release automation) → NOT a checkout; otherwise a real checkout is proven by a `.git` at the repo root (a dir, or a worktree pointer file — dev clones, CI, and the e2e harness all have one). Anything ambiguous falls through to `unknown` → launch, so a shipped app can never false-refuse to start; only a proven source checkout runs the real mtime comparison. Concurrency: **`workers: process.env.CI ? 1 : 2`** with `fullyParallel: false` kept - tests INSIDE a file share one launcher/workspace/kernel and must stay ordered, while `workers` is *file*-level concurrency, which is safe because each spec gets its own `mkdtemp` workspace, dynamic ports, and `--new` (so concurrent launchers never reap each other). **Do NOT raise it past 2**: 4 was *not* faster (the makespan is bound by a few long spec files) and broke four timing-sensitive real-kernel specs (`kernel-status-ui`, `kernel-watchdog-probe`, `interrupt-clears-queue`, `databricks-header-pill`); more concurrency needs those split into their own `workers: 1` project first. Full suite: **~2.5 min green** (was 6.1 min serial, 23.9 min stale). The unit suite (~6s, 92% of its parallel floor) and the unit CI job and the no-mistakes gate were already correct and are untouched. **e2e now GATES every PR** from its own sharded workflow (`.github/workflows/e2e.yml`, ten `--shard=i/10` runners at `CELLAR_E2E_WORKERS: 2`, MEASURED at ~5 min of wall clock against an unsharded serial run's extrapolated 45-60), so the premise that it runs nowhere but a developer's machine is retired - but it is still absent from the **pre-push no-mistakes gate**, which is vitest only (`.no-mistakes.yaml` `commands.test: 'npm test'`), and that is the gap every source guard in this file is really written against. **Four facts about that workflow are load-bearing, and three of them read as obvious things to clean up.** (1) **Sharding is only safe because Playwright splits at SPEC-FILE granularity** - tests inside a file share one launcher, one workspace and one kernel and must stay ordered (`fullyParallel: false`), so a file split across two shards would surface as flakiness rather than as an error; that is a property of the INSTALLED Playwright, so `tests/unit/e2e-ci-workflow.test.ts` drives its real sharder with `--list` (no launcher boots) and asserts no file lands in two shards and none is dropped, rather than taking it from the docs. (2) **A missing kernel runtime must ABORT, not skip.** Every spec carries `test.skip(!runtimeAvailable(), …)` and **Playwright exits 0 for a run in which everything skipped** (MEASURED: `HOME=$(mktemp -d) npx playwright test smoke.spec.ts` -> `1 skipped`, exit 0), so a job whose provisioning silently broke is a permanently green check that ran zero tests - worse than no job, because it manufactures assurance. `CELLAR_E2E_REQUIRE_RUNTIME=1` (set by the workflow) turns that skip into an abort from `globalSetup`, and it is built on the specs' OWN predicate - `runtimeAvailable()` is a projection of `runtimeMissing()`, never a second copy, because a copy that drifts re-opens exactly this hole. It is its own env var rather than a branch on `CI` so a fork without the runtime keeps the skip and so the guard is testable locally, which matters for a guard whose failure mode is silence. `scripts/ensure-e2e-runtime.js` provisions the host venv UP FRONT through the launcher's own `ensureHostEnv` (never a replayed `uv venv` + `uv pip install`, which would drift from the `.cellar-host-ready` marker the launcher checks): the lazy path is too late, since `runtimeAvailable()` reads that venv with `existsSync` when the FIRST test runs, i.e. before the launcher that would create it ever boots. (3) **`workers: process.env.CI ? 1 : 2` was NOT a measured guard** and is gone. e2e had never run in CI when #47 wrote that line, so the `1` is the file's ORIGINAL unconditional default left standing on a branch nobody had taken - there was nothing to preserve. It is now `CELLAR_E2E_WORKERS ?? 2`, with CI stating its own value in the workflow. The suite is latency-bound rather than CPU-bound (MEASURED: user 583s + sys 215s across a 1191s serial wall = 0.67 of one core), which is why a 4-vCPU runner takes more than one worker without starving - and equally why it is sensitive to contention, so raise it on evidence. (4) **Each shard BUILDS FOR ITSELF, and hoisting that into a shared `needs:` job is a PESSIMISATION, not the obvious cleanup it looks like** - the build is embarrassingly parallel across shards, so per-shard it costs its ~40s of wall clock once, concurrently, whereas a build job serialises it in front of every shard (build job incl. checkout/`npm ci`/upload, THEN each shard's setup + download + tests). It would save runner-minutes, which are FREE on a public repo, in exchange for wall clock, which is the only thing a PR check spends. The workflow header says all four so the next reader does not undo them. **Two spec-side rules the gate forced out into the open, both of which read as flakiness rather than as the bugs they are.** (a) **A spec's throwaway workspace is removed through `harness.ts`'s `removeWorkspace(ws)`, never a bare `rmSync`** - `killCellar` only SIGNALS (it is called from a synchronous hook and cannot wait), so the launcher's own SIGTERM cleanup is still rewriting `<ws>/.cellar/runtime.json` while `rmSync` walks the tree, and the removal fails **ENOTEMPTY on a directory it had just emptied**, failing a test whose every assertion PASSED. `maxRetries` is node's own remedy for that error class and costs nothing when there is no race; anything still failing is swallowed, because a `mkdtemp` directory the OS will reclaim is never a reason to red a green test. All 76 specs go through it. (b) **The assertion budgets in `playwright.config.ts` are env-tunable (`CELLAR_E2E_EXPECT_TIMEOUT_MS`, `CELLAR_E2E_TIMEOUT_MS`) and CI scales them, which is NOT slack for a flaky suite** - they were chosen on a 15-core M5 Pro, `ubuntu-latest` measures 2.3-3x slower on this repo's own build and unit steps, so a 30s wait there is 10-13s of the headroom the number was picked to give; MEASURED, three of the four timing-sensitive real-kernel failures on the first Linux runs died at **~28-33s**, i.e. at the budget rather than at anything the code did. `retries` stays **0**, so a genuine regression is still a red check - it just takes longer to say so. Timing evidence: `data/cellar-test-timing-scout-t7/report.md`. **A handful of e2e failures in a FULL run, in specs you did not touch, is usually LOAD, not a regression - measure before you chase it.** At `workers: 2` a few timing-sensitive specs sit close to their 30s waits, so on a busy machine (another Cellar with live kernels running, a build in the same shell) the suite sheds 1-5 tests per run and the count tracks the run's DURATION, not the diff. Measured on one machine across six full runs: the BASE commit alone gave 0 failures in 8.2min and 4 in 13.2min, and a feature branch gave 1/8.2min, 3/9.2min and 5/11.0min - with base and branch failing the SAME tests (`databricks-two-card-redesign:282`, `git-notebook-commits:215`, plus cases in `notebook-roots` and `upload-name-defaults`). The tell is that the failing set is DIFFERENT every run, spans unrelated spec files, and every one of them passes in isolation; a real regression fails the same test every time. So the cheap first move is to re-run the failing spec FILE alone (seconds, since each file boots its own launcher), and the decisive one is a full run on the base commit - a single green base run proves nothing, since base flakes too. Do not "fix" this by raising `workers` (that is what broke those specs in the first place) or by adding `retries`, which would hide a genuine regression. **The UNIT suite has the same load-flake shape, and two ceilings were measured too tight.** `vitest.config.ts` already records why its default budget is 30s (~180 files across `cpus - 1` forks that each spawn again). Two places needed more than that default: `databricks-logout.test.ts`'s "signs out of EVERY signed-in workspace" case, MEASURED at ~28.5s alone against the 30s ceiling (a real `databricks-sdk` python spawn per signed-in workspace) and so timing out on every full run while passing in isolation - raised to 90s; and `mcp-bridge-reattach.test.ts`'s three poll-until helpers, which waited 3s for real HTTP + `StreamableHTTPClientTransport` reconnect handshakes - raised to one shared `POLL_MS` (15s, kept UNDER the 30s vitest budget so a genuine hang still surfaces as that file's own error rather than an opaque suite timeout). They are POLL loops, so the ceiling costs nothing when things work and only decides how long a stuck bridge takes to FAIL. MEASURED on one machine: a full run on the BASE commit gave FIVE failures in `mcp-bridge-reattach` while the same run carrying the raise gave one, and a later quiet full run gave zero. Same tell as the e2e guidance: the failing set ROTATES between runs and every one of them passes in isolation, so re-run the file alone first and take a full run on base as the decisive check. Do NOT "fix" the remainder with retries. **And do not read a failure in the SHADOW of a contended run as environmental without sampling** - `interrupt-unresponsive-kernel` failed three times running right after a 17.5-minute contended e2e sweep (a real `zmq.error.ZMQError: Socket operation on non-socket` killing the kernel's socket, so Cellar force-settled the cell instead of the kernel returning its `KeyboardInterrupt`) while base passed once, which looks exactly like a real regression; three consecutive 14s passes on the same branch once the machine settled is what actually settled it. Covered by `tests/unit/build-freshness.test.ts` + `tests/unit/e2e-build-guard.test.ts`. **Every spec's `openNotebook` helper must SETTLE before it probes** (`await expect(openBtn.or(<the cell locator>)).toBeVisible()` ahead of the `isVisible()` check): the shell paints either the empty state or an already-open notebook, and probing before either arrives reports the button invisible, turns the click into a no-op, and then times out for 30s on a notebook nothing ever opened. It is a genuine race, not a slow machine - it surfaced in 3 of 3 full-suite runs under the `workers: 2` default, landing on a DIFFERENT databricks spec each time (which is exactly how it reads as unrelated flakiness), and `cell-collapse.spec.ts` had already papered over it locally with an `isVisible({timeout: 10_000})`. Fixed at all 23 call sites; keep the guard when copying the helper into a new spec - and note that TWO more helpers written since then had drifted back to the racy shape (`databricks-sdk-dbutils-warning`, whose 2-minute timeout in a full run is what surfaced it, and `notebook-column-width`), which is what the rule is for: the tell is a synchronous `isVisible().catch(() => false)` probe with no settle in front of it, and `grep -L 'openBtn.or('` over the specs that mention `empty-open-notebook` finds a candidate list to check by hand (a helper that clicks the button directly, or races two `waitFor`s, is already settled). **A SEVEN-SITE SWEEP HAS SINCE CLOSED THE REST, and the shape it closed is the one this entry already called out as papered over: `if (await openButton.isVisible({ timeout: 10_000 }).catch(() => false)) await openButton.click();`.** A longer probe only MOVES the threshold of a race, and 10s is reachable on a 4-vCPU CI runner: in one full run every remaining failure was in the virtualization family and the largest was this verbatim - `expect.poll(() => cells(page))` reading 0 for 30s because the click had been a no-op on a notebook nothing opened. One cause behind a whole cluster (`virtualization-default-on`, `virtualization-pinning`, `virtualization-remote-edit-run`, `virtualization-jump-paths`, `multi-select`, `cell-collapse`), which is why the per-run failure count fell from 9 to 2 across the runs that fixed it. Do not reintroduce a timeout in place of the settle. **WHAT THAT SWEEP DID NOT REACH, measured across the gate's first Linux runs and worth knowing before chasing any of them:** (a) **`virtualization-pinning:159/166` fails on essentially EVERY CI run and passes locally**, so it is near-deterministic on that hardware rather than flaky - the assertion is that a cell UNMOUNTS once nothing pins it, and a cell stays mounted for five different reasons (running, queued, active, focused, a transient scroll pin), which the bare boolean named none of. The suspicion is the scroll pin from the tab-jump, whose `revealRunning` target is STILL STREAMING while `scrollElementIntoView` settles on exact framing (`settle: 'frame'`) - the same growing-target problem `followCell` uses `settle: 'visible'` to avoid - but that is unproven, which is why the assertion now polls `notebook-scroll.ts`'s `mountDiagnosis` and NAMES the state it found rather than being guessed at. (b) **`cell-row-toggles:234` is a genuine run-reply wedge, not slowness**: a `time.sleep(14)` cell whose kernel connected and then went silent, with the run still reading RUNNING ~72s later and nothing in the launcher log. Note its 60s budget is SHORTER than the product's own recovery window for that state (the idle watchdog's probe-plus-three-strikes is ~90-210s), so a wedge the product WOULD clear still fails the test - raising the budget past the watchdog would convert a real wedge into a slow pass, which is why it was left alone. (c) **`notebook-roots-worktree.spec.ts`'s rotating `apiRequestContext.post: Timeout 120000ms exceeded` (`:127`, `:143`, `:160`, `:216`, plus `notebook-roots:139/:168` and the 2.5m MCP run timeouts) was a REAL BUG, now fixed: the FIRST run on a FRESHLY started kernel wedged because that connection's SHELL never answered.** Reproduced locally only under CPU contention (14 busy cores, ~2 in 5 runs of the roots + language specs) and instrumented: the websocket opens and iopub flows, but the `kernel_info_request` @jupyterlab sends on connect gets no reply and nothing later on that connection does either, while a healthy connection answers within ~10ms (max 535ms measured under load). @jupyterlab only flushes its queue after a 3s failsafe, so the startup injection went into the dead pipe and `initKernel`'s unbounded `future.done` parked the run in `getKernel`, where no watchdog can see it. `kernel.ts`'s `awaitShellHandshake` now sends nothing until `kernel.info` resolves, replaces an unanswering connection via `mgr.connectTo` (a NEW client id, so new server-side ZMQ sockets - deliberately not `reconnect()`, which reuses them; disposing a connection never touches the kernel), and after 3 attempts shuts the kernel down and refuses the start with a named reason (`CELLAR_KERNEL_HANDSHAKE_TIMEOUT_MS`, 5s, counted from the socket opening so a slow boot is not mistaken for a dead shell). Covered by `tests/unit/kernel-shell-handshake.test.ts`. Worth checking first if a (b)-style run wedge reappears on a FRESH kernel. **THE SETTLE SWEEP'S OWN SIBLING, and the same lesson one layer over (it is the sweep this refers back to, not the findings above): opening a sidebar SECTION must CONVERGE, and that rule now has one home** (`harness.ts`'s `openSidebarSection`). Fourteen specs call it; THIRTEEN of them had hand-rolled the racy shape and were converted (the fourteenth, `chat-cell.spec.ts`, had already worked the fix out in place and was folded in) - read the panel's visibility ONCE, click on that reading, then assert it visible - and a section's open state lives in the server-owned UI store, restored at HYDRATION, after the first paint: with the stored state CLOSED and the check landing first, the click opens the section locally, hydration closes it again, and the assertion waits out its whole 30s on a panel nothing will reopen. Load does NOT cause that, it only widens the window - which is exactly why it read as unrelated flakiness, and why `databricks-two-card-redesign:282` and `git-notebook-commits:215` above are named as load-flakes when they were really this. MEASURED on this machine across full runs: **19 failed / 260 passed / 48 not run** before, **1 failed / 326 passed** after, twice, a DIFFERENT documented flake each time and each passing in isolation - so the load stance above still holds for the remainder (`git-notebook-commits`'s file-tree wait), it is just no longer carrying most of the count. **`upload-name-defaults` was on that list and was NOT load either - it was its own teardown**: the `afterEach` emptied the upload fields to clean up, which QUEUED a 300ms-debounced browser write of `''` (an explicit "no prefix", which outranks the default), and when it landed after the reset had verified the store the next test inherited it - MEASURED: on every handover it was sent only 70-350ms before the reset declared the store clean, so load decided which test lost. The rule it leaves: **a teardown never writes through the UI, and a spec whose tests share a server-owned store hands over on signals** - route the page's store writes through the test, close that channel before resetting, and prove no instance still has a debounced flush pending (`routeStoreWrites`/`settleGlobalStore` in that spec; a fixed settle sleep there was the previous, timer-shaped attempt). `chat-cell.spec.ts` had already worked the fix out in place; do not re-inline it. **A CI failure that lands at almost exactly 2.5m (or 1m locally) is an MCP call that never answered, NOT a slow wait** - that is `CELLAR_E2E_MCP_TIMEOUT_MS` (150s in CI, 60s default). Read the uploaded trace's network log first (`status -1` = the request never answered) before calling the spec flaky: `foreign-action-refresh.spec.ts`'s 2.5m failures in its two restart tests were a REAL `restartKernel` hang (the restart never returned, and the next run parked behind it on the exec lock), rare enough that 46 CI passes of its shard did not reproduce it. That spec also shows the shape for NEGATIVE assertions ("nothing repaints it", "no probe fires"): wait on a signal - requests tracked to completion (`probesSettled`) and Playwright's fake clock jumped past a debounce (`page.clock.install()` before `goto`, then `fastForward`) - never a fixed sleep.
