# Notebook languages: Python, Mojo, Rust

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **NOTEBOOK LANGUAGE - Python or Mojo, chosen ONCE at the top (`notebook.metadata.cellar.language` + `src/lib/server/mojo.ts`).** **A notebook is one or the other and NEVER both** (the captain's ruling), so the choice is notebook-level and every plain `code` cell in that notebook IS a cell of that language; its source on disk stays bare Mojo and the compilation to Modular's `%%mojo` cell magic happens at RUN time, invisible to the document and to git. Design + measurements: `data/cellar-mojo-support-scout/report.md` (max 26.5.0 / Mojo 1.0.0, driven live).
  - **THERE IS NO PER-CELL `mojo` TAG AND NO `mojo` LOGICAL CELL TYPE, and that is the whole design rather than a simplification.** A second, per-cell spelling of the same fact is a setting that can CONTRADICT the notebook's - i.e. exactly the mixed-language notebook the ruling excludes - so `mojo` is absent from `LOGICAL_CELL_TYPES`, from `languageTagFor`, from the cell-type menu and from every MCP write enum. `sql` and `chat` STAY per-cell for the opposite reason: they are orthogonal cell KINDS that legitimately coexist in one notebook (a SQL cell and a chat cell sit happily in a Python one), whereas python-vs-mojo is the notebook's own axis. **NO MIGRATION AND NO SHIM** (the captain had no Mojo notebooks): a legacy per-cell `mojo` tag is simply no longer read, and reads as the ordinary code cell it already is on disk.
  - **ABSENCE IS THE PERMANENT SPELLING OF PYTHON.** `notebookLanguageOf(metadata)` is a strict `=== 'mojo'` positive test (the `databricksRuntimeEnabled` rule, for the same reason: this decides how the user's code is EXECUTED, so an unrecognised value must fall to the answer that runs the notebook the way it always has). `setNotebookLanguage('python')` DELETES the key rather than writing an explicit value, so a notebook that switches to Mojo and back is byte-identical to one that never switched - which is what "switching back leaves nothing stale" means at the file level - and no notebook is ever migrated into carrying it.
  - **EVERY LANGUAGE-RESOLVING PREDICATE TAKES THE NOTEBOOK LANGUAGE AND DEFAULTS IT TO `python`** (`cellLanguage(cell, nbLang)`, `isMojoCell`, `isPythonCodeCell`, `hasPythonDataflow`, `exportLanguageOf`), the `canExportCell(cell, lang = 'python')` pattern this repo already established. That default is what makes an untouched caller - and every Python notebook - behave byte-for-byte as before; every caller with a notebook in scope threads the real value, and TypeScript found the bare `.filter(isPythonCodeCell)` sites for free.
  - **NO CELL IS TOUCHED WHEN THE LANGUAGE CHANGES** - the language is READ from the notebook, never copied down - so markdown, raw, SQL and chat cells are unaffected BY CONSTRUCTION rather than by being skipped, there is no per-cell rewrite to undo, no git churn across the notebook, and **no kernel restart** (the `%%mojo` dispatch is decided per run in `run.ts`, so the namespace survives). Contrast the code root, whose change necessarily frees the kernel.
  - **A `.py` TEXT notebook REFUSES `mojo`** (`TextNotebookLanguageError`, reason `mojo-in-py-notebook`) at the ONE writer, for the identical reason it refuses a code root and a raw cell: it stores no notebook metadata, so the declaration would live only in memory and every cell would come back Python after a reload. Setting `python` there stays allowed (it can only remove state), and `setNotebookLanguage` is a genuine NO-OP when the language is unchanged - no persist, no export regeneration, no event - which is also what keeps that case from spending a blocking jupytext round trip to produce the bytes it already had.
  - **Surfaces:** the `language-bar` selector inside the notebook toolbar's language-and-export menu (`Notebook.svelte`: the `notebook-settings` button at the right end of `notebook-toolbar` opens a native `popover="auto"` holding `language-bar` then `export-bar`, so Escape and an outside click close it; it stays in the DOM while closed because the `pagehide` flush reads the export target input, the button LABEL names the current language so it is readable closed, a `notebook-settings-warning` dot marks an export warning the closed menu would hide, and `LiveNotebook`'s modal-keyboard dispatcher ignores keys inside any `[popover]`; offered on every `.ipynb`, unlike the code root's opt-in chrome, and absent on a `.py`. An e2e spec must close it - `harness.ts` `closeNotebookSettings` - before clicking a cell, since an open popover intercepts the pointer), `POST /api/notebooks/language` (answering the `{ok:false, reason, message}` 400 the cell routes already use, and returning the resulting export-target state because the switch may have MOVED it), the `notebook:language` SSE event, MCP `set_notebook_language`, and `get_notebook_map`'s `display.language`. The write is SETTLED by the server rather than optimistic (the `setRootValue` rule): it can be refused, so showing the switch as taken before the server agrees would claim every code cell runs in a language the document does not hold. **A REFUSAL and a FAILED WRITE are told apart BY TYPE, never by matching message text** (`TextNotebookLanguageError`/`InvalidNotebookLanguageError` vs anything else) - the `export-py` `writeFailed` precedent and for the identical reason: `setNotebookLanguage` validates BEFORE it mutates, so its one other throw is the `persist`, over a language the live document already HOLDS and `run.ts` already compiles every code cell as; reported as the same 400 the tab reverted the select and said Python over a Mojo document, with nothing left to correct it. A write failure answers its own 5xx carrying `writeFailed` (never decided from the status code, since any other 5xx landed no verdict at all) and EVERY reply carries the HELD language, so the select adopts what the document really holds on any outcome. **OPENING the document is a THIRD outcome and is checked FIRST on BOTH surfaces** (`isNotebookUnavailable`, the ONE predicate over the typed `NotebookUnavailableError` + `NotebookReadError` - the not-found throw was made typed precisely so neither surface has to match message text): `docFor` runs BEFORE the validation, so a notebook deleted, renamed or corrupted under an open tab threw there and, folded into `writeFailed`, claimed a language that never took while pointing at a save that never ran. It carries NO `language` (so the select keeps what it had rather than adopting a `python` nothing observed) and its message is stripped of the absolute server path the doc layer's throw carries (`reasonWithoutServerPath`). It is also why that branch may not re-enter the doc layer: `svc.setNotebookLanguage`'s `writeFailed` arm called `getNotebookLanguage`/`exportTargetFields`, both of which reach `docFor` and so threw AGAIN on this very path, escaping the tool's own result union - `setExportTarget`'s catch deliberately asks the document nothing, and this one now matches it. **The BROWSER half therefore reports the SAME FOUR OUTCOMES as `commitExportTarget` (`LanguageCommit` IS `TargetCommit`, so the two read as ONE convention - do not invent a second vocabulary), and `unreachable` is the member that matters**: a rejected fetch, or a reply that is not this route's own shape (a proxy 502/503, an HTML error page), landed NO VERDICT - the reachable case being a switch the server really persisted whose response died on the way back - so it KEEPS the applied language, says only that it was not confirmed and names the reload, because reverting there MANUFACTURES the divergence (the select reads Python while `run.ts` compiles every plain code cell as `%%mojo`, with nothing left to correct it - the success event is never emitted and this tab would echo-suppress it anyway). Verdicts are read from the reply BODY alone, never from a status code; there is deliberately no `superseded` member, `languageBusy` gating the function. Covered by `tests/e2e/notebook-language.spec.ts`, whose CONTROL - the route's own 400 shape still reverting and still saying why - is what keeps it from being a blanket never-revert. **THE AGENT SURFACE OWES THE SAME SPLIT, and it is the half that matters most**: MCP `set_notebook_language` caught every throw into one `notFound`, so a failed persist told the agent the call FAILED while the live document already held Mojo and `run.ts` was compiling every plain code cell as `%%mojo` - the agent then kept writing Python into a notebook that had switched (and the relayed message leaked the notebook's absolute server path). `svc.setNotebookLanguage` now makes the split the way `svc.setExportTarget` does (`refused` / `invalid` / `writeFailed`, discriminated by ERROR TYPE), and the persist case is reported as its OWN outcome naming what IS true - the language was applied in memory, every plain code cell runs as it now, the export target it moved to, and the next successful save writes it - never the refusals' remedy, which would send the agent to convert a notebook that is not the problem. Pinned in BOTH directions at the real MCP wire in `tests/unit/notebook-language-mcp.test.ts` (a `.py` notebook still REFUSES and stays Python; a failed save reports applied-in-memory and the document really holds Mojo).
  - **A LANGUAGE SWITCH LEAVES THE OLD GENERATED MODULE ON DISK, and that is SURFACED rather than silently left** (`orphanedGeneratedModule` in `export-py.ts` -> `NotebookView.exportOrphanedModule` -> the export bar's `export-orphan` line, wording in `$lib/exportRole`'s `orphanedModuleExplanation`). Re-expressing the target renames NOTHING: Cellar never deletes or truncates a generated module the user's repository holds, so in an nbdev repo `utils.py` stays git-TRACKED and importable while the notebook now writes `utils.mojo`. It is derived from the SIBLING path (the only orphan a language switch can create - `setExportTarget` refuses a mismatched extension, so the two spellings are unreachable any other way; a target repointed at a different NAME is a different, pre-existing case this does not claim), it is **PROVENANCE not existence** (the same `isGeneratedModule` header test `generatedModuleExists` uses, PLUS the `# Source notebook:` line naming THIS notebook - a hand-written module or another notebook's live target is never named), and it **narrows BEFORE any filesystem read** (`docHumanExportHazards`' precedent: no target, an unresolvable one, or one naming no module costs nothing; past that it is ONE bounded head read of ONE path). Said ONCE for the notebook, beside `exportStrandedExplanation` and outside the warning chain - both can be true at once - and it rides `notebook:export-derived` rather than an event of its own. Covered by `tests/unit/export-orphan-module.test.ts` (the real switch, both provenance refusals with their control, and the cost gate over a wrapped `node:fs`) + the orphan case in `tests/e2e/mojo-export.spec.ts`.
  - **THERE IS NO MOJO KERNEL, and that is the fact the whole design rests on.** Modular ships none; the current, official and only supported Mojo notebook workflow is a PYTHON kernel plus `import mojo.notebook`, which registers a `%%mojo` cell magic. That magic is ~58 lines: write the cell body to a fresh temp file, `mojo run` it in a SUBPROCESS with `capture_output=True`, print the captured stdout, delete the temp dir. The one third-party kernel that exists is unofficial, stale, and - MEASURED against a live one - is wedged PERMANENTLY by Cellar's own startup injections (three error immediately, the DataFrame formatter never returns, and the kernel then stops answering entirely; `import sys` alone is meaningless in Mojo). That is not a kernel quirk: every kernel-side mechanism Cellar injects is Python-shaped and has no Mojo equivalent. **Do not revisit the kernel path without an OFFICIAL Modular kernel and a fresh measurement of that injection block.**
  - **Three consequences are MODULAR's, not Cellar's, and are STATED rather than papered over.** (1) **NO VALUE persists between Mojo cells** - the subprocess and its whole namespace die with the cell. Cellar does not fake that; what it carries is DECLARATIONS (see the declaration carry-over bullet below). Cellar says so in the badge tooltip and MCP doctrine clause 12 (which states the notebook-level model, that there is NO mojo cell_type, and what such a notebook is NOT - no staleness verdict on a CODE cell (a SQL cell still gets one, `hasPythonDataflow` being `isPythonCodeCell || isSqlCell` with the SQL half language-independent), no imports cell, no import routing - while saying its cells IS exportable to the `.mojo` module its target names, so the clause cannot read as "Mojo cells are not exportable" against clause 5), and `hasPythonDataflow` keeps such a cell out of the dependency graph entirely so nothing downstream can claim a Mojo cell defined something. Do not "fix" this by faking continuity of VALUES. (2) **Output is fully buffered** (`capture_output=True`), so a long Mojo cell shows nothing until it finishes; the run watchdog is safe (the kernel is genuinely busy inside `subprocess.run`, and the watchdog only PROBES). (3) **A compile error arrives as a Python `MojoCompilationError`** naming a temp path that no longer exists, plus a `Failed to initialize Crashpad` noise line. Left as-is: rewriting a compiler diagnostic is a separate feature and a wrong rewrite is worse than a verbose right one - the line/column ARE cell-relative (the body is written verbatim with no preamble), so that future rewrite is a path substitution, not a mapping problem. Modular's spurious trailing newline (it `print`s a stdout that already ends in `\n`) is left alone for the same reason.
  - **DECLARATION CARRY-OVER (`src/lib/mojoCarry.ts` + `src/lib/server/mojo-session.ts`, wired in `run.ts`).** A Mojo cell reaches the functions, structs, traits, `comptime` values and imports of Mojo cells that already RAN OK in this kernel session, so "define here, use there" works. Values never carry. `buildMojoProgram(cellSource, carried)` is the ONE pure rule and `run.ts` hands its `program` to `mojoToCellSource`. The stored source is never touched. Rules, each MEASURED against Mojo 1.2.0:
    - **Dependency closure, not carry-everything.** Only blocks whose names the cell (or an already-carried block) mentions are appended. Carry-everything fails on the first re-declared helper, since an identical-signature `def` twice is a hard `redefinition` error. A self-contained cell is therefore sent byte-identical to before.
    - **The cell's OWN names shadow carried ones, and per name the LATEST-RUN cell wins.** That is what makes re-running an edited defining cell replace its old version.
    - **Carried code goes AFTER the cell, behind `MOJO_CARRY_MARKER`.** Mojo allows declarations after `main`, so the cell's line numbers in a compile error stay cell-relative. A line past the cell's own length names carried code.
    - **A cell with no `main` gets `MOJO_SYNTHESIZED_MAIN` appended** (a module without `main` does not compile), and `run.ts` drops the blank stdout Modular prints for it, so a definitions-only cell runs clean with no output.
    - **The record is session-scoped and holds the source that RAN.** Only an `ok` run is recorded, a failed re-run keeps the last good snapshot, a different session epoch drops everything, a deleted cell is excluded at read time (`carriedMojoCells`), and nothing is persisted.
    - **A `%%mojo`-headed cell takes no part in either direction.** It is the escape hatch and is sent as written.
    - **Stated limits:** cross-cell overloads are not merged (latest cell wins the name), `from x import *` carries only alongside another block from its cell, and the staleness graph still reports `n/a` (it is Python dataflow and has no edge for a carried declaration).
    - Covered by `tests/unit/mojo-carry.test.ts` (the rules, plus a tier gated on `CELLAR_MOJO_BIN` that drives real `mojo` with controls for both failure directions) and `tests/unit/mojo-carry-run.test.ts` (the real run queue and `executeCellRun` with Jupyter faked).
  - **`mojoToCellSource` PASSES THROUGH a source that already opens with `%%mojo`**, and both halves of that are load-bearing: pasting an example straight out of Modular's docs (which show the magic) must not produce a doubled header IPython reads as one magic whose body starts with `%%mojo`; and the magic takes a SUBCOMMAND (`%%mojo build --emit shared-lib -o m.so`, `%%mojo precompile -o kernels.mojoc`), which is the only way to reach anything but `mojo run` and would be unreachable if this always prepended a bare header. The check is IPython's own rule for where a cell magic may sit (the first non-blank line), so a `%%mojo` anywhere else is ordinary Mojo text and is wrapped normally.
  - **The magic is registered by a LAZY, BOUNDED, once-per-session PRE-FLIGHT (`kernel.ts`'s `ensureMojoMagic`), never an `initKernel` injection.** `max` is a 534 MB / 16-package dependency Cellar deliberately never installs (`venv.js` adds only `ipykernel` and `ipywidgets`), so importing it from `initKernel` would put that import in front of EVERY kernel start for every user; and sending `%%mojo` without it yields IPython's bare `UsageError: Cell magic function %%mojo not found`, which says nothing about the toolchain. `run.ts` therefore runs `MOJO_SETUP_CODE` through `runCapture` (a SILENT, INTERNAL execute holding the same exec lock as every other execute) immediately before a mojo cell's first run of a session. **Only a READY verdict is memoized** (`NotebookKernel.mojoSetup`, cleared by `beginSession` since the registration lives in the namespace a restart destroys) - a FAILURE is deliberately re-probed on every run, because the whole point of the instruction is that the user runs `uv pip install max` and tries again, and a memoized failure would make Cellar go on refusing a toolchain that is now installed. `importlib.invalidate_caches()` in the probe is the other half of that: Python caches per-`sys.path` directory listings, so without it a mid-session install stays invisible until a restart and the instruction appears not to work (VERIFIED end to end in the real UI - install into the LIVE kernel's venv, re-run, "Hello from Mojo!").
  - **THE BOUND IS A WEDGE GUARD, and its `dispose` is the load-bearing half.** `runCapture` awaits `future.done` with NO watchdog of its own, so an unbounded await here would hang the run before the idle watchdog that exists to free exactly that queue slot is armed (it runs as `execute()`'s `prepare` hook, so the run IS registered for Stop by then - see F3 in the interrupt entry - but nothing else frees it). So `runCapture` gained an optional `timeoutMs` which **DISPOSES** the timed-out future rather than merely abandoning it: abandoning leaves the per-kernel exec lock HELD for as long as the kernel stays silent, so the `execute()` the run falls through to parks behind a probe nobody is waiting for and the bound buys nothing (measured: the guard test timed out at 30s against the abandon version and passes in ~0.4s with the dispose). `timeoutMs = 0` keeps the original unbounded behaviour for the startup callers, whose kernel is freshly built. Bounding costs nothing real - the probe is one round-trip and `import mojo.notebook` MEASURED 3-25 ms against real max 26.5.0 (it pulls in argparse/tempfile and IPython's magic decorator, not the MAX engine); default 30s, `CELLAR_MOJO_SETUP_TIMEOUT_MS`. **THE BOUND COVERS THE WAIT FOR THE LOCK, NOT ONLY THE KERNEL'S REPLY** - `runCapture` takes it through `beginExecLock` and races `ready` against the same `timeoutMs`, handing the chain on with `void ready.then(release, release)` exactly as `execute()` does, so a predecessor holding the lock for minutes (a Databricks `CONNECT_CODE` on a cold cluster) cannot park the probe either. **It is ONE WALL-CLOCK BUDGET across both waits, hoisted before the lock wait and awaited again for the reply** - a fresh `delay(timeoutMs)` per race spent the bound TWICE, so a predecessor holding the lock for nearly the whole window followed by a silent kernel made the reachable worst case ~2x the 30s the knob advertises, in exactly the un-abortable window the bound exists to close; the advertised number and the reachable one have to be the same, which is what the one-budget case in `mojo-run-preflight.test.ts` pins (it makes BOTH waits bite and fails against the per-race form). Bounding only `future.done` left that shape untouched and one door further in: the lock is taken BEFORE the probe's own request, so the run sat there with `run:start` already emitted and the queue's `running` slot held while being in neither `pending` nor `activeRuns` - reachable by no abort path at all. Now it gives up and the run goes on to its own send, still registered, so the user's Stop reaches it. **A probe that could not answer is NO VERDICT (`null`), never "the toolchain is missing" - and a probe that THREW takes that SAME exit** (`requestExecute` on a dead connection, a restart landing mid-probe): both observed nothing about the toolchain, so neither may claim its absence nor prescribe a 534 MB install for a cause nobody saw, and the run falls through to `execute()`, which owns the watchdog and reports honestly. Only a probe that RAN and ANSWERED `ready:false` reports `MojoToolchainMissing`. **The probe's OWN exception split is the same rule reached from the Python side, and it is why `MOJO_SETUP_CODE` no longer catches a bare `BaseException`**: only an `ImportError` (so `ModuleNotFoundError`) is an OBSERVED absence, because the import ran and Python answered that the package is not there; everything else - a `KeyboardInterrupt` above all - sets `MOJO_SETUP_NO_VERDICT_KEY` on the same one marker line, which `parseMojoSetup` reads as `null`. That case is REACHABLE and was reported as a missing toolchain: the probe runs inside a cell that has already emitted `run:start` and holds the queue's `running` slot, so the user can press Stop while it executes, `interruptKernel` signals unconditionally, and the interrupt lands in the import - a 534 MB install instruction for a cell the user simply cancelled. The probe still never RAISES and still prints exactly one marker line; a no-verdict is expressible in that line. (An UNPARSEABLE line is deliberately different and still fails closed to `ready:false` - see `parseMojoSetup`.)
  - **DETECT AND INSTRUCT - Cellar never installs the toolchain.** A not-ready verdict becomes the cell's OWN error output (`MojoToolchainMissing`) naming what is missing, the exact `uv pip install max`, its size, and that Cellar will not do it for the user - rather than a raw traceback. The run is STAMPED with the session the probe ran in (`MojoSetup.session`, sampled BEFORE the probe so an autorestart mid-probe cannot make it claim a namespace it never touched), because the kernel really was alive and this failure is LIVE: reporting no session would drop the cell into `error_persisted`, the label INSTRUCTIONS clause 3 tells agents to distrust as a leftover. `parseMojoSetup` FAILS CLOSED on anything unreadable - a false positive sends `%%mojo` to a kernel with no such magic, while a false negative costs only an instruction the user can ignore. Note `import mojo.notebook` RAISES `NameError: Decorator can only run in context where get_ipython exists` outside an IPython context (MEASURED), which is why the probe runs INSIDE the kernel and a plain `python -c` check would report the toolchain missing on a machine that has it.
  - **THE FOUR ENGINE EXCLUSIONS ARE INHERITED BY CONSTRUCTION, not added as four `&& !isMojoCell(c)` clauses.** `cellLanguage.ts` now owns two POSITIVELY-stated predicates and every Python-semantics engine asks one of them: **`isPythonCodeCell`** (= `isLogicalCellType(cell, 'code')`, the STRICT test - the loose `logicalCellType(cell) === 'code'` maps a FOREIGN nbformat `cell_type` onto `code`) for the `ast`/`symtable` dataflow probe and the imports sweep + agent import routing (`exportRole.ts`'s `canExportCell` became TARGET-AWARE when `.mojo` export targets landed - see the Mojo module export sub-bullet - so it now asks `exportLanguageOf`, which is that same strict test plus the `%%mojo` magic reading); and **`hasPythonDataflow`** (`isPythonCodeCell || isSqlCell`) for the staleness graph, which is deliberately WIDER because `sql.ts` compiles a SQL cell to a wrapper that really does bind `_sql_df`, so it MUST stay in the graph or a Python cell reading a SQL result would never go stale. Written as the negations they replaced, every new tagged language costs one more `&&` in every engine and the engine whose clause was forgotten silently hands non-Python source to a Python parser. **MEASURED on real Mojo, both failures are silent:** the probe reads `def main(): print(...)` as Python and reports `defines=['main']` - a wholly fabricated edge, CACHED as authoritative because the batch still says ok - while `consolidateImports` LIFTS `from std.time import sleep` out of the Mojo cell into the Python imports cell and RUNS it, breaking both halves at once (the Mojo cell no longer compiles; the imports cell raises `ModuleNotFoundError: No module named 'std'` from then on). **THE NOTEBOOK'S LANGUAGE IS NOW THE OTHER HALF OF THAT SAME RULE**: in a Mojo notebook NO cell is Python, so the probe is empty, every cell reports `n/a`, `routeImports` returns early at its ENTRY (it is handed raw source rather than a cell, so it needs the guard there) and `consolidateImports` plans nothing and creates no stray imports cell. Both are pinned by regression tests that FAIL against the pre-fix shape, plus SOURCE GUARDS asserting that the three engines whose question really is "is this Python" (`server/dataflow.ts`, `staleness.ts`, `server/imports-cell.ts`) never mention `mojo` at all and each reaches the shared predicate - a behavioural test alone would pass against a `&& !isMojoCell(c)` chain and leave the NEXT language broken in four places. **THE LANGUAGE MUST BE THREADED BY EVERY CALLER WITH A NOTEBOOK IN SCOPE, never left to `analyzeDataflow`'s `python` default** - the default exists so a caller with no notebook behaves exactly as before, and a caller that HAS one and omits it hands a Mojo notebook's cells straight to the probe. That is `getNotebookStaleness`, `cellsDefiningNames` (the wipe-variables attribution), and the two MCP symbol tools `find_symbol`/`cell_impact`, which are derived from this SAME graph: left defaulted they reported a Mojo `main` as a defined Python symbol and fabricated its dependents, with the source guards above unable to see it (they watch the engines, not their callers). Pinned behaviourally in `tests/unit/notebook-language-document.test.ts`, over the REAL probe and a REAL document, with a Python-notebook control beside each. `exportRole.ts` is deliberately OUTSIDE that guard and DOES name mojo: its question is target-aware (which module language does this cell match), so naming both languages is the shape this rule argues for rather than a breach of it, and `tests/unit/mojo-export.test.ts` pins the distinction that matters there BEHAVIOURALLY - a truth table over the imported module answering both target languages for every cell language, which a flat `!isMojoCell` exclusion cannot produce (it has no `.mojo` target to answer for), so no source guard is needed or kept on that plain-TS module.
  - **The UI marks a Mojo cell and keeps its per-cell controls honest.** The `mojo-badge` stays PER CELL even though the language is notebook-wide, because its tooltip carries per-cell SEMANTICS (each cell is a separate `mojo run` program, so nothing carries over) rather than the setting; the toolbar type label and the type menu's `code` option are LABELLED by the notebook's language (`mojo`), while the option's VALUE stays `code` - converting a SQL cell back to an ordinary code cell is one action whatever language the notebook is. The staleness chip is gone by construction (staleness reports `n/a`); the export toggle IS offered, since a Mojo notebook's code cells are exactly the eligible kind for its `.mojo` module. **The imports-role menu item splits on the SAME hidden-vs-greyed rule the export toggle draws, and the split is the whole of it** (`$lib/importsRole`'s `notebookUsesImportsCell` / `importsRoleStranded`, the pure pair the component asks rather than re-deriving): MARKING is withheld outright, since the imports cell is RUN by the PYTHON kernel and `routeImports`/`consolidateImports` refuse such a notebook at their entry, so it would be a dead control - but a cell that ALREADY carries the role renders the item GREYED and CLEAR-ONLY, with the reason on its own `title` (`IMPORTS_ROLE_STRANDED_TITLE`, short and per-cell like `EXPORT_STRANDED_CELL_TITLE`; no notebook-wide sentence is added for it). **That exception is required rather than symmetric**: a language switch touches NO cell, so a role designated while the notebook was Python SURVIVES it - hidden, the user was left with `metadata.cellar.role` in their committed `.ipynb` and the `imports-badge` still asserting it, reachable only by switching the notebook back.     - Covered by `tests/unit/mojo-export.test.ts` - two tiers, the `mojo-toolchain-probe.test.ts` convention: UNCONDITIONAL (the rules, the generator, the real document write, the hazards, target validation, the `%%mojo`-into-`.py` regression, a systematic sweep of the dropped block's EDGES - every decorator shape, the body's comments/blank runs/strings/dedented continuations, and the trailing trim in both directions - and source guards on the three browser halves, all `.svelte` files) plus a tier GATED on **`CELLAR_MOJO_BIN`** with the reason IN THE SUITE NAME, which drives a real `mojo` (type-check, `mojo run` the module directly, IMPORT it from another file, the `--emit shared-lib` refusal in BOTH directions, and CONTROLS proving the un-transformed Python-path output fails on `__all__` AND on a duplicate `main`, that a stranded decorator above a `struct` and a body cut at a dedented continuation are LOUD, and - the case no compile-based assertion can catch - that a stranded decorator above a `def` is SILENT) - plus `tests/e2e/mojo-export.spec.ts` for the per-cell badge in a real browser (it appears for every cell losing a main and never for the one keeping it, appears and clears as a LATER cell gains and loses its `main`, and a `.py` module offers a `%%mojo`-source cell no toggle at all).
- **Rust notebooks run on the Evcxr kernel (`src/lib/server/rust.ts` + `notebook-language-actions.ts`).** `rust` is the third value of `notebook.metadata.cellar.language`. Unlike Mojo it has a REAL kernel, so state persists between cells and output streams live.
  - **Two axes, kept apart.** The notebook language is `python | mojo | rust`. The KERNEL language is `python | rust` (`notebookKernelLanguage`, Mojo maps to `python`). `NotebookKernel.kernelLanguage` is fixed at start and `liveKernelLanguage(nb)` reads it.
  - **A language change that crosses kernels FREES the kernel** (`syncKernelToNotebookLanguage` -> `rebindKernel`), because a process cannot change kernelspec. Python to Mojo keeps it. The language route reports `kernel_restarted`/`namespace_cleared`, read off what is left afterwards; a rebind that throws adds `kernel_error`. A teardown that lands while a kernel is still STARTING (no connection yet) is caught in `getKernel`: the process that finishes starting finds its entry gone and shuts itself down.
  - **The kernelspec is Cellar's own**, written beside `python3` under `CELLAR_KERNELSPEC_DIR` by `ensureRustKernelspec` right before every Rust start. It needs `interrupt_mode: message`.
  - **DETECT AND INSTRUCT.** Cellar never installs Evcxr. A missing binary throws `RustKernelMissing` before Jupyter is asked, and the run renders it as the cell's own error output with the `cargo install --locked evcxr_jupyter` command. The binary is looked up on every start (`CELLAR_EVCXR`, then PATH, then `$CARGO_HOME/bin`), so installing mid-session needs no restart. That refusal, and `SqlInRustNotebook`, stamp `lastRun.refused`, which MCP reports as `error_refused`: a LIVE failure, never the leftover `error_persisted`.
  - **A Rust kernel gets NO Python startup injection and no Python probe.** `initKernel` skips every snippet. The variable inspector, the wipe route and editor introspection (`not_python`) each check `liveKernelLanguage` first. The Databricks kernel ops (`not_python_kernel`, 409) decide from the NOTEBOOK's language when no kernel is live, because `execute()` would otherwise boot an Evcxr kernel and hand it Python.
  - **What a Rust notebook does not have:** an export module (`languageGeneratesModule`; a stored target is kept and reported unresolvable, a new one is refused), an imports cell, staleness, and SQL cells (`SqlInRustNotebook` refuses the run). A `.py` text notebook refuses `rust` like it refuses `mojo`.
  - **NOT VERIFIED against a real Evcxr binary.** Every test fakes Jupyter. Covered by `tests/unit/rust-kernelspec.test.ts`, `rust-notebook-language.test.ts`, `rust-kernel-start.test.ts` and `rust-notebook-document.test.ts`.
- **Deliberately NOT built for Mojo (each is a decision, not an omission):** a Mojo KERNEL (see the notebook-language entry - unshippable, and the reason is structural rather than a bug in anyone's code); making VALUES persist between Mojo cells (that is Modular's semantics and faking it would lie about what a `%%mojo` cell is; declarations do carry); auto-installing `max` (534 MB, detect-and-instruct only); rewriting the `MojoCompilationError` diagnostic onto the cell (a string transform, since the line/column are already cell-relative - a later increment); auto-injecting `import mojo.notebook` at kernel start (the lazy pre-flight is what keeps a 534 MB import off every kernel start); a real Mojo highlighter (Modular's own `language_info` asks for the Python mode); and `.mojo` FILE support in the tree/editor (a separate surface from the notebook language).
