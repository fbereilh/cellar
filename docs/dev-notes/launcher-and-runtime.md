# Launcher, runtimes, venv binding, ports and instances

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Two runtimes.** Node (SvelteKit) + a Python sidecar (Jupyter kernel service). Both are booted by the CLI launcher `bin/cellar.js` (one command → both servers up → browser opens, workspace = cwd). Distributed as an **npm package** (`package.json` `files`=`build/`+`bin/`+the node-builtins-only `src/lib/server/*.js` the launcher imports - read that array, never a copy of it here; `prepack`/`prepublishOnly` run `vite build`); launcher defaults to the prod build (`node build/index.js`), `--dev` uses Vite. `build/`/`.venv/` gitignored. A root **`Makefile`** wraps these mechanics for convenience (`make setup` = install+build+`chmod +x bin/cellar.js`+`npm link`; `make update` = `git pull`+install+build; plus `make build`/`run`/`dev`; bare `make` prints help) - it invents no new scripts, just the real npm/launcher commands. `bin/cellar.js` is committed **executable** (git mode 100755 - the shebang'd, sole `package.json` `bin` entry); preserve that bit if you ever regenerate it, or `npm link` yields a non-runnable `cellar` symlink (the `make setup` `chmod` is a belt-and-suspenders re-set).
- **Per-repo launcher + venv binding (`bin/cellar.js` + `src/lib/server/venv.js`).** `cellar` in any repo binds the kernel to the **project's** venv. Resolution (first match): `--venv`/`CELLAR_VENV` → `$VIRTUAL_ENV` → `<ws>/.venv` → create. All venv create/installs go through **`uv`** (`uv venv`, `uv pip install`) — hard requirement, fails fast if absent (no `python -m venv` fallback). Ensures `ipykernel` in the project venv; **confirms before** create/install on a TTY (`--yes`/`-y`/`$CI`/non-TTY auto-approve; `--python` = bind arbitrary interpreter, no create/install). `venv.js` uses node builtins only so it's importable by both the launcher (`../src/lib/server/venv.js`) and the SvelteKit server (`$lib`). Cellar's heavy Jupyter host env (`jupyter-server`) lives in a private `~/.cellar/host-venv`, created/cached first run, kept separate from project venvs.
- **Kernelspec = the venv lever.** The launcher writes a per-run `python3` kernelspec (`writeKernelspec`) whose `argv[0]` is the project python, into a temp `JUPYTER_PATH` dir handed to the sidecar; `startNew({name:'python3'})` then launches the project interpreter — `kernel.ts` unchanged. The dir is passed to the app as `CELLAR_KERNELSPEC_DIR` so the runtime venv control can rewrite it.
- **Sidecar cwd must equal `root_dir` (= WORKSPACE).** `bin/cellar.js` spawns the Jupyter sidecar with `cwd: WORKSPACE`, not Cellar's `REPO`. Because `startNew({name:'python3'})` passes no notebook path, `jupyter_server` doesn't derive a kernel cwd from `root_dir` and the kernel inherits the sidecar's process cwd — so anchoring it at WORKSPACE is what makes `os.getcwd()`, relative reads/writes, and repo-root walks resolve in the user's project (else they resolve in / write into Cellar's install dir). Everything else in that spawn (host python, `JUPYTER_PATH`) is already an absolute path, so it stays REPO-independent. The old follow-up here (pass a path to `startNew` so a kernel roots somewhere other than the sidecar's cwd) SHIPPED, once kernels became per-notebook and the ambiguity that blocked it went away — see **Notebook code roots** below. The sidecar cwd rule is unchanged and still what a notebook declaring NO root gets. **The launcher reads back the Jupyter port the sidecar ACTUALLY bound; it never trusts the one it asked for (`src/lib/server/jupyter-sidecar.js`).** `freePort()` closes its probe before jupyter binds, and when something takes the port in that window jupyter's `port_retries` (default 50) quietly walks to `p+1…p+4`, then to random nearby ports. The launcher used to poll the requested port, so it waited on an address nothing answered (CI: sidecar on 39656, launcher timing out on 39655, reported as `launcher exited early (1)`). Against a squatter that ACCEPTS and never answers it hung for good, because `fetch` has no default timeout. Now it scans jupyter's runtime dir (asked of the host python with the sidecar's env, bounded) for the `jpserver-*.json` carrying THIS launch's token. The token is the identity, never the spawned pid: on Windows a venv `python.exe` runs the real interpreter as a child, so the file is named after a pid the launcher never sees, and matching on the token also rules out a stale file from an earlier server. Because jupyter writes that file BEST-EFFORT (a filesystem refusing its permission check only logs a warning), the wait ALSO accepts the REQUESTED port when `GET /api` answers 2xx under this launch's token - never a 403, which is another server - each probe bounded; whichever confirms first wins. It then polls THAT port with every request bounded (`waitForHttp`) and corrects `runtime.json` and the registry entry. `--ServerApp.info_file` is NOT configurable (measured: jupyter ignores the flag with a warning), so do not retry it. A walk onto the app or MCP port this launch reserved is refused with that cause named (`sidecarPortConflict`), since on macOS it would silently serve Jupyter at the app URL. A PINNED `CELLAR_JUPYTER_PORT` gets `port_retries=0`, so a taken pin fails fast and says so. Covered by `tests/unit/jupyter-sidecar-port.test.ts` and `tests/e2e/launcher-jupyter-port-taken.spec.ts`, which squats the requested port the moment the launcher announces it and then runs a cell through the bound port.
- **Runtime venv control.** Settings → "Python environment" (`src/lib/Settings.svelte`) → `src/routes/api/venv` (GET info / POST `{path,create}`) → `src/lib/server/venv-bind.ts`: resolves/creates the venv via uv, ensures ipykernel, rewrites the kernelspec, updates in-process `CELLAR_PROJECT_VENV`, then `rebindKernel()`. Confirm-before-create is enforced in the UI.
- **Stable per-workspace ports (`src/lib/server/ports.js` + `.cellar/ports.json`).** A folder REMEMBERS the ports it got and asks for them again next launch, so a browser tab/bookmark survives a restart. A remembered port is a **PREFERENCE that must be re-earned on every launch, never a claim**: `choosePort` honours an explicit `CELLAR_*_PORT` pin verbatim (an instruction, never probed, and never RECORDED - recording it would let a pin silently outlive the run that asked for it), else uses the remembered port only when it is not held by a live REGISTERED instance, is bindable now on the host that role's server really binds, AND is free on the address the URL Cellar PRINTS connects to (`reachHostsFor`, below), else takes a fresh ephemeral port **and remembers THAT** so the next restart is stable again. **The fresh candidate is probed on the role's own bind host too**, for exactly the `bindHosts` reason below: the launcher's `freePort()` asks the kernel for a free loopback port while adapter-node binds the wildcard, so a kernel-assigned port can still be one the app's own `listen()` cannot take (and on its reach host, through the same one `unusable()` so the remembered path and the fallback can never answer the two questions differently; no grace loop - an ephemeral port that is busy is a coincidence to step over, not a previous run letting go). **A port that is unusable is reported with its OWN cause** (`FreshReason` + the `MOVE_CAUSE` phrasing map, which is keyed by reason so a new one cannot be announced without deciding what it SAYS): a live registered instance holding it and this very launch having already taken it for another role are different facts, and the move is ANNOUNCED - one merged claim set told the user another running Cellar was using a port nothing but this launch had taken, naming an instance that does not exist in the one message the feature asks them to trust. It **only ever yields and never reclaims** - Cellar has a painful history of a launch disturbing someone else's session - and a move is ANNOUNCED with its reason, since silently changing an address the user was told is stable is the confusion this removes. **Isolated / `--new` launches never touch the sticky path** (`sticky` is the launcher's `!forceNew`, the same gate as the instance lock and the reap sweep): they exist so concurrent instances cannot collide - e2e at `workers:2`, mkdtemp workspaces - and a remembered port is precisely a port another instance is likely to hold; such a launch also never WRITES the preference, or a throwaway run would overwrite the folder's memory. That guarantee is a tested behavior rather than a claim about a line of launcher code, because the whole policy lives in `resolveWorkspacePorts` and not in `bin/cellar.js`.
  - **The sticky roles are resolved FIRST and Jupyter LAST, and `fresh()` never hands back a port it knows is claimed.** Jupyter takes a kernel-assigned ephemeral port and claims it, so resolved first it could land on the very port the folder remembers: the sticky role was then pushed off its stable address and the replacement PERSISTED - silently losing the address this whole file exists to keep, on roughly one launch in eight thousand. Ordered app, mcp, jupyter it cannot happen, and Jupyter loses nothing because its own fallback already skips whatever the sticky roles took. That fallback re-asks for a port up to `FRESH_PORT_ATTEMPTS` (50) times and then THROWS rather than returning one it knows is taken: two roles binding one address surfaces much later and much worse than a launch that refuses with a reason.
  - **Which ports are sticky, and why they are NOT equal.** App and MCP are remembered; **Jupyter deliberately is not** (only the launcher and the app ever learn its port, in-process, so remembering it buys nothing and adds one more port to lose a race for). The two that are remembered earn it very differently, and that asymmetry decides how hard this tries: the **app** port is what a human holds onto (the URL, the bookmark, the open tab) and is CHEAP to keep - measured twice against a real instance, adapter-node closes its own http server on SIGTERM so the app port is bindable again within ~0ms of a Ctrl-C; the **MCP** port appears in no agent config at all (the `cellar mcp` bridge is why) and is now genuinely disposable since that bridge re-attaches by itself, while being the EXPENSIVE one - held ~6.8s after a Ctrl-C, because nothing closes the in-process MCP http server and it carries `timeout = 0`, so it is released only when the app process finally exits. Hence `PORT_RELEASE_GRACE_MS` is **500ms**: it covers scheduling jitter around the app case and explicitly does NOT try to wait out the MCP one. **Do not "fix" that by raising it** - stalling every restart by seven-odd seconds to preserve a port nothing reads would trade real launch latency for nothing, and on that path nothing in the new launch can hurry the old app along anyway (the previous launcher already unregistered itself and cleared `runtime.json`, so the take-over sweep finds nothing to await and the orphan exits only via `parent-watch`'s confirm-strike poll). It is NOT a fixed sleep - the loop re-probes every `PORT_RETRY_MS` and returns the instant the port binds, so a free port costs ONE probe. **That non-goal is affordable only because the app RELEASES the MCP listening socket on SIGTERM** (`mcp/server.ts`): nothing used to close it and it carries `timeout = 0`, while adapter-node's graceful shutdown unbinds only its OWN listener, so the port stayed bound until the process itself exited - the orphan self-exit in `parent-watch`, 5-10s later. That is what made the remembered MCP port busy on essentially every quick relaunch, so that half of the preference never converged: each launch moved and then remembered a port that would be busy again next time. `close()` frees the LISTENING socket at once (deliberately NOT `closeAllConnections()`, which would abort a run streaming its progress), which is all the next launch needs. The hook is the exported `releaseOnShutdown(httpServer, signals?)` rather than an inline block, because `startMcpServer` cannot be booted in a unit test (it wires the live document and the kernel into an `McpServer`) - split out, the behaviour `ports.js` leans on is driven directly against a REAL listening server and a REAL emitted signal (`tests/unit/mcp-http-shutdown.test.ts`), with the emitter injected so the assertions are about this hook and not about the runner's own signal handling - so waiting for that port buys nothing, rather than the move being hidden. **EVERY move is still announced with its cause**, the MCP role included: a routine restart is silent because NOTHING MOVED, not because a real move was suppressed.
  - **A bind probe MUST name the host the server really binds (`bindHosts`), or it answers a different question.** On macOS a `SO_REUSEADDR` bind of `127.0.0.1:P` SUCCEEDS while another socket holds `0.0.0.0:P`, and the reverse is permissive too (both measured) - so probing loopback reported the app port FREE while adapter-node still held it on the wildcard, which would hand the app a port its own `listen()` cannot take. The hosts mirror the real listen sites and must move with them - and the APP has TWO, because the launcher spawns a different server per branch: by default `node build/index.js` (adapter-node, `HOST` or its `0.0.0.0` default, since the launcher sets only `PORT`), and under **`--dev`** `vite dev --port <p> --strictPort` with no `--host`, so vite's own default applies and `HOST` is not read at all - and that default is the literal string `localhost`, which vite hands to `listen()` for NODE to resolve, so on a dual-stack machine it binds `[::1]` (Node 18+ resolves verbatim). The probe therefore passes the SAME STRING rather than a hand-picked address: `127.0.0.1` reports free while `[::1]:P` is held (both verified locally), the identical address-family mismatch one step narrower. `dev` is threaded in from the launcher rather than guessed in the module, because only the launcher knows which it will spawn; getting it wrong is not merely suboptimal there, since `--strictPort` makes the app child exit and the launch die, and the "successful" remembered path then rewrites the preference so every later `--dev` launch in that folder fails identically. mcp = `CELLAR_MCP_HOST || '127.0.0.1'`, jupyter = the sidecar spawn's `--ServerApp.ip=127.0.0.1`. Pinned BEHAVIORALLY, never by a grep over those files: `bindHosts` is asserted in both directions per role, and the ROUTING - which (port, host) pair each role is really asked about - is proved by an injected probe, which is stronger than a socket because it shows WHICH question was asked instead of leaning on the kernel to imply it. **The real-socket demonstration of the consequence is DARWIN-GATED and must stay so** (`describe.skipIf`, reason in the suite name): it asserts that a wildcard bind SUCCEEDS while a loopback socket LISTENS on the same port, which is BSD/macOS `SO_REUSEADDR` behaviour - Linux treats wildcard-vs-specific as a conflict once the holder is listening, so ungated it turned CI (ubuntu-latest) red while passing every local run. A test that binds on one host and asserts a probe on a DIFFERENT host is making a platform claim; one where squatter and probe name the SAME host is portable and needs no gate.
  - **BINDABLE IS NOT REACHABLE, and a WILDCARD bind is where the two come apart (`reachHostsFor`).** `bindHosts` answers "can this role's server LISTEN here"; it does NOT answer "will the address we hand the user reach that server". The launcher prints and OPENS `http://localhost:<appPort>` while adapter-node binds `0.0.0.0`, and the same BSD/macOS `SO_REUSEADDR` overlap documented above runs the other way too: a squatter on `127.0.0.1:P` leaves the wildcard probe answering FREE, Cellar takes the port and starts perfectly, and because the MORE SPECIFIC binding wins the demux every connection to that URL lands on the squatter. Nothing in the launch fails - the app is simply not where it says it is, which is worse than a visible refusal. **New with remembered ports, which is why the check belongs here**: the app port always used to come from `freePort()`, which binds `127.0.0.1`, so a loopback-squatted port could never be handed out at all. So `reachHostsFor(bindHost)` adds ONE address for a wildcard bind - the LOOPBACK OF THE FAMILY THAT WILDCARD ALREADY SERVES (`0.0.0.0` -> `127.0.0.1`, `::`/`[::]`/`::0` -> `::1`) - and NOTHING for a concrete host, which is already an address people connect to (`--dev`'s `localhost` included: it is the very name the printed URL uses, resolved the same way by the same Node). **The family match is what makes it safe to REQUIRE rather than prefer**: a machine that can bind the IPv4 wildcard has `127.0.0.1`, so this can never veto every candidate port on a machine lacking an address family and turn a hijack risk into a launch failure (which is exactly what probing `::1` under an IPv4 bind would risk - hence the STATED RESIDUAL, deliberately not chased: with the IPv4-wildcard default Cellar serves no IPv6 at all, so a `[::1]:P` squatter still wins an IPv6-preferring client's first attempt, a case `freePort()` could always produce and that this feature does not change). It gets its OWN `FreshReason` (`address-unreachable`) rather than reusing `port-unavailable`, because `lsof` would show that port bindable and "another process is using it" would send the user hunting for something they cannot find. A routine self-restart is unaffected and still silent - the previous app releases the wildcard, no loopback squatter exists, nothing moves - so this notice fires only on a genuine, unexpected conflict.
  - **Why a separate file from `runtime.json`:** that one is a LIVE-INSTANCE record which `clearRuntime` DELETES on exit, precisely so a dead instance can never be discovered - the opposite of what a durable preference needs. `.cellar/ports.json` is never cleared, and lives where every other per-project, port-independent, gitignored piece of state already does (checkpoints, ui-state), so a deleted worktree takes its preference with it and nothing accumulates in `$HOME`. It is untrusted input (a hand edit, a merge), so `isRememberablePort` is deliberately STRICTER than the pin rule (integer, 1024-65535) and a corrupt file reads as no preference. Node builtins only, so `bin/cellar.js` can import it like `venv.js`/`runtime.js`; in `package.json` `files` for the same reason. Covered by `tests/unit/ports-stable.test.ts` (the rule across every case incl. a pin, a live instance, a real squatter, a corrupt file and both claim causes; the whole-launch path over real workspaces; `bindHosts` in both directions per role; and the reachability rule - `reachHostsFor` in both directions, the extra probe ROUTED only to a wildcard role, and the darwin-gated real-socket demonstration that a loopback squatter now COSTS the app its remembered port, announced with its own cause, while the MCP role's identical squatter stays a plain `port-unavailable` on the host it binds). Deliberately NOT covered by a source guard over `bin/cellar.js`: a grep for `sticky: !forceNew` proves nothing a behavior-preserving edit cannot break while still passing, so the isolated/`--new` guarantee is pinned where it is a BEHAVIOR - `resolveWorkspacePorts` over real workspaces, which is the whole reason the policy lives there rather than in the launcher.
- **Single-instance-per-folder + reap (`bin/cellar.js` step 0 + `runtime.js` + `instances.js`).** A relaunch in a folder that already has a live cellar **takes over**: it **reaps the old instance and starts fresh**, rather than leaving the old server running with stale in-memory code. This is the fix for the pile-up: old `build/index.js` servers accumulate (a launcher killed uncleanly leaves its app **reparented to init**, still listening for hours; or a still-running instance after a code update keeps serving old MCP `instructions`/tool descriptions to agents that discover its port). Two servers also each persist `notebook.ipynb` from independent in-memory docs → last-writer-wins clobber, so exactly one at a time is enforced. **`.cellar/instance.lock`** is still an `O_EXCL` lockfile (`acquireInstanceLock`) claimed at the top of `main()`, atomically gating the folder so a rapid double-launch can't start two at once. The loser of the lock **no longer attaches** — it **reaps the owner** (`reapInstance` on the owner's registry entry when present, so its recorded app/jupyter child pids are killed explicitly, else a synthetic entry relying on the launcher's SIGTERM cascade), then re-acquires the lock (retry loop) and boots. `waitForInstanceUrl` is now unused/removed from the launcher. `--new`/`--force` skips the whole reap+lock block to run a deliberate second instance. `cleanup()` releases the lock (pid-guarded) only if we took it, and drops our registry entry.
  - **Global instance registry (`instances.js`, `~/.cellar/instances/<launcherPid>.json`).** Cross-workspace record of every instance (`launcherPid` + `appPid`/`jupyterPid` filled in after spawn, ports, workspace, `startedAt`, and a per-pid **`launcherStart`/`appStart`/`jupyterStart`** = real OS start time from `ps -o lstart=`). Lives in `$HOME` (not the project `.cellar/`) so it **survives the workspace dir being removed** — the deleted-worktree case where orphans pile up. Node builtins + global fetch only, so both the launcher and the SvelteKit server import it. `runtime.js` now **exports** `pidAlive`/`appPortResponds` for it. On launch (before the lock) the launcher also runs `pruneDeadInstances()` (drop registry files with no live process) and `reapVanishedWorkspaces()` (reap instances whose workspace dir is gone) — both always safe; a live instance for a real other project is never touched. After winning the lock it also `reapWorkspaceInstances(WORKSPACE, {excludePid})` to clear orphaned children a crashed prior launcher left for **this** folder.
    - **Identity-verified reaping — the registry keys by launcher pid, but a pid is only unique while alive.** Once an instance exits (its throwaway worktree removed), the OS can hand that exact pid to an UNRELATED process; a reaper that SIGTERMs `launcherPid` on the pid alone then kills the innocent reuser (the observed bug: a fresh launch killed a different healthy cellar + its live kernel). So `reapInstance` never signals a pid unless it is **provably still that instance**: `pidReapDecision(pid, recordedStart, startedAt)` → `verifyPidIdentity` compares the pid's live `processStartTime()` to the recorded `*Start` (exact, ±`START_TIME_SKEW_MS`), falling back to the `startedAt` window for legacy entries. `true` ⇒ kill; `false` (pid reused) or `null` (unverifiable / no `ps` / Windows) ⇒ **SKIP the kill, only prune the stale entry** — killing REQUIRES a positive match, so over-pruning is the safe direction. This is why lingering stale entries are harmless. Trade-off: a **pre-registry / lost-entry** same-workspace owner carries no `*Start`, so a take-over degrades to skip-and-reclaim-the-lock (documented at the launcher call site); every current-code instance registers `launcherStart`, so the normal relaunch take-over is unaffected. **Every reap decision is logged** (candidate `launcher`/`workspace`/`reason`, the identity result, KILLED vs SKIPPED/PRUNED). The launcher/`parent-watch`/app also log their **shutdown trigger** (SIGTERM received vs. orphan self-exit vs. child-exit vs. clean) so a killed kernel is distinguishable from a crash. `parent-watch` requires `CONFIRM_STRIKES` consecutive dead readings before self-exiting. Covered by `tests/unit/instances-reap.test.ts` (spawns a real process to prove an impostor pid survives).
  - **Orphan self-exit (`parent-watch.ts`, started from `hooks.server.js`).** The app is passed `CELLAR_LAUNCHER_PID` and polls it every 5s; when the launcher dies uncleanly the app kills the (also-orphaned) Jupyter sidecar, unregisters, and exits — so an orphaned instance reaps itself instead of lingering. A reused launcher pid reads as "alive" (safe direction: lingers, never exits a healthy server).
  - **`cellar ls` / `cellar cleanup`** subcommands (handled at the top of `bin/cellar.js`, before normal arg parsing, never boot a server). `ls` lists registry instances (with liveness) + a POSIX `ps` scan for **untracked** cellar app processes (`scanUntrackedCellarProcesses`: matches only `node <abs>/…/cellar/build/index.js` — deliberately strict, since other agents' processes carry our prompt text mentioning "node build/index.js"/"cellar" as args). `instances.js` is in `package.json` `files` (imported by the launcher at runtime).
  - **Stopping a LIVE instance is scoped to a WORKSPACE, and reaching another workspace's needs a typed phrase (`src/lib/server/cleanup-plan.js`) — this is a data-loss guard, not ergonomics. THE REPORTED BUG WAS ONE SYMPTOM OF A CLASS, which is why the change is far larger than it: every remaining way this command could silently operate on a workspace other than the one the user named was closed with it — an unrecognised POSITIONAL silently dropped (so `cleanup <path> --all` reaped the caller's cwd), a REPEATED `-w` silently first-wins, an EMPTY `-w` value falling through to the cwd, a `-w` NAMING NOTHING making `--all` a silent no-op, and running `--all` from a SUBDIRECTORY of your own project misfiling your OWN instance as somebody else's and then offering the cross-workspace flag to reach it (a safety mechanism whose failure mode is teaching people to bypass it is worse than none). The first four are refusals; the last is `resolveCallerWorkspace`.** `cleanup --all` used to stop every live cellar in EVERY workspace, and its confirmation was satisfied by `--yes`, by `$CI`, **and by a NON-TTY STDIN** — so a bare `cellar cleanup --all` from any script or agent destroyed a stranger's live notebook session (kernel, namespace, unsaved work) with no flag and no prompt. Both halves were reproduced with two real instances in two real folders. The tiers are `orphans` (default) -> `workspace` (`--all`) -> `everywhere` (`--all-workspaces`), and the axis is the **workspace an instance serves** compared against the caller's — the ONE honest signal for "is this mine to stop". `--all-workspaces` requires the literal `CONFIRM_PHRASE` (`stop-all-workspaces`), typed or as `--confirm=`, precisely because `-y`/`CI`/a pipe all mean "don't ask me about the routine thing" and cannot spell it; `--dry-run` prints the blast radius and stops nothing. **`--all` was NARROWED rather than removed, deliberately**: it is what people type meaning "clear up after me", so that is now what it does — a hard error would only have taught every reader the cross-workspace spelling instead. **Orphans stay reapable everywhere at every tier** (a dead launcher's leftovers are nobody's live session), which is what keeps the tidy case a one-word command and why the narrowing costs an ordinary user nothing. **An UNTRACKED live process (ppid != 1) is `everywhere`-only**: `ps` reports the cellar CHECKOUT it was launched from, never the WORKSPACE it serves, so it cannot be attributed and an unattributable live process counts as somebody else's — and that is the tier that protects a user's real instance whenever the registry is isolated (a temp `HOME`, i.e. every CI and agent run, where their instance is not in the registry we can see). `workspaceKey` realpaths BOTH sides (an IDENTITY test, the blessed use of realpath — a lexical compare reads `/tmp` and `/private/tmp` as two directories, i.e. every macOS `mkdtemp` workspace); a comparison that fails falls back to the lexical path, which can only ever under-reach. **CONTAINMENT enters at exactly ONE point and answers a DIFFERENT question**: `resolveCallerWorkspace` decides which workspace the caller is STANDING IN, walking UP to the deepest registered workspace containing their directory (deepest-wins, so a nested project keeps its own; UP only, so a workspace nested INSIDE the caller's directory stays a different project; boundary-safe on canonical keys, so `/tmp/projX` is not inside `/tmp/proj`). `planCleanup`'s per-entry comparison stays an IDENTITY test against that answer — containment can widen which DIRECTORY counts as yours, never which ENTRIES a directory reaches. **A `-w` that names no existing directory is REFUSED, but the entry-side lexical fallback must STAY**: the registry deliberately outlives a deleted workspace so deleted-worktree orphans remain reapable, and such an entry still needs a key; the accepted cost is that `-w <deleted dir>` no longer scopes a cleanup, which bare `cellar cleanup` and `reapVanishedWorkspaces` already cover. Whatever is left running is **reported with the FLAG that would reach it, and NEVER with the phrase**, split by whose it is (`--all` for the caller's own, `--all-workspaces` for others) — the old command was dangerous precisely because its reach was invisible, but `reportSkipped` is the ROUTINE output of the SAFE forms, so printing a ready-to-run `--confirm=` command there would have Cellar hand the deliberate-intent token to the very caller who did not ask for the wider scope (the incident WAS an agent tidying its leftovers): a confirmation you are given unprompted is not a confirmation. The phrase lives in `--help` and in the refusal, which is reached only once the wider scope has been chosen. **The caller's directory is read through `callerDir()`, which falls back to `''`** — `process.cwd()` THROWS once the working directory is removed, and a deleted worktree is exactly what PRODUCES the orphans this command reaps, so it must not be what stops the tidy; `''` is the safe fallback by construction (`planCleanup` guards on `workspace !== ''`, so `liveHere` is empty, orphans are still reaped and `--all` is inert). **Argument parsing is ONE pass that both validates and reads `--workspace`'s value**, because the two used to be separate (a loop, then a `findIndex`) and the gap between them was itself a bug. The whole vocabulary is DATA (`parseCleanupArgs` -> a typed `{all, allWorkspaces, dryRun, yes, workspace, confirm}`, which `scope`/`dryRun`/`yes`/`here`/`confirmFlag` are then derived from) rather than a chain of special cases, because three near-identical holes were found in that chain one at a time and the policy is now structural: **anything not described there is refused** - an unknown flag, a **POSITIONAL**, a `-w`/`--workspace` whose value is missing, EMPTY or flag-shaped (an empty one is the `-w "$WS"`-with-`$WS`-unset case, which used to fall through a `||` onto the caller's own cwd and stop THAT folder's session; the fallback is now `??`, so a PRESENT workspace is a usable string by construction), a **REPEATED `-w`** (naming both directories; first-wins silently discarded a directory the user typed, so a corrected typo left on the line stopped the wrong workspace under `-y` while the one they meant was reported as merely left running) and a repeated `--confirm=` with DIFFERING values (which deliberately does not echo them, one being possibly the phrase). A bare space-separated `--confirm` earns its OWN refusal naming the attached `--confirm=<phrase>` form rather than falling through to "unknown flag", which denied a flag `--help` documents on the one path reached only after the wider scope has been chosen (the space form is refused, never accepted: consuming the next token would reopen the missing/flag-shaped/repeated questions the parser just closed). Every refusal lands before `pruneDeadInstances`, so a mistyped command signals nothing and prunes nothing. **`workspaceKey` upgrades its answer IN PLACE (raw -> resolved -> realpath) rather than recomputing in a fallback**, because `resolve` consults `process.cwd()` for a RELATIVE path and THROWS once the workspace is gone, so a catch that re-ran it threw straight back out and falsified its own never-throws contract - reintroducing the deleted-cwd crash through the `-w` door. Its test must run the probe as a FILE outside the deleted directory: `node --input-type=module -e` derives the eval's base URL from the cwd and dies on its own first, which makes such a test pass for the wrong reason. A repeated BOOLEAN flag (`--all --all`, `-y -y`) is deliberately fine - the class refused is "a value you typed was silently dropped", not "an argument appears twice". **Those constants live INSIDE the function, not at module scope**: `cellar cleanup` is dispatched near the top of `bin/cellar.js`, so a module-level `const` further down is in the temporal dead zone for this very command and throws a `ReferenceError` before anything runs. `cellar cleanup <path> --all` used to DROP the path and reap the CALLER'S cwd (verified: it killed the caller's own live launcher while the named workspace was reported as left running), and `cellar cleanup -w --all-workspaces` swallowed the flag as a directory while still selecting the everywhere scope - both are this entry's own failure mode wearing different clothes, the user believing they are operating on one workspace while the tool operates on another. A positional is **refused, never accepted as a workspace**: taking a path is a deliberate design decision with its own scoping and confirmation questions, and `-w <dir>` already names another workspace. Covered by `tests/unit/cleanup-scope.test.ts` (the pure rule), `tests/unit/cleanup-command.test.ts` (the REAL CLI as a subprocess against real double-forked processes — the consent rule is a property of the COMMAND, so a plan-only test would still pass if `-y` were wired back in) and `tests/e2e/cleanup-scope.spec.ts` (real launchers in two real folders). **Both process-level tests shim `ps` to answer nothing for the machine-wide `-eo` scan and isolate `HOME`**: if this ever regresses, an unshielded run reaches exactly the live session the fix protects — a test for a data-loss bug must not be able to cause it. The unit victims are **double-forked** for a second reason: a direct child becomes a zombie that `process.kill(pid,0)` still sees while `spawnSync` blocks the reaper, so every kill waited out its full 8s SIGTERM grace (56s -> 4s).
