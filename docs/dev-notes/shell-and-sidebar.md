# Application shell, navbar, sidebar sections, kernel cards, Git section

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

Wraps the notebook in a JupyterLab-style shell. `src/routes/+page.svelte` is the shell: it owns tabs/sidebar/kernel-controls/theme and hosts one `LiveNotebook` per open notebook tab (default + each opened `.ipynb`), all kept mounted+hidden so editor/run state survives tab switches. It no longer owns `cells`: each `LiveNotebook` owns its own cells and reports the live array up via `onCellsChange(path, cells)` into a path-keyed `notebooksCells` map; the sidebar (outline/search/variables) reads `activeCells` for the focused notebook (falls back to the default when a plain file tab is active). One kernel per notebook → runs are serialized **within** each notebook by the **server-side FIFO run queue**, while different notebooks execute in parallel (see the Kernel run queue entry above); the shell's `runBusy` is only a derived in-flight counter for the kernel badge, no longer a gate.
- **A FOREIGN action must refresh every panel the OWN action refreshes (`+page.svelte`'s SSE handler).** The shell drives an action itself AND observes the same action arriving from an agent / another tab, and the two paths refresh the sidebar independently - so a panel one refreshes and the other does not goes stale for the rest of the session, and **no test that performs the action ITSELF can see it** (a self-run goes through `onRunEnd`, which already refreshes variables, so it masks the gap completely). Both known cases are fixed and pinned: a foreign `run:end` refreshes the kernel badge **and** the variable inspector (refreshing only the badge left the Variables panel empty for a whole agent session - measured against a live kernel - because the mount-time inspect is a one-shot that had no kernel to read yet), and the `notebook:opened` branch bumps `fsRefreshSignal` like every other new-file path here (without it an agent-created notebook never appeared in the file tree, its untracked git badge included). **What must match is the refresh SET, not the mechanism - and the two halves of that set are deliberately dispatched DIFFERENTLY, because a foreign run is not paced like the user's own.** The kernel badge stays immediate and ungated (`/api/kernel` only READS state, it never probes). The inspector is a real kernel EXECUTION (`/api/kernel/variables` → `inspectVariables` → `execute`), and a foreign `run:end` arrives once per CELL, so mirroring `onRunEnd` naively made an agent's `run_cells`/`run_all` cost one probe per cell **per open tab**, each serializing on that kernel's `execChain` and inserting latency between the agent's own cells. So it is **coalesced** (`scheduleForeignVariablesRefresh`, a trailing debounce of `FOREIGN_VARS_REFRESH_MS` = 300ms - one probe per burst, far below what a human reads as lag) and **scoped to the ACTIVE notebook** (`foreignRunTouchesActiveNotebook`): `inspectVariables` probes the ACTIVE notebook's kernel, so a run elsewhere can only ever probe the wrong one. Its pending timer is cleared by the SSE subscription's own teardown (the `onMount` now returns a cleanup that unsubscribes AND clears it), so a scheduled probe can never outlive the page that scheduled it. **The gate FAILS OPEN, and that direction is the rule**: the event's `nb` is ABSOLUTE while `activeNotebookPath` is workspace-relative, so the comparison goes through **`$lib/workspacePath`'s `toWorkspaceRel(workspace, abs)` - the ONE owner of that conversion, shared with `canonicalNotebookRel` so the two cannot drift** - and every case it cannot decide (no path on the event, no active notebook, a path outside the workspace) returns **true** and refreshes - a missed refresh is the bug this whole path exists to fix, so over-refreshing is safe and silently skipping never is. **That helper is BOUNDARY-AWARE, and it is not a tidiness point**: both sites used to be a bare `startsWith`, so a SIBLING sharing the workspace's name as a prefix (`/tmp/ws` vs `/tmp/ws2/x.ipynb`) read as INSIDE the workspace and yielded the nonsense rel `2/x.ipynb`, which the gate then DECIDED as a mismatch and skipped - the missed refresh reached through the one path that did not fail open. It requires a separator boundary and returns null otherwise, so an undecidable path falls into the fail-open branch; the caller supplies its own fallback for null (`canonicalNotebookRel` keeps the bare name). **The load-bearing undecidable case is `activeTabIsNotebook`**: the probe's real subject is the SERVER's `getActiveNotebookPath()`, which moves only when a `LiveNotebook` becomes `active`, so a plain FILE tab holding focus leaves it pointing at the last-focused notebook while `activeNotebookPath` falls back to `canonicalNotebookRel` - and comparing there answers about the wrong notebook, i.e. FALSE for a run in the very notebook the probe would read, this bug reappearing with the gate failing CLOSED. So the comparison is trusted only while the active TAB is itself the notebook it names; anything else refreshes. (The endpoint deliberately keeps taking no path - scoping it server-side is a separate change.) `refreshVariables` carries a `varsReqSeq` generation guard (the `kernelReqSeq`/`statusSeq`/`uploadSeq`/`diskSeq` convention): several probes can be in flight and responses are unordered, so an older namespace landing last would otherwise stick - which is also why **EVERY** LOCAL wipe goes through `wipeVariablesLocally()` (bump, then `variables = []`, the `markKernelStarted` shape): a restart/shutdown/venv-rebind that cleared the rows without bumping let a probe issued a moment earlier land after the wipe and repopulate the inspector with the dead session's (or dead INTERPRETER's) namespace, with nothing scheduled to correct it. The unit guard therefore asserts over the WHOLE file that the helper's own is the only raw `variables = []` - scoped per known call site, it let the venv rebind bypass the generation unseen. The helper also CLEARS `varsLoading`/`varsError`, because it issues no replacement request while `refreshVariables`' `finally` deliberately declines to clear the spinner once superseded - so without it a wipe landing on an in-flight probe left the Variables header spinning for good, a stale panel shipped inside the fix for stale panels. **The own-run `onRunEnd` path is untouched** - it still refreshes both immediately, so a single interactive run's result lands as soon as it exists. That immediacy is a deliberate choice and NOT a claim that the own path cannot burst: a human bulk run (**Run all / above / below / stale**) drives `LiveNotebook`'s sequential `runCodeIds`, whose per-cell `runCell` `finally` calls `onRunEnd`, so it DOES still probe once per cell - a known, accepted cost, softened (not bounded) by `inspectVariables` short-circuiting `busy` without executing once the next cell has claimed the kernel, which is a race rather than a guarantee. Coalescing it too is a separate product decision, since it would delay exactly the single-run feedback the immediacy exists for. **Kernel LIFECYCLE is covered by TAGGING the rows, not by enumerating events (`$lib/variablesNamespace`).** `/api/kernel/variables` reports the `path` + `session_id` it really read (the session the probe EXECUTED in), the shell keeps that as `varsNamespace`, and every lifecycle broadcast asks one question - is THAT namespace still alive: a `kernel:status` snapshot kills it when its notebook has no entry (shutdown, cull, rebind, a replaced server) or a DIFFERENT non-null session (restart, autorestart); `kernel:shutdown` now carries the `session_id` that died so an old event can never clear rows a newer kernel produced. Dead rows are wiped exactly as the own restart/shutdown does (no re-probe); a probe still in flight is superseded and re-read; the badge is re-read either way (`onNamespaceDeath`). Deaths are compared against the previous SSE snapshot (`lastSeenKernels`), NEVER against `kernels`, which `refreshKernel`'s unordered fetch also writes. A FOREIGN variables-wipe re-probes instead of wiping (a wipe keeps imports/functions/`spark`), told apart from our own by the `originId` the wipe route now threads onto `kernel:variables-wiped`. For the page's own actions all of this repeats what its handler already did. **Known gap, filed as a separate follow-up:** nothing re-probes the inspector when a notebook an agent worked in LATER becomes the active tab (there is no `$effect` on `activeNotebookPath`), so the panel shows another notebook's namespace until the next run or reload. The mount-time inspect is deliberately NOT gated on a KERNEL: `inspectVariables` short-circuits a not-started kernel server-side and only ever READS the status, so gating it on a kernel this page already knows about protected nothing and encoded the false premise that WE are the ones who boot it. (The one gate `refreshVariables` does carry is the notebook-LANGUAGE one, owned by the Mojo entry above - a Mojo notebook has no Python namespace to probe and its section is not rendered.) Covered by `tests/unit/shell-refresh-handlers.test.ts` (source guards on the call sites - the layer the pre-push gate sees, since e2e is absent from it - including that the foreign branch reaches the inspector only THROUGH the debounced helper, that the helper clears its pending timer, that the gate has no `return false`, and an anchor-proof on the mount block: its `blockAt` marker's `{` is INTERIOR, so a scan starting at the marker's last character opened at depth 0 and ran on into the next `onMount`'s SSE callback, silently unscoping the guard) + `tests/unit/variables-namespace.test.ts` (the lifecycle rule and the server tagging) + `tests/e2e/foreign-action-refresh.spec.ts` (a foreign restart, shutdown and wipe each clearing the panel, a lifecycle action on ANOTHER notebook leaving it alone, and the own card controls unchanged; a real `cellar mcp` agent drives every assertion and the observing page never acts; it counts the page's OWN requests by EXACT pathname - `/api/kernel` is a prefix of `/api/kernel/variables` - so an 8-cell agent batch is proven to collapse to a small handful of probes. **That bound is EMPIRICAL, not a pinned debounce count** - the trailing window collapses only the cells whose `run:end` land closer together than 300ms, and each cell costs a kernel round-trip plus a synchronous fsync'd `.ipynb` persist, so under pathological pacing the count really can approach one per cell; the assertion claims only "substantially fewer probes than cells" and is set with headroom (measured: **1** with the fix, **9** against an ungated + undebounced refresh, bound **6**), which are the figures to re-tune against rather than tightening it toward the measured 1 and inviting a flake. And a run in a notebook the user is not viewing is proven to probe ZERO times while the ungated badge refresh still fires, which is what shows a zero count is the gate rather than a missing event; each test sets itself up, because a failure restarts the worker into a brand-new workspace and the tab session is server-owned `.cellar/` state that a fresh browser context still restores).
- **Navbar** (`src/lib/Navbar.svelte`): app-menu dropdown → `src/lib/Settings.svelte` modal (theme toggle `dim`↔`cellar-light`, persisted through the per-project UI-state store as `cellar-theme` - `$lib/uiState`'s `getUi`/`setUi`, i.e. the server-owned `.cellar/` JSON, NOT `localStorage`, so it survives a relaunch on a new port - and applied via `<html data-theme>`; a persisted `nord` from before the color-theory pass is mapped forward to `cellar-light` on read); editor-style **wrapping** tab bar (tabs flow onto more rows via `flex-wrap`, never clip). Every tab (including the notebook) is closable and part of session memory; tabs carry file-type icons + a dirty dot; `preview` tabs render italic. **A notebook tab shows a run indicator while that notebook is executing/queueing a cell — background runs included** (a notebook running while you view another tab): the icon slot swaps to a `warning`-hued spinner (`data-testid=tab-running`) or a pulsing dot when queued (`data-testid=tab-queued`), matching the in-notebook running/queued affordances. **The indicator is a clickable button (`data-testid=tab-jump-running`, "Jump to running cell"): clicking it activates that notebook (if it isn't the viewed tab) and scrolls its running (or, failing that, first queued) cell into view** — the Navbar renders it as a *sibling* button of the tab-select button (a button cannot nest in a button) and rendered ONLY while `runState` is set, its `onclick` `stopPropagation()`s then calls `onJumpToRunningCell(tab.id)` so a spinner-click is an unambiguous jump while a click anywhere else on the tab still just selects it. The shell's `jumpToRunningCell(tabId)` (`+page.svelte`) activates the tab, `await tick()`s (a background pane has no geometry until active), then calls the notebook's imperative `revealRunning()` (`NotebookApiHandle`, `types.ts`). `revealRunning` reuses the follow-running-cell machinery (`ensureCellMounted` to unfold + mount, then `scrollElementIntoView` with `settle:'frame'` - it is a discrete target, not a streaming one) but is an EXPLICIT action, so it deliberately **bypasses the `follow` preference, the typing guard, and the imports-cell skip** the automatic follow-effect honors. The signal reuses the existing per-notebook run state already reported up to the shell — every mounted `LiveNotebook` publishes `onRunStateChange(path, runningId, queued)` **regardless of `active`** into `+page.svelte`'s `notebooksRunState` (keyed by the workspace-relative path = `tab.path`), so a background notebook's run is visible with no new plumbing; `+page.svelte` derives `tabRunState` (tab.id → 'running'|'queued') and passes it to the Navbar. Do NOT wire this off `runsInFlight`/`runBusy` — those are a single GLOBAL counter, not per-notebook. Covered by `tests/e2e/tab-jump-running-cell.spec.ts`.
- **Sidebar** (`src/lib/Sidebar.svelte`, foldable sections; whole sidebar collapsible + **drag-resizable** via the `sidebar-resizer` handle in `+page.svelte`, width persisted to `localStorage['cellar-sidebar-width']`, bounds 180–560px): **Files** (`src/lib/FileTreeNode.svelte`, recursive), **Git** (`gitSection` -> `src/lib/GitNotebooks.svelte`, directly under Files where VS Code puts Source Control; mounted only while the section is OPEN, and it ships collapsed, so a user who never opens it pays no `git` subprocess - see the Sidebar Git section entry below), **Kernels** (`kernelsSection` in `Sidebar.svelte`: **one card per kernel** — Cellar runs one kernel PER notebook (Phase 3), so the section renders `{#each kernelCards}` (a `KernelCard[]` derived in `+page.svelte`) with the **live kernel count** in the header. The card set = every LIVE kernel (from `listKernels()` via `/api/kernel` + the `kernel:status` SSE snapshot, so a closed-tab-but-alive kernel still shows) **plus the ACTIVE notebook** even with no kernel (a just-opened notebook reads "not started"). So shutting down a **non-active** notebook's kernel drops its card, while the notebook you're looking at always has one. Each card carries its own status badge + **Interrupt / Wipe variables (=clear the user variables, kernel stays alive) / Restart (=wipe namespace) / Shut down (=free the process, drop the card)**, all disabled until that notebook has a live kernel (`card.hasKernel`); the active one is dotted. **The card's NAME is a button that OPENS its notebook (`onOpenNotebook` -> `+page.svelte`'s `openKernelNotebook`), and three decisions there are load-bearing.** (1) **The click target is the NAME, not the row**: the row also carries four icon buttons, one destructive behind a two-step confirm, so a row-level handler would be a `role="button"` div needing `stopPropagation` on every control (a control added later silently inherits the open action) or an outer `<button>` wrapping them (invalid markup, unfollowable tab order); the name is `flex-1`, so it already spans the row minus the controls, and being a real `<button>` is what gives Enter/Space for free. It is ONE element across BOTH states - the open/closed `{#if}` split is what left a tab-CLOSED card an inert `<span>`, i.e. the one card the action exists for was reachable by neither mouse nor keyboard. (2) **It routes to `openFilePermanent`, the file tree's own double-click path**, never a second open implementation - so an open tab is promoted out of preview and focused rather than duplicated, and an already-ACTIVE one is a genuine no-op (assigning the identical `activeTabId` is not a reactive change, so nothing reloads). What it adds is a PRE-FLIGHT for the STALE card, and the reachable case is a RENAME: `POST /api/fs/op` calls `shutdownKernelsUnder` only on DELETE, so a rename/move rekeys the live document (`rekeyDocs`) and leaves the kernel registered under the OLD path - a card naming a notebook nothing can load. `GET /api/notebooks?path=` is the predicate, deliberately not a cheap `stat`, because LOADABLE is broader than ON DISK: a notebook whose file was removed outside Cellar still has its live in-memory document (closing a tab does not drop it) and that document is the user's unsaved state, so refusing to open it would strand exactly what they need back. **The CANONICAL notebook is the one path where that breadth is too wide, so it ALSO requires the file** - `loadDoc` MATERIALISES a starter document for it when the file is missing (which is what lets an empty workspace render a shell), so the load answered 200 for a canonical notebook renamed away and minted a tab holding one empty cell under the old name, whose first run wrote `notebook.ipynb` back to disk under the very name the user had renamed. The `stat` is asked BEFORE the load, so the click cannot even leave a starter document behind in `docs`. The narrowing is real and confined there: a canonical notebook whose file was deleted OUTSIDE Cellar is now refused too, where a non-canonical one still opens from its live document. A failure REPORTS on the shell's `onNotice` line and mints no tab; a `.py` whose check passed seeds `pyKindCache` with `ipynb`, since `resolveTabKind`'s own jupytext probe READS the file and would otherwise fall back to a text tab. **A REFUSAL is a claim the SERVER made, and only its OWN error shape is one** (`verdictReason`, asked of BOTH pre-flight replies so a third one cannot re-derive the rule): each route answers a verdict solely as `error(400, …)`, a JSON body carrying a string `message`, while a proxy 502/503, an HTML error page or a 404 from a mismatched route never reached the handler at all. Decided from `!res.ok` alone, those were reported with the refusal's own remedy - "Its kernel is still running - shut it down from the Kernels list if the notebook is gone" - which advises tearing down the process holding the namespace this whole action exists to give back, over a question nothing answered; the same defect one step earlier turned any non-2xx from the `stat` pre-flight into the flat claim "notebook not found". A non-verdict now says only that Cellar did not answer, names no remedy and, like every other failure here, mints no tab (the `unreachable` stance the thrown-fetch path already took, and the rule the export-target `writeFailed` split settled: a reply that is not this route's own shape landed no verdict). (3) **A card's NAME may never fall back to the kernel's own name** (`kernelCardName` in `kernelBadge.ts`): `KernelListEntry.name` is the KERNELSPEC (`python3` for every kernel Cellar starts), so a tab-closed card read `python3` - naming no notebook at all, on the card whose one job is to open one. It is the tab title when open, else the path's BASENAME (what `makeTab` titles a tab with, so a card and its tab read alike); the full path rides the row's tooltip, which is what tells two same-named notebooks in different folders apart. **The card is TWO LINES and its controls are ALWAYS VISIBLE - no hover/focus reveal of any kind, and that is the invariant, not a style choice: a control must be clickable EXACTLY when it is visible.** The name owns line 1; the `closed`/`not started` words, the RSS figure and the controls sit on a `flex-wrap` line 2 (`kernel-card-meta`), so at 180-200px the controls drop to a third line instead of squeezing anything - the card grows, it never overflows. The one-line row it replaced could not fit at all: at 180px it raised a horizontal scrollbar under `kernels-body` with the `closed` chip painted over the RSS figure, and at the 256px default the name got 0-7px. Its controls sat at `opacity-0` at rest, which is INVISIBLE BUT HIT-TESTABLE, so a click on a row's empty end fired Restart or Shut down (neither confirms). A floating hover-reveal (`absolute` + reserved gutter) was tried first and reverted after three rounds of the same class: clickable while invisible, inert while visible at the `transition-discrete` midpoint, overlap on hover-out, and a spacer forcing a horizontal scrollbar. Do not bring back any reveal - `opacity`/`visibility`/`pointer-events` toggles or `group-hover`/`group-focus` variants on the row. Covered in BOTH directions by `tests/e2e/kernel-card-narrow-width.spec.ts` (at 180/200/256px, at rest, hovered, hovered-out and keyboard-focused, with the wipe confirm armed: each control's `elementFromPoint` hit agrees with its computed visibility, plus a grid sweep of every card; also no overflow, no overlapping pieces, and the name width), mutation-checked against the reveal, a `pointer-events-none` cluster and the old row. **The stale-card refusal names the notebook workspace-relative** (`reasonWithoutServerPath` in `$lib/serverMessage`): `loadDoc` throws `'notebook not found: ' + abs`, so forwarding the server's message verbatim put an absolute server path in a user-facing toast. Same rule `GitNotebooks`' `unreadable` follows - it carries no message at all because the only thing that throw knows is an absolute path - except that here the REASON is worth keeping, so only the path is stripped. Covered by `tests/unit/kernel-card-open.test.ts` (the naming rule EXECUTED, plus source-SHAPE guards on markup and wiring - vitest runs without the SvelteKit plugin so neither component can be mounted, and e2e is absent from the pre-push gate, so those guards are its only evidence the surface exists; they are named and commented as shape guards precisely because they pass against dead code), `tests/unit/server-message.test.ts` (the path-stripping rule) + `tests/e2e/kernel-card-open-notebook.spec.ts` (real kernels: mouse and keyboard, an open notebook surfaced not duplicated, an active one proven not reloaded by counting the page's OWN `/api/notebooks` loads, the per-kernel controls unaffected in both directions, a renamed-out-from-under-its-kernel card reporting with no tab and no absolute path in the toast, the CANONICAL notebook renamed away refusing without re-creating `notebook.ipynb`, and a 502-with-an-HTML-body reply claiming nothing and advising no shutdown while a CONTROL run of the same click against the route's own 400 shape still refuses with its remedy). Live updates arrive via the `kernel:status` global SSE snapshot (published from `kernel.ts` on start / busy-idle flip / restart / shutdown / rebind, seeded on connect + replayed to late subscribers like `queue:changed`), so two notebooks running show two busy cards with no reload. **The broadcast is deduped + has a coalescing (debounced) fast path, and a busy/idle flip fans out ONLY while a USER (non-internal) run is in flight** (`NotebookKernel.userRuns`, gated in `kernel.ts`'s `statusHandler`; `scheduleKernelStatus` coalesces a run's flip burst, `emitKernelStatus` skips a byte-identical snapshot). A flip caused solely by an internal probe (inspect/variables) or a startup injection leaves `userRuns` at 0 and is suppressed - so those never flicker a card nor fan a redundant snapshot to every tab. Do NOT restore an unconditional `publishKernelStatus()` on every flip; user runs still broadcast busy→idle because `execute()` increments `userRuns` (and schedules a broadcast at the run boundary). Seeding a fresh tab is independent (the SSE route calls `listKernels()` on connect), so a deduped-away duplicate is safe. Overridable debounce window: `CELLAR_KERNEL_STATUS_DEBOUNCE_MS` (default 80ms). Startup injections (matplotlib-inline + DataFrame formatter + `%restart_python` magic + project-root `sys.path`) are coalesced into ONE silent `initKernel` exec, not four serial round-trips. Per-card control-in-flight is tracked in `actingPaths`. The notebook list is the `openNotebooks` prop derived from the shell's open notebook tabs in `+page.svelte`, so it updates live as notebooks open/close - not the server `docs` map, which lazily materializes the default notebook on SSR and would show a phantom; its `active` flag reads the same `activeNotebookPath` the Outline/Search sections use, so every sidebar section agrees on which notebook is active. **`activeNotebookPath` is null when no notebook tab is open** - it falls back to the canonical notebook only while that notebook *has* an open tab, because `notebooksCells` is seeded with its SSR cells and an unconditional fallback would fill Outline/Search from a **closed** notebook's stale snapshot (and dot it in the Kernels list). Null means "no active notebook": those sections render empty, which is the honest answer. The status→badge mapping lives in exactly one place, `src/lib/kernelBadge.ts` (`kernelBadgeClass`/`kernelStatusLabel`), imported by both `Sidebar.svelte` and the navbar badge in `Navbar.svelte` so the two cannot drift. Only `idle` may render green: `getKernelInfo()` forwards the kernel's status verbatim and the Jupyter status set also includes `restarting`/`autorestarting`/`terminating`/`unknown`, none of which mean "usable". Every card reads its badge from `card.info` through that one mapping, so a live and a not-started card can only differ where meant to. The top-level `/api/kernel` fields (+ the navbar badge / variables / Databricks panel) still track the **active** notebook's kernel via `kernelInfo`; the per-card list is separate. **Per-kernel resident memory (RSS)** rides the SAME `kernel:status` snapshot: each `KernelListEntry`/`KernelInfo` carries `memoryRss` (bytes|null), rendered compactly (`formatMemory` in `kernelBadge.ts`, e.g. `312 MB`) on each sidebar card (`data-testid=kernel-memory`) and next to the navbar badge. **Cellar has NO OS pid for a kernel** — `@jupyterlab/services` only holds the Jupyter `kernel.id`, and the kernel is a grandchild the sidecar spawns — so `src/lib/server/kernelMemory.ts` measures RSS **host-side, out-of-band**: one `ps -eo pid=,rss=,command=` scan (POSIX, KiB on macOS+Linux, the same pattern `instances.js` uses) matches each `kernel.id` in the process's `-f …/kernel-<id>.json` connection-file argument and reads its RSS. Measured from the OS, NOT via an in-kernel probe, precisely because an `execute` probe queues behind a running cell and could never report memory for a BUSY kernel (the array-allocating case the figure exists for). `kernel.ts` polls (`CELLAR_KERNEL_MEMORY_POLL_MS`, default 4s, unref'd, self-stops when no kernel remains), rounds to whole MiB (so a stable idle kernel doesn't churn the deduped broadcast), and re-publishes only on change. Main process RSS only (children excluded — Spark work runs on the remote cluster). The navbar figure is scoped to the ACTIVE notebook's OWN list entry (`activeKernelMemory` in `+page.svelte`, no fallback to `kernelInfo.memoryRss`) and gated by the badge's `started`, so it never shows a stale/other-notebook value beside a "not started" badge. Pure parse + format covered by `tests/unit/kernel-memory.test.ts`. **Kernel-status writes are generation-guarded** (`kernelReqSeq` in `+page.svelte`): `/api/kernel` responses are unordered, so a read issued before the kernel booted can resolve *after* the first run started and clobber `kernelInfo` back to not-started - the last response to *land* would win, not the last one issued. Every write bumps the generation; a response applies only if nothing newer landed while it was in flight. That guard is what lets `onRunEnd` decrement `runsInFlight` **synchronously** rather than awaiting a status round-trip (which would strand the counter if the refresh threw). `onRunStart` asserts the kernel started optimistically via `markKernelStarted()`, which also bumps the generation to supersede in-flight reads - so the card never flashes not-started while a first run boots the kernel), **Databricks** (`databricksSection` -> `src/lib/Databricks.svelte`; mounted lazily on first open, then kept mounted+hidden so collapsing does not discard the connection / cluster list / half-expanded catalog tree - and so a user who never opens it never pays for its python status probe), **Connect an agent** (`agentSection` in `Sidebar.svelte`, reframed around the zero-config flow: leads with an agent-ready banner when a project `.mcp.json` registers the `cellar` stdio server — detected server-side in `+page.server.js` load through **`harnessState('claude', …)`** - never a second copy of "is this entry ours" (its own `…cellar?.command === 'cellar'` test ignored `args`, so the banner claimed agent-ready over an entry the very next launch would rewrite), still degrading to false on any read/parse trouble rather than throwing during SSR - surfaced as `data.mcp.projectConfigured` ALONGSIDE `projectManaged` (`isHarnessAllowed('claude', …)`), because the two are INDEPENDENT and the banner may only claim the every-start repair when the harness is really managed: `cellar harness remove claude` deliberately leaves the entry in place, so a configured harness can stop being maintained, and the unconditional "checked and repaired on every start" copy then promised a self-heal that would not happen - the assert-more-than-was-verified defect. Unmanaged, it says what is true (the entry is there, Cellar is not maintaining it, `cellar harness add claude` puts it back under management), in the SAME banner shape. It is reported only for a managed harness, and its copy names the remedy that actually applies (restart without the flag, NOT `harness add`).   - **`gitCommitAt(absDir)` answers for a DIRECTORY, where every other reader in `git.ts` answers for a file or for the workspace.** Three CONCURRENT spawns (`symbolic-ref`, `log -1 --format=%H%x00%h%x00%ct%x00%an%x00%s`, `status --porcelain`) - NUL-separated so a subject carrying a tab or a pipe survives verbatim, and the raw `%ct` epoch so no locale/timezone parsing rides to the browser. Cached per directory on the SAME `cacheSig` (its own git index mtime - `preflight`'s `--absolute-git-dir` gives a worktree's own `.git/worktrees/<name>/`, not the main repo's) but at **`STATUS_TTL_MS` (1.5s), not `CACHE_TTL_MS`**, and cleared by **`invalidateGitStatusCache`**: the `dirty` bit answers to an UNSTAGED working edit, which touches neither the index nor anything else keyed on - exactly the blind spot `gitStatus()` uses that tighter backstop and that hook for. **A positive `preflight` is memoized for the process lifetime**, so a root worktree removed since then would report a repo with no branch, no commit and no changes; `buildDirCommit` therefore returns `notARepo()` when ALL THREE calls failed, discriminating on `status` (a clean checkout answers an EMPTY string, never null). Unborn HEAD (`log -1` fails, `symbolic-ref` succeeds) is `isRepo:true` with a branch and no commit - **not** detached, which is the opposite case (no branch, but a commit). A failed `status` is NOT reported dirty: this drives a visual marker, and claiming uncommitted work nothing observed is the wrong direction. **The status is SCOPED with a `-- .` pathspec, so `dirty` uniformly means "uncommitted changes in the DIRECTORY this kernel runs in"** - the same convention the file tree in this very sidebar follows, so the two can never contradict each other. Unscoped it walked the whole repo, so a workspace that is a SUBDIRECTORY of a larger one (`cd repo/analysis && cellar`) lit the marker for changes elsewhere in that repo, including paths the tree deliberately drops: "uncommitted changes" beside a visibly clean tree. For a worktree root it is a NO-OP (a root IS its checkout), which is what makes it uniform rather than a special case. Deliberately **no `pre.prefix` strip** to go with it, unlike `runStatus()`/`parse()`: those strip because they must turn porcelain's repo-root-relative paths into workspace-relative KEYS, while this reads only EMPTINESS and never looks at a path, so once the pathspec has scoped the walk a strip would be dead code. **`gitRefAt` deliberately KEEPS its own cheap two-spawn path rather than narrowing this one** (`symbolic-ref` + `rev-parse --short`, uncached): it answers the notebook root picker and MCP `list_roots`, once per root, and neither needs the dirty bit - so narrowing it would put a whole-tree `git status` walk per root on that path, on the process carrying the kernel websockets and the SSE fan-out, for a value nothing reads. The few shared lines are the accepted cost of two questions at two prices; do not "unify" them.

A declared-but-unusable root (missing, a file, escaping the workspace) returns the RESOLVER'S OWN refusal on `error` with no commit, because that is the state a RUN of that notebook is about to refuse - degrading to the workspace's commit would claim a checkout the notebook is not on, the exact silent degrade `notebookRoot.ts` exists to prevent. **A notebook whose DOCUMENT cannot be read at all is a DIFFERENT fact and rides its own structural flag, `unreadable`, never that `error` channel** (deleted/renamed outside Cellar with its tab still open, so `getNotebookRoot` -> `docFor` -> `loadDoc` throws): with no document there is no declaration to report, so routing it through `error` left the row rendering `root ?? It refetches on mount, when the open-notebook set changes (a `pathsKey` signature, not array identity), on `fsRefreshSignal`, on **any** notebook's `notebook:root` event, on `sse:open` (that event is NOT replayed to a late subscriber, so a reconnect would otherwise strand a stale commit) and on window `focus` - a commit made in a terminal notifies nothing. Generation-guarded (`seq`, the `statusSeq` convention) since focus / a root change / a tab opening can each be in flight at once - **and COALESCED on top, keyed by the query it would send** (`createCoalescedReload` in `src/lib/coalescedReload.ts`, the ONE place that rule lives - the panel keeps no private copy), because the seq guard discards a superseded REPLY without stopping its request while `gitCommitAt` writes its cache entry only after its three spawns finish, so genuinely concurrent triggers (mount racing `sse:open`; focus racing an `fsRefreshSignal` bump) all missed it and each re-spawned three `git` processes per distinct root; keyed rather than blanket, so a request whose notebook set has since changed is never handed back as this one's answer. **PLAIN single-flight is the wrong primitive here and must not come back**: handing the in-flight promise to a call that arrives DURING a run answers the new trigger with a reply issued BEFORE the change it announces, and nothing schedules another read - so a `notebook:root` landing while an unrelated window-focus read is still out left the old checkout on screen until some later, independent trigger, and the generation guard cannot help (it only decides which reply may be WRITTEN, and there is exactly one reply and it is stale).
