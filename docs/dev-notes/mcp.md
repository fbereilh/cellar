# MCP agent surface: tools, images, ergonomics, sessions, user-activity digest, run tools

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **MCP agent interface.** `src/lib/server/mcp/` — the agent surface (spec §4). `service.ts` = transport-independent tool logic (section tree from markdown headers, tiered/summarized outputs, visibility filtering, UUID-addressed read/write/execute); `server.ts` = `McpServer` + Streamable HTTP transport on its own port (`CELLAR_MCP_PORT`, default 39587 but the launcher now allocates a **free** port per instance so concurrent `cellar` runs don't collide, path `/mcp`), started once from `src/hooks.server.js`. Runs **in-process** in the SvelteKit backend so it shares the live `notebook.ts` doc + `kernel.ts` — restarting the kernel can't drop the MCP session/document (the #1 requirement). Per-cell hide/show via `metadata.cellar.hidden_from_agent` (allowlisted, visible by default) is honored in every map/read/search/section/result. Kernel service methods `restartKernel/interruptKernel/kernelStatus` live in `kernel.ts`; richer read/write (`listCells/getCell/setVisibility/moveCellTo`) in `notebook.ts`. **Coherence doctrine:** `server.ts` passes an `INSTRUCTIONS` house-style string as the `McpServer` `instructions` (advisory, delivered once at connect: imports-at-top convention, check `kernel_state` first, continue the story via `get_notebook_map`, structure with markdown) + a matching `cellar_notebook_style` prompt. The read-group **`kernel_state`** tool returns the live namespace bucketed into imports/functions/classes/variables (types, shapes, dataframe columns); it reuses `inspect.ts`'s shared probe (`kernelState()`), short-circuits to `{started:false}` when `kernelStatus()` is `not_started` (no force-boot) and to `{started:true,busy:true}` when the kernel is busy (never queues a probe behind a running cell), and dedupes imports by statement. Its `session_id` is the epoch the **probe itself executed in** (taken from `execute()`'s `kernel` event, never sampled around the `await`), so it always identifies the very session the returned namespace was read from; a restart between probe and reply yields `stale:true` rather than silently pairing an old epoch with a new namespace. `inspectVariables()` (sidebar) shares that probe but projects to the original `{name,type,shape,preview}` shape. **Live vs persisted execution (agent-safety invariant).** A cell's `outputs` live in the `.ipynb` and outlive the kernel *and* the server process, so they can NEVER answer "did this run in the kernel I'm talking to" — conflating the two let an agent trust a saved `run_status:"ok"` and build on variables that were never defined this session (→ `NameError`). `kernel.ts` owns a monotonic **session epoch** (`kernelSession()`/`currentSessionId()`), bumped on first start, `restartKernel()`, `rebindKernel()`, and jupyter's own `autorestarting`. The epoch bumps on the **failure** paths too (a `finally` in `restartKernel()`, before the replacement start in `rebindKernel()`): once the REST restart is issued the namespace is gone even if the websocket reconnect rejects, and the epoch is monotonic + opaque, so over-invalidating is always the safe direction while a missing bump re-opens the `NameError` trap. The `autorestarting` handler is identity-guarded (`currentKernel === kernel`) so a late emission from an **outgoing** kernel cannot bump the epoch of the one that replaced it, and it re-injects `initKernel()` for parity with `restartKernel()` (an autorestart clears the namespace *and* the matplotlib backend); `rebindKernel()` disconnects the handler on teardown. Both run entry points (UI `/run` route + MCP `runCell`) stamp the epoch the run **started** in onto the runtime-only `metadata.cellar.lastRun` — captured from `execute()`'s `kernel` event and **never re-read via `currentSessionId()` on the error path**, since an autorestart mid-run bumps the epoch and would otherwise stamp the *new* one, marking a cell that never touched the fresh namespace as live (it stays null when no kernel ever started, so `ran_this_session` is false). The stamp is runtime-only in **both** directions, through one shared helper (`clean.ts`'s exported `stripRuntimeMeta`, which strips every runtime-only `cellar` key - `lastRun`, `editedAt`, `importBindings` - and whose two halves must stay in lockstep): `clean.ts`'s `cleanCell` strips `lastRun` before disk (**never persist the epoch**) and `ipynb.ts`'s `deserialize()` strips it on read, so a hand-edited or externally-authored `.ipynb` cannot forge `ok_session` (epochs are small monotonic ints, so a literal `session: 1` would otherwise match the first real kernel). The stamp may only ever originate from an in-process run. `service.ts` derives `ran_this_session` + a split `run_status` (`ok_session`/`error_session` = executed against the live namespace; `ok_persisted`/`error_persisted` = saved output from a prior session; `unrun`; `error_kernel_unavailable`) from that stamp, never from `outputs.length` — a cell can run successfully and emit nothing (`lp = load()`). It checks the recorded status **positively** (`=== 'ok'`), so jupyter's `abort` reply degrades to `error_session` rather than a false `ok_session`. The epoch-equality rule lives in exactly one predicate (`isLiveSession`, wrapped by `ranThisSession`) - never re-derive it inline. **`error_kernel_unavailable`** covers the third case: `execute()` threw before emitting its `kernel` event (sidecar unreachable), so no session exists to stamp and the synthesized `CellarError` would otherwise fall through to `error_persisted` - telling the agent to ignore, as leftover, a failure the run it just requested raised seconds ago. Both run entry points record a `kernel_unavailable:true` marker on `lastRun` (runtime-only, so it rides the same strip-on-read/write guard); `runStatus` and `get_errors` surface it, but **only while the kernel is still unreachable** (`sid == null`) - the marker is *derived*, never trusted as sticky truth. That gate is load-bearing: the boot race (MCP serves before the sidecar finishes starting, the first `run_cell` is rejected, the sidecar comes up moments later) would otherwise leave one cell claiming a LIVE kernel-down failure forever, since only re-running *that* cell clears the flag - the same mislabel with the sign flipped. Once a kernel exists the cell falls back to `error_persisted`, which is honest. It is a status about the **run attempt** and is orthogonal to `ran_this_session`, which stays false - nothing executed in any session. A multi-cell read (`readCells`/`readSection`) samples the epoch **once** per response, so a restart landing mid-loop can't classify one payload against two sessions. **Every** read tool that surfaces saved outputs carries `ran_this_session`, `get_full_output` and `search_cells` included, so no tool hands an agent a stale output with no live/persisted signal; `get_notebook_map` carries a `kernel` header and `get_errors` flags stale errors. `execute()`'s `internal:true` opt-out keeps `inspect.ts`'s probes out of `execs_this_session`. Note the deliberate scope: `ran_this_session` means "this cell executed in this epoch", **not** "the cell's current source ran" — editing after a run does not clear the stamp.
- **Figures reach the agent as REAL images, not a placeholder (`src/lib/server/mcp/image.ts`).** An image cell-output (a matplotlib figure) is returned to an MCP agent as an actual **image content block** (`{type:'image', data, mimeType}`), so the agent can SEE the chart it just drew. Before, every path returned only the text marker `[image/png, 978×536, 44 KB]` and an agent authoring plots was blind to its own work - the reported workaround was a throwaway `fig.savefig()` cell, `Read` the PNG, delete the cell. **The split (deliberate, it is the cost policy):** the **run** path (`run_cell`, and therefore `add_and_run` - the single round-trip write-run-see loop) and **`get_full_output`** ship images; the **scan** paths (`get_notebook_map`, `read_cell(s)`, `read_by_location`, `read_section`, `search_cells`, `get_errors`) keep the enriched, image-token-free placeholder (`imagePlaceholder`) - a read over 40 cells must not dump 40 figures. A **batch** run (`run_cells`/`run_all`/`run_stale`/`run_range`) does not inline either (its records are deliberately compact): each record carries **`has_image:true`** and the figure is one `get_full_output(id)` away; `runCell`'s `skipImages` opt-out is what keeps a batch from decoding+resampling N rasters only to discard them. **`buildImageBlocks` in `image.ts` is the ONE policy seam** - every tool that ships images goes through it, so the bound cannot drift: PNG downscaled to `IMG_MAX_EDGE` (768px longest edge, ~1600 image tokens → ~590; `size:'full'` still returns the ORIGINAL bytes), at most `MAX_IMAGE_BLOCKS` (4) per **automatic run** result, and a decoded-byte/per-edge SHIP ceiling (`IMAGE_BLOCK_MAX_BYTES`, `MAX_IMAGE_EDGE_HARD`) checked by `withinHostLimits` on the raster actually EMITTED, so an oversized `full` image is downscaled to FIT rather than shipped. Nothing is dropped silently: whatever is declined is reported in `images_omitted` with a reason + the route to it - and **that route is real, which is why the 4-cap is caller-scoped**: `getFullOutput` (an EXPLICIT per-cell request) ships up to `MAX_FULL_OUTPUT_IMAGE_BLOCKS` (20), far past the run result's four, so the `limit` note is not a promise nothing keeps. **But every bound stays FINITE - an earlier `limit: Infinity` there was wrong** and must not come back: each image over `IMG_MAX_EDGE` is a synchronous decode + resample + re-encode on the shared event loop that also streams SSE frames and services every other kernel and MCP session, so an unbounded pass over a cell that plotted in a loop (30-50 figures is ordinary) stalls the whole process for seconds and, on `size:'full'`, returns tens of MB. Two AGGREGATE budgets bound one result alongside the count: `IMAGE_RESULT_MAX_BYTES` (8 MB of shipped raster - the per-image `IMAGE_BLOCK_MAX_BYTES` bounds ONE, nothing else bounded N) and `MAX_RESULT_DECODE_PIXELS` (40 MP of SOURCE pixels handed to the decoder - the CPU sibling, since a downscaled output's size says nothing about what it cost to produce; charged BEFORE the decode whenever the cost is knowable, so a decode that would blow the budget never runs, and charged even when the block is then declined on bytes). **NO path may decode uncharged, and the two leaks that made that untrue are both closed:** a raster already inside `maxEdge` **on dimensions the caller already parsed never reaches `PNG.sync.read` at all** (`downscaleImageForBlock` early-returns those dims - decoding a whole image merely to re-read a width and height it was handed allocates the w×h×4 buffer and discards it, and `willDecode` reported that as no-decode, so it was free); and a raster whose header would NOT parse (`dim === null`, which nothing upstream can pre-charge and `exceedsDecodeBound` cannot refuse) is charged AFTER the fact from the raster pngjs really read. `ScaledImage.decodedPixels` is **required, not optional** - every return path has to STATE its cost, so a future path cannot quietly omit it - and `buildImageBlocks` refuses to even START such an unpredictable decode once the budget is spent, which bounds the overshoot to a single image. **That refusal is gated on a decode really being about to happen, through `willDecode` on BOTH paths** (which therefore reports an unparseable-header PNG on the DEFAULT path as a decode - `downscaleImageForBlock` skips both early returns without dims and does reach `PNG.sync.read`; a predicate that is false exactly where a decode happens is a landmine in a module whose invariant is that none goes uncharged) - only a PNG is ever handed to pngjs, so an unreadable-header JPEG/GIF, or a `full` PNG already inside the host ceilings, costs the decoder NOTHING; withholding one on a spent pixel budget charged a figure for CPU that was never going to be spent, which is the mirror-image error of an uncharged decode. **The pixel budget is charged on the `size:'full'` path too, and that is not a detail** - `full` skips the ROUTINE downscale, but `fitImageBlock` still falls back to a real decode+resample whenever a full-size original breaches a host ceiling, and that fallback emits a SMALL block, so the byte budget cannot see it either. `willDecode` therefore asks "will this decode", not "is this the default path" (`!withinHostLimits(...)` on the `full` branch); without it one `get_full_output(size:'full')` over a cell of oversized figures ran up to 20 decodes of up to 32 MP each, entirely uncharged - exactly the event-loop stall the budget exists to bound. **What makes all three capability-free is the ROUTE, not lifting them**: every `limit`/`budget` omission names `get_full_output(id, images_from: <that output_index>)`, a real param that resumes at exactly the figure which did not fit - so a hundred-figure cell is PAGED, never truncated. **A CONSECUTIVE run declined by the SAME aggregate bound collapses into ONE `images_omitted` entry** carrying `count` + that resume index, because a `limit`/`budget` decline is one bound hit once and says nothing about the individual figure: 60 loop-plotted figures used to return 4 blocks and 56 near-identical ~105-char notes (~8 KB) on the very path the 4-cap exists to keep cheap, and because an `images_from` page re-emits the shrinking tail, the omission text over a full page-through was QUADRATIC in the number of figures. The nothing-declined-silently contract still holds literally - the collapsed entry says HOW MANY were declined and names the call that resumes at the first of them. **`count` means CONSECUTIVE outputs, so the collapse is tracked by an `openBound` entry that ANY other outcome clears - never by "the last omission has the same reason"**: both budgets are `spent + cost > max` tests, not latches, so a large figure can be declined and a smaller FOLLOWING one still fit and ship; merging across that shipped image would make one entry claim a run that COVERED an output the result actually delivered, which is the very promise the agent pages on. A per-figure reason (`unsupported_mime`, `too_large`) names a specific figure AND a specific cause, so it is never merged - and it breaks a run too, since the images either side of it were declined for unrelated reasons. **The pixel bound is checked BEFORE any decode (`MAX_DECODE_PIXELS`, 32 MP, via the header-only `exceedsDecodeBound`), and that ordering is the point** - `PNG.sync.read` allocates width×height×4 up front, so one pathological figure (`plt.figure(figsize=(100,100), dpi=300)` → 30000×30000) would ask pngjs for gigabytes, and a genuine OOM is not catchable: it kills the single shared Node process, taking every notebook's kernel websocket, every SSE stream and every other agent session with it. Such a raster is omitted `too_large` and keeps its text placeholder, never decoded (the guard sits in BOTH `fitImageBlock` and `downscaleImageForBlock`, so no future caller can route around it). **That pre-decode refusal is TOTAL PIXELS ONLY, never the per-edge `MAX_IMAGE_EDGE_HARD`** - `w×h×4` is the entire allocation risk, and a single long edge costs nothing to decode: a stacked-subplot / FacetGrid figure (`plt.subplots(30,1,figsize=(8,60),dpi=150)` → 1200×9000, ~11 MP) is past the edge ceiling yet far under 32 MP, and MUST be decoded, downscaled to 768px and shipped. Refusing it pre-decode returned a placeholder for a figure that fits perfectly - do not re-conflate the two bounds. The edge ceiling is enforced where it belongs, on the EMITTED raster (`withinHostLimits`), which a downscale always satisfies; a non-PNG cannot be resampled, so an over-edge JPEG/GIF is still declined there. **`INLINE_IMAGE_MIMES` is an ALLOWLIST, and that is load-bearing** - an LLM host accepts a bounded raster set and REJECTS the whole tool result on anything else, so an `image/svg+xml` figure (matplotlib's svg backend) must keep its text placeholder or it would fail the very call that drew it. **`image/webp` is deliberately OUT** for the sibling reason: the module ships only a raster it has VERIFIED is inside the ceilings, and `imageDimensions` has no webp parser, so an oversized webp would pass the dimension check vacuously (and could not be resampled to fit) - re-adding it means adding a VP8/VP8L/VP8X header read first. Same reason `blockMime()` normalizes the unregistered `image/jpg` bundle key to `image/jpeg` when BUILDING the block: the output is still shown, but the emitted `mimeType` must be a type the host accepts. When ONE bundle carries several rasterizations of a figure (matplotlib `figure_formats={'png','svg'}` emits both), `service.ts`'s `imageKey` prefers an INLINABLE key over the merely-first one, so the agent gets the PNG rather than an `unsupported_mime` decline - and because the placeholder derives from that same function, `images[i].mime` and `outputs[i].image` can never disagree for one `output_index`. `has_image` on a batch record is decided by the policy's own header-only predicate **`canInlineImage`** (not merely by the mime), so the flag means what its description promises - a figure `get_full_output` can actually SHOW, never a round trip that returns the same placeholder. **A cell hidden from the agent ships NO image** - `runCell` gates `images` on `isHidden(cell)` beside the existing `hidden:true` annotation, because a picture reveals far more than the outputs TEXT a hidden cell has always returned (that text is pre-existing behavior and stays; this must not widen what `hidden_from_agent` discloses), and `getFullOutput` refuses a hidden cell outright - so without the gate the two tools disagreed about what the flag withholds. Whether a hidden cell may RUN is unchanged, and the batch path already skips hidden cells entirely. **Layering:** `service.ts` (transport-independent) decides WHICH images ship and at what size and returns them on `result.images`; `server.ts`'s `textWithImages` lifts the base64 out of the JSON text into image blocks - never both, or the same raster is billed twice. Every output still appears in `outputs` with its placeholder, and each image names its `output_index`, so the agent knows which output the picture is. **Two cost rules on the way there, both load-bearing because they run for every image of every result:** the base64 payload is read with `asText`, NEVER `String()` (nbformat stores a raster as an ARRAY of lines, and `String(['ab','cd'])` comma-joins it into base64 a strict host validator rejects - failing the ENTIRE tool result, the exact failure the ceilings exist to prevent) **and the emitted payload is whitespace-stripped once at the BUILD site** (`base64Payload` in `fitImageBlock`'s `build`, not in any one branch): nbformat splits with `splitlines(True)`, so the line terminators SURVIVE that join, and a terminator is the same class of non-alphabet character as the comma - every non-re-encoding path (`size:'full'`, any JPEG/GIF, a PNG already inside `maxEdge` - the common 640×480 matplotlib default - and the decode-failure fallback) ships the payload verbatim, which is why the strip belongs where the block is built. It copies, unlike `base64Bytes` which counts in place, and that is affordable for exactly that reason: at most `limit` blocks per result, versus several times per image; and `imageDimensions` decodes only a bounded PREFIX of the base64 (`HEADER_B64_CHARS`, with a larger window for JPEG, whose SOF sits past the APPn segments) rather than the whole raster - allocating megabytes to read a 24-byte header, several times per image, is what made the "header-only, costs nothing" claim false. `base64Bytes` counts in place for the same reason (a `replace(/\s+/g,'')` copied the whole payload). Parsed dims are THREADED through `exceedsDecodeBound`/`downscaleImageForBlock`/`withinHostLimits`/`fitImageBlock` instead of re-derived at each, and they are also the FALLBACK for a block's own `width`/`height`: those used to be a side effect of the downscale decode, so a `size:'full'` block and every JPEG/GIF carried no pixel size while a downscaled one did - metadata we already had in scope. `clean.ts` is untouched: this is a read-time projection, so the `.ipynb` and the UI render are unaffected. Covered by `tests/unit/mcp-image-blocks.test.ts` (policy + transport) + `tests/unit/mcp-image-downscale.test.ts` (downscale + the default-vs-full contract) + `tests/e2e/mcp-agent-sees-figures.spec.ts` (real matplotlib → `add_and_run` over a real `cellar mcp` bridge → a viewable image block, with the human's browser still rendering the same figure).
- **Agent-ergonomics conventions on the MCP surface (handles everywhere, batch writes, bounded inspection, cheap schemas).** Four rules that came out of real agent feedback and now bind every future tool. (1) **Every cell reference is a HANDLE, including a DESTINATION.** `move_cell` used to take only an absolute `position`, so an agent had to fetch `get_notebook_map` just to learn an index for a move it could already name; it now takes `after_id`/`before_id` (`position` still works and means *the index the cell ends up at*, which is exactly what `moveCellTo` wants). The off-by-one lives in ONE place, `service.ts`'s `destIndex`: `moveCellTo` inserts into the array AFTER the cell is lifted out, so an anchor BELOW the moved cell shifts up by one - do not re-derive that at a call site. An anchor equal to the moved cell is refused (`same_cell`), never silently treated as a move. The anchor goes through `asFullId` in the service as well as `resolveOne` at the boundary, keeping the documented symmetry that the ids this layer EMITS can be fed straight back into the ids it ACCEPTS. (2) **A repeated write gets a BATCH tool, not a loop of calls** - `delete_cell` became **`delete_cells(ids)`** (mirroring `read_cells`: a single-element array deletes one cell, so there is one tool, not two schemas). Addressing is **all-or-nothing** - every ref resolves before anything is deleted, so a typo in the fifth handle cannot leave the first four gone - duplicates collapse, and the whole batch takes **ONE** `checkpointBeforeDestructiveAgentAction` - never throttled, so the human's undo restores the state before the pivot rather than after seven eighths of it. A batch that would delete EVERY cell is **refused** by the shared non-empty invariant (`deleteCells`), and `removeCells` looks that refusal up through `deleteWouldEmptyNotebook` BEFORE checkpointing, so a refused batch mints no snapshot - see the Multi-cell selection entry. **`clear_outputs(ids?)` is the second application of that rule** (`server.ts` registration -> `service.ts` `clearOutputs` -> `notebook.ts` `clearOutputsForCells`): same handle addressing, same all-or-nothing resolve, same ONE checkpoint, and - like `deleteCells` and for the same reason - ONE document write plus one `cell:cleared` per cell, never a loop over the single-cell `clearOutputs` (which persists the whole `.ipynb` per cell; a 300-cell clear-all would be 300 whole-file writes). Its ADDRESSING rule is the one thing a future edit must not blur: **omitting `ids` clears EVERY cell, an explicitly EMPTY array is a REFUSAL** - an agent whose computed id list came out empty must never wipe the notebook by accident, mirroring `delete_cells`' empty-batch refusal. Only cells that HAVE outputs are touched (the UI `clearAll` guards the same way), so an output-less cell is a genuine no-op: not listed in `cleared`, no event, and a batch that would change nothing takes no checkpoint and writes nothing. **`lastRun` is deliberately untouched**, matching the UI clear exactly: `run_status`/`ran_this_session`/staleness derive from the run stamp and NEVER from `outputs.length`, so clearing output flips only `has_output` - do not "fix" this by also clearing the stamp. **Three further rules govern what the RESULT may CLAIM.** (a) A cell whose run is IN FLIGHT is **skipped, never cleared**, and named in `skipped`: an agent's call is a ONE-SHOT REPORT rather than a live view, so reporting a cell as cleared while its run goes on emitting describes a state the very next flush has already moved past. **The older reason - that the next accumulator flush (`setOutputsLive`) and `run:end` (`setOutputs`) would write the outputs straight back - NO LONGER HOLDS and must not be restated**: the shared clear path truncates that run's accumulator (`truncateActiveRunOutputs`, see the notebook-toolbar entry), so a clear of a running cell now STICKS and only post-clear output is persisted. The divergence from the UI clear is therefore a deliberate choice of SURFACE, not a mechanism - do not "reconcile" the two. "In flight" is read from the **run queue's `running` entry** for that notebook (`queueStateFor`) - the in-memory outputs cannot answer it, since `setOutputsLive` keeps them current mid-stream and a mid-run buffer is indistinguishable from a settled one - and the skip is checked BEFORE the has-outputs guard, since it is about the cell being in the kernel's hands, not about whether its buffer happens to be empty right now. A merely QUEUED cell has emitted nothing yet, so clearing it is honest and it is NOT skipped. (b) The **clear-all form filters a cell hidden from the agent out of `cleared`/`count`/`skipped`** while still clearing it: it addresses cells the agent never named, so returning a hidden handle would disclose both the cell's existence and its address, which `hidden_from_agent` ("honored in every map, read, search, section and result") forbids - `run_all` draws exactly this line (it RUNS hidden cells, it just omits them from results), and `count` is `cleared.length` AFTER the filter so the two cannot disagree. An EXPLICIT id list is deliberately NOT filtered - those handles came from the agent, so echoing one back discloses nothing new, the same reason `delete_cells` reports named cells. (c) **UNDO IS PROMISED, because the shared checkpoint rules now keep that promise for THIS tool** - a clear takes the DESTRUCTIVE-tier snapshot (`checkpointBeforeDestructiveAgentAction`), which is never throttled and never caps the outputs it stores, and it REFUSES before clearing anything when that snapshot could not store them, with `allow_unrecoverable:true` as the knowing opt-out. The two tiers, what decides which one an action takes and why the cap and the throttle belong to only one of them live in the checkpoints entry below - do not restate them here. **`delete_cells` IS the same case and is fixed the same way**, as are the `set_cell_type` conversions that drop outputs and a `consolidate_imports` sweep that would delete an output-carrying cell. What is unchanged is the rule about what the RESULT may claim: it carries **`undo: {outputs_recoverable:false, reason}`** whenever the checkpoint the service just took cannot give the outputs back - now reachable only on the WAIVED path, and reported the same way by all four of those tools rather than by this one alone - read off the `CheckpointMeta` that call already returns, so it changes no checkpoint behavior; both the flag and the description's honesty are pinned by tests so the over-claim cannot regrow. Finally `clearOutputsForCells` guards its persist with `doc.jpFormat` exactly as `setOutputs` twenty lines above it does - and the SINGLE-cell `clearOutputs` the UI drives carries the same guard, so which surface the human used cannot decide what the disk does: a `.py` notebook carries no outputs on disk, so the write would be a blocking `spawnSync` jupytext conversion producing byte-identical bytes and churning mtime - the `cell:cleared` EVENTS still fire unconditionally, so every open tab clears. Covered by `tests/unit/mcp-clear-outputs.test.ts`. (1), (2) and `clear_outputs` are covered by `tests/unit/mcp-move-delete-ergonomics.test.ts` / `tests/unit/mcp-clear-outputs.test.ts` (real service + notebook: move by handle with the `destIndex` off-by-one and the `same_cell`/anchor-both refusals, batch delete all-or-nothing + one checkpoint, clear by handle + clear-all + the empty-list refusal + the `lastRun` invariant + the running-cell skip against a REAL queue ticket + the hidden-cell filter in both directions + a `.py` doc clearing with no jupytext write + the refusal BEFORE clearing when the pre-clear checkpoint cannot store the outputs, the `undo` warning present on the WAIVED path and ABSENT on an ordinary clear that really holds them + the description's honesty and its length bound) alongside `tests/e2e/mcp-ergonomics.spec.ts` (real wire). (3) **`inspect_variable` is bounded on every axis a value can grow along, and SAYS which bound bit.** A row count alone does not bound a head: ten rows of a 1024-float embedding column is ten thousand numbers (the reported bug - one call cost thousands of tokens). So `inspect.ts` exports `INSPECT_HEAD_ROWS`/`INSPECT_ARRAY_HEAD_ROWS`/`INSPECT_ARRAY_ITEMS`/`INSPECT_STR_CHARS`/`INSPECT_HEAD_BUDGET`/`INSPECT_ARRAY_REPR_CHARS` and interpolates them into BOTH the python probe and the tool description, so prose and policy cannot drift (the `IMAGE_DOC` precedent). The probe's `_cellar_arrayish` decides the row cap **before** serializing (`to_json` on ten array rows materializes the very payload being bounded) and `_cellar_shrink` bounds each value; the shrink is applied **per RECORD, never over the record list** - shrinking the outer list would cap the ROW count at `INSPECT_ARRAY_ITEMS` and quietly shorten an ordinary scalar head. A dict keeps EVERY key (a spent budget yields `…`, never a missing column - an absent column reads as a frame that does not have it), an array truncation carries `… N more (M total)`, and `head_truncated` + `head_note` name only the bounds that ACTUALLY bit (a two-row frame of arrays is not "capped at 3 rows"). Once the head is bounded the `repr` is cut to `INSPECT_ARRAY_REPR_CHARS` too - it is the same arrays a second time. Scalar variables are untouched. `list_variables` needs none of this (no head; `repr_short` is already 140 chars). - **MCP run tools + the queue.** `run_cell` **waits** its turn and then returns the real outputs annotated `queued:true` / `queue_position` / `waited_ms` - it does *not* return early as "queued". Waiting is what keeps `run_cells`/`run_all`/`run_range` meaning "these ran, here is what they printed"; they drive `runCell` sequentially and depend on its outputs. The one early return is the **dedupe** case: `{status:'queued', queue_position}` if that cell is already pending, `{status:'running'}` if it is executing right now - so an agent is told it was accepted and never that a run finished when it did not. A dropped pending run returns `{status:'cancelled', reason}` and `runCells` **stops** there (the rest would run against a namespace their predecessors never populated). `runCell` pins `nb = nbArg ?? getActiveNotebookPath()` at call time and threads it through `getCell`/`setOutputs`, since the UI may focus another notebook while the run waits. New read tool **`run_queue`** (a per-notebook map, so an agent sees each notebook's OWN queue); `INSTRUCTIONS` gained a "runs serialize only within a notebook" clause (don't interrupt/restart just because a run is slow - that drops YOUR notebook's queued runs too). **Long-run keepalive (the silent-hang fix).** Because a run tool `await`s the whole run and holds the HTTP response open, a cell longer than the MCP CLIENT's per-tool-call timeout (Claude Code default ~60s) made the client give up and DISCARD the eventual result - the agent hung and never got the output even though the cell finished server-side. Fix lives entirely in `mcp/server.ts` `withProgress(extra, fn)`: it wraps every run tool handler (`run_cell`/`add_and_run`/`run_cells`/`run_all`/`run_stale`/`run_range`) and, while `fn` is pending, emits an MCP **progress notification** every `PROGRESS_INTERVAL_MS` (15s) against the request's `_meta.progressToken` via `extra.sendNotification` - which resets the client's timeout (when it sets `resetTimeoutOnProgress`, as Claude Code does) so the FINAL result is delivered when the run completes. It's a **wall-clock heartbeat, NOT output-driven** (the canonical `time.sleep(90)` emits nothing until it ends); a client that sent no progressToken gets a no-op passthrough (never push unsolicited notifications); send errors are swallowed and the timer is `unref`'d. The tool contract is unchanged (still returns the full outputs at the end). The `httpServer.requestTimeout = 0` / `timeout = 0` in `startMcpServer` is belt-and-suspenders (Node's 300s `requestTimeout` measures request RECEIPT, not the long response, so it never actually cut a run). The stdio↔HTTP bridge relays notifications verbatim and imposes no per-request timeout. **Residual cap:** if a client sets a hard `maxTotalTimeout`, no amount of progress overrides it - that's a client config choice, not something Cellar can fix.
