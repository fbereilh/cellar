# Modal keyboard, shortcut registry, multi-cell selection

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Modal keyboard + shortcut registry.** Jupyter-style command/edit modes. **`src/lib/shortcuts.svelte.ts` is the single source of truth**: `DEFAULT_SHORTCUTS` declares every binding as `{id, keys, mode:'command'|'edit'|'global', description, category}`, and the `shortcuts` store merges user rebindings (`localStorage['cellar-shortcuts']`, only overridden ids stored, so a later change to a default reaches every user who never touched it) over them. Bindings are *chord* strings in CodeMirror's syntax (`Mod-Shift-ArrowUp`, `Shift-Enter`, `j`), produced from an event by `chordFromEvent` and rendered for display by `chordTokens`. A binding may also be a **space-separated chord sequence** (`d d` = delete cell): the dispatcher holds the leading chords as a pending prefix (`SEQUENCE_TIMEOUT_MS`, resolved by `resolveChord`) and fires only on the full match, so a lone `d` does nothing; the prefix is discarded the moment the mode changes, which is what keeps it from leaking into an editor. Sequence length is unconstrained, so Jupyter's `i i` / `0 0` need no new machinery. `bindingsCollide` treats a prefix-vs-exact pair (`d` vs `d d`) as a conflict, since the shorter would always win. A chord names the **unshifted** key (`Ctrl-Shift--`, as JupyterLab writes it): `chordFromEvent` reads the key token off `e.code` when Shift is held together with a real modifier (`SHIFTED_BASE_KEY`), because the browser reports `_` for that keystroke. Split-cell is the one platform-conditional entry (`Ctrl` on macOS, `Mod` elsewhere - Jupyter means the literal Ctrl key on both). **Adding a shortcut = a registry entry + an action in `LiveNotebook`'s `actions` map; nothing else may bind a notebook key** (Cell's CodeMirror deliberately carries no run/escape keymap - it was removed so there is exactly one dispatcher). **An action may return `false` to mean NOT HANDLED**, and the dispatcher then leaves the keystroke completely alone - no `preventDefault`, no `stopPropagation`, so it bubbles on. That opt-out exists because the dispatcher is a **capture-phase window** listener covering the whole app: consuming a key an action did nothing with silently kills every other listener for it (the `Escape` that `clear-selection` binds is also how the sidebar dismisses its context menu, from a plain bubble-phase window listener). Anything else - a promise from an async action included - counts as handled, so an action has to decline deliberately; `clear-selection` declines when the selection is already a single cell. `LiveNotebook.onKeydown` is that dispatcher: one window capture-phase listener, registered only while that notebook is the active tab, so it beats CodeMirror + the browser. It reads the keystroke's mode **off the DOM** (`target.closest('.cm-editor')` -> edit, else command), never off the `keyMode` state - that is what guarantees a command-mode letter (`j`, `a`) can never fire while the user is typing; it also bails on `.modal-open`, on form fields, and on targets outside this notebook's `rootEl`. `keyMode` (visuals only) is driven purely by the editor's own focus/blur, so the indicator cannot drift from the DOM. Each `Cell` hands up an imperative API via `onRegister(id, {focus, focusCell, blur, enterEdit, editorOverlayOpen, run, isMarkdown, currentSource, cursorOffset, replaceSource})` (this replaced the old `focusers` registry); `run` goes through `doRun` so a shortcut always uses the editor's *live* text, not the 500ms-debounced `cell.source`. Cut/copy (`x`/`c`), the heading keys and split-cell compose the last three primitives: `currentSource` is the live editor text, and `replaceSource` rewrites the doc through the remote-apply path (cancels the debounce, suppresses the echo) leaving the **caller** to persist - never call one without the matching `editCell`. The selected cell shows a mode-colored gutter bar + ring + `cmd`/`edit` badge (`info` = command, `success` = edit - semantic tokens, not hardcoded hues, so every theme stays coherent). A newly activated notebook tab focuses its `rootEl` (`tabindex=-1`) so command keys work without first clicking a cell. `keyMode` and the `onRegister`/`onEditorFocus`/`onEditorBlur` props must stay wired all the way down (`LiveNotebook` → `Notebook` → `Cell`): drop any one and the whole modal keyboard goes silently dead, since `cellApis` never fills and the mode never leaves `command`. Fold shortcuts (`h`/Left, `l`/Right) reuse `toggleFold`, and `j`/`k` skip cells a folded heading hides.
  **Focus must follow the selection.** Because the dispatcher reads a keystroke's mode *and* its target off the focused element, a selection the focus doesn't track is a selection the next key doesn't act on (it would reach whatever button or rendered-markdown body the user last clicked). So the cell card itself is focusable (`tabindex=-1`, `outline-none`; its ring already marks selection) and every command-mode selection change goes through `LiveNotebook.selectAndFocus` (= `selectAndAct(id, focusCell)`, which MOUNTS the target through `ensureCellMounted` before it lands - an unmounted cell has no registered API, so under windowing the focus would go nowhere and take the whole modal keyboard with it; see the virtualization entry) -> `Cell.focusCell()`: `j`/`k`, `a`/`b`, a command-mode move, Escape out of an editor, `Shift+Enter`'s advance, and a **local** delete (a remote/agent delete only moves the selection - it must not yank the caret out of a cell this user is typing in). `Cell.focus()` means "advance into this cell": its editor, or the cell itself when it is rendered markdown (that editor is `display:none` and cannot take focus). `toggleFold`/`setAllFolded` likewise re-seat the primary when a fold hides it - command mode may never act on a cell the user cannot see - but they **RE-SEAT, they do not collapse**: the primary moves to the nearest still-visible MEMBER of the selection (`cellSelection.ts`'s `reseatHiddenPrimary`), so the set the user built survives a chevron (a selection may legitimately HOLD fold-hidden cells - a Shift range fills in by document index and select-all takes the whole order). Only when the fold hides EVERY member is there nowhere inside the selection to put the primary, and only then does it collapse onto the cell holding the header that swallowed it - through `selectOnly`, never a bare `activeId` write, since the primary must stay a member or `pruneSelection`'s `kept.add(activeId)` would silently widen the set on the next refetch.
  **Cut / copy / paste / undo-delete.** Cut, copy and delete address the WHOLE selection (see the Multi-cell selection entry below); the clipboard (`src/lib/cellClipboard.ts`) is a plain module singleton shared by every notebook in the tab (copy here, paste there - Jupyter's behavior), deliberately **not** the system clipboard (the toolbar's copy-input/copy-output buttons are the separate, system-clipboard copy - see the UI entry; the two never share a buffer); an entry is `{cell_type, source, cellar}` and carries **no outputs**, since a pasted output would be a saved result the live kernel never produced. **The `cellar` namespace is carried WHOLE, and the clipboard and the undo record are ONE snapshot (`clipboardCellFrom`), because a named subset is what drifted**: the entry used to name `output_scrolled` alone, so an ordinary copy/paste silently DOWNGRADED a cell - a SQL cell pasted as plain Python (wrong grammar, wrong run path, its `-- >>` binding gone), along with `role`, `export`, `hide_input` and `hidden_from_agent` - while the undo record already carried the namespace whole, so `z` after a cut restored a SQL cell that a paste of the same cell would not. The ONE allowlist stays on the SERVER (`seedCellar`'s `DURABLE_CELLAR_KEYS`), where it also strips the runtime-only records, so an entry can never write an undeclared key into the user's `.ipynb` nor forge a `lastRun`; the server likewise owns what a namespace MEANS in its new home (the imports `role` is one per notebook, so a copy pasted beside its original does not claim it while a CUT one does). **A paste's `.py` refusal therefore asks the LOGICAL type** (`entries.map(clipboardCellType)` against the shared `offersCellType`), never `cell_type`: now that `cellar.language` travels, a chat cell really does arrive as an nbformat `code` cell such a document cannot hold, and `assertCanHoldCell` refuses it server-side - a `cell_type === 'raw'` test would leave the user a thrown insert where every other surface gives a named notice. Covered by `tests/unit/cell-clipboard.test.ts` (the rule, the real paste/undo document write, and source guards on the wiring - vitest cannot mount `LiveNotebook.svelte`, and e2e is absent from the pre-push gate) + `tests/e2e/clipboard-cell-metadata.spec.ts` (the keystrokes, single and bulk, asserted against the SERVER document; each test seeds its own cells through the add route, since rewriting the `.ipynb` on disk does NOT reset the live server-owned doc). Undo (`z`) is a per-notebook, **local-only** stack: it records what *this* user deleted, so it can never resurrect a cell an agent (or another tab) removed. Paste/undo/split all go through `insertCellAt`, which seeds the new cell server-side via `addCell(afterId, cellType, nb, originId, source, cellar)` - one persist, one `cell:added` event carrying the real text plus whichever durable `cellar` keys `seedCellar` allowlists (paste and undo both restore the whole namespace, split inherits `splitInheritedCellar`'s deliberately narrower subset) - and appends-then-hoists for an insert at index 0 (the add API can only insert *after* an id). `deleteCell` enforces the notebook's **≥1 cell** invariant (the same one the toolbar's delete button enforces by disabling at one cell), so `dd` and `x` are no-ops on a lone cell rather than leaving nothing to type in.
  **Escape is CodeMirror's first.** The dispatcher hands Escape back to CM whenever CM has an overlay of its own open (`Cell.editorOverlayOpen()` = `completionStatus() != null || searchPanelOpen()`), so Escape closes the completion tooltip or the search panel before it ever exits to command mode - Jupyter's behavior. Keystrokes inside a `.cm-panel` (the search bar) are CM's entirely. This is why `@codemirror/autocomplete` and `@codemirror/search` are **direct** dependencies, not just transitive ones under `codemirror`.
  **`Shift+Enter` is one path for both cell types**: `Cell.doRun(advance)` renders a markdown cell / runs a code cell, then `runAndAdvance` selects the next (creating one at the end) and moves focus there - into its editor from edit mode, onto the cell from command mode. A markdown cell never re-enters its own editor on `Shift+Enter`.
  `Settings.svelte` renders the registry grouped by category and rebinds a chord in place, warning on same-mode collisions. A chord that would **type a character** (no modifier but Shift; `typesACharacter` in the registry) bound to an `edit`/`global` shortcut makes that character untypable in every cell: Settings **warns and confirms, but never refuses** (`shortcut-hazard-confirm`, then a standing `shortcut-hazard-warning` on the row). The freedom is deliberate; the surprise is what's refused.
- **Multi-cell selection (`src/lib/cellSelection.ts` + `LiveNotebook.svelte`).** Cells select as a SET, not one at a time. `LiveNotebook.svelte` is the authoritative model and holds three deliberately separate pieces: **`activeId`** (the PRIMARY - what takes DOM focus, what a single-cell op addresses, the moving end of a range), **`anchorId`** (where a Shift range starts from; kept apart from `activeId` so a second Shift+click re-ranges from the same origin, the platform convention), and **`selectedIds`** (the selection, which ALWAYS contains `activeId` - so a plain single selection is the degenerate `{activeId}` and every bulk op is the single-cell op at size 1, which is what keeps the common case from regressing). Every rule is a pure function in `$lib/cellSelection` (`rangeIds`/`toggled`/`applyGesture`/`extendSelection`/`moveSelectionPlan`/`selectionAfterRemoval`), unit-tested in `tests/unit/cell-selection.test.ts`. **Gestures:** plain click collapses; **Shift**+click ranges contiguously from the anchor; **Cmd/Ctrl**+click toggles one cell (non-contiguous); **Shift+J/K** and **Shift+Arrows** extend; **Mod+A** selects all; Escape / a plain click / entering an editor collapses. **`selectAllCells` takes the FULL `cellOrder`, fold-hidden cells INCLUDED** - one rule for what a selection may contain, and it is the one `rangeIds` already follows. Selecting only the visible cells made a bulk move destructive: with a section collapsed it selected the heading but not its body, so `moveSelectionPlan` swapped each heading past the first cell of its own section, shuffling headings into the sections they title. The deliberate asymmetry that REMAINS is correct: `extendSelection`'s HEAD walks the SELECTABLE list, so Shift+J/K skips fold-hidden cells exactly like plain `j`/`k`, while the resulting RANGE fills in by full-document index. Select-all also leaves the two ENDS spanning the document (anchor at the first cell, head at the last) - `extendSelection` rebuilds the selection as `rangeIds(anchor, head)`, so a head left wherever the primary happened to be made the very next Shift+J/K discard everything past it. **A SELECTION CHANGE IS NOT A NAVIGATION, and the seam that states that is `mountAndFocus`** - `ensureCellMounted`'s opt-in **mount-only mode (`{reveal:false}`)** plus `focusCell` (already `{preventScroll:true}`), shared by `selectAllCells` and `activateCell`'s modifier-gesture branch; there is deliberately ONE such path, not one per caller. The mount is not optional because `activeId` is ALSO the PRIMARY every single-cell action addresses through `apiOf(activeId)`: leaving the head unmounted made `run-cell`, `edit-mode`, `command-mode` and `split-cell` silently no-op right after Cmd/Ctrl+A on any notebook long enough to window the last cell out. But `scrollCellIntoView` is the wrong seam for both, for the two side effects nobody asked for - the viewport chasing the primary somewhere the user did not ask to go, and, because `ensureCellMounted` REVEALS by default, a collapsed section silently unfolding with `saveFolds()` PERSISTING it. That hit Cmd/Ctrl+A (which expanded whichever section happened to hide the last cell, and the change survived a reload) and, once a selection could legitimately hold fold-hidden cells, the Cmd/Ctrl DESELECT too: `rangeIds` fills in by document index and select-all takes the whole order, so a mere deselect could permanently open a section the user collapsed. Keep `reveal:false` opt-in: every path that genuinely NAVIGATES (`selectAndAct`, `jumpToCell`, follow-running, the outline/search jumps) must keep unfolding, since scrolling to a `display:none` cell shows nothing. A fold-hidden head therefore neither mounts nor takes focus (a `display:none` cell cannot), so focus stays where the user was - the accepted cost of not writing fold state. It also means the head may be a fold-hidden cell, so **BOTH keyboard moves resolve a head absent from the walk by DOCUMENT position through the ONE exported `stepFromUnwalkableHead`** (the nearest walkable cell in the direction of travel): `extendSelection` for Shift+J/K and `selectRelative` for plain `j`/`k`, which took a bare `findIndex` miss as "restart at `walk[0]`" and so flung the selection to the TOP of the notebook on the very next keystroke after Cmd/Ctrl+A whenever the tail section was collapsed. Only a head gone from the document order too has no position to step from. **Toggling a cell OUT moves the primary ONLY when that cell WAS the primary** (`nearestSelected`'s contract is the primary's REPLACEMENT, and `applyGesture` used to apply it to any toggled-out id): deselecting some other member would otherwise silently relocate DOM focus and re-seat the origin of the next Shift range, neither of which a deselect asked for. A modifier click is handled in `Cell.svelte`'s `onCardPointerDown`, which **`preventDefault`s so the press never opens the editor** (JupyterLab does the same - a cell is mostly editor, so without it Shift+click would drop into edit mode and collapse the range it was asked for) and exempts a control, an editor that ALREADY has the caret (`view.hasFocus`, not `keyMode`, which lags a focus change by an event), and the two READING surfaces - rendered markdown and the output block - where Shift+click must stay the browser's own text-selection gesture (grabbing part of a traceback or a printed table), since cancelling `pointerdown` suppresses the compatibility mouse events that drive it. **An exempted MODIFIER press then PRESERVES the selection rather than falling through to the plain activation**, for the same reason it was exempted at all: the press belongs to the browser / CodeMirror / the native text gesture, so it is not a cell-selection gesture and must not COLLAPSE a five-cell selection on its way past (Shift+dragging across part of a traceback used to discard one). Preserved the same way the non-primary branch preserves it - by not collapsing, never by cancelling - so the `focusin` that follows settles it: it promotes this cell to primary when the selection already holds it, and collapses to it when it does not, exactly as an unmodified click on the same spot does. `LiveNotebook` then focuses the resulting primary itself, since the dispatcher reads a keystroke's mode+target off the focused element. The `focusin` that follows carries no modifiers, so it is tagged `fromFocus` (`CellActivation` in `types.ts`) and suppressed when it merely re-states the existing primary - otherwise it would collapse the range built one event earlier. **A SECONDARY press selects nothing** - a context-menu/auxiliary gesture, and the plain path collapses the selection to the clicked cell, so it would destroy a five-cell selection before the menu opened. **What counts as secondary is a PLATFORM question, decided in ONE pure place (`cellSelection.ts`'s `pointerIntent(e, mac)`, unit-tested for both platforms) so this file can never disagree with the toggle modifier about what Ctrl means**: a non-primary button, and on **macOS a CTRL+CLICK**, which is the platform's context-menu press and arrives as `button === 0` with `ctrlKey` set while the toggle modifier there is Cmd - so testing the button number alone read the everyday Mac right-click as a PLAIN click and collapsed the selection an instant before the menu opened. Off macOS Ctrl+click IS the toggle and must stay so. A secondary press yields no extend/toggle whatever else is held (Ctrl+Shift on macOS still opens the menu), since preserving the selection is the safe direction. Skipping `onActivate` is not the whole story (the card is `tabindex=-1`, so the browser focuses it and the `focusin` would collapse onto whatever it landed on), but the answer is NOT to `preventDefault` that press: cancelling `pointerdown` suppresses the compatibility mouse events, so a right-click inside a code cell stops focusing its editor (the native menu's Cut/Copy/Paste then act on nothing) and X11 middle-click paste stops working. **A selection is preserved by NOT collapsing it, never by cancelling the event** - so the `fromFocus` branch spares any cell the selection ALREADY holds, promoting a member to primary (anchor follows, as after a toggle) instead of collapsing. Accepted cost: a right-click on an UNSELECTED cell no longer selects it first.
  **THE WINDOWING CONTRACT (why the model is shaped this way).** Windowed rendering is ON by default, so most of a large notebook has NO DOM at all. Selection therefore lives on document-model ids resolved against the full `cells` order and is **never** computed by walking the DOM - a range whose endpoints are 200 cells apart must select every cell between them. Selected cells are deliberately **NOT** added to `pinnedCellIds`: pinning them would mount the whole range and undo windowing. A windowed-out member simply renders selected when it scrolls back in, because `selected` is a prop derived from the set (the same "a Cell instance is DISPOSABLE" rule as `rawEdits`/`editorCollapsed`). Covered end-to-end by `tests/e2e/multi-select.spec.ts`, whose assertions read the SERVER document, not the DOM.
  **Bulk ops go through ONE batch request, `POST /api/cells/bulk` (`{op:'delete'|'move'|'type', ids, …}`) → `deleteCells`/`moveCells`/`setCellTypes` in `notebook.ts`.** Delete, move and change-type act on the whole selection; so do cut/copy (the clipboard has always held a list). **The batch is about ATOMICITY, not round trips**: a loop over the single-cell routes serializes+fsyncs+renames the whole `.ipynb` once per cell and walks the file through N-1 intermediate states, and a bulk delete would leave N undo entries where the user performed one action (so `deletedCells` is now a stack of GROUPS - `z` restores the whole batch). Each batch emits the ORDINARY per-cell events (`cell:deleted`/`cell:moved`/`cell:type`), so other tabs apply patches they already understand and no new event shape exists; the move plan is a sequence of ADJACENT SWAPS precisely so replaying those events reproduces the persisted order. Move semantics are JupyterLab's and need no special case for a scattered selection: each selected cell swaps with its unselected neighbour, so a contiguous block slides as a block and a scattered selection steps one place each, keeping relative order and gaps - a move never "gathers" a selection the user built. The move is BLOCKED entirely when the selection touches the edge it is moving toward (a partial slide would silently reorder the selection relative to itself), and a delete covering EVERY cell is refused - a notebook always keeps somewhere to type. **That invariant is SERVER-enforced, in `deleteCells` itself** (returning `{ok:false, reason:'would-empty-notebook'}`, refusing the WHOLE batch: nothing removed, nothing persisted, no events - a partial delete nobody asked for is worse than a refusal, and it is the shape the client already models), because only the server knows the real cell count: the browser compares against ITS list, which is stale for as long as an agent's `cell:deleted` events are in flight, so a selection covering everything the server still has would otherwise persist a zero-cell `.ipynb`. **`deleteCell` (singular) IS `deleteCells` of one** - one implementation, one refusal shape, so the guard holds for EVERY caller: leaving the single-cell path unguarded reopened the identical race through `DELETE /api/cells/[id]` (a `dd` on what the browser thinks is one of several removing the server's LAST cell). Living in the shared layer also covers MCP **`delete_cells`**, which never had the check at all (`removeCells` reports it as `{ok:false, refused}` so an agent is never told `count:N` over a document that did not change) - and it looks the refusal up through the shared `deleteWouldEmptyNotebook` predicate BEFORE checkpointing, since a checkpoint is a snapshot of the state a mutation is about to leave behind: checkpointing a refused batch put an 'agent'-triggered entry in the human's History for a document that never changed (the one-checkpoint-per-batch property for a batch that DOES delete is unchanged). The bulk route surfaces it as a 400 in its existing `{ok:false, reason}` shape and the single-cell DELETE route the same way; both client guards (`deleteSelection`'s `ids.length >= cells.length`, `deleteCell`'s `cells.length <= 1`, and `cutActive`'s, since a cut that cannot delete would be half a cut) STAY as the optimistic mirror, the same client/server pairing as `clampMoveIndex` - and each SAYS so through `onNotice` -> the shell's existing transient status line (`data-testid=app-notice`) rather than returning silently: a keystroke refusal sends no request that could fail and disables no affordance, so Cmd/Ctrl+A then `dd`/`x` doing nothing at all is indistinguishable from a dead keyboard. **The RACE path says it too** (`noticeRefusal`, shared by `bulkOp` and the single-cell `deleteCell`): the optimistic guards compare against a list that is stale while an agent's `cell:deleted` events are in flight, so the server can legitimately refuse a delete the browser already rendered as gone, and the recovery - a refetch - is that same silent refusal with the cells simply reappearing. It is driven by the reason the server ACTUALLY returned (`{ok:false, reason:'would-empty-notebook'}` off the 400 body), never assumed from the failure: a refetch caused by a dropped connection or any other error must not claim a rule the server never invoked. **That status line is REPEATABLE and self-dismissing, and its dismissal rule is PER-CALL because two opposite kinds of message ride one channel** (`src/lib/notice.svelte.ts` `createNoticeChannel`, the ONE owner of both rules - `+page.svelte` reaches it only through `showNotice`/`clearNotice`, never a bare `notice = …`): each call bumps a **nonce** the markup is `{#key}`ed on - re-assigning an identical string is a reactive no-op, so a second refused `dd` while the toast is still up would otherwise change nothing on screen - and a **RESULT** (this refusal, an export/checkpoint outcome) arms a `NOTICE_TIMEOUT_MS` auto-dismiss, since a refusal the user retries must not need dismissing first. **`{sticky:true}` is the opt-out and PROGRESS needs it**: a message posted BEFORE a long operation must stay up until the outcome REPLACES it - a blanket timeout took `doConvertToIpynb`'s "Converting: running all cells…" off screen mid-convert (it runs every cell, minutes), leaving the user only the app-menu spinner inside a `:focus-within` dropdown they have usually clicked away from. So classify a new caller by WHEN it posts, not by assuming they are all one-shot (that assumption is what caused the regression); the ✕ preempts either kind. Covered by `tests/unit/notice-channel.test.ts`. (The refusal rule itself is unchanged - Cellar deliberately does NOT adopt JupyterLab's delete-all-and-leave-one-empty-cell behavior), and the client's single delete now pushes its undo record only once the server confirms (a refusal refetches, so a phantom group would make `z` duplicate a cell that never left). Optimistic client halves mirror the server's `clampMoveIndex` guard the way `moveCell` already does; a failed bulk request **refetches** rather than swallowing, since the events that would correct a divergence are the ones it never published. **A REFUSED batch is not an HTTP failure** - `moveCells` returns `[]` when its recomputed plan is blocked and `setCellTypes` `[]` when it matched nothing, both under `{ok:true}` - so `bulkOp` compares the COUNT the server reports acting on (`removed`/`moved`/`changed`) against what the caller rendered and refetches on a mismatch. That check is load-bearing rather than belt-and-braces: these events carry the initiating tab's own `originId`, so that tab suppresses its echo and the very events that would correct the divergence are the ones it will never apply. Its `applied` count is derived through the SAME rules the server uses (which is why `setCellTypes`' "already this type" test is the shared `isLogicalCellType`, not a second copy), so a batch the server legitimately skipped is never mistaken for a refusal. **That shared predicate is deliberately stricter than `logicalCellType(cell) === cellType`**: the latter maps every non-markdown cell to `code`, nbformat `raw` cells included (`ipynb.ts` passes those through untouched), so skipping on the logical type alone left a raw cell raw under a bulk retype-to-code while the single-cell `setCellType` - which has no "already" check at all - converted it, and the client predicted the same skip so nothing revealed it; `isLogicalCellType` requires the nbformat `cell_type` to match too. `raw` is still not a Cellar logical type, it is simply never "already" anything. `bulkOp` **returns whether the server confirmed**, and the delete's undo group is pushed only then (the snapshots are still TAKEN before the cells leave the model - the only moment their live source is readable): a refused batch refetches the cells back, so a phantom group would make `z` re-insert copies of cells that are still there. **The restore is symmetric and SINGLE-FLIGHT**: `undoDelete` leaves the group on the stack until every insert has landed (an insert can reject, and discarding it first would half-restore the notebook with the only record of what was deleted already thrown away), which is exactly why a second `z` - or plain key auto-repeat - inside that multi-fetch window would otherwise read the SAME group and persist the cells twice, so an `undoInFlight` guard admits one restore at a time. Each record is dropped from the group the instant ITS cell is back (the group is sorted ascending and shifted, which is also the order that lands every cell at its recorded index), so what stays on the stack after a rejected insert describes exactly what is still MISSING - a retry resumes instead of replaying, which would insert the cells that already landed a second time; the rejection is caught rather than escaping, since an unhandled one also skipped the selection restore. **The undo record IS a `ClipboardCell` plus an index** (`DeletedCell`), taken through the SAME `clipboardCellFrom` snapshot cut/copy takes - see the Cut/copy/paste/undo-delete entry for why that is one rule and not two: undo is the path where a user expects EXACT restoration, so a record that dropped `language` brought ten deleted SQL cells back as ten plain Python ones, along with the imports `role`, the nbdev `export` flag and the `hide_input` report-view choice; bulk delete is what turned that from a one-cell annoyance into a ten-cell one. It is applied in the SAME add rather than by a PATCH per key - `addCell` takes an optional `cellar` and `notebook.ts`'s `seedCellar` merges it - so a restore stays ONE persist and ONE `cell:added`. **The seed is an ALLOWLIST of the DURABLE `cellar` keys, and the RUNTIME-only records are stripped server-side through the same `stripRuntimeMeta` the disk write uses** - `clean.ts` keeps the `cellar` namespace WHOLE through a save, so assigning the client's object wholesale would make this route a path from arbitrary request JSON into the user's persisted `.ipynb`, and the strip alone cannot stop a key nobody declared. Neither can a client-supplied snapshot become a forgery route: `lastRun` is the sole evidence a cell ran against the LIVE namespace and may only originate from an in-process run, and `importBindings` was just recomputed by `newCell` for the source the cell is born with. **SPLIT-CELL is the other caller of that seed, through its own rule `src/lib/splitCell.ts`** (`splitInheritedCellar`): the lower half is the same cell's second half, so it inherits what says how that cell is READ and DISPLAYED - `language` (without it a split SQL cell minted a plain Python lower half that compiles through the Python path, silently), `hide_input`, `output_scrolled`, and `hidden_from_agent` (not inheriting it would DISCLOSE the code the user hid) - but NOT the imports `role` (one per notebook; the upper half keeps it) nor the nbdev `export` flag (a designation about the ORIGINAL cell, so inheriting it doubles what the module writes out). A durable key is not inheritable merely because it is durable, hence an explicit list rather than forwarding the namespace. Covered by `tests/unit/split-cell.test.ts` (the rule + the real document write) and the split case in `tests/e2e/insert-cell.spec.ts` (the wiring).
