# Notebook checkpoints (snapshot / undo)

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Notebook checkpoints (snapshot / undo).** `src/lib/server/checkpoints.ts` snapshots a notebook's full cells (source + outputs + metadata, deep-cloned) to a restorable checkpoint. **Storage** mirrors `ui-state.ts`: a single `.cellar/checkpoints.json` (gitignored, per-project, port-independent), keyed by workspace-relative path, bounded to 25/notebook (FIFO). **OUTPUTS ARE STORED OUT-OF-BAND**, one file per checkpoint at `.cellar/checkpoints/<id>.json`, with the index holding only sources + metadata - inline they sat in the single index file (held in memory, re-serialized on EVERY write), so a per-snapshot 2 MB cap had to DROP them, and it dropped them for exactly the output-heavy notebook `clear_outputs` exists to shed weight from, leaving undo with nothing to restore. The only per-snapshot cap left is the RECOVERABLE tier's `MAX_SNAPSHOT_BYTES` (2 MB), which rides with that tier's THROTTLE and is licensed by the same one fact (what those actions overwrite can be produced again) - so past it that tier drops the outputs, keeps sources + metadata and flags `outputsTruncated`, while the DESTRUCTIVE tier gets NEITHER cap nor throttle and undo after a clear is bounded by nothing; the store-wide bound is a workspace-wide sidecar budget (`CELLAR_CHECKPOINT_OUTPUT_BUDGET_BYTES`, 256 MB) whose eviction is **NEWEST-WINS** - the snapshot just taken always keeps its outputs even when it alone exceeds the budget, and older sidecars are shed and flagged `outputsTruncated` (they still restore their sources). That inversion IS the guarantee. A checkpoint written by an older Cellar carries its outputs inline and still restores. Runtime metadata (`lastRun`/`editedAt`/`importBindings`) rides in the snapshot (ephemeral `.cellar`, never the `.ipynb`) so a restore reproduces run-status **and** staleness; the epoch check keeps `ran_this_session` honest, and the restored import-binding baseline keeps an imports-cell edit scoped to its real dependents (a restored stamp predating `sinceAt` reads as 0, so its removal record is kept). **Triggers:** a **manual** "Checkpoint now" (trigger `manual`) and an **automatic** pre-action snapshot before any AGENT mutation/run (trigger `agent`), in **TWO TIERS decided by what the action DESTROYS, not by how important it is**. RECOVERABLE actions (`addCells`/`editCell`/`moveCell`/`runCell`, and a `consolidate` sweep that deletes nothing; `addAndRun`/`runCells`/`runAll` compose these) call `autoCheckpointBeforeAgentAction(nb)`, which THROTTLES BY COUNT - the first agent action for a notebook, then one per `CHECKPOINT_EVERY_N_ACTIONS` (5), with a `CHECKPOINT_MAX_GAP_MS` time backstop. That is safe only because the state they overwrite can be produced again (a run's outputs come back by re-running). **DESTRUCTIVE actions - the ones that DELETE saved outputs - call `checkpointBeforeDestructiveAgentAction(nb, {retention})` and are NEVER throttled**: `removeCells`, `clearOutputs`, `setType` ONLY when the conversion drops outputs (leaving nbformat `code` with outputs present - a sql/mojo retype destroys nothing and stays on the throttled tier), and `consolidate` ONLY when its sweep would really DELETE a cell carrying saved output (an imports-only cell routinely does - `import tensorflow` leaves a FutureWarning - and the sweep deletes any cell it empties; the decision is `imports-cell.ts`'s `consolidateDestroysOutputs`, which PLANS the sweep without touching the document through the same `planConsolidate` the sweep itself runs, so the everyday idempotent re-consolidate deletes nothing and stays on the cheap tier). **Both of those tools decide the tier from what the action would destroy in THIS document, never from the tool being called.** Under the old single tier four out of five `clear_outputs` calls were preceded by NO snapshot at all, so the position of a clear in the agent's action sequence decided whether the user's results were recoverable. The two tiers share the store but NOT the counters, in either direction. **The tier really asks TWO independent questions - may this snapshot be throttled away, and must it PRESERVE its outputs at any cost (an uncapped sidecar, a synchronous index flush, and the refusal below) - and `removeCells` is the one caller that answers them differently** (`OutputRetention`): a delete destroys the cell's SOURCE whether or not that cell holds outputs, and that source may exist in NO snapshot if the cell was created inside the current throttle batch, so it is never throttled unconditionally - while a delete that removes no outputs takes the capped, debounced snapshot rather than synchronously writing the whole unrelated output set of an output-heavy notebook for results it was never going to touch (the stated cost: past the cap, undoing such a delete restores the cell's source with the notebook's other outputs blank, flagged `outputsTruncated`, exactly as every throttled run checkpoint already does at that volume). `setType` and `consolidate` destroy nothing at all when their guard is false, so for them both answers fall together and they drop to the throttled tier entire - do not collapse the two questions back into one. **The remaining unrecoverable case is REFUSED BEFORE it destroys anything**, never reported afterwards: if the sidecar could not be WRITTEN (a full disk, an unwritable `.cellar/`) **all FOUR destructive tools** - `clear_outputs`, `delete_cells`, an output-dropping `set_cell_type` and an output-deleting `consolidate_imports` - return `{ok:false, refused:'outputs_unrecoverable'}` and name the `allow_unrecoverable:true` opt-in, which exists because clearing outputs is itself how a user frees a full disk, so a flat refusal would trap them. **A refused call's snapshot is ABANDONED before it is ever entered in the store (`createCheckpoint`'s `abandonIfOutputsLost`), never entered and then removed - and that difference is a real one**: `list.push` is what triggers FIFO eviction, so at `MAX_PER_NOTEBOOK` a call about to refuse had already destroyed the OLDEST snapshot and `rmSync`'d its sidecar (possibly a human's own `manual` save point) while its refusal said "nothing was changed". Abandoned, nothing is pushed, nothing is evicted, no `checkpoints:changed` is published, the store is not marked dirty and the throttle counters are untouched. The guard lives once, in `service.ts`'s `destructiveCheckpoint`, so a tool that DELETES saved outputs cannot land on the never-throttled tier while still destroying silently - which `set_cell_type` and `consolidate_imports` each did until they were wired through too. **DURABILITY: a DESTRUCTIVE-tier checkpoint that really WROTE a sidecar flushes the index SYNCHRONOUSLY** (`createCheckpoint`, past the ordinary 250ms debounce): the destruction it protects is persisted synchronously, so a SIGKILL in the debounce window left the undo record unreferenced - and `sweepOrphanOutputs` then actively DELETED bytes still sitting recoverable on disk on the next start. One small index write beside a synchronous whole-file sidecar write is a rounding error. **Scoped to that tier because that is the only tier with such a window**: a recoverable-tier checkpoint destroys nothing, so it keeps the ordinary debounced write rather than paying a synchronous whole-file index write on the highest-frequency agent action there is - as does a checkpoint that stored NO sidecar, which has nothing a sweep could delete. For the same reason a FAILED sidecar write deletes its own partial file (ENOSPC truncates mid-write, and an abandoned entry leaves nothing to attribute the file to). **That flush is a second way the guarantee can fail, so it is CHECKED rather than swallowed**: `flush()` clears `dirty` only after a successful write (cleared first, a failed write was indistinguishable from a successful one and the process-exit hook then wrote nothing either) and returns its verdict, and an index write that fails on this path is treated exactly like a sidecar that could not be written - the same `outputs_unrecoverable` refusal and the same `allow_unrecoverable` waiver, since an entry that never lands leaves the sidecar an orphan the next start's sweep deletes. It is settled BEFORE eviction, because abandoning may only un-do what this call did and eviction `rmSync`s an older snapshot's sidecar; the ordinary debounced path still swallows the error, as it always has, because that path destroys nothing. **Restore** replaces the live doc via `notebook.ts` `replaceCells` (deep-clones, persists clean-on-save → `.ipynb` git-clean, publishes `notebook:restored` so every tab refetches via `LiveNotebook.load()`); it snapshots the pre-restore state first (trigger `restore`) so restore is itself undoable. `undoLastAgentAction` restores the newest `agent` checkpoint - the headline "undo last agent action" flow (which is why the agent-facing `create_checkpoint` tool tags its snapshots `manual`, not `agent`, so a deliberate agent save point is never what undo reverts to). Covered by `tests/unit/checkpoints-throttle.test.ts` (the two tiers and their independent counters), `tests/unit/checkpoint-output-storage.test.ts` (the sidecar contract, the budget's newest-wins eviction, the legacy inline shape, the synchronous-index-flush durability rule in both directions, and the two tiers observably differing on ONE notebook - the throttled one dropping outputs over the cap and staying on the debounce even when it DID store a sidecar, the destructive one keeping the same volume and flushing), `tests/unit/mcp-clear-outputs.test.ts` (the clear/retype tiers, the refuse-before-destroying guard, and a refusal at the history cap evicting NOTHING), `tests/unit/mcp-consolidate-checkpoint.test.ts` (the consolidate tier in both directions plus its refusal) and `tests/e2e/mcp-ergonomics.spec.ts` (the headline flow end to end: a mid-sequence clear of an over-cap notebook, undone through the same route the History panel's Undo button posts to). **Surfaces:** routes `GET/POST /api/checkpoints` (create / restore / undo-agent); sidebar **History** section (`Checkpoints.svelte`, key `history` in `sidebarSections.ts`) lists checkpoints (relative time + trigger badge) with inline-confirm Restore + an Undo button; navbar app-menu "Checkpoint now" / "Undo last agent action"; MCP `create_checkpoint`. The panel refetches on a `checkpoints:changed` global event. Restore reverts the DOCUMENT, not the kernel namespace (re-run to sync; staleness flags it).
