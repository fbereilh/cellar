# Databricks: connect, auth, liveness, Spark progress, dbutils widgets, runtime toggle

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Databricks (`src/lib/server/databricks.ts` + `src/lib/Databricks.svelte` + `src/routes/api/databricks/*`).** Native connect: pick profile → pick cluster → `spark` + `w` bound in the kernel. **Auth is the SDK's profile auth and nothing else** - `WorkspaceClient(profile=…)` / `DatabricksSession.builder.profile(…)` read `~/.databrickscfg` themselves. Never shell out to the `databricks` CLI, and **never** glob for the VS Code extension's bundled binary (the boilerplate this replaced did; it is the thing we deliberately do not do). **`resolveAuth` (`databricks.ts`) trusts that SDK profile auth: a *named* profile - with OR without a `token` - resolves to `{mode:'profile', profile, host}` and is handed to the SDK by NAME (`Config(profile=…)`), which authenticates it however the profile says (a PAT, or a `databricks-cli`/keyring/cached-OAuth credential - e.g. the captain's no-PAT `DEFAULT`, whose `auth_type=databricks-cli` auths silently, no browser).** Do NOT re-collapse a no-token profile into Cellar's own browser OAuth or discard its name (the `cellar-dbx-auth-profile-drop` bug: a no-PAT SDK-authable profile was misclassified `mode:'oauth'`, its name dropped, and gated behind a spurious `oauth_login_required`). Cellar's own external-browser OAuth (`{mode:'oauth', host}`, gated by `assertSignedIn`+`signedInHosts`) is reserved for a **bare typed host with no profile**; MOST profiles are never pre-gated - a genuine need for a fresh interactive login surfaces reactively (the SDK error → `classify()` → `oauth_login_required`), which the `login` subprocess then satisfies. **The ONE gated profile shape** (so a listing/connect can never itself pop the SDK browser): a no-token `auth_type=external-browser` profile - `resolveAuth` flags it `needsSignIn:true` and `assertSignedIn` holds it behind sign-in exactly like a bare host (tracked in the `signedInProfiles` sibling of `signedInHosts`), still authenticating by NAME (`Config(profile=…)`), just after the deliberate `login`. The gate keys on `external-browser` SPECIFICALLY - never on a merely missing `auth_type` (the captain's `DEFAULT` has no `auth_type` line and the SDK infers `databricks-cli`, so gating on "no auth_type" would re-break it). Same split in the UI (`Databricks.svelte`): a databricks-cli/PAT profile lists immediately, a bare host OR a no-token external-browser profile (`profileNeedsSignIn`) signs in first; `oauthRequired` (set only from a real `oauth_login_required`) also drives the sign-in button. Covered by `tests/unit/databricks-auth-resolve.test.ts`. **An EXPIRED named profile is its own case, and must never be routed to that sign-in button (task `cellar-databricks-profile-reauth-r2`).** A `databricks-cli` (or otherwise CLI-managed) profile keeps its credential in the **databricks CLI's own store**, not in the SDK's python-local OAuth cache Cellar's browser sign-in mints into - so when its refresh token dies, "Sign in with Databricks" writes a token that profile never reads and the user is stuck forever. That is exactly what happened to the captain's `DEFAULT`: the SDK raised `ValueError: default auth: databricks-cli: cannot get access token: … the refresh token is invalid. To reauthenticate, run: $ databricks auth login --profile DEFAULT`, whose `discovery_url=…/oauth-authorization-server` matched the PROBE `classify()`'s `'oauth' in low` rule → `oauth_login_required` → the dead-end button. The fix is a distinct code **`profile_reauth_required`** (401) decided in **Node**, not python: `classify()` sees only the message, while **`reclassifyReauth(auth, result)` (`databricks.ts`)** also has the resolved `Auth`, i.e. WHICH profile was asked for - which is what lets the real name ride out on `DatabricksError.profile` so the sidebar prints a command that is never hardcoded. Applied at exactly two seams, both of which produce this failure: inside **`probe()`** (every listing/login/cluster op) and in **`connect()`** right after `CONNECT_CODE` (which hardcodes `auth_failed` for the Config/WorkspaceClient step). **The RECONNECT ladder must preserve that verdict, and preserving it needs its own mechanism - `ConnState.reconnectError`.** The likeliest way a user meets an expired profile is a session that was already WORKING, so what they touch is the sidebar Reconnect button / `databricks_reconnect`, not a fresh connect - and both rungs that rebuild a session are driven fire-and-forget by callers that must never throw, so each swallows its error (rung 2 `autoReconnect` → `false`, rung 3 `reconnectAfterKernelRestart` → a string `reason`). That flattening dropped `code`/`profile` and `reconnectSession` raised the generic `reconnect_failed` ("reconnect from the Databricks sidebar section") - the exact dead-end button this feature exists to stop offering, with `throwReconnectFailure`'s `clusterState` probe unable to rescue it since it runs on the SAME expired auth and can only answer `null`. So the classified `DatabricksError` is recorded at **`reconnectTo`** - the ONE seam both rungs already funnel through, hence no second reconnect path - and `throwReconnectFailure` re-throws it **before** the cluster probe when its code is `PROFILE_REAUTH_CODE`. `reconnectSession` clears the field before walking the ladder, so a recorded verdict can only ever belong to THAT attempt. **The AUTO-HEAL status surfaces read that same field, through the one accessor `pendingReauth(s)`** - because the explicit Reconnect button is not where most users meet this: the panel polls (`getStatus`→`liveConnection`) and the agent asks (`databricks_status`→`agentStatus`), and both run the self-heal. The state that heal leaves behind is the load-bearing detail: a failed heal runs through `connect()`, whose failure path NULLS `s.connection` (without an `s.lost`), so the panel drops to the **picker card** - the one offering "Sign in with Databricks", the exact dead end - and `agentStatus` falls to its not-connected branch. So the verdict rides EVERY not-live shape (`liveConnection` attaches `reauth`, rendered by the `sessionReauthBox` snippet on the expired/lost/picker cards; `agentStatus` returns `reauthFields()` = `reauth_required`/`profile`/`reauth_command` + a note that tells the agent to relay the command and NOT to point at the sidebar), not just the brief `expired` window. Two fences keep it honest, and both are mutation-tested: it needs a still-bound notebook (`reconnectTarget`), and any successful `connect()` RETIRES it (`s.reconnectError = null` beside `s.lost = null`) - a live session is proof the credential works, so a later loss can never be blamed on a sign-in the user already fixed. One expired profile fails EVERY operation that touches it at once (the session heal, the cluster listing behind the picker, an explicit Reconnect), so the box would stack two or three identical copies on one card; the de-dupe lives in **`errorBox` itself** (`duplicatesSessionReauth`, matching on code AND the same named profile - a non-reauth failure and a *different* profile both still render, since a hidden real error is worse than a repeated one), never at the call sites, and `sessionReauthBox` renders through **`errorBody`** directly because it is the copy that survives and must not suppress itself. The renderer **fails closed**: `reauthProfile` no longer falls back to the picker's selection (a different profile than the dead session's, or `''` while connected), so with no name on the error the box explains without naming one and shows NO command row - `databricks auth login --profile ` with an empty tail is worse than no command, since the copy button hands it over verbatim. **Scoped deliberately, and this is the no-regression rule:** only `mode:'profile'`, and never a `needsSignIn` profile - a bare typed **host** and a no-token `auth_type=external-browser` profile are precisely the two shapes whose token Cellar's OWN sign-in re-mints (`hasCellarCachedOAuth`), so for them `oauth_login_required` stays correct; redirecting those to the CLI would be the same dead end with the sign flipped. The pure rule + the copy live in the browser-safe **`src/lib/databricksReauth.ts`** (shared by server and sidebar so they cannot drift): `isProfileReauthError` matches a dead refresh token (`refresh token is invalid|expired|not set`, `invalid_refresh_token`) OR the databricks-cli strategy failing *together with* the CLI's own `databricks auth login` remedy sentence - each signal alone is too loose - and `reauthMessage()` puts Cellar's actionable head in front of the SDK's own text (so logs and MCP results are actionable too) with `reauthDetail()` splitting it back off, so the sidebar's detail row never repeats the remedy the box above already spells out. **Cellar deliberately does NOT run `databricks auth login` for the user** (and there is no MCP tool for it): it is interactive, opens a browser, can prompt for a workspace choice on a TTY Cellar does not own, and with `auth_storage = secure` writes through the OS Keychain - a hung subprocess and a half-written credential are the failure modes, so showing the exact copyable command is the reliable remedy. The sidebar renders it as a `reauthBox` snippet inside `errorBox` (`Databricks.svelte`), with the command built from the shared `REAUTH_COMMAND_HEAD`/`REAUTH_PROFILE_FLAG` constants and the flag held in a `whitespace-nowrap` span - in the ~200px box the command MUST wrap, and a browser breaks after a hyphen, which split `--profile` into `-` / `-profile`. Every Databricks route now returns its failure through the one shared **`src/routes/api/databricks/error-response.js`** (`databricksErrorResponse`) so the new `profile` field cannot be dropped by one of the nine catch blocks. Covered by `tests/unit/databricks-profile-reauth.test.ts` (the REAL SDK error text committed verbatim as a fixture; both seams; the two regressions) + `tests/e2e/databricks-profile-reauth.spec.ts` (mocked routes). **The split is the design:** *listing* (profiles/clusters/catalogs/schemas/tables) runs **server-side** in a short-lived subprocess of the project venv's python (`projectPython()` = `CELLAR_PROJECT_VENV`, the same interpreter the kernel uses - so "can the kernel import the SDK" and "can our listing import the SDK" can never disagree); *the session* runs **in the kernel**, because `spark` must live where the user's cells can reach it. One python script (`PROBE`) serves every listing op, driven by a JSON command in `argv[1]`; it **always prints exactly one `__CELLAR_DBX__`-prefixed JSON line and never raises**, so a missing package / bad profile / unreachable workspace arrives as `{ok:false, code, message}` rather than a traceback we would have to guess at. `code` is the contract: the sidebar's `REMEDY` map turns it into actionable copy, and `statusFor()` into an HTTP status. Embedded as a JS string (not a sibling `.py`) because `$lib/server` is bundled into `build/` - the same reason `inspect.ts` embeds its probe. Both halves scrub `DATABRICKS_*`/`SPARK_CONNECT_*` from the environment, **keeping `DATABRICKS_CONFIG_FILE`** (the one deliberate divergence from the boilerplate: it is what says where the config we just parsed lives). Profiles are parsed **in Node** so the picker renders before the SDK is installed; a section without a `host` is not a profile (the CLI writes `[__settings__]` into that same file). **Connection state is epoch-scoped**: `connect()` stamps the kernel-session epoch from `execute()`'s `kernel` event, and `connectionStatus()` reconciles against `currentSessionId()` on every read - the exact `lastRun` doctrine, for the exact reason (a restart destroys `spark`; reporting "connected" from a dead namespace hands the user a `NameError`). **The epoch cannot see a session that died WITHOUT a restart** (idle-timeout / cluster-GC expiry, or a locally CLOSED Spark Connect client), so a second, real-liveness layer sits on top: `assessLiveness()` (the ONE decision, shared by `agentStatus` heal:true / `getStatus`→`liveConnection` heal:false → live/reconnected/expired/unverified), backed by the cached `PING_CODE` probe and `autoReconnect` (rung 2, reuses `connect()` via `reconnectTo` - never add a second reconnect path). **The load-bearing signal is `spark._client.is_closed`, checked in `PING_CODE` BEFORE `SELECT 1`:** a closed client is a definitive, synchronous, no-round-trip dead-session fact, and when set the `SELECT 1` only raises `[NO_ACTIVE_SESSION]` (which the message-matching set + `isSessionClosed()` now include). The prior bug reported `connected:true, liveness_unverified:true` over a closed client because the probe swallowed `NO_ACTIVE_SESSION` as a transient error and never confirmed expiry - so `is_closed`/NO_ACTIVE_SESSION MUST classify as `expired` (→ heal), never `unverified`. `w`-only ops are unaffected (only the Spark session is probed/healed). The UI (`getStatus`) fires the heal fire-and-forget so a poll never blocks minutes on a cold-cluster reconnect. Covered by `tests/unit/databricks-liveness.test.ts` (closed-client + NO_ACTIVE_SESSION cases). Connect/disconnect/preview run through `execute(..., {internal:true})`, so they bypass the run QUEUE (like `inspect.ts`'s probes) and never inflate `execs_this_session`; the per-kernel exec lock (`execChain`, see kernel.ts) still serializes them behind a running cell - two `requestExecute` on one kernel must never overlap (that collision wedges `future.done`; the `cellar-runall-kernel-wedge-z3` root cause). A connect can legitimately take minutes (Databricks Connect starts a cold cluster), which is why the route just waits. `databricks-sdk`/`databricks-connect` install into the **project** venv via `venv.js`'s `installPackages` (the one place Cellar adds anything to a project venv). **`databricks-connect` MUST be ≤ the cluster's DBR** (a newer client hard-fails the session: "Unsupported combination of Databricks Runtime & Databricks Connect versions"), so it is pinned to the cluster's DBR **major.minor** line (`databricks-connect==17.3.*`, newest patch of that minor). `installDeps({version})` does the pin; `connect()` enforces it in **two layers** (pure decisions in `dbrVersion.ts`, unit-tested with no cluster). **Part A (prevention):** before building the session, `connect()` resolves the cluster's `spark_version` via the `PROBE` `cluster` op (`w.clusters.get(id).spark_version`, authoritative, not trusted from the picker), `dbrMajorMinor`→line, and `ensurePinnedConnect` reinstalls a matching client only when the installed one is provably NEWER than the DBR (numeric major.minor compare — the actual hard-fail condition; a too-old-or-equal client connects fine and an unparseable version is left untouched, so neither reinstalls nor restarts) — restarting the kernel **only if `databricks.connect` was already imported** (a fresh first-connect import picks up the new client with no restart, so the user's namespace survives). **Part B (safety net):** if a mismatch still surfaces (unresolvable/serverless DBR), `parseVersionMismatch` reads the runtime off the SDK error itself, re-pins from it and retries once (loop-safe: `ensurePinnedConnect` returns false unless it actually reinstalled); a persistent mismatch throws a dedicated **`version_mismatch`** code with an actionable, user-facing message (`versionMismatchMessage`, names both versions + the exact `==X.Y.*` pin) that the sidebar `REMEDY` map surfaces. **Serverless is not pinned** (no classic DBR; `dbrMajorMinor`→null skips the pin) and is not regressed. Covered by `tests/unit/dbr-version.test.ts` (pure) + `tests/unit/databricks-version-pin.test.ts` (the real `connect()` turning the raw error into `version_mismatch`). **Agent side:** `kernel_state` + `get_notebook_map` carry a `databricks` block, `INSTRUCTIONS` clause 9 tells the agent to use `spark`/`w` instead of writing boilerplate, and the read tools (`databricks_status`, `databricks_list_catalogs/_schemas/_tables`, `databricks_preview_table`, `databricks_list_clusters`) reuse the **same** server-side plumbing as the UI tree (`forAgent`/`listClusters`), so the two views cannot disagree. **Agent-driven reconnect/connect (task `cellar-mcp-dbx-cluster-connect-n6`):** the agent MAY restore or connect a session but never chooses compute lifecycle or drives the OAuth browser. Two write tools, both **thin orchestration over the ONE existing recovery/connect machinery - NEVER a second reconnect path** (reviewers must reject one): (1) **`databricks_reconnect`** → `reconnectSession(nb)` (`databricks.ts`) walks the ladder cheapest-first - rung 1 `refreshKernelConnection` (kernel socket, namespace-preserving), rung 2 `autoReconnect` via `agentStatus` (server-side expiry), rung 3 `reconnectAfterKernelRestart` (kernel restart) - all funnelling through `connect()`; restores the cluster the USER already chose (the stored `reconnectTarget`), never a new one, and returns `connectedPayload` + honest **`kernel_restarted`/`namespace_cleared`** flags (a version re-pin restart clears the namespace - detected by an epoch delta across the op, the same `NameError`-trap doctrine as `lastRun`); `not_connected` when there is no target. (2) **`databricks_connect`** → `connectCluster(...)` connects a CHOSEN cluster (D1) by reusing `connect()` wholesale, gated: `assertSignedIn` refuses an un-signed-in OAuth host with `oauth_login_required` (browser sign-in stays human), and a down cluster (state from the extended `cluster` PROBE op) is refused `cluster_terminated` because **compute lifecycle is human-only (D2)** - the agent may LIST/report clusters but not start/stop/restart them; same side-effect flags. Both are wrapped in `databricksTool` + `withProgress` (a re-pin reinstall can take minutes). New `DatabricksError` codes: `cluster_terminated`, `reconnect_failed` (both 409 in `statusFor`). Covered by `tests/unit/databricks-agent-reconnect.test.ts` (each rung branch + the connect auth gate). The UI's table preview appends+runs a real cell (`spark.read.table(...).limit(N).toPandas()`) because there the cell *is* the deliverable; the agent's `preview_table` reads through `spark` and touches nothing, because an agent peeking at a table must not append to the human's document. `LiveNotebook`'s `onRegisterApi` (`insertAndRunCode`) is how the sidebar reaches the active notebook - same registry shape as `onRegisterFolds`; it deliberately does **not** move `activeId` (focus must follow selection, and the user's focus is in the sidebar). **User-facing Reconnect (task `cellar-databricks-sidebar-redesign-d5`):** the bound-but-not-live states (`expired`/`lost`) in `Databricks.svelte` show a **Reconnect** button → `POST /api/databricks/reconnect` → `reconnectSession(nb)` - the SAME ladder the agent's `databricks_reconnect` and the auto-reconnect self-heal walk, so it is **NOT a second reconnect path** (reviewers must reject one). The section follows the shared sidebar-section pattern: its header carries only the DATABRICKS label + a `refreshBtn`, wired via `Databricks.svelte`'s `export function refresh()` and a `bind:this` handle in `Sidebar.svelte` (the same `bind:this` seam Environment/Checkpoints use). There is deliberately **no** header status pill in any state (expanded or folded) - the connection status lives in the panel's connected view, not the header (the earlier redesign added an `onStateChange`-fed header badge; it was removed in full, plumbing included, by `cellar-databricks-remove-pill-dp3`). The connected view is a compact dot+name+meta line (not the old tinted `<dl>` card) and the cluster picker uses the borderless kernel-row idiom (leading state dot + trailing state text); the runtime toggle stays `toggle-success` green (a deliberate Databricks cue, unlike Files' `toggle-primary`). **Redesign v2 (task `cellar-databricks-redesign-v2-k4`) - the section is now a set of clearly separated bordered cards** (`rounded-lg border border-base-300 bg-base-100 p-2.5`, the same card idiom as the "Packages missing"/expired boxes, each with a small uppercase `CLUSTER`/`UPLOAD`/`RUNTIME` label - **the UPLOAD one was later split out of the Cluster card** (`uploadCard`, `data-testid=databricks-upload-card`, rendered between the two, still only while connected): it acts on workspace FILES and never on compute, and it carries two fields, their token dropdowns, a live preview and a two-step replace confirm, which nested under Switch/Disconnect read as more connection controls. Switch/Disconnect/Log out STAY in the Cluster card - those really are connection controls): a **Cluster card** (the connection identity + Switch/Disconnect, OR the connect-form picker when disconnected, OR a warning-tinted degraded card + Reconnect + pick-another when expired/lost) and a **separate Runtime card** (the `DATABRICKS_RUNTIME_VERSION` toggle + version + a live `● active`/`off` status), with the Unity Catalog `data` browser as a subordinate labeled region below (not a card). The connect/toggle in-progress state is decided by the ONE rule in `$lib/databricksPanelState` (a transition over a live session HOLDS the connected view and only the Cluster card changes face - see the flicker entry below) and `settleConnection()` polls until the post-restart reconnect re-establishes the session, so the panel NEVER flashes the "session lost" card during a connect or a toggle restart - do not remove that guard/poll. **A CONNECTING STATE IS A STATE OF THE CLUSTER CARD, NEVER A REPLACEMENT FOR THE PANEL (task `cellar-dbx-cluster-switch-flicker`), and the ONE rule that decides it lives in `src/lib/databricksPanelState.ts` (`databricksPanelState`) - not in the template.** The reported defect was "when i change dbx clusters there is a flickering of the screen": the connecting card was rendered as a SIBLING BRANCH of the connected view, so a cluster SWITCH unmounted the Cluster card, the Upload card, the Runtime card and the whole Unity Catalog browser down to one ~144px card and sprang all four back a moment later - measured in a real browser at **971px -> 144px -> 709px**, which on a warm cluster is one hard blink and on a cold one is a panel that empties out for minutes (everything below it in the sidebar rides that 800px both ways). `runtimeApplying` already had the right treatment - keep the cards, say it in the card header - and the connect path simply never got it, so the fix EXTENDS that blessed pattern rather than inventing one. A transition with a live session under it **HOLDS** the connected view and renders the transition INSIDE the Cluster card (the badge slot reads "connecting", the identity row names the cluster being connected TO, the `spark`/`w`-are-ready line yields to the wait's own sentence, and Switch/Disconnect stay mounted-but-disabled); only a transition with **nothing** to hold - a FIRST connect from the picker, or an expected restart whose session is already gone - keeps the standalone card, where it is an honest progression (picker -> connecting -> connected) rather than a collapse. **The hold keys off a LATCH (`connectOverLive`, set from `connected` BEFORE the await and cleared in `connect`'s `finally`), NEVER off `connected` read per frame**: a switch to an older-DBR cluster makes `ensurePinnedConnect` re-pin databricks-connect and restart the kernel mid-connect, and the status read that follows honestly reports the session lost - that is exactly the frame that must not unmount the panel, and keying off the live flag reopens the defect through a different door. **A LATCHED TRANSITION CARRIES THE NOTEBOOK IT WAS LATCHED FOR (`transitionPath` -> `panelOwnsTransition`), because the panel is ONE long-lived component whose `notebookPath` follows the active tab while every transition flag it owns (`busy`, `restarting`, `runtimeApplying`, `connectOverLive`) is panel-wide**: a connect can run to MINUTES, so tabbing to another notebook mid-connect is ordinary, and unscoped the widened hold rendered the WHOLE connected view - Cluster, Upload, Runtime and the Unity Catalog browser - over a notebook with no session, masking its own lost/expired card (the same `const target = notebookPath` idiom `uploadToWorkspace` already uses). `applyRuntime` is its SINGLE writer - it cannot run while `busy` is set, so a connect can never take it over - while `beginBusy`/`busyPath` answer for every other verb; and it is deliberately NEVER cleared, since it is only consulted while a restart flag is set and clearing it in a `finally` would let a connect settling on notebook A wipe the ownership a runtime apply started on B. The SERVER half (`connection.restarting`) is exempt and must stay so: it arrives on THIS notebook's status, so it is already scoped - which is why the rule takes `restarting` and `serverRestarting` separately rather than the merged `expectedRestart` it replaced. **The `disabled` gating asks that SAME question** (`ownedTransitionFlags`, read by the Cluster card's Switch/Disconnect, `uploadConfirmBusy` and every Runtime-card control): scoping only the VIEW left a second connected notebook rendering a plain connected card whose every control was greyed out with nothing saying why - and a click there is safe, since `connect`/`disconnect`/`uploadToWorkspace`/`applyRuntime` each re-guard on `busy`/`runtimeApplying`, so a live control whose handler declines is honest in a way a mute grey one is not. Deliberately NOT applied to the picker, sign-in, install or reconnect controls - **not** because they sit outside the connected card (the picker really does render INSIDE it, under `{#if switching}`), but because each already re-guards on the RAW `busy` (and `connect` on `runtimeApplying` too, which is what stops a cluster row starting a connect through a runtime-apply kernel restart), so a live-but-declining control is honest there by the same argument and silencing the flag for a foreign notebook would only admit a click the handler is about to refuse; log out DOES render inside the connected card and stays on the raw flags for a THIRD reason - it is app-wide, so a panel-wide `busy` genuinely blocks it and disabling it is honest. The Runtime card's version INPUT keeps the raw flags too, and is the one control that re-guards its own handler: a button whose handler declines is a visual no-op, while a keystroke there persists the workspace-wide version preference and only then meets a declining `commitVersion`, leaving a stored version nothing restarted onto. **But `busy` is attributed through its OWN latch, `busyPath`, set where `busy` is ASSIGNED (`beginBusy`) - never through `transitionPath`**: only `connect` and `applyRuntime` start a view transition while all SEVEN verbs hold `busy`, so read through `transitionPath` the other five were credited to whichever notebook last started a transition, or - on a fresh reload, where it is still `undefined` - to none at all. That unlocked the upload confirm's Cancel while its own replace was on the wire, which bumps `uploadSeq`, discards the reply and presents a clobber that HAPPENED as one the user aborted: the exact invariant `uploadConfirmBusy` exists for. The two latches answer different questions and must stay separate - reusing `transitionPath` for every verb would let a `disconnect` on B claim B is restarting while a runtime apply on A still holds the panel-wide `restarting`, and sharing ONE latch the other way let a connect on B INHERIT a runtime restart still settling on A (B's own connect wore the "restarting" badge over the outgoing cluster's name while A, having lost the latch, fell back to the standalone connecting card or a spurious "lost" - this module's own collapse, from both ends at once). So each has exactly ONE writer: `busyPath` is set at the single place `busy` is assigned (`beginBusy`, covering all seven verbs) and owns the connect half (`connect`, `connectOverLive`, which live exactly as long as `busy === 'connect'`), while `transitionPath` is written only by `applyRuntime` - which cannot run while `busy` is set - and owns the restart half, which outlives the request that asked for it. **A live-but-declining control is honest only where the control is a BUTTON**: the Runtime toggle is a one-way `checked={runtimeEffectiveOn}` checkbox with no `bind:`, so a declined click leaves the DOM flipped over a preference that never moved - `toggleRuntime`'s decline path therefore restores `checked` before returning. **Every fallback the connecting face reads is scoped to the notebook it was recorded for** (`lastMetaPath` beside `lastProfile`/`lastHost`; `connectingName` withheld unless `panelOwnsBusy`) - the panel follows the active tab, so unscoped they rendered another workspace's profile and host, or named another notebook's target cluster, under this notebook's identity row; rendering nothing beats rendering someone else's state. **And the meta line's workspace half falls back to the last LIVE connection while the card holds EITHER face** (`connectionMetaLine`): the DBR yields on the connecting face alone, since only a switch changes cluster, but a kernel restart under either face - the re-pin one mid-switch, or the one a runtime toggle issues - reports the session lost, and that payload carries no top-level `profile`/`host`; read straight from it the line came out EMPTY, its `{#if}` unmounted and the card lost a row for the whole restart - the layout jump this task exists to remove. A `settled` flag keeps the `close` that follows a spawn FAILURE (`error` fires, `exit` never does) from re-reporting it as an empty-stdout crash. Pinned by `tests/unit/databricks-probe-drain.test.ts`, which fakes `spawn` to emit `exit` BEFORE its stdout - the interleaving the OS is allowed to produce and JavaScript cannot provoke. **The same lesson for the TESTS: a canned-output `#!/bin/sh` stub interpreter is a real subprocess, so a pure-logic assertion should not use one** - `databricks-logout.test.ts` intercepts `spawn` for its fake interpreters instead (the marker file is deliberately non-executable, so a broken interception fails loudly rather than passing by luck) and keeps real spawning only for the `skipIf(!python)` block that genuinely exercises the SDK.
