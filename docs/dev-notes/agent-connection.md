# Connecting agent harnesses: `cellar mcp`, the stdio bridge, harness config

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Zero-config agent connection (`cellar mcp`).** Because the MCP HTTP port is not fixed (a folder now PREFERS the one it had last time - see the stable-ports entry - but that preference yields to anything holding it, and an isolated / `--new` launch is always ephemeral), agents are pointed at the stdio command `cellar mcp`, never a URL. On launch `bin/cellar.js` writes `<ws>/.cellar/runtime.json` (`{mcpPort,appPort,jupyterPort,pid}`, ephemeral - gitignored, cleared in `cleanup()` on shutdown) and writes/merges `<ws>/.mcp.json` with a `cellar` stdio entry (`--no-mcp-config` opts out). `runtime.json` lives in `src/lib/server/runtime.js` (node-builtins + `fetch` only, importable by launcher and `$lib`); the `.mcp.json` merge lives entirely in `src/lib/server/harness.js` (see the next entry) - `runtime.js` writes no agent config - and is idempotent and preserves other servers. The `mcp` subcommand (handled at the top of `bin/cellar.js`, before normal arg parsing) calls `runMcpBridge` in `src/lib/server/mcp-bridge.js`: reads runtime.json, verifies alive (pid AND a GET to `/mcp`), then transparently proxies JSON-RPC both ways between a `StdioServerTransport` and a `StreamableHTTPClientTransport` to the live server (schema-agnostic, so it never drifts). Missing/dead instance at STARTUP → exit 1 with a stderr message that names the CAUSE (nothing is running here, the bridge never starts one) rather than reading as a misconfiguration, and prints the `cd <ws> && cellar` that fixes it - deliberately still a message, NOT an auto-launch (booting a headless second Cellar behind the user's back is a separate decision). An instance that goes away AFTER the bridge is running is a different case and must NOT exit - see the re-attach entry below. `runMcpBridge` returns a promise that stays pending until shutdown - the launcher must `await` it (an early `process.exit` kills the bridge right after connect). Both new modules are added to `package.json` `files`. The sidebar "Connect an agent" panel is reframed around this flow (see Sidebar entry below).
- **`cellar mcp` RE-ATTACHES across a Cellar restart - the bridge must never treat a dead upstream as its own shutdown (`src/lib/server/mcp-bridge.js`).** The reported pain was "cellar changes port on every restart, so I have to restart the MCP each time", and **the port was not the cause** - reproduced end to end with the port held FIXED (`CELLAR_MCP_PORT`) across a restart and the failure was identical, so a stable port is no cure at all and pinning one only ever masked it by accident. **Trigger:** a restart replaces the app process and every Streamable-HTTP MCP session with it. **Mechanism:** the bridge is a SEPARATE process the AGENT'S HOST owns, so it outlives that and goes on holding a session id no new server recognises; it wired `shutdown()` to `upstream.onclose` alone, but `StreamableHTTPClientTransport` reports a dropped/refused connection through **`onerror`** (`onclose` fires ONLY from its own `close()` - one call site, verified in the SDK at v1.29.0), so the bridge never exited, never re-read `runtime.json` and never re-initialized. **Masking condition:** an MCP host respawns a stdio server only when its child process EXITS, and a live-but-useless child looks perfectly healthy, so nothing ever triggered a reconnect. **Symptom:** every later tool call failed - `fetch failed` on a moved port, `-32000 No valid session; send an initialize request first.` on the same port - surfacing to the human as a hang and then `MCP error -32001: Request timed out` at 60004ms, curable only by reconnecting `/mcp` by hand. **The fix is re-attachment, and its rules are each load-bearing:** the bridge CAPTURES the agent's original `initialize` request and replays it (under a SYNTHETIC `cellar-bridge-init-<n>` id) against the replacement server, followed by `notifications/initialized`, so a fresh session is minted without the agent knowing; the replay's reply is SWALLOWED, never relayed (the agent finished its handshake long ago, so a second `initialize` result under an id it is not waiting on is a protocol surprise) - **EXCEPT when the message that failed IS the agent's own `initialize`**, i.e. Cellar was replaced in the window between the bridge's startup attach and the agent's handshake: that replay STANDS IN for a handshake the agent is still waiting on, so its reply is relayed under the AGENT's id (`ownIds` maps the synthetic id to the agent's, or to `null` for an ordinary re-handshake) and the request is NOT re-sent (`handedOff`) - a transport is initialized exactly once, and a second `initialize` earns `-32600 Server already initialized`, failing the very handshake the recovery is completing. `detach()` clears `onmessage`/`onerror`/`onclose` **before** `close()`, so a deliberate swap cannot cascade into the very shutdown this exists to prevent, and `onerror`/`onclose` now only LOG - **nothing about a dead upstream may be fatal**, because a bridge that exits is a bridge the host must respawn, which is the whole defect.
  - **RE-ATTACHING IS DRIVEN BY EVIDENCE THE SESSION IS GONE, NEVER BY "a send failed" - this is the rule most likely to be quietly undone, and undoing it is worse than the bug it fixes.** A re-attach CLOSES the session, and with it the open POST and SSE stream every in-flight request is riding; Cellar's run tools deliberately hold that POST open for the WHOLE cell run (minutes, streaming progress notifications), so an over-eager trigger aborts a multi-hour job over a stale keep-alive socket or a 429. `send()` rejects for three quite different reasons and `classifyUpstreamFailure` is the ONE place that tells them apart. (a) **`session-gone`** - the server itself refused us (a 400 carrying `-32000`/a session phrase, or a 404 to a request bearing a session id, which the Streamable HTTP spec defines as re-initialize): this IS the evidence, re-attach at once. (b) **`connection`** - nothing answered (`fetch failed`, ECONNREFUSED/ECONNRESET, socket hang up, and an ABORT, since our own `detach()` aborts in-flight sends): ambiguous, because a replaced instance and a healthy one behind a dropped keep-alive socket look identical, so it is CONFIRMED first (`instanceVerdict()`: `runtime.json` naming a DIFFERENT mcp port, or a different PID, or the instance it names not answering) and an unconfirmed blip is retried ONCE on the SAME session, which a fresh socket satisfies. **The PID is load-bearing and the port alone is NOT sufficient**: once a folder REMEMBERS its ports, the same port coming back is the EXPECTED shape of a restart rather than evidence of continuity, so the port comparison passed, the liveness probe was answered by the REPLACEMENT, and a genuinely replaced instance read as present - a request failing ambiguously on a stale keep-alive socket then declined its resend AND skipped the heal, so a long run already in flight hung until the host's timeout. A different pid is POSITIVE evidence of replacement, so it strengthens the evidence rule; an instance recording no pid falls back to the port-and-liveness signals unchanged. (c) **`other`** - a live, session-valid server rejecting THIS message (429, 500, bad params): relayed as an error for that ONE request, with no detach, no re-handshake, and no disturbance to anything else in flight. **The status short-circuit outranks the message text, and must stay that way**: the SDK folds the response BODY into the error message, so text-matching a 500 let Cellar's own outer catch (`mcp error: <anything>`) tear down a healthy session whenever a tool failure merely MENTIONED a session (a Spark Connect one, say) - the same over-trigger reached through the other door. Text is consulted only for a failure carrying no usable status.
  - **ONE EVIDENCE READER, TWO BARS - because the two callers are not equally destructive** (`instanceVerdict` -> `replaced` | `unreachable` | `present`). `deliver` reaches its verdict only after a send has already FAILED, which is independent evidence in its own right, so ONE reading decides and that path is unchanged. **The stream-loss heal has no such evidence**: it fires on a signal the SDK itself treats as recoverable (`onerror` precedes its own reconnect attempts), and its only NEGATIVE signal is `mcpPortResponds`' 1500ms GET timing out - which a perfectly healthy Cellar produces whenever it blocks its own event loop (a synchronous jupytext `spawnSync` persist, a `git blame`, a large notebook `JSON.stringify`), while `pidAlive` still says the launcher is up. Acting there DETACHES, and `detach()` aborts every in-flight POST with it - so on a single timed-out reading the heal tore down a healthy session and answered the long run it exists to protect with `LOST_RESULT_MESSAGE`, the outcome this module's own header calls worse than the bug being fixed (the exposure window is EXACTLY while a run is streaming, since that is what puts an id in `strandedRequestIds()` at all). So the heal is held to the corroboration doctrine this repo already applies to destructive verdicts (`pidReapDecision`: killing REQUIRES a positive match; the kernel watchdog's `SUSPECT_STRIKES`): `healConfirmsGone()` acts at once on POSITIVE evidence (a moved port, a different pid, no record at all) and otherwise needs `HEAL_CONFIRM_PROBES` (2) CONSECUTIVE unreachable readings, with a single `present` acquitting immediately. A read that THREW is `unreachable`, never `replaced` - it establishes nothing about a replacement, so it may not be spent as positive evidence. **Stated residual**: a stall outliving every probe still convicts; the bar is raised from one window to two, not removed. **The two RE-HANDSHAKE sends in `attach()` are the one thing given a DEADLINE** (`HANDSHAKE_SEND_TIMEOUT_MS`, 10s, on the `probeKernelLiveness` precedent that a probe must always settle): they are `fetch` calls the SDK gives no per-request bound, so against a wedged-but-accepting instance - the kernel completes the TCP handshake while the app's event loop is blocked - they parked until undici's ~300s `headersTimeout`, and while parked `reattaching` never settles, so every `deliver` awaiting it hangs AND the heal is disabled for the whole window (it sets `healingStream` before awaiting), i.e. minutes past the 60s host timeout this module exists to avoid. The REPLAY's timeout also `detach()`es (that transport is brand new and carries nothing but these two messages, so cancelling it destroys no protected work and releases the socket); the NOTIFICATION's may not, the session being already minted with the replay's reply on its way. **Ordinary relayed sends stay UNBOUNDED** - a run tool legitimately holds its POST open for the length of a cell run, so bounding those would abort exactly the work being protected. **AT MOST ONE RESPONSE PER REQUEST ID, which is a protocol requirement and not a nicety.** **THE STREAM-LOSS HEAL is the one recovery `deliver` cannot drive** (`healAfterStreamLoss`, from `t.onerror`): every other path runs per SEND, so a request already IN FLIGHT when the instance dies was answered only if the agent happened to send ANOTHER message - and MCP hosts serialize tool calls, so for the headline case (a long `run_cell` in flight across a restart) there IS no next message and the call hung until the host's 60s timeout, the very symptom this bridge removes. The doctrine is applied there rather than relaxed: the error is still never the trigger, `instanceGone()` is asked FIRST (it needs no error message), a live instance means nothing happens at all, and nothing is ever RE-SENT - the requests are answered with `LOST_RESULT_MESSAGE`. **Stated residual**: a stream that dies against an instance that is still ALIVE leaves its request unanswered, because tearing down that session would abort exactly the work this protects and the SDK may resume the stream itself. Other in-flight requests are failed ONLY after a genuine re-attach (their replies provably can never arrive) and exactly ONCE, in the single-flight `reattach()` continuation - swept per CALLER, two concurrent failures each failed the OTHER's request and then retried it, so one id got both a `-32001` "it was not completed" and a real result, telling an agent a call it completed had not. Five things make that hold together: `relaying` (registered SYNCHRONOUSLY at the top of `relayUp`, before any await, so a re-attach cannot start in the gap) exempts a request whose own relay will answer it; **`handedOff` is exempt from the sweep for the SAME reason** - the attach that just succeeded replayed the agent's own `initialize` under a synthetic id, so its answer is ALREADY on the wire and comes back under the agent's id, and once that relay has returned the id sits in `pending` but no longer in `relaying`, so a SECOND re-attach swept it: the agent got a `-32001` AND, moments later, the replay's result for one id, and the very handshake the recovery exists to complete was failed; `failRequest` is idempotent, using `pending.delete`'s own verdict as the guard, and **BOTH branches of `wire()`'s response path use that same guard** (`if (!pending.delete(id)) return;`) so the invariant holds LITERALLY rather than only where the sweep is well behaved - the ORDINARY branch needs it as much as the handed-off one, because `attach()` returns false BEFORE it detaches, so a re-attach that finds nothing serving leaves the old transport fully wired while the heal answers its stranded ids, and a long run whose POST stream is still open then delivers its real result: relayed unguarded that is a SECOND response for an id the agent was already told was lost; and a relay that finds its id gone re-sends nothing. **A hand-off is only ever as true as the stream carrying the replay, so `attach()` CLEARS `handedOff` wholesale before anything else** (before the liveness check, so the early return - nothing serving the folder - is covered too; a successful attach re-registers it once its own replay is really on the wire): left standing past its transport it exempted an id from every sweep with nothing left to answer it, and for the agent's own `initialize` that is PERMANENT, the host having no next message to send. **`healAfterStreamLoss`'s own gate therefore counts STRANDED ids, not LOST ones** (`strandedRequestIds` = pending minus `relaying`, EXCEPT that a handed-off id counts even while its relay is still running - `relaying` exempts an id because that relay answers it ITSELF and a hand-off is precisely the relay DELEGATING that, and both are true for one whole microtask turn, which is exactly the turn an error landing inside the attach is re-examined in; `lostRequestIds` subtracts `handedOff` on top and is what the post-re-attach SWEEP uses, where the hand-off really is fresh) - asked the lost set, the heal found nothing to do and returned without even asking `instanceGone()` in exactly the state where the bridge would hang for good and, never exiting, never be respawned either. Whether those ids are truly unanswerable is still decided by `instanceGone()`, not by the error. **And a re-attach already RUNNING is waited out, never a reason to give up on the error**: `attach()` adopts its new transport before it sends anything, so a replacement dying mid-handshake reports it while `reattaching` is still set - and returning there dropped that error for good, since the attach's own sweep skips the id it has just handed off and the relay that triggered it returns without answering, leaving the same permanent hang one door further in. Waiting decides nothing on its own; every check is re-asked afterwards and the recovery is still gated on `instanceGone()`. **`settledByRecovery` asks both of those ONCE, at every site where a re-attach may have run, and it is asked BEFORE any other verdict `deliver` would reach** - reached after the resend gate instead, an ambiguously-failed `initialize` was answered with the ambiguous-write error while the replay that had just minted a working session was still in flight, so the replay's real result found the id gone and was dropped and the agent's handshake failed for the life of that spawn. **That includes outranking the FAILED-re-attach verdict, which is safe only because `attach()` registers the hand-off AFTER the replay send resolves** - registered before it, a throw in the send left an id marked handed-off with nothing on the wire and so answered by nothing; registered after, a claim really does mean a result is coming. It is also asked before EVERY send rather than only after a re-attach of our own, since a concurrent relay can hand this id off in the gap a `continue` leaves and a second `initialize` earns `-32600 Server already initialized`. **And `attach()`'s SECOND send (`notifications/initialized`) may not fail the attach**: the replay before it already minted the session and its result is on its way, so a courtesy notification failing is caught and logged - failing the attach there answered the agent's `initialize` with an error while a working session sat attached, and the real result was then dropped as a duplicate. A relay also ADOPTS a session a concurrent relay just established rather than minting a second one, which would close the transport that relay is about to send on, and the whole recovery is bounded (current session, one same-session retry, one adopted-or-minted session) so a flapping instance cannot spin - **with the two bounds kept apart, because `sameSessionRetried` counts RESENDS while `instanceGone()` answers whether the SESSION is gone, and it is asked before EVERY re-attach**: letting the retry counter switch the confirmation off meant a second blip fell through to a re-attach with no evidence at all, tearing down a session against an instance provably alive on our own port (every in-flight POST aborted, every pending request swept as lost) - so a message that has already been resent once against a live instance is given up on rather than escalated. An unrecoverable failure answers `-32001` (`NO_INSTANCE_ERROR_CODE`) with a message naming the workspace and the `cd <ws> && cellar` that fixes it, and the bridge stays alive so the NEXT call heals once Cellar returns.
  - **RE-SENDING is a SECOND, narrower question than re-attaching, and its answer is deliberately ASYMMETRIC (`provesNotDelivered`).** Re-attaching asks about the SESSION; putting a failed message on the wire AGAIN asks about that MESSAGE, and conflating them silently duplicates a non-idempotent write - `add_cells`/`delete_cells`/`edit_cell` applied twice corrupts the user's notebook, which is their PRIMARY data (`run_cell` is largely spared only by the run queue's own dedupe, which is not a general defence). So ONE gate sits in front of all three resend paths (adopting a concurrent relay's session, the same-session retry, and the resend after a re-attach), and a REQUEST passes it only where the failure PROVES nothing ran: a server that ANSWERED with a session refusal (`-32000`, or a 404 to a request carrying a session id - it rejected the message before dispatching it) or a connection that was never ESTABLISHED (`ECONNREFUSED` and friends - nothing was written). **A failure carrying an HTTP STATUS is never judged by its message text** - the SDK folds the response body into that message, the same trap `classifyUpstreamFailure`'s status short-circuit exists for - so a live server's 500 whose body happens to read "connection refused" can never come back as replayable. **Those two are exactly the two shapes a restart takes** - same port and moved port - so the headline "restart Cellar and the agent's next call just works" flow is untouched. A socket that OPENED and then broke (`ECONNRESET`, `EPIPE`, `UND_ERR_SOCKET`, `socket hang up`, a bare `fetch failed`, an abort from our own `detach()`) cannot tell "never arrived" from "arrived, ran, and the reply died with the socket", so the request is FAILED with a message saying the call may or may not have been applied - the same honesty rule the rest of this codebase follows, since a visible failure beats a silent duplicate mutation and only the agent can decide what to do. A NOTIFICATION carries no id and earns no response, so a duplicate delivery of one is invisible: it keeps the full recovery, which is what makes the asymmetry structurally free (the handshake's `notifications/initialized` still survives a blip). **DECLINING THE RESEND IS NOT DECLINING THE HEAL**: the ambiguous path still asks `instanceGone()` and still re-attaches, because that repairs the transport for every OTHER message riding it and its sweep is what promptly answers the requests whose replies died with the old server - collapsed into one early return, a long `run_cell` already in flight hung on a dead session until the host's 60s timeout, the exact symptom the bridge exists to remove. **The sweep's own message obeys the same honesty rule** (`LOST_RESULT_MESSAGE`): a swept id's send had RESOLVED, and the SDK resolves a send once the POST headers arrive, so the old server had ACCEPTED it and its handler was running or had run - strictly the MORE confident case of the two - so it may only say the RESULT can never be delivered and that the call may or may not have been applied, never that it "was not completed" and never "call again", which is what applies a write twice.
  - Covered by `tests/unit/mcp-bridge-reattach.test.ts` (the REAL bridge against a real HTTP fake reproducing `mcp/server.ts`'s session rule, with only the stdio side faked; the SAME-port case is what pins "the port was never the cause", and it is the test to keep if any is ever dropped; plus the resend asymmetry in both directions over a flaky proxy - a request refused rather than replayed while a notification is still retried and the long run streaming on that session is untouched - and the handed-off `initialize` answered exactly ONCE, with its RESULT rather than the sweep's error, across two re-attaches; plus the two outcomes of a handed-off replay whose stream then DIES with the agent sending nothing further - answered honestly when nothing serves the folder, and the handshake COMPLETED when a replacement does - the same pair again for an error landing INSIDE an in-flight attach (the fake parks the re-handshake by never answering its `notifications/initialized`, which is the only deterministic way into that window), and a long run answered by the heal whose own POST stream then delivers its real result, which must go nowhere; plus the corroboration rule in all three directions over a scripted liveness probe - a single timed-out reading leaving a streaming run and its session untouched, two consecutive ones still answering it, and a changed pid convicting on the first reading while the probe says alive - and a wedged instance that accepts connections but never answers `initialize` failing the agent's call promptly instead of parking the recovery).
- **Harness MCP setup (`src/lib/server/harness.js`) - one registry, an ALLOW-LIST reconciled every start, two entry points.** Every agent harness needs the SAME stdio server (`cellar mcp`) in a DIFFERENT file, and the difference is the whole reason this exists: **Codex does not read `.mcp.json`** (it reads a project `.codex/config.toml` `[mcp_servers.cellar]` table, and only for a project the user has TRUSTED), so Cellar's zero-config `.mcp.json` was silently invisible to it. `HARNESSES` maps each supported harness to its workspace-relative config path + format (`claude` → `.mcp.json` JSON; `codex` → `.codex/config.toml` TOML - the exact shape `codex mcp add` itself writes, verified against a real Codex CLI); **adding a harness is a DATA addition, never new control flow**, and it reaches both entry points at once. Node builtins only (no TOML dependency), in `package.json` `files`, so `bin/cellar.js` imports it like `venv.js`/`runtime.js` - and it is the ONLY writer of an agent config, so the automatic per-launch write and an explicit `cellar harness add claude` are one code path (`runtime.js` used to carry `writeMcpConfig`/`mcpConfigPath` aliases; they were deleted once every caller moved here, rather than kept as a second name for the same rule). **The durable state is an ALLOW-LIST of harnesses Cellar may configure here, and the launch RECONCILES it on every start** (`reconcileHarnesses` → `configureHarness` per allowed harness): each one's config is checked and, if it is missing, stale or was deleted, repaired. That is what makes the list a standing instruction rather than a one-off write - delete `.mcp.json` and the next `cellar` puts it back. **It replaced a DECLINE marker, and the reason is the whole design:** a decline model made the most reflexive answer the most destructive one - the prompt runs before the per-launch write, so on a new workspace Claude Code always read "not configured", and pressing Enter recorded a decline that permanently switched off the zero-config `.mcp.json` write. An allow-list inverts that: nothing is ever declined, a harness is either on the list or not yet on it, and **no answer - or absence of one - can take capability away**. Claude Code is on the list BY DEFAULT (`defaultAllowed`), so a workspace with no marker behaves exactly as it always has, with no migration. Scope is per-workspace (the same `.cellar/harness.json`), deliberately not global: which agent you point at a project is a property of that project, and a fresh clone should get the defaults rather than inherit another machine's answer - the GLOBAL default lives in the registry as `defaultAllowed`, which **SEEDS** a workspace and does not override it: the first write freezes today's defaults into an explicit list, and from then on that list is AUTHORITATIVE, including against a harness a LATER release marks `defaultAllowed`. That is deliberate and is what an allow-list means - it may only grow by an explicit act, so upgrading Cellar must never silently begin writing a NEW config file into a project the user already answered for. The cost is discoverability, paid by `promptedFor` (below), never by unioning the defaults at read time. `readAllowList` falls back to the defaults ONLY when no list was ever written, which is why `disallowHarness` must persist an explicit (possibly empty) list - otherwise the fallback would silently re-add what `cellar harness remove claude` just took out. `--no-mcp-config` passes the harness owning that FILE as `exclude` (derived from the ONE registry helper **`mcpJsonHarnessNames()`** - `configPath === MCP_JSON_CONFIG_PATH`, never a pinned name), and an exclusion is per-launch only - never a change to the list. **Because it is per-LAUNCH, the app cannot infer it from the workspace marker**, so the launcher passes it through the app spawn env as `CELLAR_NO_MCP_CONFIG` and `+page.server.js` reports it as a THIRD fact (`projectRepairPaused`) beside `projectConfigured`/`projectManaged`: without it the sidebar banner claimed the every-start repair over a `.mcp.json` this instance deliberately leaves alone. The three are kept apart because their remedies differ - `cellar harness add claude` for an unmanaged entry, relaunching without the flag for a paused one - and `paused` is reported only for a MANAGED harness, since an unmanaged one is not repaired by any launch. **Writes MERGE and refuse rather than clobber** (these files hold the user's other MCP servers and settings): idempotent (`already` → zero bytes written), and anything it cannot edit confidently returns an actionable `skipped` - a file that cannot be READ at all (EACCES, or a directory where the config should be; both formats go through the ONE `readConfigText`, so neither throws a raw stack trace out of `cellar harness list`/`add` where only the JSON side used to be guarded), non-object JSON, a **non-object `mcpServers`** (the JSON sibling of the `mcp_servers = { … }` refusal below - the merge would otherwise swap the user's value for `{ cellar: … }` and report success), unreadable TOML, or a `cellar` server defined in another legal TOML form (inline table, dotted key), which is DETECTED so a duplicate is never appended. **The merge reaches INSIDE the `cellar` entry in BOTH writers, and idempotence is decided on MEANING, not on bytes.** Cellar owns `command`/`args` and nothing else, so a key the user added beside them (`env`/`type`/`cwd`) survives - the JSON writer spreads the existing entry under the canonical one exactly as the TOML writer rewrites only its two lines; replacing the entry wholesale dropped them. And an entry that already matches returns `already` and writes NOTHING whatever the file's formatting: comparing our re-serialized bytes against the user's meant a correct config indented differently was reported `updated` and rewritten on **every single launch**. The TOML writer is **text-surgical, deliberately not a parse/serialize round-trip**: it rewrites only the `command`/`args` lines inside the existing table (or appends the table), so comments, key order and every unrelated setting survive byte-for-byte - **per KEY, not merely per table**: a splice replaces whole physical lines, so a key already SAYING what Cellar would write is left alone (rewriting `command = "cellar"  # the stdio bridge` because its `args` sibling is wrong destroyed that comment to change nothing). What "already says it" means lives ONCE, in `tomlKeys`, which also builds the appended block and backs `tableMatches`, so the idempotence check and the writer cannot disagree. The scanner it reads that through is the SHARED `toml.js` (see the nbdev entry below - it was lifted out of this module), the ONE place that decides what is STRUCTURE and what is a VALUE, and it must track BOTH continuations to do it: an open `"""` multi-line string (a `[table]`-lookalike in one is DATA, and reading it as a table reports an unconfigured harness as already done) **and an open bracket**. Every structural decision - the `[`/`]` depth of a value, the `=` that opens one - reads a STRING-MASKED copy of the line (`scanLine`'s `masked`, same length so indices align), never the raw text, and `parseTomlDoc` records each key's value span ONCE (`valueFrom`/`last`) so `readAssignment` reads it back instead of re-scanning. Getting either wrong does not look like a parse error, it looks like a config that quietly lost something: counting an in-string `[` ran a value's span to the end of the table and the rewrite **spliced the user's sibling keys away**; a `[1, 2]` array element read as a table header truncated the span, so a key that WAS present read as missing and a **duplicate** was inserted (invalid TOML); and re-scanning let a `command = "…"` line inside a `"""` block be rewritten while the real key kept its wrong value. Refusal covers the rest: a value whose brackets never close is `malformed`, and a `cellar` defined in another legal form is `skipped` - including `mcp_servers` itself assigned as a VALUE (`mcp_servers = { cellar = … }`), whose key path is a mere PREFIX of `mcp_servers.cellar`, because TOML forbids extending an inline table so appending the canonical one would leave the whole file unparseable. Both writers replace the file **atomically** (unique temp in the target's own dir → fsync → rename, `writeFileAtomic`), so a crash mid-write cannot truncate a config holding the user's other MCP servers and settings. Cellar deliberately does NOT write Codex's project TRUST (it lives in the user's global `~/.codex/config.toml` and widens the agent's sandbox - the user's call), so the result carries that note instead. **Entry point 1: the first-run prompt** (`maybePromptHarnessSetup` in `bin/cellar.js`, placed **before the single-instance takeover** and the slow toolchain work - the question is answered while the terminal is quiet, and, load-bearing, a relaunch must never reap the instance that owns this folder and THEN sit waiting for an answer, leaving the user with no running Cellar at all). Every gate is the pure, unit-tested `shouldPromptHarnessSetup`: asked ONCE PER HARNESS via a durable `.cellar/harness.json` marker (`promptedFor` records WHICH harnesses the question covered, so a harness registered by a later release is still presented once instead of inheriting an answer given before it existed; an OLDER marker carrying `promptedAt` but no `promptedFor` reads as having covered today's registry, so an upgrade never re-asks about what the user was already shown - at the stated cost that such a marker also silences the question for a harness registered after it was written, a gap bounded to markers predating the field), never without a TTY (`-y`/`$CI`/piped stdin all fall through), never offering a harness the launch would not write anyway (**`--no-mcp-config` passes the `auto` harness as `exclude`**, so the prompt cannot write the exact `.mcp.json` that flag refuses - it is OMITTED, never declined, since a decline would outlive the flag), and wrapped so it can NEVER abort a launch - **nor STALL or SUSPEND one, which takes TWO mechanisms because they cover different failures**. `ask` covers a stdin that is merely SILENT: it gives up on a close, a read error, or `HARNESS_PROMPT_TIMEOUT_MS` (30s), and its timer is deliberately **not** unref'd - the launch awaits that promise, so a timer the loop may ignore would let the process fall out from under the prompt instead of giving up and continuing. A **backgrounded `cellar &`** is a different failure and the timeout is NOT a substitute for it: it reads `stdin.isTTY` as true (so `autoYes` stays false), and reading the controlling terminal from a background process group raises SIGTTIN, whose default disposition **STOPS** the process - and a stopped process runs no timers, so no timeout can ever fire and the job sits suspended until `fg`. **Overriding that with a SIGTTIN listener is measurably WORSE, do not "fix" it that way**: with a handler installed the read returns EIO, libuv retries it, and the process spins at **100% CPU** without ever reaching the JS handler or the timer (measured on a real pty; the unhandled case sits in state `T` at 0% instead). The only fix is not to read at all, so the prompt is gated on **`inForegroundJob()`** (`ps -o pgid=,tpgid= -p <pid>`, the same `ps`-scan convention as `instances.js`): a **proven** background job (`=== false`) is skipped outright, records nothing, and launches normally. Unknown - no controlling terminal, a `ps` without `tpgid`, Windows (which has no such stop) - still prompts behind the timeout, because reading unknown as "background" would silently retire the prompt everywhere that `ps` differs. **The question can only ADD, and that is the invariant to preserve:** it offers only harnesses NOT already on the allow-list (an allowed one is already kept in place, so there is nothing to ask), and no path through it ever calls `disallowHarness`. So a bare Enter, an explicit `no`, a typo, a closed stdin, the timeout and a background job are all harmless and differ only in bookkeeping: a real answer (Enter included) records `promptedAt` + `promptedFor` and closes the question for the harnesses it showed; a NON-answer (`parseHarnessAnswer`'s `answered` - no answer at all, or one nothing in which resolved) records nothing, so the next interactive launch asks again. **Ctrl-C is the ONE answer that stops the launch, and it needs `ask`'s OWN `rl.on('SIGINT')` listener**: readline runs in terminal mode here (stdout is a TTY), which puts stdin in raw mode and SWALLOWS ^C, so the module-level `process.on('SIGINT')` never fires and the keystroke read as "no answer" - the launcher then went on to reap instances, boot the sidecar and open a browser, the opposite of what it means. The listener closes the interface (restoring the terminal) and hands off to the launcher's EXISTING `shutdown(0, …)`; it records nothing, and it does not weaken the never-abort rule, which is about the prompt failing on its OWN. **`parseHarnessAnswer` classifies a token into FOUR buckets, and only the last may be reported as unrecognized** - reporting a name the module DOES know as "unrecognized" asserts something false about a valid answer: a name/number on the offer is `chosen`; a registered harness already on the ALLOW-LIST comes back in `managed` (understood, nothing to write - the prompt names those one line above the question, so typing one is the natural reply, and it COUNTS as an answer, settling the question instead of reading "nothing recognized" and re-asking on every later launch); a registered harness this offer does not carry is `notOffered` (reachable today - `harness remove claude` leaves it registered, off the list and settled - answered by naming `cellar harness add <name>`, and deliberately NOT counted as an answer, since unlike `managed` it asks for something the prompt declined to offer and says nothing about what WAS offered, so closing on it would retire an open question); only a name that is no harness at all is `unknown`. **The affirmative set mirrors the already-generous decline set** (`y`/`yes` alongside `a`/`all`/`*`): the offer is usually a SINGLE harness, so the question reads as a yes/no and `y` is the most reflexive positive reply - landing it in `unknown` meant the user said yes, nothing was wired up, and the same question came back next launch. The prompt names what is already handled before asking ("Already set up and kept in place: Claude Code"), so the question visibly reads as additive. **`record` is separately false when the offer was FILTERED** (`--no-mcp-config` hid a harness that is not yet allowed): closing the question over a partial view would suppress it forever for a harness that launch never showed. **Entry point 2: `cellar harness list` / `add <name…|all>` / `remove <name…> [--strip]`** (handled at the top of `bin/cellar.js` before arg parsing, never boots a server; honors `--workspace`). `add` puts a harness on the allow-list AND configures it now; `remove` takes it off so Cellar stops reconciling it but LEAVES its config entry in place, because "stop managing this" and "delete this from my config" are different requests and only one edits the user's file - `--strip` is the opt-in that also removes the entry (`stripHarness`, which refuses in exactly the cases the writers refuse, and which removes the cellar table **plus every table NESTED under it** - `[mcp_servers.cellar.env]`, array-of-tables forms included - because an orphaned sub-table leaves a `cellar` server with an `env` and no `command` that `codexState` then reads as `other-form`, refusing every later `configureHarness('codex')` for good). **A removal also records that harness in `promptedFor`** (`disallowHarness`), because an explicit removal IS an answer about it: a `harness remove claude` run before the first interactive launch leaves an empty list and no `promptedAt`, so without it the next start offered to add back exactly what the user had just taken away. Recorded PER HARNESS, never by stamping `promptedAt`, which would close the question for every other harness too - including one never shown, the very gap `promptedFor` exists to close (hence `promptedHarnesses` reads a `promptedFor` list on its own, and falls back to "everything registered" only for an OLDER marker that carries `promptedAt` with no list). `list` shows BOTH facts per harness - managed here, and configured right now - because the gap between them is the interesting state: a managed harness whose config is missing is precisely what the next start repairs. Both surfaces print that the tools arrive only **while `cellar` is running in that workspace** - the config alone is inert, since `cellar mcp` bridges to a live instance (see the entry above). The registry refuses what it cannot edit, but the WRITE can still fail on the filesystem (a read-only workspace, ENOSPC, EACCES on `.codex/`), so `add` catches **per harness** and prints that in the same one-line `[cellar] …` shape: `add all` continues past one failure and the exit code still says something failed, instead of exiting on an unhandled exception. **Both write paths record the ALLOW-LIST BEFORE writing the config** (`allowHarness` then `configureHarness`, in the prompt loop and in `harness add`): the list is the standing instruction and the write is only its FIRST reconcile, so a filesystem failure must leave a MANAGED harness the next start repairs. Ordered the other way, a throw skipped `allowHarness` while the prompt's `markHarnessPrompted` still closed the question, and the user's explicit "wire up Codex" was lost for good - nothing recorded, so no reconcile ever covered it. **All THREE `configureHarness` call sites catch per harness** - that verb, the launch-path write, and the PROMPT's own configure loop - for the same reason the prompt is wrapped: agent wiring may never abort a notebook launch. The prompt's is load-bearing beyond the outer catch, since a throw there escapes past `writeHarnessSetup`, discarding a successful sibling write AND the answer itself, so the question would come back on every later interactive launch. Three further write rules, all learned the hard way: the atomic replace **FOLLOWS a symlink** (`realpathSync` first, temp staged in the RESOLVED file's own directory), because rename installs a new inode over whatever it lands on - so staging beside the LINK replaced a dotfile-manager's symlinked `.mcp.json`/`.codex/config.toml` with a regular file and silently detached that setup; resolving first keeps the link AND the atomicity, and a target that does not exist yet resolves to nothing and is written in place. It **carries the target's MODE across, applied to the temp BEFORE the bytes go in** (temp+rename installs a new inode, so without it a `chmod 600` config - these routinely hold another server's `env` block with an API token - came back 0644; and because the temp sits in the TARGET's own directory, writing first left a complete copy of that config readable at the default `0o666 & ~umask` for the length of every write, so "set the mode on the finished file" - the obvious reading - is the wrong one, and the order is pinned by a source guard), and an INSERTED line **wears the file's own line ending** (emitting LF into a CRLF config left mixed endings, i.e. a two-line edit that diffs as the whole file; untouched lines keep their own bytes, so only new lines consult `dominantEol`). And a REFUSAL is not success: `cellar harness add` exits non-zero on `skipped`, or a scripted `add all` reported success having configured nothing. Covered by `tests/unit/harness-registry.test.ts` (both writers byte-for-byte, merge safety, idempotence incl. equivalent TOML spellings, the refusals, the value-vs-structure traps in both directions - an in-string bracket, a nested array, a multi-line string holding a lookalike key, the inline-`mcp_servers` prefix - the allow-list's persistence in BOTH directions incl. removing the DEFAULT harness sticking, reconcile repairing a deleted/edited config and writing nothing when correct, `stripHarness` in both formats plus its refusals, the prompt-once / non-interactive / can-only-ADD rules with a source guard that no prompt path calls `disallowHarness`, an explicit removal not being offered back while a harness never shown still is, the four token classes - `y`/`yes` taking everything offered, an already-managed reply settling the question and writing nothing, a not-offered one leaving it open, and no REGISTERED name ever landing in `unknown` - the filtered-view `record` rule in both directions, a source-order guard that the prompt precedes the takeover, the three no-answer outcomes exercised against the SHIPPED `ask` over fake stdio (closed stdin, read error, timeout), the pure `foregroundFromPs` verdicts in all three directions plus a guard that the gate is `=== false` and sits above every write, mode preservation (plus a source guard that the temp is tightened BEFORE the bytes), a symlinked config surviving a write AS a symlink with the real file receiving the merge, the launcher passing `CELLAR_NO_MCP_CONFIG` through and deriving the flag's harness from `mcpJsonHarnessNames()`, and CRLF, an unreadable config refusing rather than throwing in BOTH formats, and the CLI verb over a real `bin/cellar.js` spawn - list showing both facts, add/remove/--strip, and a refusal exiting non-zero). Note `inForegroundJob()` guards the harness PROMPT only: the sibling `confirm()` (venv/ipykernel) still reads stdin, so a backgrounded `cellar &` can be stopped by SIGTTIN there - a known pre-existing gap, deliberately left alone because refusing to read would change what such a launch DOES.
