# Cell and notebook UI: editor, markdown, math, rendered links, row toggles, layout

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **UI.** `src/lib/Cell.svelte` = one cell — CodeMirror editor (language via a Compartment: python / markdown). **Editor theming is centralized in `src/lib/editorTheme.ts`, which exports one constant extension `EDITOR_THEME`** shared by `Cell.svelte` and `FileTab.svelte`. It is deliberately **theme-independent**: every color is a `--cellar-cm-*` custom property resolved in `app.css` by `light-dark()` against the **resolved `color-scheme`** daisyUI sets on `<html data-theme>` (never a theme-name allowlist), so a theme toggle is a plain CSS repaint that dispatches **nothing** into any editor. **Do not reintroduce a theme `Compartment`**: swapping a theme through one makes CodeMirror re-mount the single shared `<style>` element it keeps in `document.head`, invalidating document-wide style, and doing that once per mounted editor turned a toggle into N full-document style+layout recalcs (~16ms each → ~800ms of blocked main thread at 61 cells; now ~23ms flat). The consequence: the editor never sets CodeMirror's `dark` flag, so `EDITOR_THEME` must itself supply every color the library's `&light`/`&dark` base rules would have picked (panels, tooltips, buttons, text fields = the search panel + autocomplete popup) — add a token there, not a `dark:` option. The live editor palettes are Atom "One Light" (retuned for WCAG AA) on the grey editor surface and One Dark ported verbatim (the `@codemirror/theme-one-dark` dep is gone); the HTML export keeps the older pygments "default" light scheme. Palette provenance + license notices live in `THIRD-PARTY.md`. `light-dark()` takes colors only, so the few non-color values that differ by scheme (syntax font weight/style) key off `<html data-color-scheme>`, an attribute `applyTheme()` in `+page.svelte` derives from that same resolved `color-scheme`. There is no `theme` prop on `LiveNotebook`/`Notebook`/`Cell`/`FileTab`. `Cell.svelte` also carries the per-cell toolbar and renders nbformat outputs. **Copy input / copy output** (`data-testid=copy-input`/`copy-output`, beside the run/clear controls; the text rule lives in `src/lib/copyCell.ts`): both read the cell MODEL - `currentSource()` and `cell.outputs` - never a rendered node, so they work for a cell windowing has never mounted. The rule is *copy gives you, as text, what the cell SHOWS*, so `copyCell.ts`'s mime priority mirrors `renderOutput` below and a picture / plotly chart / live widget contributes NOTHING (an image-only cell's button is therefore disabled rather than copying matplotlib's `<Figure …>` placeholder repr). **A DataFrame copies the TABLE the grid shows, not pandas' elided repr**: the structured payload outranks `text/plain`, and a SAVED one - whose structured MIME clean-on-save strips - is recognized through the SAME `parseDataFrameHtml` (`$lib/dataframeHtml`) `renderOutput` re-parses it with, never a second parser, so a live and a re-opened DataFrame copy the same shape. **ALL `text/html` outranks `text/plain`, not only the DataFrame shape** - html is what `renderOutput` SHOWS (in a sandboxed iframe) and IPython attaches a placeholder `text/plain` repr to almost every rich object, so preferring the repr pasted `<folium.folium.Map …>` for a map the cell renders in full; html that parses as a DataFrame copies its table, any other rich html is tag-stripped to a tab-separated table, never pasted as markup, and an all-script bundle (folium, Bokeh, Altair, plotly's html renderer) strips to nothing and so DISABLES the button - the image/plotly outcome, never a placeholder (that parse is browser-only, so outside a DOM a saved DataFrame repr falls through to the tag-strip rather than to `text/plain`, and `parseDataFrameHtml` answers a bundle carrying neither of its cheap admission tokens - `dataframe`, or a Styler's `col_heading` - by a regex scan rather than a full DOM parse it would only reject). **A `text/html` payload over `MAX_HTML_COPY_CHARS` (512 KiB) is refused outright**, measured off the nbformat line ARRAY so an oversized bundle is never even joined into one buffer: that decision runs inside the `$derived` on the cell-mount path AND during SSR, on the process carrying the kernel websockets and the SSE fan-out, and what exceeds it is an inline JS bundle (Bokeh `INLINE`, plotly `include_plotlyjs=True`) that is all script and would disable the button anyway - the same cheap-refusal spirit as `dataframeHtml.ts`'s `/dataframe/i` pre-check, with pandas' own repr (60x20 by default, ~25 KiB) three orders of magnitude clear of it. **Whitespace inside a `<pre>` is CONTENT, so those bodies are lifted out before the per-line tidy and put back after it** (`PRE_BLOCK` -> `preformattedText`, parked behind a NUL sentinel `decodeEntities` refuses to mint, so no payload can forge a slot): collapsing space runs and stripping indentation there destroyed the alignment of pygments-highlighted code, an aligned ASCII table or a `<pre>`-wrapped `to_string()`. The placeholder carries the trailing newline the `</pre>` it replaces would have emitted and no leading one, so block boundaries around a `<pre>` are unchanged. A **TRUNCATED** frame keeps pandas' own `[N rows x M columns]` footer, built in the ONE `dataframeTable` from `total_rows`/`total_cols` so the live and the saved payload copy it identically - that completeness signal is what the elided repr carried for free and what the grid shows as a truncation banner, and without it a 1M-row frame pastes 500 rows saying nothing; the totals are validated, never trusted (a missing or non-numeric one falls back to the counts present, so the footer can never read `[undefined rows …]`), and a non-truncated frame gets none. **A trailing TAB is a real, empty last column, so only ONE is ever trimmed** (`trimCopyText`, plus the per-line ` *\t? *$` in `htmlToPlainText` and its non-`.trim()` tail): a greedy trailing-whitespace trim pasted a row whose last cells are empty one column short of its siblings, i.e. ragged data in exactly the paste-a-table case this conversion exists for - text that is nothing BUT whitespace is still nothing to copy, which is what keeps a bare `print()` disabled. **The leading trim is `^\n+`, NOT `^\s+`**, for the same reason at the other end: a pandas Styler's header line opens with the tab of its blank index heading, and eating it left the header one column short of every row. **Whitespace touching a TABLE-STRUCTURE tag is absorbed first** (`TABLE_LAYOUT_WS`, before the tag strip): a jinja-templated Styler the grid refused - which ships no `text/plain` and no `class="dataframe"`, so this path is all it has - puts a newline plus an indent between every cell, and those newlines survived the strip, so each cell landed on its own line and the whole frame pasted as ONE vertical column. Scoped to the table tags deliberately, never a blanket inter-tag collapse: a newline between two `<span>`s IS the line break in pygments-highlighted code. Both shapes (compact and pretty-printed) are pinned by test, since a fixture written with no whitespace between its tags cannot see either bug. **`copy-output` is disabled exactly when the copy would be EMPTY** - the enabled test reads the CONVERTED text, not the mere presence of a mime, so a bare `print()` (stream text `"\n"`) and an all-script Bokeh/Altair bundle disable it instead of admitting a click that copies nothing; `hasCopyableOutput(outs) === (copyOutputText(outs) !== '')` holds by construction because both read one per-output conversion memoized on output ELEMENT identity (a WeakMap, like `renderCache`), which is what keeps the `$derived` off a multi-MB regex+DOMParser pass on every ~40ms stream flush. The disabled REASON rides the `aria-label`, since a disabled control gets no pointer events and its `title` can never be hovered. The button is omitted entirely on a markdown cell; `copy-input` is always available. A MISSING value copies as a BLANK cell where the grid draws an italic `NaN` - the one **stated exception** to the shows-what-you-see rule (both payload sources reach `cellStr` as `null`), because a blank pastes into a spreadsheet as a real empty/NA cell while the literal `NaN` would paste as TEXT; the accepted cost is that a missing value and a genuinely empty-string cell copy identically, and live-vs-saved parity is untouched (one path, one string). `asText`/`stripAnsi`/`DataFramePayload` are shared with `$lib/search.ts` via `$lib/outputText.ts`, but the two PRIORITIES deliberately differ in TWO places (search returns the `<Figure …>` placeholder as searchable text where copy returns nothing; and search never touches `text/html` AT ALL, falling through to `text/plain`, where copy reads it both ways - so a SAVED DataFrame value the grid shows but the elided repr hid is copyable yet not findable, while a folium map is findable by its placeholder repr yet honestly not copyable - a PRE-EXISTING search-side gap, not a regression, whose fix would put a DOMParser parse and a multi-pass string conversion on the search hot path) - decide for both before changing either. A denied `navigator.clipboard.writeText` resolves to `false` and simply shows no confirmation. Covered by `tests/unit/copy-cell.test.ts` + `tests/e2e/copy-cell-io.spec.ts`. **Image outputs** (`image/png`/`jpeg`/`gif` base64, `image/svg+xml` URI-encoded) render as an `<img data-testid=output-image>` via `imageDataUrl()`; the image mime is **preferred over `text/plain`** so a matplotlib figure shows the plot, not its `<Figure … with N Axes>` repr (the kernel's inline-backend injection is what makes `image/png` present - see the Kernel bridge entry). **Double-click an image toggles fit-to-width ↔ natural pixel size** (JupyterLab behavior): in full size the `<img>` (`max-w-none`) is wrapped in an `overflow-auto` box (`data-testid=output-image-wrap`, capped `max-h-[80vh]`) so it scrolls within the output area instead of widening the notebook. The choice is **view-only** local `$state` keyed by output index (`fullImages` Set) - a re-run resets it, never touches the `.ipynb`. Because that wrapper owns its own scroll, a full-size image (like a DataFrame grid) is excluded from the outer output-scroll auto-contraction and hides that toggle (`ownsScroll = hasDataframe || hasFullImage`), so there is never a nested double-scroll. Markdown cells render to sanitized HTML (markdown-it `html:false` + DOMPurify, client-only via `browser` guard); double-click / pencil button → raw edit; Run/⌘Enter renders in place, Shift+Enter renders+advances. Type toggle is the far-right `python3`/`markdown` label. Editor source autosaves via debounced `PATCH`. Dev exposes `window.cellarViews[id]`. **Active cell** = `LiveNotebook` `activeId` (set on a Cell's `onfocusin`/`onpointerdown`, and on keyboard move); the active Cell gets a `border-primary` ring + a left accent bar (`data-active`), works in both themes. **Drag-to-reorder cells**: a per-cell grip handle (`data-testid=drag-handle`, `draggable`) + HTML5 DnD drop zones in `Notebook.svelte` → `onMoveToIndex` → the move route's `{toIndex}` → server `moveCellTo` (persists + git-clean like any move; keyboard ⌘/Ctrl+Shift+Arrow still works). **Scrollable outputs** (Jupyter "Enable Scrolling for Outputs"): a per-cell toggle contracts a tall output to a fixed-height scroll box; auto-applies above `SCROLL_THRESHOLD` px unless overridden. The choice persists in `metadata.cellar.output_scrolled` (undefined=auto / true / false) — round-trips through clean-on-save; note `cellView` in `notebook.ts` now carries `metadata` so the browser sees it, set via PATCH `{scrolled}`. **Collapsible code editor** (sibling of scrollable-outputs, code cells only): the editor grows with content up to `EDITOR_MAX_PX` (576px = `max-h-[36rem]`), then a per-cell toggle (`data-testid=editor-collapse-toggle`, same style/placement as the outputs-scroll toggle) contracts it to that fixed scrollable box; auto-caps tall editors unless overridden (tri-state undefined=auto / true / false; a `ResizeObserver` on `editorEl` measures unclamped `scrollHeight`, covering content growth + the hidden→visible tab transition). **Both** expand toggles (this one and the outputs-scroll one) must clear the scroll box's vertical scrollbar, so neither is pinned at `right-1` — each measures its box's scrollbar width (`offsetWidth - clientWidth`, via `measureEditor` / a `ResizeObserver` `$effect`) and insets `style:right` by `scrollbarClearRight()` = `max(1rem, calc(0.25rem + Wpx))` (the measured term keeps a constant ~4px gap past a classic gutter of any width; the `1rem` floor covers macOS overlay scrollbars that measure 0 but paint over the edge on hover). Re-pinning to `right-1` reintroduces the overlap. Unlike `output_scrolled`, this choice is **runtime-only** like fold state — `LiveNotebook` `editorCollapsed` map persisted through the per-project UI-state store (`$lib/uiState`'s `getUi`/`setUi`, key `cellar-editor-collapsed:<absPath>`, i.e. the server-owned `.cellar/` JSON, NOT `localStorage` - there is deliberately no `localStorage` mirror, so it survives a relaunch on a new port), **never** written to the `.ipynb` (zero git-diff). Markdown edit views keep the original `max-h-96` cap. **Full-cell collapse** (`src/lib/cellCollapse.ts` = the pure rules; `LiveNotebook.svelte` owns the record, `Cell.svelte` draws the chevron + the collapsed render): a per-cell chevron (`data-testid=cell-collapse-toggle`, deliberately the same glyph + rotation as the heading fold-toggle, so the two collapse gestures read as one vocabulary) hides the cell's **input AND output**, leaving the toolbar row - which already carries the cell id, the type, the run controls and the run/stale badges - plus a one-line source preview (`data-testid=collapsed-preview`, `flex-1 min-w-0 truncate`, rendered ONLY while collapsed so the expanded layout is untouched), so a collapsed cell stays identifiable AND actionable; the chevron, or a click anywhere on the collapsed header that is not one of its own controls, expands it. **Orthogonal to its two neighbours and to heading folding, and that separation is the design**: `editorCollapsed` contracts only a TALL editor (output untouched), `hide_input` hides the input and KEEPS the output, a heading fold hides a RANGE of cells outright - a full collapse supersedes them only VISUALLY, and expanding restores exactly what they were. State is a `Record<id,true>` keyed by cell id, **never off a mounted node** (windowing means most cells have no DOM at all), persisted per notebook through the SAME UI store as `editorCollapsed` (`cellar-cell-collapsed:<absPath>`) - "hide this cell" is a durable intent, so it survives a reload - and never reaching the `.ipynb` (zero git diff). Expanding **DELETES** the entry rather than storing `false`, which is what doubles as the delete-path cleanup (`forgetCollapsed`, called from the local delete, the bulk delete and the `cell:deleted` event). **The two LOCAL deletes prune only once the server CONFIRMS** (inside `deleteCell`'s `res?.ok` branch and `deleteSelection`'s `if (await bulkOp(...))`, beside the undo group those already hold back for the same reason), because unlike its `setRawEdit` neighbour this record is PERSISTED: an optimistic prune the server then refuses (`would-empty-notebook`, via the stale client cell-count race) or that never lands (the `fetch(...).catch(() => null)` network path) has already written the state away for good - `load()` puts the cell back and `loadCellCollapsed()` re-reads the ALREADY-PRUNED record, so nothing restores it. A stale entry in the interim is harmless; the next load's `pruneCollapsedToCells` is the backstop. The `cell:deleted` event is a genuine server-confirmed delete and keeps pruning immediately. That covers the deletions a tab OBSERVES; the ones it cannot (a cell deleted while it was disconnected - the reconnect/seq-gap refetch - or a checkpoint restore) are caught by the load-time reconcile `retainCells`/`pruneCollapsedToCells`, which prunes the record to the cells the load actually returned, so **together** they are what makes "the persisted record can never leak an entry for a cell that is gone" true in general. Both are identity-preserving: a load with nothing to drop writes nothing. Two windowing couplings, both load-bearing: `estimateHeight(cell, collapsed)` returns the header-only `COLLAPSED_CELL_PX` (34 - the measured row) so a collapsed cell that has never been on screen reserves no phantom flow; and `focusEditorOrCell` focuses the CARD, because a `display:none` editor cannot take focus and a focus that silently went nowhere takes the modal keyboard with it. **Edit-intent (`enterEdit`) EXPANDS first** - asking to type in a cell is asking to see it - but a mere navigation or selection does **not**: landing on a collapsed cell (`j`/`k`, follow-running, the find bar) leaves it collapsed, the deliberate contrast with a FOLD, which must unfold because a `display:none` cell shows nothing at all. **The find bar is the deliberate, decided case of that rule**: a CONTENT match inside a collapsed cell is counted but not painted, left that way because a `hide_input` (report-view) cell's match is equally invisible today (so the two hide features stay consistent) and because a Ctrl+F sweep must never silently discard collapse state the user set by hand - do not "fix" it by expanding on a search jump or by dropping collapsed cells from the search count. **The ONE thing a collapsed cell still paints is a `field:'id'` match** (searching a cell by its handle - see the search-engine entry): its surface is the toolbar chip, which is exactly what a collapse keeps on screen, so that highlight is visible precisely where the content ones cannot be. The same rule governs the header click: `onHeaderClick` runs a click carrying a SELECTION modifier through the shared `pointerIntent` and **returns without expanding** (a Shift range / Cmd-Ctrl toggle landing on the header is a selection, not a disclosure) - necessary because `click` is NOT one of the compatibility mouse events `onCardPointerDown`'s `preventDefault` suppresses, so it arrives here regardless. The body blocks hide by one of two mechanisms, chosen per block rather than uniformly: `{#if}` where the content is purely derived (rendered markdown, the show-code bar, the "changed on server" banner), `display:none` where a re-mount would reset view state (the editor's CodeMirror cursor/undo, the output's DataFrame-grid page, an `HtmlOutput` iframe that would RELOAD). **That split is why `cellCollapsed` is a tracked dep of `Cell.svelte`'s search-highlight `$effect`**: the `{#if}` DROPS the rendered-markdown block, detaching the very nodes this cell's registered `cellar-search` Ranges point at, and nothing else changes on expand - so without it a re-expanded markdown cell painted no highlights while the find bar still counted its match (a code cell's editor/output survive `display:none`, so their Ranges stay valid and repaint on their own). While collapsed all three CONTENT surfaces CLEAR rather than keeping registry entries with nothing to paint - the id chip (`K_ID`) is the deliberate exception and keeps painting (both halves pinned by the collapse cases in `tests/e2e/find-highlight.spec.ts`). **EVERY block below the toolbar is guarded, the "changed on server" banner included** - that is what makes the header-only `COLLAPSED_CELL_PX` the window plans against TRUE, and it also stops the banner offering a Load button acting on an editor the user cannot see. It takes the `{#if}` form because its content is purely derived from `remoteChanged`/`pendingRemoteSource`, which are Cell-instance state the collapse never touches: **collapsing must NEVER call `clearRemoteStash`** (that would silently discard an agent's edit), so expanding shows the same banner and a windowed teardown still hands the marker back via `cell.remoteEdit`. **One accepted seam with FOLDING, deliberately not worked around**: the fold chevron and the "N cells hidden" chip live inside the rendered markdown, so collapsing a markdown cell whose heading is currently FOLDED hides them with the body and the folded range stays hidden with no in-notebook marker of why. It is cosmetic, arises only from deliberately folding AND collapsing the same cell, is recoverable three ways (expand the cell, the sidebar Outline chevron, `h`/`l`), and the collapsed header's preview still reads the heading itself (`## Setup`). Do NOT put a fold marker on the collapsed header (the minimal row is the point of the feature) and do NOT touch fold state on collapse in either direction - refusing to collapse, or auto-unfolding, means writing state the user never asked to change. Per the per-cell-affordance rule the chevron addresses ITS cell only, never the multi-selection, and there is deliberately no shortcut binding yet. Covered by `tests/unit/cell-collapse.test.ts` (the pure rules + the collapsed height estimate) + `tests/e2e/cell-collapse.spec.ts` (real browser at the windowed default: hide/round-trip, persistence in both directions, a modifier click selecting without expanding while a plain one still expands, a windowed-out collapsed cell staying collapsed and compact, running from a collapsed header, `j`/`k` landing without expanding, delete cleanup, a delete the server never confirms leaving the persisted entry INTACT, the remote-changed banner hidden while collapsed and its stash surviving both an expand and a windowed remount, and independence from editor-collapse + folding). Those tests share ONE workspace and ONE persisted collapse record and several select their target by SOURCE pattern, so a test that rewrites a source or leaves a cell collapsed must put it back (`restoreCell`) or it silently re-points a later test's selector at a different, possibly windowed-out cell. **Markdown tables in text/stream output** are parsed (header + `|---|` separator) and rendered as sanitized daisyUI `table table-zebra table-xs` (`renderOutputMarkdown` - the same markdown-it config + DOMPurify path as markdown cells, minus math: kernel output is data, so a `$` in it stays a `$`); non-table text is unchanged. **Collapsible headings** (Jupyter "Collapsible Headings"): **the foldable unit is a heading *occurrence*, not a cell.** A markdown cell may hold several headings (`# Intro` / `## Setup` / `### Details` in one cell is ordinary), so `src/lib/headings.ts` splits each markdown source into segments at its heading lines (fence-aware) and addresses each heading by a **fold key**: the plain cell id for a cell's *leading* heading, `<cellId>#<segIndex>` for the rest. That is what lets **every** heading level carry its own chevron (`data-testid=fold-toggle`, rendered inline beside the heading in `Cell.svelte`'s rendered markdown, not in the toolbar) - keying folds by cell id could only ever fold the first heading of a cell. A heading's section runs until the next heading of the **same or higher** level, wherever it lives: later in the same cell, or in a following cell. Nested folds compose. `computeFolding(cells, foldedIds)` returns `{hidden, segs, counts}` - whole cells to drop (`Notebook.svelte` `class:hidden`s them), per-cell segment indices an *outer* fold hides inside a still-visible cell, and the whole-cell count per fold key. A folded heading keeps its own line, tinted with an ellipsis + "N cells hidden" chip, so a collapsed section reads as collapsed. Both directions therefore stay in sync by construction. - **nbdev/Quarto `#|` directive comments are coloured apart from ordinary comments (`src/lib/directiveComment.ts`).** `#| default_exp training` CHANGES what Cellar does (`server/export-py.ts` reads it as the export target), so it must not look like a dead comment - but the Python grammar tags it as an ordinary `Comment`, so no tag-based rule in `editorTheme.ts` can separate the two. `directiveCommentRanges(source, tree)` is the ONE rule, called by both render paths: the live editor through `directiveCommentHighlight` (a mark-decoration `ViewPlugin`, the `cmSearchHighlight.ts` shape) and the static no-editor render inside `staticHighlight.ts`, so a directive cannot change appearance when the lazy editor is summoned. **Ranges come from `Comment` NODES in the parse tree, never a regex over raw text**, which is what keeps a `#|` line inside a triple-quoted string string-coloured; a TRAILING comment (`x = 1  #| foo`) is not a directive, matching `storedExportTarget`'s own `^`-anchored regex. **EVERY `#|` line is highlighted, not only the directives Cellar acts on** - `#|` is a syntactic class in the nbdev/Quarto ecosystem whatever this tool does with a given one, and highlighting only the recognised subset would render a valid-but-unrecognised nbdev directive as a dead comment, the exact confusion this fixes; a name allowlist would be a regression and a test guards against one. Scoped to the PYTHON-family surfaces (`langFor`'s `python()` branch in `Cell.svelte` and `FileTab.svelte`, `lang === 'python'` in `staticHighlight.ts`) and deliberately NOT put in the shared `EDITOR_THEME`, since `#|` carries no such meaning in SQL, markdown, YAML or TOML. **The colour is `--cellar-cm-tok-directive` in `app.css` (deep pink/magenta, the one hue neighbourhood no other token occupies; 6.9:1 light / 6.1:1 dark on the editor surface), and its CSS rule needs THREE selectors, the middle one being the trap**: CodeMirror's mark decoration WRAPS the highlight span (`<span class=directive><span class=TOKEN>…</span></span>`) rather than merging classes, and a child's own `color` beats anything inherited from an ancestor whatever the specificity - so `.cm-content .cellar-directive span` is what actually paints the editor, while the static path (which puts both classes on ONE span) needs `.cm-static-content .cellar-directive`. Drop the descendant selector and the editor silently keeps painting comment grey while the static render looks right. PRESENTATION ONLY - nothing here parses a directive's name or moves any export behaviour. **A test that reads a live editor's syntax-derived DOM must SETTLE the parse first** (`forceParsing(view, doc.length, Infinity)`): CodeMirror parses a new state for at most 20ms of wall clock and finishes from a background worker, so on a loaded machine an immediate read sees a PARTIAL tree (measured: 2-3 failures per ~36-96 runs under 30 CPU burners). The product is correct there - the plugin's tree-identity check rebuilds the decorations when the worker lands, pinned by the starved-clock cases in `directive-comment.test.ts`; an e2e read of the same surface polls. - **TeX math in rendered markdown (KaTeX; authoritative wiring: `src/lib/markdown.ts`).** `$…$` inline and `$$…$$` display (Jupyter's delimiters) typeset in **authored prose only**: notebook markdown cells and `.md` file previews. `markdown.ts` owns every markdown engine in the app and exposes exactly THREE renderers, all funnelling through ONE `sanitize` call site - `renderMarkdown` (AUTHORED prose: notebook markdown cells and `.md` previews; math ON, `MARKDOWN_SANITIZE_CONFIG`), `renderOutputMarkdown` (the markdown-table-in-KERNEL-OUTPUT path; math OFF) and `renderChatReply` (a MODEL-GENERATED reply: prose shape, so math is ON, but machine-emitted, so it renders as OUTPUT). `md` itself is **not exported**, so no surface can reach `md.render` and bypass DOMPurify. **The three-renderer split is by CONTENT CLASS on TWO axes, not the renderer drift the consolidation removed.** MATH is the first: kernel output is arbitrary data and a printed price column ("$5", "$1,200") is the everyday case, so $-scanning it would false-typeset the user's own DATA; rendering real `text/latex` output is a separate feature keyed on the output's MIME type (deliberately NOT $-scanning arbitrary cells). PROVENANCE is the second: the two OUTPUT renderers additionally carry the no-fetch image rule and the `OUTPUT_SANITIZE_CONFIG` profile because their content is machine-emitted, while the authored-cell renderer is deliberately left byte-unchanged (that rule, and why it keys on provenance rather than on the cell, is owned by the chat-cells entry below - do not restate it here). Beyond those two axes the three are identical - same markdown-it config, same sanitize call site - so do not re-fork a renderer per surface, do not give the kernel-output one math, and do not put the no-fetch rule on the authored one. That is also why `Cell.svelte`'s `renderTable` calls `renderOutputMarkdown` instead of keeping its own markdown-it + DOMPurify pair. Engine is **KaTeX via `@vscode/markdown-it-katex`** (the plugin VS Code's own markdown preview uses — maintained, markdown-it v14) — KaTeX, **not MathJax**, because it typesets at PARSE time into a static HTML+MathML tree: no runtime script, which is exactly what lets math survive DOMPurify and Cellar's script-free rendering contract. The options object is spread into `katex.renderToString`, so KaTeX's own knobs ride along: `throwOnError:false` (an invalid formula renders KaTeX's inline red error node — one bad expression can never blank a cell or a preview), `trust:false` (refuses every command that could emit raw HTML or a URL — `\href`, `\url`, `\includegraphics`, `\html*` — which is load-bearing, not decoration), `strict:false`, and **`maxSize:10` (em)** - `trust:false` does NOT gate `\rule`/`\hspace`/`\genfrac` sizes, so at KaTeX's default of `Infinity` a downloaded notebook containing `$\rule{1em}{9999em}$` blows out the cell or preview around it; capped, it still renders. `maxExpand` is deliberately untouched (its default is 1000, NOT `Infinity`, so macro-expansion DoS is already bounded). **Currency stays prose:** the plugin's own delimiter rules reject a `$` pair that would open or close against a word character, so "it cost $5 and $10 total" is untouched (pinned by a test — `\(…\)`/`\[…\]` are NOT supported by this plugin, and `$`/`$$` is the required Jupyter-native set).

The workaround is the one a user reaches for anyway and is pinned by test: math is NOT parsed inside an inline code span (`` `$ npm install` ``) or a fenced block, which is where shell commands belong. The accepted behavior itself is pinned too, so changing it has to be deliberate.
	- **The DOMPurify allowlist is extended by exactly TWO tag names, and that is the whole security surface** (`MARKDOWN_SANITIZE_CONFIG`). DOMPurify's defaults already pass KaTeX's `<span class="katex">` tree (`class`/`style`/`aria-hidden` included) **and** its MathML — everything except `<semantics>`/`<annotation>`, the pair carrying the original TeX. Without them DOMPurify **UNWRAPS** the annotation rather than dropping it, so the raw TeX leaks into the MathML as text a screen reader reads aloud while the visible math still looks perfect: a silent regression, which is why the test asserts the ELEMENTS and their `encoding`, never just the rendered text. Nothing else is relaxed — `html:false` upstream still escapes all raw HTML in the source, no `ADD_ATTR`, no `ALLOW_UNKNOWN_PROTOCOLS`, and emphatically **not `annotation-xml`** (an HTML integration point and the seam behind DOMPurify's known MathML mXSS vectors; KaTeX never emits it). A unit test pins the config's exact WIDTH so growing it has to be a deliberate edit.
	- **Accepted narrowing, do NOT "fix" it by widening the allowlist:** the HTML parser re-namespaces an element nested in a MathML *text integration point* (`mi`/`mo`/`mn`/`ms`/`mtext`) into the HTML namespace, and DOMPurify then drops it if its name is a MathML tag — which happens for the `<mo><mrow>…` KaTeX emits for `\mathop{\rm lim}`-style constructs. It costs that construct its screen-reader text only; the visible rendering and the `<annotation>` TeX are intact, and ordinary `\lim`/`\operatorname`/`\sum` are unaffected. Recovering it means disabling exactly the mXSS guard that matters.
	- **CSS + fonts are BUNDLED, never a CDN.** `import 'katex/dist/katex.min.css'` sits in `markdown.ts` beside the engine (so "add a markdown surface" can't also mean "remember the math stylesheet"): Vite emits it into the app CSS and rewrites `url(fonts/KaTeX_*)` to hashed assets copied into `build/client/_app/immutable/assets/`, with the one font under the 4 KB inline limit riding along as a `data:` URI — offline-safe, CSP-tight, verified in the PACKAGED build. `app.css` adds only four `.cellar-md` rules (size, display-math horizontal scroll, block margin, error node); KaTeX sets no color, so math tracks `base-content` in both themes for free. **`katex` is a TOP-LEVEL dependency (`^0.16.47`) for that import, and its range must stay compatible with the plugin's own (`^0.16.4`)**: the stylesheet has to belong to the very katex the plugin typesets with. Both ranges resolve to ONE hoisted copy today; a bump that split them into two installed versions would ship a CSS/JS pair disagreeing about class names and font metrics - which surfaces as broken glyphs, not as an install error.
	- **The plugin is CommonJS and the two builds interop with it DIFFERENTLY.** Vite bundles it for the browser and yields the `.default` function; SvelteKit leaves it **external** in the server build, where Node's own interop yields the whole `module.exports` (`{default: fn}`). `markdown.ts` normalizes that. Skip it and `md.use()` throws `plugin.apply is not a function` at module load, so **every SSR page 500s and the app never boots** — a failure the Vite-bundled unit suite structurally cannot see. That is why `tests/e2e/markdown-math.spec.ts` boots the REAL packaged launcher; it also asserts a KaTeX font actually LOADED (not merely referenced) and that no request left Cellar's origin.

Making it typeset would mean inlining KaTeX's CSS + ~1 MB of fonts into every exported file; the cheap future move is KaTeX `output:'mathml'` there (native browser MathML, zero assets), deliberately not done here.
	- **Math is ONE OPAQUE UNIT to find-in-page, and that is what keeps the active match honest** (`domHighlight.ts`'s `MATH_SELECTOR` + `mathSourceText`). KaTeX writes each expression's text into the container THREE times - the clipped screen-reader `.katex-mathml` MathML, its `<annotation>` raw TeX, and the visible aria-hidden `.katex-html` glyphs - while the search engine counts the expression ONCE from the cell source (`strippedMarkdown` does not strip `$…$`). A plain text walk therefore counted three occurrences per expression, so the model's ordinal slid onto an invisible node (Ctrl+F emphasized a 1px clipped MathML node and the painted count diverged from the reported one). `buildTextRanges` now REPLACES a `.katex`/`.katex-error` subtree with the expression's own source TeX between its delimiters - the same string the model counted - and returns a **POSITIONAL** array whose entry is `null` where an occurrence cannot be painted (inside math: the glyphs are a different string from the source). Callers index by ordinal and must tolerate the hole; compacting it slides every later ordinal, which is the bug. What must be preserved is the SEQUENCE of occurrences, not the region's length - so the substitution reads what the SOURCE wrote, never what KaTeX chose to render, in two places that are easy to get backwards. **The delimiter comes from the plugin's `<p class="katex-block">` wrapper alone**, which marks a `$$…$$` source and nothing else: the plugin promotes inline `\begin{align|equation|gather|cd|alignat}` math to `displayMode`, so `.katex-display` appears over a single-`$` source and keying off it rebuilt `$$…$$`, inventing two `$` per side. **And TWO different nodes wear `katex-error`, carrying the TeX in OPPOSITE places** - KaTeX's own (`renderError`, the `throwOnError:false` `ParseError` swallow) puts the expression in the visible text and the message in `title`, while the markdown-it plugin's own `catch` (reachable because `throwOnError` suppresses only `ParseError`, so a `RangeError` from deeply nested input still propagates) puts the latex in `title` and the message in the text. They are told apart STRUCTURALLY (`isKatexNativeError`: KaTeX always builds a `<span>` and sets `title`+`style="color:…"` on the same three lines; the plugin sets no `style` and its block form is a `<p>`, a shape KaTeX never emits), never by guessing which string looks like a message. Correspondence is exact up to `strippedMarkdown`'s own light syntax stripping - which is also why the `` $`x`$ `` form reconstructs WITHOUT its backticks (the model's stripped text has none either) - plus two accepted narrowings: a fenced `$$` block loses the newline after its opening delimiter, so only a query spanning that newline is affected; and `strippedMarkdown` collapses `_x_`/`*x*`/`~~x~~` pairs across the WHOLE source, math included, while the walk rebuilds the TeX verbatim, so a query matching a bare emphasis character drifts (`Use $x_1$ and $y_1$; snake_case names.` = one `_` in the model, three in the walk). That one changes the occurrence COUNT, not just a length, and is left alone on purpose - `strippedMarkdown` is the engine's cached hot path and is deliberately math-unaware, while emphasis-collapsing the TeX instead is simply wrong (`x_1` is a subscript). A `.katex` subtree with NO `<annotation>` contributes the DELIMITERS ALONE, never the `.katex-html` glyphs (a different string ⇒ shifted ordinals); unreachable unless someone sets `output:'html'`/`'mathml'` in `MATH_OPTIONS` or drops `annotation` from the sanitizer allowlist. Painting inside math is the deliberate cost of that exactness.

- **RENDERED CONTENT MAY NEVER UNLOAD THE LIVE SESSION - a rendered link OR FORM opens in a NEW TAB, decided at the ONE browser-side sanitize boundary (`src/lib/sanitizeHtml.ts`).** Cellar is a LIVE SESSION - the kernel, the running notebook and every unsaved editor buffer live in the tab that renders the content - so an `<a href>` in a markdown cell, a chat reply, a `display(Markdown(...))` output or a widget's `text/html` repr is not an ordinary link: clicking it navigates that tab away and takes all three with it. A `<form action>` in that same content is the IDENTICAL harm at the IDENTICAL boundary (a submit IS a same-tab navigation), so it carries the same policy - links were the instance the feature was requested for, not the boundary of the guarantee, and covering forms COMPLETES an existing guarantee rather than adding a new one. Both therefore get `target="_blank"` plus `rel="noreferrer noopener"` (the pair `ChatPanel.svelte`/`Databricks.svelte` already write by hand on their own hardcoded links; `noopener` is what denies the opened page a handle on the window running the notebook, so it is not optional).
	- **It is a DOMPurify `afterSanitizeAttributes` HOOK, not a markdown-it `link_open` rule, and that is MEASURED rather than a preference**: DOMPurify's default attribute allowlist does NOT include `target`, so a target written by a renderer rule is stripped one step later and the whole feature is silently inert. The alternatives were widening `ALLOWED_ATTR` - the exact width of `MARKDOWN_SANITIZE_CONFIG` is pinned by test precisely so a widening is a deliberate act - or setting the attribute AFTER the attribute filter, which is what the hook is for. The hook is installed LAZILY and idempotently, because `DOMPurify.addHook` does not exist until a DOM does (`isSupported` is false under plain Node, which is also why these renderers are `browser`-guarded).
	- **`sanitizeHtml` is the boundary, so the policy is INHERITED rather than remembered** (requirement: a renderer added later must not have to know about this): `markdown.ts`'s one `sanitize()` funnels all three renderers through it, and the two raw-`text/html` widget surfaces (`WidgetOutput.svelte`, `WidgetOutputArea.svelte`) call it directly - which is also why the policy lives at the sanitizer and not in a markdown-it rule, those two having no markdown-it at all. A **source guard** in `tests/unit/rendered-link-target.test.ts` pins that no other file imports `dompurify` for a VALUE at all (a type-only import, which `markdown.ts` still needs for `Config`, reaches no runtime binding and is allowed); a surface that reached for it directly would opt out with nothing failing.
	- **A SAME-DOCUMENT anchor (`#section`, or a bare `#`) is left ALONE**, `target` actively removed rather than merely not added (the attribute cannot have come from Cellar, so honoring one from untrusted content on exactly the links this rule protects would be the bug with the sign flipped). `opensInNewTab` is the one place that distinction is decided, and it is deliberately NOT "is this cross-origin": a relative `./data.csv` or `?q=1` unloads the tab exactly like an absolute URL, so it opens out too. Cellar's OWN chrome is untouched by construction - nothing the app authors is sanitized, so no in-app navigation can reach the hook, and internal links keep navigating in place without an exception in the rule. **A SAME-DOCUMENT fragment is the ONLY thing that stays in place, and in particular an EMPTY `href` does NOT** - absent and empty are different cases and `opensInNewTab` must keep them on separate branches. `null`/`undefined` means the attribute is GONE, which is what DOMPurify leaves behind when it REFUSES an href (a `javascript:` URL - MEASURED: it removes the attribute rather than blanking it), so there is nothing to follow and no target is written; `''` or whitespace-only means the attribute is PRESENT and resolves to the CURRENT DOCUMENT's URL, so a click RELOADS the Cellar tab and destroys the very session this feature exists to protect. It is reachable from ordinary content - markdown-it renders the empty link `[x]()` as `<a href="">` and DOMPurify keeps an empty value - so it opens OUT like any other outbound link. The accepted cost is that a stray `[x]()` opens a SECOND Cellar tab, which was CHECKED rather than assumed: two tabs against one instance and one notebook is a supported, already-tested arrangement (`tests/e2e/cell-row-toggles.spec.ts` drives two pages and asserts SSE keeps them in sync), kernels are server-side and per notebook with runs serialized by the run queue, and nothing in `src/` guards against a second tab - so an odd extra tab is harmless where a reload is destructive. Stripping the `href` instead was considered and rejected: it silently rewrites the user's own content. **NAMESPACE TRAP, and it is why the element test is `localName` rather than `tagName`:** only an element in the HTML namespace uppercases `tagName`, so an `<a>` inside an `<svg>` reports `'a'` and slipped past an uppercase `Set` entirely - reachable, since neither sanitize config restricts `ALLOWED_TAGS`/`USE_PROFILES` (so DOMPurify's default profile keeps SVG) and the two widget surfaces hand a kernel's raw `text/html` straight to `sanitizeHtml` (markdown is spared only because `html:false` escapes raw HTML). **The href has TWO spellings there too**: SVG 1.1's `xlink:href` is still followed by browsers and still survives DOMPurify (MEASURED, along with a `javascript:` value in it being refused exactly like the plain spelling), so `linkHref` reads `href` first (SVG 2's own precedence) and falls back to the namespaced `xlink:href` - reading only the HTML spelling left an `<svg><a xlink:href=…>` navigating the session away with no target on it.
	- **THE FORM HALF IS UNCONDITIONAL, and its rule is the LINK RULE'S OPPOSITE in two places - do not reuse `opensInNewTab` for a form.** There is no such thing as a submit that stays in place: an ABSENT `action` (which is also what DOMPurify leaves behind when it REFUSES `action="javascript:…"`) defaults to the DOCUMENT'S OWN URL so submitting RELOADS the tab - the destructive case, where an absent `href` is the inert one - and a FRAGMENT `action="#x"` is a navigation rather than the in-place scroll the same value means on an `<a>` (a GET replaces the query with the serialized form data). So EVERY form gets a target. **MEASURED against dompurify 3.4.11, not assumed:** `form` survives with `action`/`method`/`enctype` while `target` on it is STRIPPED (so the exposure is real, and nothing untrusted can pre-set a target to defeat this), and the submit-control OVERRIDES that would otherwise beat a target set on the form - `formaction`, `formtarget`, `formmethod`, `formenctype`, `formnovalidate` on `<button>`/`<input type=submit>`/`<input type=image>` - are ALL stripped, as is the form-owner `form="id"` attribute that would re-associate a submit control with a form outside the sanitized tree, so covering the form ELEMENT covers the whole vector. **SCOPE: only the two raw-`text/html` widget surfaces can reach it** (`WidgetOutput.svelte`, `WidgetOutputArea.svelte`) - every markdown renderer runs markdown-it with `html:false`, so no markdown surface can emit a form at all and the markdown paths were never at risk. **What makes an unconditional rule safe is VERIFIED rather than assumed:** every INTERACTIVE ipywidget (`Text`, `Textarea`, `Password`, `Button`, `Dropdown`, `Checkbox`, `RadioButtons`, `Select`, `SelectMultiple`, `Combobox`, `ToggleButtons`, the sliders and number inputs) is rendered as a native Svelte control whose interaction travels over the widget COMM (`$lib/widgetActions` -> `POST /api/widgets/<comm_id>`), never an HTML form submit - ipywidgets is a comm protocol in which a form has no role - so only the `HTML`/`HTMLMath` widget kinds and an `Output` widget's captured `text/html` reach the raw sanitize path, and both are display-only; Cellar's own source contains no `<form>` at all, so its own chrome cannot reach this hook and internal navigation is untouched.
	- **Three surfaces were audited and deliberately NOT changed.** The rich `text/html` cell output (`HtmlOutput.svelte`) already carries `<base target="_blank">` in the srcdoc IT owns; the `.html` file preview (`HtmlPreview.svelte`) passes the file VERBATIM by design (never inject into a workspace `.html`) and needs nothing, because a link there navigates the FRAME and the sandbox omits `allow-top-navigation`, so the session is unreachable either way - and in both, a popup inherits the frame's opaque origin (no `allow-popups-to-escape-sandbox`), so it gets no usable `window.opener`. The HTML EXPORT (`server/export-html.ts`) is a file rather than the live session, has no DOM and so no DOMPurify, and opened inside Cellar it IS that iframed preview; it is left byte-identical rather than given a second copy of the rule.

Route field: `PATCH /api/cells/[id] {hiddenFromAgent}`. **This toggle DELIBERATELY does NOT follow `setExport`/`setHideInput`'s fire-and-forget convention, and that divergence must not be harmonised away**: those two are PREFERENCES whose failure is cosmetic (`setExport` reads its reply for ONE refusal only - the nbdev `#| export` directive owning the cell, `docs/design/nbdev-export-directives.md` §3.1 - and still discards every other failure), while this is a WITHHOLDING control whose failure is a false claim of CONCEALMENT - a row reading "hidden from AI agents" over a document that still hands the cell to every agent read, chat transcript and MCP tool. A later refetch corrects it, which makes that window rare rather than honest. So the write is REPORTED at both layers: the route returns `{ok:false, reason:'no-such-cell'}` at 404 when `setVisibility` reports the cell is gone (a client cannot read a verdict the server refuses to send; **scoped to this field and to `export`'s directive refusal alone** - the remaining sibling setters in that handler still discard their boolean, `export`'s OWN `no-such-cell` included, and widening them is a separate change), and `setHiddenFromAgent` READS the outcome as the SAME three-way split `commitExportTarget` already uses in that file (`VisibilityCommit` mirrors `TargetCommit` member for member, so the two read as ONE convention - do not invent a second vocabulary for it): a `refused` reply (`no-such-cell`) and a `writeFailed` one both put the flag back and SAY what is true on the shell's existing `onNotice` line, never merely that a request failed, while **`unreachable` - a rejected fetch, or any reply not carrying this route's own `{ok:false, reason}` shape (a proxy 502/503, an HTML error page) - CLAIMS NOTHING and must not revert**. That last case is not a nicety: a rejected fetch does not mean the write did not happen, and the reachable path is a SHOW the server applied and PERSISTED whose response was lost coming back (the connection dropped - a second `cellar` launch in the folder reaps the running instance, `cellar cleanup`, a transient socket error), so the document already holds the cell VISIBLE and reverting is what MANUFACTURES the divergence, under a sentence asserting a concealment that was just revoked. It leaves the flag as applied, says only that the change could not be CONFIRMED, and lets the ordinary refetch paths settle it - deliberately no bespoke `load()`. **The server half owes the same invariant, which is why `setVisibility` ROLLS BACK and rethrows when `persist` throws**: it mutates the in-memory doc first, and that doc IS the agent surface (every MCP read/search/section and every chat transcript reads it through `docFor`), so a failed write on a SHOW used to leave the cell readable by every agent while the browser reverted the row and announced it was still hidden. RESTORE-ON-FAILURE rather than persist-first, deliberately: `persist` serializes the LIVE doc and there is no persist-this-candidate form, so persisting first would mean deep-cloning the whole notebook per toggle - costly, and a shape no other setter there uses. The rollback puts back the EXACT prior shape (key-ABSENT and an explicit `false` are different states here) plus any namespace that call itself created, and that key ALONE, so a concurrent change to another `cellar` key is not clobbered; the `emit` sits after the persist, so a failed write publishes nothing. The route reports it in its own idiom - **`{ok:false, reason:'write-failed'}` at 500 beside the existing 404** - so the failure is a stated outcome rather than an incidental stack trace, and it stays scoped to `hiddenFromAgent`. **The network write is also SERIALIZED PER CELL** (`agentVisibilityWrites`, a `Map<cellId, Promise>` whose entry is dropped when that cell's chain drains, the `withPathLock` shape): two rapid flips of one toggle are two PATCHes of one field to one URL, and settling out of order left the server on the first click's value while the row showed the second's - silently, since both replies are `ok` and both `cell:visibility` echoes carry this tab's `originId`. Only the FETCH is serialized - the optimistic apply stays IMMEDIATE, or the row stops responding to a click while a request is in flight - and that is safe BECAUSE of the generation guard rather than instead of it: the second click's optimistic apply bumps the generation, so when the first write's turn comes and it fails, its revert sees itself superseded and does nothing. The two are one mechanism; do not "simplify" either half without the other. The chaining is deliberately scoped to THIS disclosure control and NOT extended to `setExport`/`setHideInput`, which stay preferences. The revert is SUPERSEDE-SAFE by GENERATION (`agentVisibilitySeq`, the per-cell `pinSeq` shape and the `exportTargetCommit`/`statusSeq` reasoning), **never by comparing the cell's VALUE against what was written** - it is bumped by every local write of the flag AND by every applied `cell:visibility`, and CLEARED wholesale by `load()` - which replaces `cells` with server truth, so every in-flight local write is superseded at once and a write predating the load must neither revert nor claim anything; that third carrier is the one a generation map naturally misses (a `notebook:restored`, an `sse:open` reconnect and a seq-gap refetch all reach it through `load()`), and without the clear a failing hide reverted over the server's own newer state. The revert fires only while that generation still names our write. A value test cannot tell "the cell still holds what WE wrote" from "another writer just wrote the same value": an agent's `set_cell_visibility(id,true)` landing during this tab's own FAILED hide carries no `originId`, so it is applied rather than echo-suppressed, passed the value test, and the revert then deleted the key locally and announced the cell was still visible to agents - the row and the sentence asserting the OPPOSITE of what the server holds, i.e. the same false-claim class this control exists to remove with the sign flipped. A superseded write therefore does NOTHING: no revert, and no notice either, since another writer owns the cell and anything said about it would describe a state this tab no longer owns. When it does fire it restores THAT KEY alone rather than a whole metadata snapshot, which would clobber a concurrent change to the export flag one control along.

- **Per-cell render error boundary (`Notebook.svelte`'s `cellRow` + the pure `src/lib/cellRenderFailure.ts`).** Cellar renders ARBITRARY kernel output, so a renderer that throws is a recurring failure CLASS, not a one-off. Svelte flushes the whole document in one pass, so before this an uncaught render throw in ONE cell took the entire notebook's render tree with it (windowed: everything below stayed permanently blank and the jump paths died with it; `?virtualize=0`: NOTHING rendered - measured at 0 cells). Each row is now wrapped in a **`<svelte:boundary>`** whose `failed` snippet is an inline placeholder (`data-testid=cell-render-error`), so the next unknown instance costs one cell. **THE HARD PART IS THE HEIGHT, not the boundary**: windowing plans the flow from the measured-height cache, so a placeholder that collapsed to the height of its own message would trade a fatal bug for the height-cache mismatch class windowing exists to remove. It therefore RESERVES `reservedFailureHeight` (the cell's last measured height, else the SAME `estimateHeight` the window planned its spacer at) **and then MEASURES ITSELF back through the same `recordHeight`**, so the plan converges on what the DOM really renders instead of being frozen at a height nothing occupies - which is what makes a failed cell's spacer reproduce its placeholder exactly, so nothing below it moves as it fails or as it scrolls in and out of the window. The placeholder carries **`data-cell-id`** (`ensureCellMounted` resolves nodes by it, so without it every jump path would silently no-op on a failed cell) but deliberately **NOT `data-testid="cell"`** - it is not a cell, and claiming otherwise would make every "the cells are there" assertion in the suite pass over a notebook of placeholders. The error is **REPORTED to the console** (`onerror` → `[cellar] cell <id> failed to render`) and never swallowed: a boundary that made a broken renderer survivable AND silent would also make it undetectable, retiring the console assertions that are how several specs catch a render regression; the placeholder shows only the error's `name: message` (`failureDetail`), never a stack. **Knock-on for every spec that guards against a render throw: a `pageerror`-only listener no longer sees one**, because a caught throw surfaces solely as that console report - so such a spec must ALSO collect the boundary's own report and/or assert `cell-render-error` absent, or it keeps passing for a weaker reason (`toolbar-interrupt-clear-all.spec.ts` does both, filtered to the boundary's prefix because that test interrupts a kernel mid-run and unrelated console noise there is legitimate; `dataframe-duplicate-index.spec.ts` collects unfiltered, which its plain-load scenario can afford). **Scope, stated:** a boundary catches only RENDER-time and effect throws - an event handler or a `setTimeout` is unaffected - and Svelte boundaries are inert during SSR, which costs nothing here because `LiveNotebook` starts with zero cells and fetches them on mount, so no cell ever renders server-side. **THE PLACEHOLDER IS NOT A DEAD END, and that took the boundary's SECOND snippet argument.** A `<svelte:boundary>` stays failed until its `reset` is called, and BOTH render branches key the row by `cell.id`, so nothing recreates it on its own: a `load()` refetch, a `cell:cleared` and a fresh `cells` array all reuse the same block. Windowing tears the row down when the cell leaves the window, but `planWindow` emits no spacers at all when every cell fits the viewport and the "Render all cells" opt-out never windows - so for a small notebook the placeholder was permanent until a page reload, while its own copy told the user that clearing the output or re-running would resolve it. The `failed` snippet therefore takes `(error, reset)` and the placeholder carries a **Try again** control (`data-testid=cell-render-retry`) wired straight to it, so the copy names a route that exists. **There is deliberately NO automatic reset**: it would have to be driven by a real per-cell change signal rather than a reactive tick, or a persistently-broken payload becomes a throw/reset/throw churn on the main thread - a deliberate user gesture cannot loop, so the explicit control needs no such proof. The button GROWS the placeholder, which is harmless precisely because it measures itself back into the cache (the two height halves above are untouched). Covered by `tests/unit/cell-render-boundary.test.ts` (the pure rules EXECUTED, incl. a spacer reproducing the reserved height, plus source guards that every `<Cell>` really sits inside the boundary, that the placeholder reserves + measures + stays addressable, and that the `failed` snippet really threads `reset` into a Try again control) and `tests/e2e/cell-render-boundary.spec.ts` (a genuinely malformed structured DataFrame payload - `data` an object rather than rows, so `DataFrameGrid`'s `rawData.map` throws - rendering as a placeholder while its neighbours run cells against a real kernel, the windowed flow proven not to move as it fails or as it scrolls out to a spacer and back, and a failed cell recovering IN PLACE - in a notebook short enough that no spacer is ever emitted, so windowing can do nothing for it - once Clear all outputs has removed the cause and Try again is pressed). **The two halves need DIFFERENT cases and a test for one is blind to the other:** the RESERVATION is caught by the placeholder's own height (without it, 110px where ~220px was planned), while the MEASUREMENT only bites where the placeholder renders TALLER than was reserved - a FULLY COLLAPSED failing cell, which reserves the 34px header row and then renders the ~110px message, so its spacer is 76px short until the measurement lands. That case has its own test and seeds the collapse through the `.cellar/` UI store; the round-trip `offsetTop` check cannot see it (the placeholder is mounted at both ends), so it is the document's total extent placeholder-vs-spacer that catches it.
