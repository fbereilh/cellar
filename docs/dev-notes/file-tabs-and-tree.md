# File tabs, previews, external edits, file tree, git decorations, blame, tabs

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **File tabs** (`src/lib/FileTab.svelte`): CodeMirror editor over a workspace file, ⌘S save; syntax-highlighted by file extension (`langFor`: python / markdown / json+ipynb / yaml / toml / html, else plain text), sharing `editorTheme.ts`'s one static `EDITOR_THEME` with cells. TOML has no lezer grammar, so it uses the official `@codemirror/legacy-modes` stream mode via `StreamLanguage`; its tokens land on the same highlight tags as every other language, so both themes style it with no theme-side work (`.toml`/`.yaml`/`.yml` share the `config` icon in `fileIcons.ts`). HTML comes from `@codemirror/lang-html`, promoted from a transitive to a **direct** dependency because the code imports it - the same convention as `@codemirror/autocomplete`/`@codemirror/search`. Dirty state bubbles up to the tab bar. Notebook + all file tabs stay mounted (hidden via `.hidden`) so editor/run state survives tab switches.
- **Rendered previews in a file tab (markdown + HTML).** Two file kinds carry a **Source/Preview** toggle in the tab header (`data-testid=file-view-source`/`file-view-preview`), one shared mechanism in `FileTab.svelte`: `previewKind` ('markdown' | 'html' | null) picks the renderer, the mode is a session-wide preference per kind (`localStorage['cellar-md-view']` / `['cellar-html-view']`, read **synchronously at init** so an HTML file paints its preview on the first frame rather than flashing the source view), and `liveSource` carries the editor buffer into the preview so a preview always shows unsaved edits and toggling back re-renders from current content. **`liveSource` is SAMPLED, not mirrored**: it is read from the editor doc when a preview is entered (`setViewMode('preview')`) and once after the initial load, **never per keystroke** - the editor is `display:none` under a preview so the USER cannot change its document while one is on screen, and a per-keystroke `doc.toString()` on a multi-MB export was a real regression that was removed. Do not reinstate an `updateListener` write. **The one thing that DOES rewrite that hidden document is an external on-disk sync**, so that path assigns `liveSource` itself (see the external-edit entry below) - without it the preview keeps rendering pre-sync text while the editor under it holds the new content, which is half the feature missing. The editor stays mounted-but-hidden under a preview (CodeMirror state / git baseline / unsaved edits survive the toggle). **Defaults differ by kind on purpose:** markdown → Source (you open a `.md` to edit it), `.html`/`.htm` → **Preview** (you open an export to look at it), and the toggle lists the kind's default first.
- **`.html` preview = a SANDBOXED iframe (`src/lib/HtmlPreview.svelte`), the security-critical surface here.** A workspace `.html` is UNTRUSTED content (it is usually machine-generated: plotly/bokeh exports, nbconvert reports), so it renders the way rich `text/html` cell outputs do (`HtmlOutput.svelte`, the precedent — keep the two in step on the SECURITY posture, and only that; the two deliberate divergences are named below): `sandbox="allow-scripts allow-popups allow-downloads"` and **never `allow-same-origin`** (paired with `allow-scripts` that hands the file the app's origin — its DOM, cookies, `localStorage`, same-origin `fetch` — and the isolation is gone), fed by **`srcdoc`** so the app never serves workspace HTML as `text/html` from its own origin (a route that did would be a stored-XSS surface reachable outside any sandbox — the same reason `/api/fs/raw` serves images only). The content is passed **verbatim**: no wrapper document, no injected script, so a full `<!doctype html>` export renders as authored; the iframe ELEMENT paints white so a document declaring no background stays readable under a dark app theme. **That verbatim pass is the FIRST deliberate divergence, and it is a hard rule: NEVER inject `OUTPUT_HTML_CSS` (or any other stylesheet) here.** `HtmlOutput.svelte` injects it because it OWNS its srcdoc wrapper around a bare fragment the kernel emitted; a workspace `.html` is a finished export the user opened precisely to view AS AUTHORED, so restyling it - re-padding its tables, re-aligning its cells - would be a defect, not parity with the output surface. Do not read "keep the two in step" as an instruction to mirror that stylesheet. **`allow-downloads` is the second deliberate divergence from `HtmlOutput.svelte`** (a cell output is a different surface and keeps its own token set): it grants NO origin access, so the no-`allow-same-origin` invariant is untouched, and without it the browser blocks every in-page save - silently killing plotly's modebar "Download plot as PNG" on exactly the exports this preview targets. **HTML gets its own, higher size cap** (`MAX_HTML_FILE_BYTES` = 15 MB, resolved through the same `isHtmlPath`, never an ad-hoc extension test): self-contained is what makes these files big (plotly `write_html(include_plotlyjs=True)` ≈ 3.5 MB, bokeh `INLINE`, nbconvert base64 figures, Cellar's own `export_html`), so the ordinary 2 MB `MAX_FILE_BYTES` refused precisely the files the feature exists to open. It is raised, not removed, and `MAX_FILE_BYTES` still governs every other text file - both directions are pinned by unit tests. **Raising the read cap does NOT raise what git will decorate:** line-level decorations are gated at `MAX_DECORATION_BYTES` (= `MAX_FILE_BYTES`, in `git.ts`) - see the git-blame entry below. **The read cap and the WRITE cap are one pair, and live together in `src/lib/server/limits.js`** (no imports at all, but SERVER-only: it is reached exclusively through `$lib/server` (`fstree.ts`), so it rides the normal bundle into `build/` and is deliberately NOT in `package.json` `files` - the launcher does not import it). `writeWorkspaceFile` refuses a save past the SAME `maxFileBytesFor(relPath)` the reader enforces (measuring UTF-8 BYTES, and refusing *before* `writeFileSync` so the original file is untouched), because a save the reader will not reopen strands the file the moment its tab closes. **The TRANSPORT is the third limit, and Cellar deliberately does NOT raise it.** adapter-node caps a request body at **512 K** (`BODY_SIZE_LIMIT`), rejecting a save *before* the route handler runs - and that setting is read once at module load and applied upstream of EVERY route, so it cannot be relaxed for the save endpoint alone. Raising it would raise how much memory any unauthenticated request can make the app process buffer (adapter-node binds `0.0.0.0`, and that process also carries kernel streaming, SSE and the in-process MCP server), so `bin/cellar.js` leaves it alone. **Reading is untouched by this** - a file arrives in a GET *response*, so a 15 MB export still opens and previews. What changes is the SAVE direction: `src/lib/saveLimit.ts` (pure, browser-safe) computes the exact serialized size of the PUT body (`saveBodyBytes` walks the string once, allocation-free, applying JSON's own escaping rules - a raw-length guess would either refuse files that fit or admit files that 413) and `FileTab.svelte` decides from the loaded content whether the document `saveFitsTransport` - once per LOAD, plus once per external on-disk apply (see the re-decide note below), never per keystroke. The verdict is **exact but never paid for in full** - this runs on every file tab's load path, before it paints, and a 15 MB export is settled by its first ~512 KB: every UTF-16 code unit contributes AT LEAST one byte (a surrogate pair is 2 units → 4 bytes), so `content.length > limit` refuses in O(1) with no scan, and the count itself stops the moment it passes `limit`. Both shortcuts are provably conservative, so the boundary lands byte-for-byte where a full count puts it (swept across it per counter branch in the unit tests). **The ceiling it compares against is the one ACTUALLY in force, never a client-side guess** - only the server knows it, so `effectiveBodyLimit(process.env.BODY_SIZE_LIMIT, dev)` is computed in `GET /api/fs/file` and carried to the tab as `bodyLimit` (`resolveBodyLimit` reads it back; the 512 K `DEFAULT_BODY_SIZE_LIMIT` is only the fallback for a value that cannot be determined, and an unrecognised wire value falls to it rather than to "no cap"). That plumbing is load-bearing in both directions: **`cellar --dev` runs Vite, whose handler calls `getRequest()` with NO `bodySizeLimit` at all**, so under `--dev` nothing is view-only for transport reasons (a hardcoded 512 K made a 600 KB `.md` uneditable there); and an operator who sets `BODY_SIZE_LIMIT` genuinely widens the editable range, since the app-spawn env is a `process.env` spread AND the app now reports their value. `parseBodySizeLimit` mirrors adapter-node's own `parse_as_bytes` (`K`/`M`/`G` suffix, `Infinity` = uncapped). If not, the tab opens **view-only**: `EditorState.readOnly` + `EditorView.editable.of(false)` + **`EditorView.contentAttributes.of({tabindex:'0'})`**, no Save button, a `data-testid=file-view-only` chip saying why - and the preview fully available. **That tabindex is load-bearing, not decoration:** `editable.of(false)` sets `contenteditable="false"` and adds NO tabindex, so `.cm-content` - the element CodeMirror attaches its key handlers to - could not take focus at all (a click landed on `.cm-scroller`), silently costing keyboard selection and the editor's own search panel. **Cmd/Ctrl+S is owned by the TAB, not by any one view - the shell holds it, `FileTab` binds NO editor keymap.** A CodeMirror keymap fires only while `.cm-content` holds focus, which is false in every view where the editor is not the focused surface - a rendered preview hides it with `display:none`, and a `display:none` subtree can hold no focus at all - so in Preview (**the default view of every `.html`**) the keystroke reached Chrome's own "Save page as…" dialog and a dirty document went unsaved. So `+page.svelte`'s capture handler now answers for BOTH kinds: the active notebook, or the active file tab through `fileTabApis` (a `FileTabApiHandle {requestSave}` registry mirroring `notebookApis`; `activeTabIsNotebook` only picks WHICH). One owner - reintroducing the editor keymap would double-save. It saves when the document is saveable and, when it is not, pulses the view-only chip (`data-flash`) rather than adding a second copy of the same sentence, since a keystroke that appears to do nothing reads as a bug. The one case no parent handler can serve is a keystroke inside the preview's sandboxed iframe, which never reaches this document - the accepted price of the opaque origin. Deciding at LOAD is sound for TYPING precisely because a document ruled view-only is then read-only, so the user cannot grow it past the line it was measured against; a document edited past the limit after loading is caught by the backstop below. **The verdict is NOT frozen, though** - an EXTERNAL on-disk sync writes the document whatever `EditorState.readOnly` says, so the extensions live in a `Compartment` and the verdict is re-decided on every such apply, in both directions (see the external-edit entry below); it is still never re-decided per keystroke. A refused save is **visible**: `FileTab.svelte` keys oversize off the **413 status** (a front-end 413 carries no JSON message of ours, so parsing the body is what used to swallow it) into its own `saveError` state rendered in the tab header - deliberately NOT `errorMsg`/`status`, which would turn a perfectly loaded document into a load-error view - and it is cleared on the next `docChanged`, so it never keeps asserting something about content the user has already changed. The write cap's own refusal ("file too large to save (over the 15 MB limit)") is distinct from the transport 413 - both read honestly. **Known limitation, by design:** a `srcdoc` document inherits the PARENT's base URL, so a page that pulls sibling files (`<script src="report_files/x.js">`) cannot load them — the request goes to the app and 404s. `src/lib/htmlPreview.ts` `hasRelativeAssetRefs()` (pure, unit-tested) detects that case and the tab says so in one line rather than showing a mysteriously empty page. It is a quote-aware string scan (never a DOM parse) and **under-reporting is its contract** - a false notice on a genuinely self-contained export is worse than a missing one - so it skips comments, inert bodies (`<script>`/`<style>`/`<textarea>`/`<title>`/`<template>`), attribute VALUES, and a `<link>` whose `rel` is not one the browser fetches to render (`stylesheet`/`preload`/`modulepreload`; `canonical`/`alternate`/`icon`/absent do NOT convict), and an **absolute `<base href>`** (`https://cdn/x/`, or protocol-relative `//cdn/x/`) suppresses the notice outright since it rebases every relative ref - a deliberate whole-document PRE-scan (one regex), because `<base>` is legal AFTER the refs it rebases and the walk's early-exit on the first relative ref is what keeps a multi-MB export cheap; a root-relative/absent/unparseable `<base href>` does not suppress. Known misses named at the seam and deliberately not chased: `srcset`, `poster`, `url()` in CSS, and plain `<a href>`. **Do NOT "fix" it with a blob URL:** Chrome's blob-URL partitioning blocks blob fetches from an opaque origin, so that trades a 404 for a preview that does not render at all. Covered by `tests/unit/html-preview.test.ts` (incl. a source-level guard on the sandbox attribute — the isolation is one word wide) + `tests/e2e/html-file-preview.spec.ts` (the fixture probes `parent.document`/`localStorage` from inside the frame and asserts both are blocked).
- **An open file tab tracks EXTERNAL on-disk edits (`src/lib/server/fileWatch.ts` + the `FileTab.svelte` half).** A `FileTab` used to read its file exactly once, in `onMount` - no polling, no revalidation - so its content was a snapshot taken at open time forever, and a save from that stale tab wrote the snapshot back over whatever an agent had since written. The server now watches every OPEN file and publishes `file:changed` on the ordinary event bus (`events.ts` `publishGlobal` - no `nb`, no `seq`: each event is a full statement about one file, so a missed one self-heals); the tab applies it. Scoped to `file`-kind tabs, which is `.md` and every other text file, since `FileTab` is one component and the mechanism is content-type agnostic. **Notebooks are deliberately OUT** - `GET /api/fs/file` is the sole registration point and only `FileTab` calls it, so a `.ipynb`/jupytext doc (whose server-side in-memory doc, cell-id merge and per-run `persist()` make it a different problem) is untouched; the silent-clobber hazard there is real and is a separate task. **Three mechanism decisions are each forced by a MEASUREMENT** - re-measure before changing any, and `tests/unit/file-watch.test.ts` pins all three: (1) **watch the containing DIRECTORY, never the file** - `fs.watch(<file>)` binds to the inode and goes permanently silent at the first rename-replace, not only for that rename but for every later IN-PLACE write too, and rename-replace is exactly how an LLM edit tool writes (Claude Code's own `Edit`/`Write` were measured staging a sibling `<name>.tmp.<pid>.<hex>` and `rename()`ing it over the target), so a per-file watch appears to work in a one-edit hand test and then silently stops - the worst failure shape, which is why a **CONTROL test** pins that a naive per-file watch misses changes the directory watch catches; (2) **debounce (`SETTLE_MS`, 120ms of quiet) before reading** - bursts coalesce unevenly, and a NON-atomic writer (a shell redirect, a python script) is observable mid-write, so reading on the first event returned a 0-byte document; (3) **decide on a content HASH, not on the event** - macOS reports every `fs.watch(dir)` event as `rename`, including a plain overwrite, so the event name carries no information, and the same hash doubles as echo suppression (`noteKnownContent`, called by the `PUT` route BEFORE the write, since the event can arrive as soon as the bytes land) so a Cellar save never bounces back into the tab that made it. Deliberately NOT a recursive workspace watch (it fires for `.git`/`build/`/`.venv`/`node_modules` - the very `IGNORE_DIRS` `fstree.ts` exists to exclude - and every kernel run rewriting an `.ipynb` would ripple through it); watching only the directories holding open files bounds event volume by what the user has open, not by workspace size. Deliberately no `chokidar` (~15 transitive deps to replace this module; revisit only if it ever needs to become a recursive watch). **Registration is on READ, LRU-bounded** - the `GET` that opens a file IS the "someone has this open" signal (the server has no other; tabs are client state) and it already holds the content, which seeds the echo hash for free; nothing has to report a closed tab because `MAX_WATCHED_FILES` (64) evicts the coldest, so a killed browser leaks nothing. Cost is one handle per DIRECTORY, not per file. **That seed is FIRST-REGISTRATION ONLY - an EXISTING entry wins over the caller's content, and the ordering is load-bearing, not tidiness.** Every window's focus revalidation issues that same `GET`, so a read landing inside a pending settle window re-seeded the hash to the very content `settle` was about to deliver, `settle` then found no change and published NOTHING: the reading tab was fine (the content is in its own response) while every OTHER browser window silently missed the edit until its own focus - defeating precisely the multi-window live sync the no-unwatch-on-close rule exists to protect. Delivering once more to the tab that read it is the harmless direction (the client short-circuits when the content already matches). `noteKnownContent` is deliberately NOT the same case and must keep OVERWRITING: the `PUT` path is a statement that we wrote those bytes, i.e. the echo suppression itself - **but only once they LAND, which is why a failed write re-seeds through `resyncKnownContent`**: the declaration is made BEFORE the write (it has to be), so a write refused for size or failing on EACCES/ENOSPC left the hash describing bytes disk never got, and echo suppression then silently swallowed a later GENUINE external change producing exactly those bytes - the everyday agent shape, where the agent writes the very edit the user was racing to save. An explicit reseed is REQUIRED precisely because an existing entry now wins over a re-read's content, so nothing else would ever correct it. **`unwatchUnder(path)` is the one deliberate stop**, called by the explorer's delete/rename/move ops beside the `dropDocs`/`shutdownKernelsUnder` already there: no window can be watching a name that is gone, so its entry could only settle into a deletion nobody is listening for while holding an LRU slot a genuinely open file could use (and a renamed file's tab had no live sync until its next window focus). Folder-shaped like its two neighbours, since a folder op takes every file under it. **The rename/move calls sit behind the SAME `res.from && res.from !== res.path` guard the neighbouring `rekeyDocs` uses, and that guard is load-bearing**: `renameEntry` returns no `from` for a rename to the same name and `moveEntry` returns `from === path` for a same-parent move, so nothing moved on disk and the file is still open under that very name - unwatching there silently switches that tab's live sync off for good, since it never remaps, so it never remounts and never re-issues the read that is the sole registration point. **The invariant that makes the LRU a real bound is that a known-hash entry NEVER outlives the watcher behind it**, and there are two ways it can: a directory whose `fs.watch` THROWS (unsupported network mounts and container overlays really do; the entry was seeded before the attempt, so every read on such a filesystem added a permanent one the LRU could not prune - the catch deletes it), and a file past **`MAX_WATCHED_FILE_BYTES`** (= `MAX_FILE_BYTES`, 2 MB - the sibling of `git.ts`'s `MAX_DECORATION_BYTES`), which is refused at registration by a `statSync` BEFORE any state is recorded and dropped outright by `settle()` if it GROWS past the ceiling later. That ceiling is what bounds the one genuinely expensive thing here: every settled event is a synchronous whole-file `readFileSync` + sha256 on the process that also carries the kernel websockets, the ~40ms SSE fan-out and the in-process MCP server, and `readWorkspaceFile` admits `.html` up to `MAX_HTML_FILE_BYTES` (15 MB), so an agent regenerating a self-contained export in a loop charged a 15 MB read+hash per settle AND again on the refetch the inline gate forces. It is `MAX_FILE_BYTES` **uniformly, without the per-path `.html` exception**; the deliberate, accepted cost is that a >2 MB export no longer live-syncs and falls back to the tab's window-focus revalidation. Deliberately NOT a `statSync` size/mtime pre-check before each read - the 120ms settle debounce already collapses the multi-event writes that would catch, so it is cost with no bound. **The apply rule mirrors the notebook's "changed on server" banner** (`Cell.svelte`), because the hard thinking about never clobbering active typing was already done there: **clean ⇒ apply silently** (the common case and the thing being asked for), **dirty ⇒ do NOT touch the buffer**, stash it and offer Reload / Keep mine, **deleted ⇒ banner only whatever the dirty state** (the buffer is kept, a save recreates the file; clearing the editor would destroy work in response to something the user did not do here). "Keep mine" advances `savedContent` to what disk holds so the SAME change is not re-announced on every window focus, while a later DIFFERENT one still raises the banner. **A banner is a claim about what disk holds RIGHT NOW, so the "disk already equals what we believe" path RETIRES it rather than merely staying quiet** - that early return used to fire before anything could be cleared, so an agent that UNDID its own edit left a Reload button offering bytes disk no longer held (clicking it wrote them back and recorded them as saved), and a file deleted then restored with identical content kept its "deleted on disk" banner for good. Both clear `pendingDisk`/`preReadyDisk`/`diskState` first. Which is also why **`revalidateFromDisk` no longer short-circuits on equal content** and delegates to the shared `applyDiskObservation` instead: a second copy of "disk agrees" is how a stale banner survives the very backstop meant to catch it. **The pre-editor flush is the third caller and goes through the funnel too** (an event landing between the load `GET` and the `EditorView` existing): calling `applyDiskContent` straight lost both of the funnel's rules - the "disk agrees" short-circuit, so the common case where that event carries the same bytes the load returned ran a full apply including a redundant git-baseline + `git blame` pair, and the seq check, so an event whose settle-read predated the load's read reverted the editor. **That funnel is also where the ORDERING guard lives** (`diskSeq`/`claimDisk`, the `kernelReqSeq`/`statusSeq` convention this codebase already uses for unordered responses): two paths fetch asynchronously - the window-focus revalidation and the refetch for a file past the inline ceiling - so a slow GET resolving last used to REVERT the editor and then record its stale bytes as `savedContent`, which suppresses the correction, since the server's known hash is already the newer content's and no further event follows. Every path that settles what we believe disk holds claims the slot, **a synchronously-applied inline event, a save, a Reload and a Keep-mine included** - guarding only the fetching paths leaves the reported case (inline B applied, older GET A resolves and reverts) wide open. **The save's `setDirty(false)` is guarded on the buffer still matching what was written** for the same class of reason: keystrokes typed during the in-flight `PUT` are unsaved, and a false clean flag does not merely mislabel them - it routes the next external change down the SILENT-apply path instead of the Reload / Keep-mine banner, so they are overwritten without ever being offered (`savedContent` still advances either way - disk really does hold those bytes). A silent apply goes through **`src/lib/externalSync.ts` `externalEdits`** - the MINIMAL edits derived from `gitdiff.ts`'s Myers line diff, dispatched as ONE transaction carrying an `externalSync` **Annotation** (not a mutable flag, so an early return cannot leave it set) that the update listener reads to avoid reporting the tab dirty for content that came FROM disk. Whole-document replacement is the thing that rule exists to avoid: it throws the caret to the end, scrolls the view and wipes the undo history, i.e. the sync would be more disruptive than the staleness it fixes. It also assigns **`liveSource`** explicitly - that value is SAMPLED on entering a preview, never mirrored per keystroke, so without it the rendered markdown keeps showing pre-sync text while the hidden editor holds the new one (the preview is half the feature, not a bonus). Two further couplings: the event **inlines content only under `MAX_INLINE_EVENT_BYTES` (256 KB)** and otherwise announces path+hash for the tab to refetch (that SSE stream also carries kernel output deltas at ~40ms and pays per byte), with `deleted` an EXPLICIT flag so an omitted-because-large payload can never read as a deletion; and the window-`focus` handler that already re-fetched git HEAD/blame now also **revalidates content**, the backstop for an event a network/virtual filesystem drops, a file the watcher refuses for its size, or one the LRU evicted - **fired on the SSE `sse:open` frame too**, since `file:changed` is NOT replayed to a late subscriber the way `queue:changed`/`kernel:status` are, so an app-server restart (the single-instance takeover) or a transient drop otherwise left a tab permanently stale with `focus` unable to help, the window never having lost focus (`LiveNotebook` already refetches on that frame; `FileTab` was the one subscriber ignoring it). **That revalidation is STAT-FIRST** (`GET /api/fs/file/stat` -> `statWorkspaceFile`, size+mtime, no read; the content `GET` and the `PUT` return the same stat so the tab can record a baseline at the load, at an accepted observation and after a save): every file tab stays mounted, so one focus ran a read for each of them, and `readWorkspaceFile` admits an `.html` export up to 15 MB - the very file the watcher declines, so focus is its ONLY mechanism - putting a multi-MB read + `JSON.stringify` + transfer + whole-string compare on the shared event loop per alt-tab back into the browser, the exact workflow the feature exists for. **The invariant is that the stat may only ever cause an EXTRA read, never a MISSED change**, so every doubt takes the read path: no baseline recorded, a failed or unparseable stat, a file that is gone (a failure is emphatically NOT a deletion - reporting those is the watcher's job). Correctness therefore never depends on catching every path that moves what we believe disk holds; an observation carrying no stat (an inline event) CLEARS the baseline rather than keeping a stale one. Stated residual: a write leaving BOTH size and mtime identical is invisible here - a non-issue under `MAX_WATCHED_FILE_BYTES`, whose content hash the watcher checks each settle, and this fallback carries only the oversize and LRU-evicted cases. Note this is NOT a reversal of the "no `statSync` pre-check" decision on the WATCH path: there the 120ms settle debounce already collapses the redundant reads, while this path has no debounce and no change signal at all. **A sync also RE-DECIDES the view-only verdict, through a CodeMirror `Compartment`** (`viewOnlyExtensions`, reconfigured from `applyDiskContent` against the `bodyLimit` captured at load - the ceiling belongs to the running server, so it is never re-fetched): `saveTooLarge` was settled once from the loaded content on the premise that a read-only document cannot grow past the line it measured, and an external sync retires that premise - `view.dispatch` applies changes whatever `EditorState.readOnly` says. Frozen into the initial state it went stale BOTH ways: a file grown past the ceiling stayed editable and only failed as a 413 on save, and one shrunk back under it kept a now-false "too large" chip and no Save for the tab's life. Still never per keystroke - typing genuinely cannot cross the line in a read-only document. The banner takes the notebook banner's warning TINT but its copy is `base-content`, NOT `text-warning`: amber-on-amber measures 1.8:1 on that background in the light theme (far under WCAG AA), so the icon carries the signal and the words stay readable - and both buttons are equally quiet, since Reload DISCARDS unsaved edits and emphasising it would make the destructive choice the one a misclick lands on. Covered by `tests/unit/file-watch.test.ts` (real filesystem, real write patterns, no `fs` mocking - a mocked watcher would happily pass the design that is measurably broken) + `tests/unit/external-sync.test.ts` (the offset arithmetic at every document edge, checked by replaying the edits, since a wrong offset silently corrupts a file the user then saves) + `tests/e2e/md-external-sync.spec.ts` (the only level that proves the SSE hop and the CodeMirror apply: repeated temp+rename edits, burst coalescing, the RENDERED preview updating, the dirty no-clobber path in both directions, echo suppression over the real wire, caret+scroll preserved across a sync, a deletion, a banner retired when disk reverts or the deleted file comes back identical, the view-only verdict flipping in both directions as an external write crosses the transport ceiling, a stubbed-stale GET resolving after a newer inline change and changing nothing, characters typed during a held-open save surviving behind the banner, and a focus costing ONE stat and zero reads when nothing moved while a broken stat endpoint still reaches the read).
- **File tree UX (VS Code-style).** Folders start **collapsed**, only root visible. **Expansion is the SIDEBAR's, one set of paths (`$lib/treeExpansion`), never a row's own `$state`** - a row reads `ops.isExpanded(path)` through the `cellarFileOps` context - because the **reveal** (clicking a tab opens every ancestor of its file, selects it and scrolls it into view, VS Code's `explorer.autoReveal`) has to open a whole ancestor chain the sidebar does not render itself. The shell raises a `revealRequest` whenever the active tab's PATH changes (keyed off a derived string, never `activeTab`, which re-derives on every `tabs` rewrite and would re-open folders the user just collapsed) and on a click of the already-active tab; the sidebar honours it only while the person-level `TREE_AUTO_REVEAL_KEY` (default ON, read with `getUserSettingDefaultOn`, so only a stored `false` is off) allows, and leaves focus on the tab. The set is pruned on every tree load and remapped on rename/move, so an open folder stays open under its new name. Covered by `tests/unit/tree-expansion.test.ts` + `tests/e2e/file-tree-reveal.spec.ts`. Entries carry self-contained inline-SVG **file-type icons** (`src/lib/fileIcons.ts`, keyed by extension, no CDN/network — offline-safe). **Git decorations**: `src/lib/server/git.ts` + `src/routes/api/fs/git` return `git status --porcelain -uall` as `{isRepo, files:{relPath→letter}}`; the tree colors names + shows a status letter (M gold, A/U green, D/C red) and rolls child status up to collapsed folders (a dot). Refreshed on mount, manual refresh, window focus, after file saves, and on a foreign `notebook:opened` (an agent creating a notebook - all through the `fsRefreshSignal` bump); a non-git workspace returns `isRepo:false` → clean tree, no errors.
- **Git change decorations below the file level (line + cell).** The tree says *which files* changed; these say *which lines* (editor gutter bars) and *which cells* (notebook accent bars). **Baseline, not diff:** `gitHeadFile()` (`git.ts`) + `GET /api/fs/git/head?path=[&kind=notebook]` hand the browser the file's git-HEAD text **once** (the `kind=notebook` form parses it through `ipynb.ts`'s `deserialize`, so both sides of a cell diff are normalized identically and nbformat's multiline `source` arrays never read as a change); the client re-diffs the live buffer against it. That is what keeps markers live per keystroke without a `git` process per keystroke — do NOT "optimize" this into a server-side `git diff` route. `tracked:false` (not a repo / no commits / untracked / binary / unparseable) ⇒ **no decorations at all**, matching VS Code: the tree's `U`/`A` letter is already the whole story. Baselines refetch on mount, on `fsRefreshSignal`, on window `focus` (a commit made in a terminal), and after an external on-disk change is applied to a file tab (the working tree moved under the bars).
- **`src/lib/gitdiff.ts`** is the shared, pure, browser-safe engine. `lineChanges()` = Myers' greedy line diff (common prefix/suffix trimmed first; bails to one whole-region hunk past `MAX_EDIT_DISTANCE`), returning per-line `add`/`mod` plus deletion seams. `notebookCellChanges()` matches cells **by id, never by index** — Cellar owns nbformat 4.5 ids, so an id survives inserts and reorders, whereas index matching would paint every cell below an insert as modified (a HEAD notebook with missing/duplicate ids falls back to index matching). It compares `source` + `cell_type` only: **outputs are deliberately excluded**, so re-running a cell to the same result never lights up a bar. A pure reorder is flagged `moved` on the *minimal* set of cells (the complement of the LIS of HEAD positions), so dragging one cell up marks one cell, not every cell it jumped. A removed cell has no cell to decorate, so its marker anchors to the next surviving HEAD cell (`removedBefore`) or falls off the end (`removedAtEnd`), rendering as a dashed seam in `Notebook.svelte`.
- **`src/lib/gitGutter.ts`** is the CodeMirror half (`FileTab.svelte` only; notebook cells use the `Notebook.svelte` bars instead). Its `gutter()` is listed **after `basicSetup`** so the bar is the rightmost gutter, hard against the code. Two sharp edges: `highlightActiveLineGutter` classes the caret's line in *every* gutter, so `.cm-gitGutter .cm-gutterElement` must force `background: transparent` and the change bars must be `::before` overlays — otherwise the active line shows a phantom bar; and the deletion triangle uses `::after`, so one line can be both changed and a deletion seam.
- **Git decoration colors are NOT daisyUI semantic tokens.** Those are accent colors and their hues are not stable across themes (`dim` makes `secondary` and `error` both salmon; `nord` makes `info` pink), so added/modified/removed would stop reading as added/modified/removed. They are fixed palettes in `app.css`, resolved per scheme by CSS `light-dark()` against the `color-scheme` daisyUI sets on `<html data-theme>` — the same source of truth `editorTheme.ts` uses, so every future theme is handled with no per-theme work. There are **two** sets, because the two surfaces follow different conventions: `--cellar-git-*` for the diff bars (`gitGutter.ts`, `Notebook.svelte`: added green / modified **blue** / moved purple / removed red), and `--cellar-git-tree-*` for the file explorer's names and status letters (`FileTreeNode.svelte`: untracked+added green / modified **gold** / deleted red, VS Code's explorer convention). Both sides of each `light-dark()` are that scheme's own value — VS Code's *dark* decoration hues sit near 1.5:1 on a light background, which is what made the tree's green unreadable.
- **Git blame in the bottom status bar (GitLens-style).** For the active **file tab's** cursor line, the shell footer (`+page.svelte`) shows "author, relative date" with the commit short-sha + summary on hover; uncommitted lines read "You, uncommitted" (hover "Not committed yet"). `gitBlameFile()` (`git.ts`) runs `git blame --line-porcelain -w` and parses one record per line (`{commit, shortSha, author, authorTime, summary, notCommitted}`; the all-zero SHA means `notCommitted`); route `GET /api/fs/git/blame?path=` returns `{isRepo, tracked, lines}`, `tracked:false` (untracked/binary/non-repo) hides the bar. **Whole-file cache, not per-keystroke git:** `FileTab.svelte` fetches the blame array once (on mount, `gitRefresh` bump, window focus, after its own save, and after an EXTERNAL on-disk apply - which moves the working tree under both the blame cache and the gutter baseline exactly as a save does) and maps the cursor line to a record on a 90ms-debounced `selectionSet`/`docChanged`, reporting up via `onBlame(path, report|null)` into `+page.svelte`'s `blameByPath` map; the footer picks an entry with **`activeBlameFor(activeFilePath, activeNotebookPath, blameByPath)`** (pure, in `src/lib/blame.ts`, unit-tested by `tests/unit/blame-status.test.ts`), which selects by **which tab is active, never by truthiness** - both keys are live at once (`activeNotebookPath` falls back to the canonical notebook while a plain file tab holds focus, and a `LiveNotebook` keeps publishing its focused cell's record under it), so an `||` chain fell through a correctly-null file report and credited that notebook cell's author to the file. A focused file tab therefore answers with its OWN record or nothing - and nothing is the COMMON case here, since the generated `report.html` this feature targets is normally gitignored or never added. **Line-level decorations (this blame AND the gutter's HEAD baseline) are size-gated at `MAX_DECORATION_BYTES`** (= the ordinary `MAX_FILE_BYTES`, so nothing openable before the HTML exception loses them; only the export-sized files that exception admits do). They are the one git surface whose cost scales with the whole FILE - a `--line-porcelain` blame of a 10 MB report measured ~2.6s and ~46 MB of stdout, then a record per line and a synchronous `JSON.stringify` of the lot, on the same thread as kernel streaming/SSE/MCP, re-run on mount + every save + every window focus. The guard is a `stat` that gates the blame/`git show` (the point is not paying for them, not discarding the result afterwards; the mtime cache is probed first, which costs two `stat`s and no spawn, so the refusal is cached like any other answer) and on the BLAME half it answers **`tooLarge:true`, never a bare `tracked:false`** - "too big to blame" and "untracked" are different facts, so `FileTab` reports `{unavailable:'too_large'}` (the `BlameReport` union in `src/lib/blame.ts`) and the footer reads "too large for blame" instead of going blank; the change bars are simply absent. **Size alone may NOT claim that fact** (`decorationRefusal`): the file this ceiling exists for is a GENERATED `report.html`, normally gitignored or never added, which has no blame for an entirely different reason - so an oversized file first costs ONE path-scoped `git ls-files --error-unmatch` (an index lookup, a different cost class from the blame, and it runs only once the size gate has tripped - an ordinary file never pays it) and only a **tracked** one reports `tooLarge`; an untracked/ignored one reads as untracked, exactly what VS Code shows. `git status --porcelain` is the wrong tool for that half - it cannot see ignored files at all. **The HEAD-baseline half deliberately does NOT pay that lookup** (`gitHeadFile` refuses on the `stat` alone and always reports `tooLarge:false`): a refused baseline and an untracked file draw the identical empty gutter, so the distinction has no surface to render on, and computing it would have cost an `ls-files` per mount / `gitRefresh` bump / window focus for a value no caller reads. Only the blame, which has a status bar that can speak, buys it. **The NOTEBOOK path opts out** (`gitHeadFile(nb,{sizeGuard:false})`): per-cell decorations cost in SOURCE, not in the outputs that make an `.ipynb` big (its blame is already `-L`-scoped), so gating there would strip the bars off an ordinary plot-heavy notebook. Covered by `tests/unit/git-decoration-limit.test.ts`, whose refusing half asserts **which git subcommands ran** (`gitSpawnLog()`) across all three states (tracked+big, untracked+big, ignored+big) - a test that only checked "no blame shown" would pass while the 2.6s still ran, and a bare spawn COUNT of zero would now forbid the cheap lookup instead of the expensive call. Relative dates use `relativeTimeLong()` in `relativeTime.ts` (weeks/months/years horizon, separate from the run-badge's day-capped `relativeTime`). Footer text is a daisyUI semantic token (`text-base-content/55`), theme-agnostic by construction - unlike the diff-bar colors, blame is neutral chrome, not an add/mod/del signal.
- **File management (VS Code-style explorer).** Create/rename/delete/cut-copy-paste (move/copy) for files + folders. **Backend**: `fstree.ts` exports `createEntry`/`renameEntry`/`deleteEntry`/`moveEntry`/`copyEntry` (folders recursive via `cpSync`/`rmSync`), all path-guarded through `resolveInWorkspace` + a `resolveInside` helper that also refuses the workspace root; single-segment name validation (also rejects `.`-prefixed hidden names, which the explorer never lists); moving/copying a folder into itself/a descendant is refused and a move within the same parent is a no-op; paste auto-suffixes on collision (` copy`, ` copy 2`, …), create/rename reject on collision. One dispatch route `POST /api/fs/op` (`{op, …}`) returns the affected workspace-relative path(s). Delete/rename/move also sync the live notebook doc map server-side (`+server.js` calls `notebook.ts`'s `dropDocs`/`rekeyDocs`): a deleted path (or any doc nested under a deleted folder) is dropped from the `docs` Map so a later UI/MCP persist can't `writeFileSync`-resurrect the removed file, and a renamed/moved path is rekeyed to its new absolute id (folder ops rekey nested notebook docs too) so edits keep landing in the live doc; the `activePath` pointer follows (reset to null → default notebook when a dropped doc was active). **Frontend**: `Sidebar.svelte` owns the file-ops state (clipboard, inline rename/new, context menu, delete-confirm modal) and exposes it to the recursive `FileTreeNode.svelte` via the `cellarFileOps` **context** (getters forward `$state` so nodes stay reactive — avoids prop-drilling). Inline rename + new-entry use `TreeEntryInput.svelte`. Right-click any node (or empty files-body / root) → context menu; F2/Delete/⌘·Ctrl+C/X/V shortcuts; a cut entry dims until pasted. Paste is always in the menu, disabled with a tooltip while nothing is copied, and on a FILE (menu or ⌘·Ctrl+V) it pastes into that file's folder (`$lib/filePaste`'s `pasteTargetDir`). Duplicate copies a file or folder beside itself through the same `copy` op, so it takes the same ` copy` / ` copy 2` name, and selects the copy. After every op the tree + git decorations refresh, and `onFsChange({type,from,path})` bubbles to `+page.svelte` so open tabs are closed (delete) or remapped (rename/move) — no tab left dangling at a gone path.
- **Paste files from another app (⌘·Ctrl+V in Files).** Files copied in Finder and image data such as a screenshot arrive on the browser's `paste` event as File objects. Chrome fires `copy`/`cut`/`paste` at the document body when focus is on a tree row, so `Sidebar.svelte` listens on the window and acts only while focus is inside the Files section. The bytes go through `POST /api/fs/upload` in 256 KB chunks, because adapter-node's 512 K `BODY_SIZE_LIMIT` refuses a bigger request body (see `$lib/saveLimit.ts`). `fstree.ts`'s `writeUploadChunk` appends each chunk to a part file, checks the offset, fsyncs, and places the file under a free name (`copyName`, the same rule as Copy/Paste). The part file is staged in the OS temp dir under `cellar-uploads/<hash of the workspace root>`, never in the project folder. The server clears that staging folder at start (`sweepStagedUploads` from `hooks.server.js`), and the browser's abort `DELETE` removes one part file. The finish step is a hard link. When the staging folder is on another filesystem or hard links are unsupported, it is an exclusive copy (`COPYFILE_EXCL`). Neither replaces an existing entry: a taken name, a broken symlink included, moves to the next candidate, and the paste fails with a clear error after 1000 names. The route refuses a body that is not `application/octet-stream`, an `Origin` header that names another host, and a destination folder with a hidden path segment, so a page on another site cannot write files. `MAX_UPLOAD_BYTES` (1 GB, `limits.js`) caps one file. A folder copied in another app is refused with a message, and a paste with no file data says so. **The most recent copy wins.** Every explorer Cut/Copy also writes the path to the system clipboard as text, so files still on the system clipboard at paste time were copied later (`pasteSource`). When that write is unconfirmed, the explorer's clipboard keeps first claim. The menu's Paste reads only the explorer clipboard: reading system files outside a paste event needs a permission prompt. Covered by `tests/unit/file-paste.test.ts` + `tests/e2e/file-tree-paste-duplicate.spec.ts`.
- **Move a file/folder by DRAGGING it onto a folder (`src/lib/fileDrag.ts` + the `FileTreeNode`/`Sidebar` halves).** The one gesture the tree was missing while cells, tabs and sidebar sections all had it, so a user who had learned it found it silently did nothing here. Native **HTML5 drag-and-drop**, the idiom the sidebar's own section reorder and the notebook's cell reorder already use - a drop ONTO a target, which is what this is, rather than the tab strip's pointer-driven insertion between wrapped rows (that one is pointer-based because it needs a lifted-tab visual and two-dimensional hit-testing on a wrapping strip; this needs neither). **The SERVER stays the authority and nothing here re-implements it**: `fstree.ts`'s `moveEntry` already refuses a folder into itself or a descendant, treats a same-parent move as a no-op and de-duplicates a colliding name (` copy`) rather than clobbering, and the drop goes through the SAME `POST /api/fs/op` + `onFsChange` that cut/paste does - one `commitMove` shared by both, so the two gestures cannot drift about what a move means.
  - **The DROP ASKS; it never moves.** A confirmation names what is moving and where it is going (`move-modal`, the same daisyUI shape as the delete confirm - one dialog idiom in that file), and Cancel leaves everything untouched because nothing has been written at that point. Most file managers do NOT confirm a same-workspace move, since it is trivially reversible; the captain asked for it anyway and the reasoning holds - a drag is far easier to trigger by accident than cut-then-paste, especially while scrolling a long tree. Escape dismisses it (and, in the same pass, the delete confirm beside it: a confirmation you cannot abandon from the keyboard is the wrong shape for a dialog, and cancelling is the safe direction for both).
  - **The rules are PURE and live in `$lib/fileDrag.ts`** (the `tabReorder.ts`/`cellSelection.ts` precedent: vitest runs without the SvelteKit plugin, so a rule left in a component could not be driven at all, and drag behaviour rots silently). Only a FOLDER or the tree's root area is a target - dropping on a FILE is REFUSED rather than redirected to that file's parent, which is what VS Code does but moves the entry somewhere the pointer was never over; Paste is different on purpose: on a file it pastes into that file's folder, because a paste names no drop point the pointer could miss. `dropVerdict` returns a REASON rather than a boolean because the reasons are different facts: `same-parent` is **not a mistake** - the entry is already there, the server would no-op, so it is silently declined with no modal AND no error, since a confirmation (or an error) for an operation that does nothing is noise; the other three are reported. A rule that drifts from the server can therefore only ever be over-STRICT (an offer withheld), never over-permissive in a way that reaches the filesystem.
  - **A REFUSAL IS REPORTED FROM `dragend`, NOT FROM THE DROP, and it cannot be otherwise:** `preventDefault` on `dragover` is what MAKES an element a drop target, so a refused row is never armed and **the browser delivers no `drop` event to it at all** - the reason had nowhere to be said. Calling `preventDefault` anyway to get the event would hand that row the "you may drop here" cursor, a lie about the very thing being refused. So the cursor stays honest (the native no-drop one) and the reason follows a beat later on the existing `files-op-error` line - never a second error channel.
  - **THE TRAP, MEASURED against Chromium rather than assumed: a drag that ENDS over a row fires `dragleave` on that row with `relatedTarget === null`, immediately before `dragend`.** A genuine move away carries the element being ENTERED. They are indistinguishable by anything else, so a `dragleave` handler that clears state unconditionally wipes the refusal microseconds before the one place that would report it - which is exactly how the two refusal tests failed on the first cut. Hence `dragLeave(node, genuine)`: the highlight clears either way, the recorded refusal only on a real move. Anything else that ever needs to survive a drag's teardown has to make the same distinction. **An ABORT is not reported**: releasing on the dragged row ITSELF is `into-itself` (checked first, file or folder) and silent, and an Escape-cancel is detected from MEASURED Chromium behaviour - the page gets no `keydown` for it, the drag ends with NO terminal `dragleave(null)` over the row, and `keyup` lands after `dragend` - so a refusal is reported only for a real release over the refused row (`releasedOn`, the INNERMOST terminal `dragleave`, since it bubbles to the root handler) and only after a short grace window an Escape retracts. The root area also grows a `files-root-drop` strip while an entry that is NOT already at the root is being dragged, since rows are `w-full` and the padding alone was too thin a target for the only drag route out of a folder.
  - **A control inside a tree row stays a control**: a row being RENAMED is a `TreeEntryInput`, a different `{#if}` branch entirely, so it is neither draggable nor a drop target by construction. A row's background is ONE choice (`rowBg`) rather than two Tailwind utilities layered and left to stylesheet order - drop-target outranks selection, being what the pointer is asking about right now. Rows `stopPropagation` their own `dragover`/`drop` so the root area only ever answers for the space AROUND them.
  - Covered by `tests/unit/file-drag.test.ts` (the rules, incl. a differential block that DRIVES the real `moveEntry` over a temp workspace, so every offered drop really moves and every refused one really throws or no-ops) + `tests/e2e/file-tree-drag-move.spec.ts` (the gesture in a real browser via `dragTo`, which really does drive Chromium's own drag machinery: confirm, cancel, a folder with its contents, the ` copy` collision, each refusal with its reason, a self-release and an Escape staying silent beside a control that still reports, a nested entry dragged to the root strip, the mid-drag highlight asserted as a real REPAINT rather than a `data-` attribute, the drag not toggling the folder it started on, and cut/paste unchanged). Every assertion reads the FILESYSTEM as well as the tree, since the tree is a view a stale refresh could make agree with a move that never happened.
- **Tabs — session memory + preview.** Open-tab set is persisted per workspace through the per-project UI-state store (`$lib/uiState`'s `getUi`/`setUi`, key `cellar-tabs:<workspace>`, i.e. the server-owned `.cellar/` JSON, NOT `localStorage` - so it survives a relaunch on a new port), holding each tab's path + preview flag + kind, in ORDER, plus the active id. **First-ever open** (no key) → empty state (`data-testid=empty-state`, no tabs); returning → tabs restored. Single-click a tree file → transient **preview** tab (one at a time; next single-click reuses its slot); **double-click** (tree or tab) or **editing** promotes it to permanent (VS Code semantics). All tab logic lives in `+page.svelte`.
  - **Drag-and-drop tab reordering (`src/lib/tabReorder.ts` + the `Navbar.svelte` strip).** Grab a tab, drop it in a new slot. **The persisted ARRAY ORDER is the strip order**, so reordering needs no storage of its own - `reorderTabs` returns a new `tabs` array and the existing session `$effect` writes it; there is deliberately no parallel order key. The pure rules (hit-testing + the resulting order) live in `tabReorder.ts` because vitest runs without the SvelteKit plugin, so a rule left in the component could not be tested at all (`virtualization.ts`/`cellSelection.ts` precedent).
    - **POINTER-driven, not HTML5 DnD** - the deliberate divergence from the cell/sidebar-section grips. Three things follow: the press becomes a drag only past `DRAG_THRESHOLD_PX` (4), so an ordinary click is never misread as one; the TAB ITSELF follows the pointer (a `translate`), not the browser's washed-out drag image; and the drop indicator is drawn from a layout snapshot we own, so it names an exact slot on an exact ROW.
    - **The strip WRAPS, so hit-testing is two-dimensional.** `dropIndexAt` picks a ROW first (nearest by vertical distance; a pointer above/below every row still names a definite slot, so the indicator never blinks out at the strip's edge) and only then the gap within it. A single left-to-right scan puts the marker on the wrong row the moment the tabs spill onto a second line.
    - **Geometry is SNAPSHOTTED when the drag begins, not re-measured per move** - the dragged tab is translated away from its slot, so its live rect no longer reports the box hit-testing needs, while its LAYOUT box is unchanged. That holds only because the marker is **entirely OUT OF FLOW** (`position:fixed`, placed from that same snapshot), which is also what stops the strip shifting around as you drag. **The marker's PLACE is threaded out of the hit test with the slot (`dropTargetAt` -> `DropTarget.marker`), and that is a correctness rule on a wrapped strip, not tidiness**: at a wrap boundary the end of one row and the START of the next are the SAME insertion index, so the index alone cannot say which of the two places the pointer meant - and rendered the obvious way, as a zero-width flex item before tab `index`, the row-start one cannot be drawn AT ALL, because a zero-hypothetical-size item always fits the line it is being collected onto and so stays on the row ABOVE. It pointed at the end of a row the pointer had already left. Anchoring in `dropTargetAt` settles it (the row's first tab's left edge when the drop starts that row, else the right edge of the tab it lands behind, which is on the same row by construction) and keeps slot and marker from ever disagreeing. `pointer-events-none` on it is load-bearing too - it is drawn exactly where the pointer is heading. The snapshot is taken at the THRESHOLD, not at pointerdown, so an ordinary tab click costs no forced layout.
    - **Dropping back where it started is a genuine no-op**: `reorderTabs` returns the SAME array reference when the slot is one the tab already occupies (`insertAt === from` or `from + 1`), so nothing is written and the session `$effect` never fires. The keyboard step goes through that same function - `stepSlot` only names its slot (`index + 2` to the right, since the tab is still in the array when the slot is chosen) - so a step off either end is that same no-op rather than a wrap-around, and there is ONE reorder rule rather than one per gesture.
    - **A drag must never select the file it dropped on**, so the synthesised `click` is swallowed by a capture listener torn down on a `setTimeout(0)` (the click is dispatched in the same turn as the pointerup, so it can never eat a later real click). **Escape leaves the gesture RUNNING and merely flags it `cancelled`** rather than tearing it down - the pointer listeners must survive so the eventual release is swallowed too, else abandoning a drag selected the tab it was released over. **That flag is then honoured by EVERY handler the gesture drives, `onPointerMove` first** - the threshold is measured from the ORIGINAL press point, which the pointer is by then far away from, so a move handler that checks only `dragId` re-crosses it and RESTARTS the drag the user just called off: the tab lifts again, the indicator returns, and the drop silently does nothing. A cancelled gesture stays cancelled for the rest of its life. **And a gesture may never OUTLIVE its own release**: a `pointerup` that never reaches this document leaves the drag standing, and the next ordinary tab click then SETTLES it - an unrelated tab jumps and the click that should have switched files is swallowed. It is reachable, not theoretical: the app is full of sandboxed `srcdoc` iframes (every rich `text/html` cell output, every `.html` preview) and a release inside one is delivered to the FRAME. Two independent defences, and neither covers the other's case: `setPointerCapture` on the tab at pointerdown (released in `endDrag`) makes the release ours whatever it is released over - the real fix - while `onTabPointerDown` ALSO `endDrag()`s any gesture still standing before starting the next, which is the backstop for a pointer that could never be captured (a synthetic one, or a browser that refused) and is what makes the invariant hold BY STATE rather than by trusting a release to arrive. `onPointerUp`/`onPointerCancel` then require a live `press` whose `pointerId` matches, and only a drag whose `dragId` IS that press's may settle there.
    - **A tab's classes are decided in ONE place (`tabClass`), and the background MUST be a single choice.** `hover:bg-base-200/50` out-specifies a plain `bg-base-200`, and a lifted tab is by definition under the pointer - layered, it rendered at 50% alpha with the tabs it floated over reading straight through it. The hover tint is dropped from EVERY tab mid-drag, and the marker sits at `z-30` (above the `z-20` lifted tab, which necessarily covers the very gap it is asking about).
    - **PANE order is OPEN order (`Tab.seq`), never strip order** - `fileTabs`/`imageTabs`/`ipynbTabs` sort by it. Svelte's keyed `{#each}` MOVES a reordered pane's node, and moving an `<iframe>` RELOADS it, so deriving pane order from the strip blanked and re-fetched every `.html` preview and every rich `text/html` cell output as a side effect of dragging a tab. Pane order is invisible (every pane but the active one is `hidden`), so fixing it costs nothing; a rename carries `seq` forward. Pinned by the iframe-reload case in the e2e, which must drag the HTML tab ITSELF - dragging another tab past it moves only that other pane and passes either way.
    - **Keyboard + ARIA: the WAI-ARIA tabs pattern, roving tabindex included.** The strip is a `role="tablist"` of `role="tab"` elements (`aria-selected`, `aria-label` carrying "tab N of M") with Enter/Space selecting, and each tab `aria-controls` the pane it switches to, which is `role="tabpanel"` and points back at it (`$lib/tabIds` owns that id scheme, so the two components cannot drift). **The whole strip is exactly ONE Tab stop**: one tab is tabbable (`rovingTabId` - the FOCUSED tab, falling back to the selected one and then to the first, so there is a stop even before the strip has been focused) and every other carries `tabindex=-1`, reached with bare `ArrowLeft`/`Right`/`Home`/`End`, which move FOCUS only (manual activation - browsing must never switch the file under you). Keying the stop off FOCUS rather than off selection is what makes tabbing away and back return to where the user was. Without it the document's Tab order grew by one stop per open file and another per close button, i.e. it scaled with how many files happen to be open rather than with what the strip MEANS. **The per-tab close and jump-to-running buttons are therefore `tabindex=-1` too, and EACH owes the keyboard a replacement route** - taking a control out of the Tab order without one makes its feature pointer-only, which is the regression the pattern is most likely to ship. Close's is `Delete`/`Backspace` on the focused tab; the run spinner's is the registry's **`jump-to-running-cell` (`Mod-Shift-Enter`, global)**, which unlike the reorder chords is dispatched from **`+page.svelte`'s window handler** rather than from a focused tab, precisely because it must fire with NOTHING focused - it acts on the notebook that is BUSY (the viewed one when it is, else the first running, else the first queued; `jumpTargetTabId`), not on whatever has focus, and with nothing running it takes no keystroke at all. It reaches the SAME `jumpToRunningCell` the spinner click does, never a second implementation. Focus then lands on the tab that takes the closed one's SLOT, else the one before it; the roving pointer is moved off the dying tab BEFORE the close, and a closed tab is pruned from it, so a reopened tab can never claim the stop over the tab the user is looking at. Both buttons keep `data-tab-nodrag` so a press on them never begins a drag. Reordering is `move-tab-left`/`move-tab-right` (`Mod-Shift-ArrowLeft`/`Right`, the horizontal echo of `move-cell-up`/`down`), DECLARED in `shortcuts.svelte.ts` so Settings lists and rebinds them, but DISPATCHED from the focused tab's own keydown in `Navbar.svelte`: the gate is then structural - the event target IS the tab - so the chords can never fire while a notebook has focus. A keyboard move re-focuses the tab after `tick()` (the keyed each moves the node, which drops focus) and announces the new position on an `aria-live` region, the keyboard having no visual drag to watch. **A tab id is pasted into a DOM id, so `$lib/tabIds` PERCENT-ENCODES ASCII whitespace** (and the `%` escape itself, in ONE pass so the encoding stays INJECTIVE): a file tab's id is `file:<workspace path>`, `my report.html` is an ordinary filename, an HTML `id` may not contain whitespace, and `aria-controls`/`aria-labelledby` are IDREF **LISTS** - so raw, the value parsed as two tokens and NEITHER resolved, silently costing exactly those files their tab->pane pairing and their pane its accessible name. Do NOT "simplify" that to a lossy `replace(/\s/g,'-')`: `a b` and `a-b` are two simultaneously-openable files and one DOM id between them means one tab's `aria-controls` resolves to the OTHER tab's pane.
