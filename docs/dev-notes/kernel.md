# Kernel bridge: execution, watchdog, interrupt, restart, introspection, lifecycle

Design notes and decision records. Each entry states a decision and the reason for it. The code shows what it does; this file says why it is shaped that way. When an entry says "see the X entry", X is a bold entry title, and it may sit in another file in this folder. The short list of rules every change must follow lives in `AGENTS.md`.

- **Kernel bridge = the de-risked core.** `src/lib/server/kernel.ts` connects to Jupyter over REST+WebSocket using `@jupyterlab/services` (spec §2). Node's global `fetch` is passed into `ServerConnection.makeSettings`; **the global `WebSocket` is passed ONLY WHEN IT EXISTS, and that conditional is load-bearing** - it is **Node 22+** (21 had it behind `--experimental-websocket`, 18 and 20 have none), while `Private.makeSettings` spreads `...options` OVER its defaults, so passing it unconditionally sent `undefined` on Node 20 and CLOBBERED @jupyterlab's own default - which in Node is the `ws` package it already depends on. Every `new settings.WebSocket(...)` then threw `WebSocket is not a constructor`, so NO CELL COULD EXECUTE on the versions `engines: >=18` declares, and the cell's own OUTPUT was that message. Invisible for as long as it was because the only layer that boots a kernel is e2e, which had never run in CI, and every dev machine here is on Node 26; the FIRST Linux run of `.github/workflows/e2e.yml` failed exactly the three tests of its shard that execute a cell. Omitting the key (never passing `undefined`) keeps the global on Node 22+ and falls back to `ws` below it - no polyfill and no new dependency. Pinned by `tests/unit/kernel-websocket-settings.test.ts`, which deletes the global to reproduce Node 20 on any interpreter, because the failing axis is the NODE VERSION and e2e cannot vary it: the suite runs on whatever Node the runner has, and the workflow deliberately pins **Node 20** so CI keeps exercising the declared floor and the `ws` fallback that real Node-20 users get. `execute()` emits real nbformat output objects so the same shape streams live to the browser and is persisted. `rebindKernel()` (added) tears down + restarts the kernel so it re-reads a rewritten kernelspec onto a new interpreter (a plain `restart()` reuses the original argv and would NOT switch venvs). **Startup injection (`initKernel`):** every kernel silently runs `%matplotlib inline` on fresh start **and** after `restartKernel()` (restart clears the namespace + backend), so matplotlib figures emit `image/png` even when the project's default backend isn't inline (e.g. `MPLBACKEND=agg`/macosx); guarded by try/except so it's a harmless no-op when matplotlib is absent.
- **Run watchdog = liveness PROBE, never silence (`kernel.ts` `execute()`).** `await future.done` is unbounded (a stalled websocket / an undelivered `execute_reply` / a dropped autorestart wedges the queue slot forever), so a watchdog guards it - but **silence is NOT death, and must never abort a run.** A Spark query (`sql.ts` compiles to `spark.sql(...).limit(N).toPandas()`), a big pandas op, or untraced training is ONE blocking call emitting NOTHING until it returns; the old abort-on-idle-window watchdog could not tell a 20-minute cluster job from a dead kernel and killed the user's real work ("Kernel went unresponsive (no activity for 900s)" on a healthy kernel). So `CELLAR_KERNEL_IDLE_TIMEOUT_MS` is now a **probe interval, not a deadline** (default **30s**, was 15min - a probe is cheap and no longer destructive, so a wedged notebook recovers in one window (proven death) to three (`SUSPECT_STRIKES`), ~30-90s, instead of waiting 15min for the watchdog's one shot). Expiry only runs `probeKernelLiveness`; **only its verdict may abort**. Any kernel traffic still re-arms, so a cell that emits output is never probed at all. **`CELLAR_KERNEL_IDLE_TIMEOUT_MS=0` disables the per-run watchdog entirely** (`kernelIdleTimeoutMs` maps an explicit `0` to the `WATCHDOG_DISABLED` sentinel; `armWatchdog` never arms → never probes, never aborts, run relies only on the force-abort path), matching the culler's `CELLAR_KERNEL_IDLE_TIMEOUT=0`; empty/unset/non-numeric/negative still fall back to 30s via `envMs`, and the probe TIMEOUT knob keeps rejecting non-positive values as typos.
  - **The one out-of-band signal is the sidecar's REST view - `GET /api/kernels/<id>` (`KernelAPI.getKernelModel`).** Empirically verified against a real sidecar running a blocking `time.sleep`: it answers in **~3-5ms with `execution_state:'busy'` while the shell channel is blocked**, because it is the Jupyter SERVER's own bookkeeping. **What does NOT work, and why (do not retry these):** a `kernel_info_request` - or ANY `execute`, **`{internal:true}` included** (that bypasses Cellar's run queue, NOT the busy kernel) - rides the **shell channel** and QUEUES behind the running cell, so it answers only once the cell ends and would read "unresponsive" for exactly the workload this protects; and `getKernelInfo()`/`listKernels()` report the **local** `connection.status`, which a stalled websocket freezes at `busy` forever. A gone kernel surfaces as `getKernelModel` resolving **`undefined`** (it resolves the 404, it does not throw); a throw means the sidecar itself was unreachable.
  - **Abort rule:** Gone-from-server (`undefined`) or `execution_state:'dead'` ⇒ **proven dead**, abort immediately (not a race that resolves) - the REST verdict outranks any socket state, since a kernel the server no longer has is dead whatever the socket says. Else the server still HAS the kernel, so the verdict turns on whether we can still HEAR it, and **exactly two readings may accrue a strike**: (a) `connectionStatus==='disconnected'` ⇒ **suspect** - @jupyterlab exhausted its 7 retries, so the reply can never arrive whatever the kernel's state; (b) `connectionStatus==='connected'` **and** `execution_state!=='busy'` ⇒ **suspect** - we are connected, so we would have heard the reply, and the kernel is not running our cell: the genuine lost-reply case, the transport failure this exists for. Connected **and** `busy` ⇒ **alive**, re-arm (repeats indefinitely - a 3-hour job survives). Any other socket state - in practice **`'connecting'`**, @jupyterlab mid-reconnect - ⇒ **unknown/inconclusive, re-arm, NEVER a strike, regardless of `execution_state`**. That last rule is load-bearing in BOTH of the blip's shapes: `busy` is proof the kernel works, and `idle` does **not** mean the reply was lost - a cell that FINISHED mid-blip leaves the kernel idle with its `execute_reply`/iopub **buffered** for replay (`buffer_offline_messages`, default on), so convicting there would destroy a result already computed and report a loss that is about to arrive. Either way it would abort exactly the silent multi-hour Spark job this exists to protect. A truly dead socket is not spared, only slower: @jupyterlab exhausts its retries (~120s) into `'disconnected'`, which convicts via (a)'s strike path - so dead-socket recovery costs **~120s + the strike window (~90s at the default) ≈ 210s, delayed but never lost** - the explicitly accepted price. A suspect verdict aborts only after `SUSPECT_STRIKES` (3) **consecutive** readings, like `parent-watch`'s CONFIRM_STRIKES. Probe threw **or timed out** ⇒ the one reading with no view of the kernel at all, so it turns entirely on the socket (`probeFailureVerdict`): with the socket `'connected'`/`'connecting'` it is **inconclusive, NEVER abort** - the instance-reaper's stance (`pidReapDecision`): killing REQUIRES a positive match, because the costs are asymmetric (a false abort destroys an hour-old cluster job; a false re-arm only delays recovery of a notebook the user can restart by hand). That is what keeps a silent Spark query safe through a flaky sidecar: its socket is connected, so failing probes alone can never convict it. **EXCEPT** a failed/timed-out probe **and** `connectionStatus==='disconnected'` ⇒ **suspect** (the third strike-accruing reading, converting through the normal strike path): the websocket rides the SAME sidecar, so HTTP failing and the socket having exhausted its retries are two INDEPENDENT, CORROBORATING signals that we cannot hear this kernel by ANY route - a positive match, which UPHOLDS the doctrine rather than weakening it. Without that carve-out an unconditional `unknown` reset the strikes forever, so a **persistently** wedged sidecar (HTTP black-holed while the TCP socket stays up) wedged the queue slot PERMANENTLY - the exact failure the watchdog exists to clear, and one the old 15-minute abort did free. The inconclusive stance is for a **transient** failure only. Its message obeys the same honesty rule and is the strictest case: having lost BOTH routes we know LESS about the cell than any other path, so it says only that the kernel is unreachable by any route and the run was abandoned - never that the cell stopped. (Deliberately NOT implemented: preserving strikes across `unknown`, which would let a purely transient flake accumulate toward conviction.) Aborts keep the same `KernelExecuteAborted`/`'idle_watchdog'` reason + single-release path, but the message now names the real cause, not "no activity for Ns". **Each verdict carries its OWN complete sentence** (`ProbeResult.message`) - never a shared prefix in front of a fragment, because the paths know different things: gone/dead and connected-but-not-busy may say the kernel is no longer running the cell (the server lost it / we are connected so we would have heard the reply), but **`'disconnected'` may NOT** - without the socket we cannot see whether the cell is still running, and on a healthy kernel it very likely is, so it says only that the connection was lost and the run abandoned. Asserting a cause a reading did not establish is the exact defect ("no activity for 900s") this whole watchdog exists to retire; don't reintroduce it on the one path least able to know. A kernel PROCESS death is not this probe's case: jupyter **autorestarts** it and `abortActiveRuns(…,'kernel_autorestart')` already settles the run. Covered by `tests/unit/kernel-execute-watchdog.test.ts` + `tests/e2e/kernel-watchdog-probe.spec.ts`. **Its sibling is INTERRUPT (below), and the two stances are deliberately opposite for one reason: the watchdog acts on SILENCE, where killing destroys work nobody asked to kill, while an interrupt is the user ASKING - so it escalates to a force-abort where the watchdog must never.**
  - **Dead-socket self-heal = `refreshKernelConnection(nb)` (rung 1 of the reconnect ladder).** Convicting a `disconnected` socket **frees the run's slot but does NOT repair the transport**: the dead `KernelConnection` stayed in the `kernels` map, the PROCESS was still in the server's running list (so `reconcileCulledKernels` never dropped it), and `getKernel` handed that same dead socket to the next run - whose messages sat in @jupyterlab's `_pendingMessages` awaiting a reconnect whose 7 retries were spent, so **every later run silently wedged, was convicted again, and the notebook was broken until a manual restart** (the `cellar-dead-connection-refresh-x8` bug). The fix is a transport-only refresh built on `@jupyterlab/services`' **`KernelConnection.reconnect()`** (*"refreshes the connection to an existing kernel … does not restart the kernel"*): it rebuilds the websocket to the SAME kernel id and re-flushes pending messages, so the **namespace and any running cell survive**. **A plain `teardownKernel` is the WRONG fix** and must never replace this - a `disconnected` socket does NOT prove the process is dead; on a healthy kernel the user's cell is very likely still executing (the multi-hour Spark job the watchdog exists to protect), and teardown would destroy exactly that work. So teardown is gated behind the watchdog's own **"gone-from-server ⇒ proven dead"** rule: `refreshKernelConnection` first runs `probeKernelLiveness`, and only a **`dead`** verdict (server no longer has the kernel, or reports it dead) falls through to `teardownKernel` (rung 3) + lazy restart; a `disconnected` socket with a **present** model is `suspect`, not `dead`, so it reconnects the socket. On a successful refresh there is **NO epoch bump** (the session never changed), so `connectionStatus()`/`ran_this_session`/`spark`/`w` stay valid. **Idempotent + single-flight** per notebook (`NotebookKernel.refreshInFlight`, mirroring `livenessInFlight`), so the **two triggers converge on ONE reconnect - keep the reconnect model single, never add a second path**: (1) the watchdog conviction fires it fire-and-forget when `connectionStatus==='disconnected'` and changes the abort message from "Restart the kernel to recover" to "the connection is being refreshed; re-run the cell"; (2) **`execute()` defensively refreshes before dispatching a run** whose cached connection reads `disconnected` (this is what actually closes "every later run hangs"). The reconnect handshake is bounded by `reconnectTimeoutMs()` (**15s**, `CELLAR_KERNEL_RECONNECT_TIMEOUT_MS`); a timeout is non-fatal (`reconnect_timeout`) since a later run retries. Rungs 2 (session expiry, `reconnectTo`) and 3 (process restart, `reconnectAfterKernelRestart`) live in `databricks.ts` and are untouched. Covered by `tests/unit/kernel-connection-refresh.test.ts` + the self-heal case in `kernel-execute-watchdog.test.ts`.
  - **A restart must END - usable or refused - in bounded time (`restartKernel`).** Reproduced hanging 30-90s+ under CPU load with the Variables panel polling. **The seen cause was LOCK OWNERSHIP, not a silent shell**: a probe arriving mid-restart took the (free) exec lock and went on the wire to the DYING kernel (the old kernel's `shutdown_reply` clears @jupyterlab's "restarting" hold), never got a reply, and the post-restart injection waited behind it. So `restartKernel` CLAIMS the exec lock synchronously before `restart()` and holds it through the injection (`initKernel(..., {locked:true})`); everything arriving meanwhile reaches the NEW kernel. The fresh-start shell guard (`awaitShellHandshake`) could not have caught that, but its question is ALSO asked after a restart: `shellAnswers` against the reconnect's own `kernel_info_reply` (`watchConnectHandshake` - `kernel.info` is one-shot and already resolved), re-asking every 250ms because one lost reconnect request is measured-normal (~1 in 15). And the injection itself is ACK-bounded (`runSilent`'s `ackTimeoutMs`: any message parented by the request, i.e. its iopub `busy`) because an execute sent right after an ANSWERED handshake was measured lost too. Only acknowledgement is bounded, never execution. Any miss tears the kernel down with a reason naming which step went silent. Healthy-path latency is unchanged (idle median ~360ms before and after). Covered by `tests/unit/kernel-restart-handshake.test.ts`. The FRESH-start injection and the autorestart re-injection are still not ack-bounded (never observed failing; the unit fakes across the suite emit no acks).
  - **The probe MUST always settle, or it disarms the watchdog it drives.** `armWatchdog()` only re-arms *after* a probe settles, so a probe that never resolves is strictly worse than one that aborts wrongly: the watchdog stops cycling for the rest of the run and the wedged queue slot it exists to free stays wedged forever. `fetch` has **no default request timeout**, so a sidecar that accepts the connection and then says nothing (black-holed socket, wedged jupyter-server) hits exactly that. So the probe threads an `AbortSignal` through `makeSettings(signal)` (`ServerConnection.ISettings.init`, which @jupyterlab merges into the request as `{...settings.init, ...init}` - note it **replaces** the library's default `init`, hence `cache`/`credentials` are restated there) and races it against `probeTimeoutMs()` (**10s**, `CELLAR_KERNEL_PROBE_TIMEOUT_MS`), so the hung request is **cancelled**, not merely ignored and left leaking a socket. That controller is **hoisted into `execute()`**, so the run's `finally` also cancels a probe still in flight when the run settles (its verdict is already discarded by the settled/aborted guard) rather than letting a hung GET hold its socket for the rest of the timeout. The timeout is a **fixed constant, deliberately NOT derived from `idleMs`** - tests drive that window to 40ms and would time out every probe. At the **30s default window** it cannot cause overlapping probes: `armWatchdog()` re-arms only after a probe settles, and the only other arming path (`resetWatchdog`, on kernel traffic) cannot fire a second probe inside a window longer than the timeout. Probes are **not** sequential by construction, though - drive the window below the probe timeout and traffic mid-probe can start a second one; that is tolerable (and deliberately carries no overlap guard) because a verdict only ever re-arms or accrues a strike. A timed-out probe is `unknown` (re-arm, strikes reset) while the socket is still connected/reconnecting, **never** an abort - a hung sidecar alone proves nothing about the kernel, and the point is only that the watchdog keeps CYCLING so it can still convict on a later real dead/suspect verdict (or once the socket itself gives up: see the corroborated carve-out in the abort rule above).
- **Interrupt ESCALATES: signal, grace, then force-settle (`kernel.ts` `interruptKernel`) - "stop means stop" is a promise the signal alone cannot keep.** SIGINT is a REQUEST; the RUN only ends when the kernel sends its `execute_reply`, and the old implementation signalled, returned `ok:true`, and never checked - so where the reply never came the cell read "running" forever while the tool reported success. Two ordinary ways in, and the second is the one the captain hit. **F1** - the kernel is signalled and the running work does not surrender, so `future.done` never settles; the idle watchdog deliberately will NOT rescue this (it probes, sees a genuinely BUSY kernel, re-arms forever - silence is what a healthy long Spark job looks like), which is correct and must stay. **F2** - the cell NEVER REACHED THE KERNEL: it holds the run queue's `running` slot and has emitted `run:start` (so it reads RUNNING) while parked on the per-kernel exec lock behind an INTERNAL execute. Registered in `activeRuns` only AFTER that lock, such a run was reachable by NOTHING - no longer in the queue's `pending` (`clearRunQueue` drops only pending) and not yet in `activeRuns` (`abortActiveRuns` could not see it). **F2 is why the bug reads as Spark-specific, and a session FAILURE is what triggers it**: a failed session makes the Databricks status poll fire `void autoReconnect(abs)` fire-and-forget, whose `CONNECT_CODE` runs through `runInKernel` → `execute({internal:true})` and legitimately holds that lock for MINUTES while a cold cluster starts; the user, seeing their session break, re-runs their cell and it parks behind that connect. Only Databricks work runs kernel ops that long, so only a Spark notebook meets it routinely. **The fix is two coordinated halves.** (1) `beginExecLock` hands `release` back BEFORE the wait (`acquireExecLock` survives as the thin awaiting wrapper for `runSilent`, which has nothing to cancel), so `execute()` registers its `ActiveRun` FIRST and races the lock wait against its own abort - a parked run is now abortable. **Its release is DEFERRED to `execReady`, never immediate**: the chain node is installed synchronously, so releasing before the PREDECESSOR finishes would put two `requestExecute` on one kernel, the collision that mis-pairs the interleaved idle/reply and wedges `future.done` (this bug's cousin); the caller still gets its rejection at once, so the queue slot frees immediately. Pinned by a `maxLive` concurrency assertion, not by ordering. (2) `interruptKernel` drops the pending queue, signals **BEST-EFFORT and BOUNDED** (`signalInterrupt`), waits `interruptGraceMs()` (**5s**, `CELLAR_KERNEL_INTERRUPT_GRACE_MS`; `envMs` rejects non-positive values so the escalation cannot be typo'd off) polling a SNAPSHOT of `activeRuns` taken BEFORE the SIGNAL (`watched`; read after it, a cell that surrenders promptly is already out of the set and its clean stop reports as `idle`) every `INTERRUPT_POLL_MS` (25ms) so an ordinary cell pays a tick rather than the window, then `abortActiveRuns(…, INTERRUPT_ABORT_REASON, watched)` - which aborts ONLY the watched runs, the `only` argument existing precisely so restart/teardown keep their whole-set semantics (their kernel change invalidates everything). **The snapshot is load-bearing in BOTH directions**: a run that STARTS during the grace window is deliberately NOT this interrupt's to kill (force-aborting it would destroy work nobody asked to stop, and would report `forced` for an interrupt whose own run surrendered perfectly), while the INTERNAL exec-lock holder - the `CONNECT_CODE` execute of F2 - IS in `activeRuns` at signal time and MUST stay in it, since settling that holder is what unwedges the notebook parked behind it. **Leaving the snapshot is not by itself a kernel surrender**, so the verdict also reads `ActiveRun.aborted` (set in `execute()`'s one `triggerAbort` door, so the watchdog's convictions count too): a concurrent interrupt, restart or watchdog abort empties the set without the kernel having answered, and reporting that as `kernel` would be the stop-we-did-not-observe this whole path exists to refuse - it reports `forced`. **THE SIGNAL MAY NEVER GATE THE ESCALATION**, or the promise goes straight back behind an operation that can fail or hang - the defect class this whole entry is about. @jupyterlab's `KernelConnection.interrupt()` REJECTS outright for a kernel it believes is dead and for any failed REST POST, and that POST is **unbounded** (`fetch` has no default request timeout and the shared manager's settings carry no signal), so `await`ing it directly left a black-holed sidecar - HTTP wedged while the TCP socket stays up, the state `probeFailureVerdict` contemplates - hanging `interruptKernel`, the `/api/kernel/interrupt` route and the MCP tool forever, with the cell reading RUNNING and the UI's bare `catch {}` showing nothing. So the request goes through `KernelAPI.interruptKernel` with an `AbortSignal` threaded via `makeSettings` and raced against **`interruptSignalTimeoutMs()`** (5s, `CELLAR_KERNEL_INTERRUPT_SIGNAL_TIMEOUT_MS`) - the `probeKernelLiveness` treatment, on its OWN knob because a probe is a background read while this is the user holding down stop - so a hung request is CANCELLED, never merely ignored; a kernel the connection already knows is dead is reported undelivered with NO post at all. **THAT RULE BINDS EVERY STEP ON THE WAY TO THE KERNEL, NOT ONLY THE POST**, which is why REACHING it is bounded too (`awaitKernelStart`, **`interruptStartTimeoutMs()`** 5s, `CELLAR_KERNEL_INTERRUPT_START_TIMEOUT_MS`): a cached `startPromise` is `mgr.startNew` (an unbounded `fetch` - `makeSettings` passes no signal on that path) followed by `initKernel`'s injections (an unbounded `await future.done`), and `await`ing it outright put the same promise back behind the same shape ONE LINE EARLIER, where it was worse - nothing downstream even ran, so against a black-holed sidecar the route and the MCP tool never returned at all while the user's run sat in `getKernel` holding the queue's `running` slot with `run:start` already emitted. It has its OWN knob deliberately (the signal's bounds a single localhost POST; this bounds a process spawn plus its startup injections) and it is **ABANDONED rather than CANCELLED** - unlike a hung POST, a start is work that should still finish and a later run awaits the same promise, and there is no signal threaded into `startNew` to cancel it with (`getKernel`'s own `.catch` is what keeps abandoning the race from surfacing an unhandled rejection). It covers the REJECTING half too: a sidecar that refuses the start used to propagate straight out of `interruptKernel`, handing the caller an exception instead of a verdict and skipping the escalation entirely. **The three bounds are never additive**: giving up here means the kernel was never signalled, so the signal and the grace window are both skipped, exactly as an undeliverable POST skips the grace window. The `watched` snapshot is therefore taken BEFORE this await as well as before the signal, so nothing that can block or fail gates it - and the return's `status`/`id` fall back to `nbKernel.connection` (a fact even mid-start, since `getKernel` binds it before the injections run) and then to `starting`, the same convention `listKernels` uses for a booting kernel's card, rather than blocking on the very promise the bound exists to avoid. **F3 - the run parked on the kernel START, closed by registering the `ActiveRun` at `execute()`'s ENTRY, before the first await.** `getKernel` creates and maps the entry SYNCHRONOUSLY (only the process start is async), so the handle goes onto it before `await getKernel` and every pre-send await - the start, the defensive socket refresh, the Mojo pre-flight, the exec lock - is raced against the run's own abort; an interrupt then settles it exactly like F2 (aborted unsent while the start is still pending past `interruptStartTimeoutMs`). Before, such a run held the `running` slot and read RUNNING while in neither `pending` nor `activeRuns`. Three rules came with it, each load-bearing: (a) **the defensive refresh's OWN `kernel_gone` teardown is FOLLOWED, not obeyed** (`followRefresh`) - the run moves its handle to the fresh entry exactly as it ran on before it was registered this early, while ANY other teardown in that window still ends it; (b) **`ActiveRun.sent`** is set once `requestExecute` is on the wire, and `settleAfterInterrupt` reports a watched set that ended on its own as `kernel` only if one of them was sent BEFORE the signal went out, else `idle` - a run whose START FAILED while it waited was never surrendered by any kernel - and every watched run still unsent is marked `interruptRequested`, so it REFUSES to send when its start or exec lock resolves inside the grace window (the code the user asked to stop never reaches the kernel). That refusal is NOT an abort (`ActiveRun.aborted` stays false), and the verdict reads ONLY runs sent at signal time: a run stopped before it sent - refused, or aborted while still parked - never yields `forced`/`forced_no_signal` (both claim the kernel may still be executing), so it reports `kernel` when a sent run surrendered and `idle` when none was sent; (c) **an interrupt that stops a run before its code was sent says so** (`abortMessage(reason, {sent})`: "Run stopped before it reached the kernel: this code was not executed.") rather than claiming the kernel "may still be executing" it - true of F2's lock-parked run too. **The Mojo pre-flight moved INSIDE that window** as `execute()`'s `prepare` hook (a throw ends the run unsent; `run.ts`'s `MojoNotReady` carries the not-ready verdict out), because on a notebook's first run the pre-flight is what waits out the start - in front of `execute()` it reopened this exact window one door earlier. Covered in `kernel-interrupt-stops.test.ts` ("reaching the kernel is bounded too"), `kernel-connection-refresh.test.ts` and `mojo-run-preflight.test.ts`, each mutation-checked. **A signal that could not be delivered escalates SOONER, never not at all**: nothing was asked, so there is no surrender to wait for and the grace window is skipped outright (the run-already-ended check still runs first). **Escalating here is right where the watchdog's abort-on-silence was wrong: the user ASKED.** **The result reports WHICH stop happened (`stopped`: `kernel` | `forced` | `forced_no_signal` | `chat` | `idle` | `no_kernel`) and never claims one it did not observe - nor a REQUEST it did not make, which is why the undeliverable case is its own verdict and its own abort reason (`interrupt_undelivered`, saying Cellar could not deliver the interrupt) rather than borrowing `interrupt_unresponsive`'s "the kernel did not respond in time", a claim about a request that was never sent** - `abortMessage` is keyed by reason because each family knows a different thing, and there are THREE: a RESTART (`kernel_restart`/`kernel_autorestart`) really did restart the kernel and says so; a TEARDOWN (`kernel_shutdown`, `kernel_culled`, `notebook_deleted`, `kernel_gone`, `kernel_rebind`, `kernel_restart_failed`) establishes only that the kernel this run awaited is GONE - a cull, a delete and a proven-dead process are not restarts, so it names no cause beyond that; an interrupt may claim NEITHER (it says Cellar stopped waiting, that the kernel MAY STILL BE EXECUTING, and names restart as the guaranteed escape - the "no activity for 900s" defect with the sign flipped). A forced abort deliberately does **NOT** restart the kernel (that would destroy a namespace nobody asked to lose) and does **NOT** stop the runaway code, so the NEXT run queues behind it inside jupyter - stated in the message rather than compensated for, which is the detect-and-offer-the-remedy stance. The MCP description and INSTRUCTIONS carry the same rule so an agent relays "forced" instead of reporting a clean stop. **An abort is NOT a kernel-down**, which is a distinction the F2 path newly made reachable: `run.ts`'s `kernelDown` means only that `execute()` threw before it ever had a kernel in hand (the sidecar was unreachable), inferred from the ABSENT session epoch - and a run force-settled while parked also throws with no epoch, over a kernel that was demonstrably alive and busy, so `KernelExecuteAborted` is excluded from that inference. Left in, MCP `run_cell` returned `kernel_unavailable:true` for a reachable kernel and the cell then read `error_persisted`, i.e. the label clause 3 tells an agent to ignore as leftover from a previous session, for a run aborted seconds ago. **The SAME defect lived one layer up, in `databricks.ts`'s `runInKernel`, and the escalation made it routine**: it relabelled EVERY `execute()` throw as `kernel_unavailable` ("the Python kernel could not be reached", which the sidebar renders as "Restart Cellar, then connect again"), which was safe only while an unreachable sidecar was the sole way to throw - and the interrupt deliberately force-settles the INTERNAL `CONNECT_CODE` execute holding the exec lock, since settling that holder is what unwedges the notebook parked behind it. So on the HEADLINE F2 path the connect came back blaming an unreachable kernel that was demonstrably alive and busy. Told apart by TYPE (`instanceof KernelExecuteAborted`, never by matching the message), it is now its own code **`operation_aborted`** carrying the abort's OWN sentence - so the specific cause (interrupt / restart / teardown / proven-dead) rides along rather than being guessed at - wired through `statusFor` as **409, deliberately not `kernel_unavailable`'s 503** (nothing observed an unreachable kernel and the remedy is to try again once the kernel is free, never to restart Cellar) and given its own `REMEDY` entry in `Databricks.svelte`, which blames neither the kernel nor the credential. - **Kernel lifecycle & memory (Phase 6 - completes the kernel-per-notebook migration).** With N kernels = N Python processes (100s of MB each with pandas/pyspark), three safety nets keep RAM bounded. (1) **Idle culling** leans on the sidecar's own `MappingKernelManager` culler, configured in `bin/cellar.js` `cullingArgs()`: `CELLAR_KERNEL_IDLE_TIMEOUT` (default **7200s/2h**, `0` disables) + `CELLAR_KERNEL_CULL_INTERVAL` (default `min(300, timeout)`). **`cull_connected=True` is load-bearing** - Cellar holds a persistent websocket to every kernel, so with jupyter's default (`false`) an idle kernel is "connected" and never culled. Node-side reconciliation: `kernel.ts` `getManager()` connects the `KernelManager.runningChanged` poll (~10s) to `reconcileCulledKernels()`, which tears down any Map entry whose connection vanished from the server's running list (the manager also disposes that connection itself). A culled kernel therefore drops its sidebar card (`publishKernelStatus`) and bumps its epoch, so its cells read `not_run`/`ran_this_session:false` - the run-status doctrine stays honest. (2) **Soft cap**: `src/lib/kernelCap.ts` (`parseMaxKernels`/`isOverKernelCap`, `DEFAULT_MAX_KERNELS=8`) drives a **warn-only** banner in the Kernels sidebar past `CELLAR_MAX_KERNELS` live kernels (`0` disables) - it **never blocks a run** (the Nth run still lazily starts its kernel); surfaced via SSR `data.maxKernels`. (3) **Shutdown-on-delete**: `shutdownKernelsUnder(path)` (in `kernel.ts`) frees the kernel process of a deleted notebook (or every notebook under a deleted folder), wired into `src/routes/api/fs/op/+server.js`'s `delete` case beside `dropDocs`; idempotent. All three route through **`teardownKernel`**, now idempotent (removes the Map entry synchronously up front) with an `{alreadyGone}` opt-out of the REST shutdown for an already-culled kernel, and it publishes a per-notebook **`kernel:shutdown`** event (`publish`, has `nb`+`seq`) so `LiveNotebook` refetches staleness/run-status (cells read "not run this session"); manual shutdown + `rebindKernel()` fan-out (venv change → tears down EVERY live kernel + clears each queue) emit it too. Tab close does NOT shut a kernel down (keep-alive until cull/manual), and kernels are NOT pre-warmed on tab open (both deliberate - lazy-start's memory win). Covered by `tests/unit/kernel-lifecycle.test.ts` (cull reconciliation, shutdown-on-delete, rebind fan-out) + `tests/unit/kernel-cap.test.ts`.
